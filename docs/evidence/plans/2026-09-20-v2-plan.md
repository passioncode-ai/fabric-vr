### The six rules every remaining spec is executed under

Each is derived from an observed failure in this repository, not from general advice.

1. **Re-resolve every `file:line` against `HEAD` first, and correct them in the same commit.** The
   landed commits moved `TodayScreen.kt` by 32 lines and deleted 13 strings; 26 specs carry a stale
   receipt, and the doc gate exempts specs by design.
2. **Trace the spec's printed code against the spec's own Tests table before writing a line of
   it.** T-007 printed code its own test forbids, and fifteen more specs do. If they disagree, the
   code is wrong — the test was written from the defect.
3. **`backgroundScope` is only for a collector whose completion nothing asserts.** Production work
   a test waits on gets a scope the test owns on the same scheduler. A thread name recorded under
   any `TestDispatcher` is the test's own thread, and `advanceUntilIdle()` cannot see
   `Dispatchers.IO`, `Graph.scope`, a `flowOn` or `MockWebServer`.
4. **A new gate carries a canary and a planted red, or it is not a gate** — and its precondition is
   checked before it is switched on. Five gates in these specs delegate their proof to a grep whose
   empty output is indistinguishable from a grep that read nothing.
5. **A test that restates the rule proves nothing.** If planting the defect leaves it green, it is
   at the wrong level. Name in the commit which half of a defect a test actually reaches.
6. **Before starting, diff what has landed since the plan was written and say what it moved under
   this spec.** `git diff 6372316..HEAD --stat` is the whole of it, and it is how the vault trash,
   the cut assistant and a lying string each reached six specs unnoticed.

## The rule this plan is built on

*Every task leaves the tree green, the gates passing, and the app on the headset no worse than it
was.* A task that cannot do that is split until it can. That is the whole reason the order below
is not "blockers first": three of the blockers cannot be fixed safely until something else exists,
and two of them would destroy a person's notes if done in the obvious order.

## The three ordering constraints that decide everything

**1. Nothing can be verified until the suite is honest.** `PanelSmokeTest` asserts two strings no
screen renders, so the instrumented suite is red at `HEAD` while the handoff claims "13 tests, 0
failures" (F-02, F-03, E). There is no CI, so no gate runs unless an agent remembers to run it
(H-08). Until that is fixed, "the tests pass" is not evidence about anything, and every task after
it would be landing blind. **WP-0 is first, and it is small.**

**2. A signed release deletes the person's notes.** Both headsets carry a debug-signed APK. A
release build is signed differently, so `install -r` fails and the only way through is
`adb uninstall`, which removes `filesDir` — the notes database, the whole vault, the 190 MB model
and every Keystore value. `allowBackup="false"`, and the app has no export path of any kind (H-23,
G-01). **An export must exist before a signed install is attempted, not after.** This is the single
most expensive ordering mistake available in this plan.

**3. The Space's Compose hosts are wrong in a way that makes other fixes land badly.** Three of the
four owners we supply shadow working SDK-provided ones (axis I, settled by disassembly), and our
`onDestroy` clears the ViewModelStore before the composition is disposed — so `flush()` on exit
fires into a dead scope, deterministically, in the Space (I-03). Any editor or capture fix that
relies on a view-model scope surviving an exit is worthless until this is corrected. **WP-2 comes
before the screen work, not after.**

### What steps 4 and 5 taught, and what moves because of it

Eight tasks landed (T-012, T-016, T-015, T-013, T-018, T-019, T-020, T-021) and the group
verification — three independent readings — returned `fail` on all three tiers. Four facts the
plan did not have:

1. **A spec's own prediction can be the thing that is wrong.** `T-013` was written to delete the
   Space's back dispatcher on the strength of a measurement that had not landed where it thought.
   `T-019` predicted a checker baseline of eleven and the true number was one, because `T-017` had
   already moved those reaches behind constructor defaults. **Neither was a stale spec; both were
   specs whose reasoning was sound and whose input was wrong.** Where a spec's decision turns on a
   measurement, take the measurement *and* ask what would make it lie.
2. **The tasks are colliding with each other now, not with the audit.** `T-013` gave the Space's
   exit its own word; `T-020` greyed it out four hours later; nothing in either spec saw the
   other. `DEC-0034` resolves it. Steps 6–11 touch fewer shared surfaces, but `T-028`…`T-032`
   rebuild the Today surface that three of these tasks just changed — **read `DEC-0029`, `0032`
   and `0034` before opening `T-030`**, not the specs alone.
3. **The device has been away for the whole group**, and seven rows now wait on it:
   `B-115` (does a controller's B arrive), `B-117`, `B-119`, `B-120`, `B-122`, `B-123`, `B-124`,
   `B-130`. None of them blocks another task. **T-014 is the only task blocked on a headset**, and
   its own spec forbids writing any of it first — so it stays where it is and step 6 goes next.
4. **Threading changes need a third kind of test.** Two tiers of verification found defects no
   unit test could have: a window opened by making a function `suspend`, and a flow that freezes
   rather than ends. Both are state-machine holes, and both were found by reading the *callers*.
   For steps 6–11 the rule is: when a function becomes `suspend`, enumerate what reads the state
   it used to set synchronously.

**No re-ordering follows.** Step 6 (T-022 + T-027, then T-048) has no device dependency and no

### What the first group taught, and what moves because of it

Steps 1–3 are done — T-017, T-023, T-047, T-009, T-010, T-011 — and the group produced three facts
the plan did not have.

1. **An unworn headset on a desk answers far more than the plan assumed.** Three probes, two
   instrumented test classes and a full export round-trip were taken without anyone wearing

   is two, and the larger half needs no person at all. **Everything still blocked on a human is now

   task.
2. **Three of the project's own gates could not fail, and a fourth ran only in CI.** That last one
   made `check-all.sh`'s own opening sentence false — "green locally and green in CI cannot mean
   two different sets" — and it is fixed by moving the check rather than by remembering. Every gate
   now carries a canary *and* has been watched failing against a planted violation, which are two
   different claims and only the second one is about the gate.
3. **The estimate that keeps being wrong is the seam.** Three for three, a task needed an
   unbudgeted production parameter before its defect could be constructed in a test. That is now
   rule 6's corollary and it is why T-017 moved to first.

**T-027 rises from 6 to 9.** It carries `A-12`: `MIGRATION_1_2` silently deletes every duplicate
`dayKey` row but the oldest and emits no `NoteChange`, so an upgrade loses notes and the vault
mirror never hears about it. A prio-9 data-loss row sitting inside a prio-6 task is a
mis-prioritisation, not a detail.

## Corrections the spec-writing pass made to this plan

Writing the specs was itself a check on the plan, and it found the plan wrong in fourteen places.
Ten `Closes` columns cited the wrong finding id — corrected above. Four things the specs found that
no audit row carried, now folded in:

- **Two whisper contexts can coexist**, about 1.11 GB, through `Graph.withEngine`'s throwaway engine
  while a selected one is loaded. No axis noticed. Owned by **T-018**.
- **`ImmersiveLaunchTest`'s crash assertions can never fire**: instrumentation runs in the app's own
  process, so a crash kills the test run, and `getHistoricalProcessExitReasons` cannot report a live
  process. It also uses `RunningAppProcessInfo.REASON_UNKNOWN` where it means `ApplicationExitInfo`.
  Owned by **T-016**.
- **`*.keystore` and `*.jks` are in neither `.gitignore` nor `check-secrets.sh`**, while
  `keystore.properties.sample` resolves `storeFile` relative to the repository root — the shortest
  path from the sample to a working build puts an unrecoverable private key in a tracked directory.
  Owned by **T-039**, which must close that gate before a keystore exists to leak.
- **No task asked for a maximum recording length.** Owned by **T-020**.

Three findings were shown to be wrong and are corrected in the specs that cite them: `C-22`/`I-27`
claim `composedAtLeastOnce` is never reset (it is, at `ImmersiveLaunchTest.kt:34`); `H-23` claims
`adb uninstall` is the only way past a signer change (APK signature scheme v3 key rotation is
available on API 34, and a refused `install -r` writes nothing — so the rotated install is a free
attempt that must be tried first); `H-25` gives the wrong reason for the missing v1 schema (it was
`exportSchema = false`, not a Room version that predated the feature).

## How a task is finished

1. The spec's **Definition of Done** is met, every item.
2. The tests the spec names exist, and each was watched failing before the fix.
3. `./gradlew testDebugUnitTest lintDebug` green; the four gates green.
4. The commit message says what changed and what it traded away.
5. The board row moves with the commit that closed it.

A task that needs a headset says so in its spec and names the exact observation. Those rows stay
open until a person makes it.
