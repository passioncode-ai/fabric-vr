## What is wrong, in the person's terms

Three things, and the third is the one that will actually bite.

**The app uses ten times more memory than the sound it is holding.** A minute of dictation is
1.9 MB of audio and about **19 MB** of Java objects. Ten minutes is 190 MB — next to whisper's own
190–574 MB native context, Compose, and an OpenXR session, on a headset with no swap. The
allocation also churns: every chunk builds a new list and the accumulator periodically copies the
whole thing.

**Nothing stops a recording.** There is no maximum length. If the person starts dictating and
something distracts them — they take the headset off, they walk away, they get talked to — the
microphone keeps recording until the process dies of memory. Then everything they did say is gone
too, because the recording only becomes a file when they stop.

**And the microphone stays hot with nothing on screen saying so.** The Today header's *Search*,
*Assistant*, *Space* and *Settings* buttons are live while recording. Tap any of them and the
screen changes, the view model survives in the back stack, and `recordJob` keeps reading the
microphone with no indication anywhere. `docs/modules/app.md` cites exactly this risk as the
reason the product originally chose hold-to-talk — in a build that no longer holds.

## Where it is

**The boxing, `feature-stt/.../AudioRecorder.kt:35,60-73`:**

```kotlin
fun record(onSamples: (List<Short>) -> Unit): Flow<Level> = callbackFlow {   // :35
    …
    val buffer = ShortArray(bufferSize / 2)                                   // :57  — unboxed, good
    var total = 0
    try {
        while (isActive) {                                                    // :60
            val read = recorder.read(buffer, 0, buffer.size)                  // :61
            if (read > 0) {                                                   // :62  — C-05 lives here
                var sum = 0.0
                val chunk = ArrayList<Short>(read)                            // :64  — a new list per chunk
                for (i in 0 until read) {
                    chunk.add(buffer[i])                                      // :66  — boxes every sample
                    sum += abs(buffer[i].toInt()).toDouble()
                }
                onSamples(chunk)                                              // :69
                total += read
                trySend(Level(rms = (sum / read / Short.MAX_VALUE).toFloat(), samples = total))
            }
        }
    } finally { runCatching { recorder.stop() }; recorder.release() }
}.flowOn(Dispatchers.IO)                                                      // :79
```

**and `app/.../ui/VoiceViewModel.kt:59-68`:**

```kotlin
private val bufferLock = Any()                                                // :59
private val buffer = mutableListOf<Short>()                                   // :60

private fun appendSamples(samples: List<Short>) = synchronized(bufferLock) { buffer.addAll(samples) }  // :66
private fun drainBuffer(): ShortArray = synchronized(bufferLock) { buffer.toShortArray() }             // :67
private fun clearBuffer() = synchronized(bufferLock) { buffer.clear() }                                // :68
```

**The arithmetic.** On ART a `java.lang.Short` outside the −128…127 cache is a 16-byte object plus
a 4-byte array slot: **≈20 bytes per 2-byte sample**. Speech amplitudes are overwhelmingly outside
that cache, so essentially every sample allocates.

| Dictation | Raw PCM | Boxed, retained | Also churned |
|---|---|---|---|
| 10 s | 320 KB | ~3.2 MB | the same again in per-chunk lists |
| 60 s | 1.9 MB | **~19 MB** | ~19 MB |
| 10 min | 19 MB | **~190 MB** | ~190 MB |

**The lock, seen from Main (I-10).** `appendSamples` is called from `Dispatchers.IO`
(`AudioRecorder.kt:69,79`); `drainBuffer` and `clearBuffer` are called from Main
(`VoiceViewModel.kt:84,110`). The critical section is `ArrayList.addAll` over a boxed list, which
periodically reallocates and copies an array of up to 960 000 references **while holding the
lock**. The longer the dictation, the longer Main waits at `stopAndTranscribe`. The lock itself is
correct — its KDoc (`:54-58`) records the `ConcurrentModificationException` it was added to fix,
and `stopAndTranscribe` additionally `cancelAndJoin`s the producer before draining (`:109-110`).
**The defect is the size of the critical section, not the presence of the lock**, and that matters
because the obvious "fix" is to remove the lock.

**The unbounded lifetime (E-03).** `recordJob = viewModelScope.launch { … }` (`:86`).
`viewModelScope` is not lifecycle-bound. `TodayScreen.kt:127-138` renders five header actions and
disables none of them on `VoiceState.Recording`. Navigating to Settings leaves Today's entry on the
back stack, so its `VoiceViewModel` survives and the flow keeps collecting.

**The spin (C-05).** `recorder.read()` returns a negative error code — `ERROR_INVALID_OPERATION`
(−3), `ERROR_DEAD_OBJECT` (−6), `ERROR` (−1) — when the session dies or the microphone is taken by
the shell's voice command, another app, or Meta Virtual Display. `if (read > 0)` skips the body
and `while (isActive)` immediately calls `read()` again: **one core at 100%**, the meter frozen at
its last value, the UI still saying *Recording*, and when the person stops, the buffer is short so
they are told "nothing was heard" — the one failure mode a dictation app must not have.

**And there is no test.** `VoiceViewModelStateTest` never constructs the view model; both its
tests re-implement a guard as a local `if`. Nothing exercises `AudioRecorder` at all.

## The decision, and what was weighed

**Chosen: the buffer is a growable `ShortArray` owned by one small class; the recording has a hard
maximum that stops and transcribes rather than discarding; and the recording ends when the screen
that owns it goes away, with the controls that would take it away disabled while it runs.**

### 1. The buffer shape

The callback changes to `(ShortArray, Int)` — the recorder's **own** buffer plus a count — so the
producer allocates nothing per chunk:

```kotlin
fun record(onSamples: (ShortArray, Int) -> Unit): Flow<Level>
```

The contract is stated where it can be read: *the array is reused and is only valid for the
duration of the call; the caller copies what it wants.* The consumer becomes:

```kotlin
/**
 * The recording, as 16-bit samples and nothing else.
 *
 * It was an `ArrayList<Short>`: ~20 bytes per 2-byte sample on ART, so a 60-second dictation
 * retained ~19 MB and churned the same again, and `addAll` copied an array of up to 960 000
 * references while holding the lock Main was waiting on. Here the critical section is a
 * `System.arraycopy` of the chunk.
 *
 * Bounded on purpose: nothing else in the app stops a recording, and an unbounded one on a
 * headset with no swap ends as an OOM that takes the recording with it.
 */
class PcmBuffer(private val maxSamples: Int) {
    private val lock = Any()
    private var data = ShortArray(INITIAL)
    private var size = 0
    /** @return false when the recording has reached [maxSamples] and this chunk was refused. */
    fun append(src: ShortArray, count: Int): Boolean = synchronized(lock) { … }
    fun drain(): ShortArray = synchronized(lock) { data.copyOf(size) }
    fun clear() = synchronized(lock) { size = 0 }
    val sampleCount: Int get() = synchronized(lock) { size }
}
```

Growth is doubling with `copyOf`, and the initial capacity is one second (`SAMPLE_RATE`), so a
ten-minute recording performs about 10 reallocations total instead of continuous churn. It lives in
`feature-stt` beside `AudioRecorder`, because the constraint is the recorder's.

### 2. The maximum, and what happens at it

**Chosen: 10 minutes, and at the limit the recording *stops and transcribes*. It is never
discarded.**

| Limit | Raw PCM | WAV on disk | Transcription time at the measured 1.31× real time (small model, 4 threads) |
|---|---|---|---|
| 2 min | 3.8 MB | 3.8 MB | ~2.6 min |
| 5 min | 9.6 MB | 9.6 MB | ~6.5 min |
| **10 min** | **19.2 MB** | **19.2 MB** | **~13 min** |
| 30 min | 57.6 MB | 57.6 MB | ~39 min |

Memory is not what bounds this — 19 MB of `ShortArray` is nothing. **Transcription time is.** A
ten-minute dictation takes about thirteen minutes to transcribe on the default model, during which
the person has a screen that says *Transcribing* and a native context they cannot interrupt
(T-018). Anything longer is a promise the device cannot keep. And the WAV is kept forever
(G-02/G-16), so 19 MB per dictation compounds.

At 9 minutes the meter turns to a countdown and the screen says so; at 10 the recording stops
exactly as if the person had pressed stop. **Discarding at the limit would be the A-03 mistake in a
new place** — the app deleting a recording it told the person it was making.

**Open to the operator, one line:** is 10 minutes right? The alternatives, with their trade-offs,
are in the table. **10 minutes is this spec's recommendation and its reason is the transcription
time, not the memory.** If the operator wants longer, the honest way is chunked transcription
(whisper already works in 30-second windows), which is a feature, not a constant.

### 3. What stops a recording

Three mechanisms, layered, because any one alone leaves a hole:

- **The header actions are disabled while `VoiceState.Recording`.** The person cannot navigate
  away mid-dictation by accident. This is E-03's own second proposal and it is the cheapest of the
  three.
- **A `DisposableEffect` on the screen calls `voiceViewModel.stopAndTranscribe(completed = true)`
  on dispose** — *transcribe*, not discard. The view model outlives the composition (it is scoped
  to the back-stack entry), so the transcript lands in `VoiceState.Ready` and is waiting when the
  person comes back. Discarding here would throw away speech the person produced deliberately.
- **`ON_STOP` stops it too.** The headset coming off, or another app taking the foreground, must
  not leave the microphone live. A `LifecycleEventEffect(Lifecycle.Event.ON_STOP)` in the same
  place. **This only works in the Space after T-012**, because today the Space's shadowing
  lifecycle owner never receives `ON_STOP` (I-12) — which is worth stating in the code comment, so
  that whoever reverts T-012 finds out here.

### 4. The negative read

```kotlin
val read = recorder.read(buffer, 0, buffer.size)
if (read < 0) {
    // ERROR_DEAD_OBJECT (-6) when the session dies; ERROR_INVALID_OPERATION (-3) when it is not
    // started yet. Spinning on it burned a core at 100 % with the meter frozen and the UI still
    // saying "Recording", and the person was then told "nothing was heard".
    if (read == AudioRecord.ERROR_INVALID_OPERATION && retries++ < MAX_TRANSIENT_RETRIES) {
        delay(RETRY_MS); continue
    }
    close(SttException(AppError.SttFailed("audio-record", IllegalStateException("read=$read"))))
    return@callbackFlow
}
if (read == 0) { continue }
```

The error code goes into the exception so a logcat line names which one happened.

### Alternatives considered

- *Keep `List<Short>` and pre-size it.* Rejected: pre-sizing removes the reallocation and keeps the
  boxing, which is 90% of the cost.
- *Accumulate into a `ByteArrayOutputStream` and convert at the end (E-02's second suggestion).*
  Rejected narrowly. It is unboxed and it grows well, but the consumer needs a `ShortArray` for
  `WhisperEngine.transcribe(pcm: ShortArray, …)` and for `WavWriter.write(file, pcm)`, so the end
  of the recording would do a byte→short conversion pass over 19 MB on whatever thread called
  `drainBuffer`. A `ShortArray` is the shape both consumers want; ending with `copyOf` is one
  `arraycopy`.
- *Remove the lock and use a channel from the recorder to the view model.* Rejected for now, and
  it is the shape to reach for if this ever gets more complicated. It replaces a 10-line class with
  a producer/consumer protocol, a buffering policy and a cancellation story — and the lock is not
  the problem. The KDoc at `VoiceViewModel.kt:54-58` records a real
  `ConcurrentModificationException` that the lock fixed; removing it to fix a *performance*
  finding would be re-opening a correctness one.
- *Have `AudioRecorder` own the accumulation and hand back a finished `ShortArray`.* Considered
  seriously. It would put the buffer, the cap and the lock in one place and give `VoiceViewModel`
  nothing to get wrong. Rejected because `AudioRecorder.record`'s KDoc (`:29-33`) states the
  opposite contract deliberately — "The caller owns the accumulation — and owns its locking" — and
  the meter's `Level` flow and the sample stream would then have two different lifetimes. **The
  compromise is `PcmBuffer` in `feature-stt`**: the recorder does not own it, but the knowledge of
  how to accumulate whisper-shaped audio lives next to the recorder rather than in a view model.
- *Discard at the limit rather than transcribing.* Rejected; see above.
- *No limit, and rely on the OOM killer.* Rejected, obviously, but worth naming: today that is the
  design.
- *Move the whole recording to a foreground service so it survives navigation.* Rejected. It is the
  opposite of what E-03 wants: the risk is the microphone being live with nothing on screen saying
  so, and a service makes that the intended behaviour. It would also need a notification, which on
  Horizon OS is a different surface again.

## Decomposition

**Step 1 — write the failing tests first.**

`feature-stt/src/test/kotlin/ai/passioncode/fabricvr/stt/PcmBufferTest.kt` (new, pure JVM):

1. `appending then draining returns exactly the samples appended` — including across a growth
   boundary.
2. `the buffer holds no more than its maximum` — append past `maxSamples`, assert `append` returns
   false and `drain().size == maxSamples`.
3. `drain does not clear` / `clear resets the size` — the two callers depend on both.
4. `concurrent appends and drains never lose or duplicate a sample` — 8 producer threads, one

   after** — the lock is being made cheaper, not removed.
5. `the retained size is proportional to the samples, not to 10x the samples` — allocate 16 000 ×

7. `a transient ERROR_INVALID_OPERATION is retried a bounded number of times` — returns −3 twice

## Blast radius, and what NOT to touch

- **Touches:** `AudioRecorder.kt` (the signature, the loop), a new `PcmBuffer.kt`,
  `VoiceViewModel.kt` (five members become one, plus `stopForNavigation`), `TodayScreen.kt` and
  `NoteEditorScreen.kt` (two effects, five disabled actions), two strings, two new test files, one
  deleted test file, `DECISIONS.md`, `docs/modules/feature-stt.md`, `docs/ux/scenarios.md`.
- **Do not touch:** `WavWriter`. It already takes a `ShortArray` and it is tested
  (`WavWriterTest`). Whether a failed write is swallowed (G-05) is a different row.
- **Do not touch:** `VoiceViewModel.cancel()`'s deletion of `lastAudioPath` (`:201`). *Retry*
  reaching `cancel()` is **T-005**, and it lands in the same file. Coordinate: if T-005 has
  already landed, `cancel()` is only reachable from *Discard the recording* and the
  `DisposableEffect` must not call it. If T-005 has not landed, **do not fix it here** — two
  data-loss fixes in one commit means neither can be reverted alone.
- **Do not touch:** the `bufferLock` pattern's *intent*. The lock stays; only what happens inside it
  changes. A commit that deletes the synchronisation while claiming a performance fix will pass its
  tests and reintroduce a `ConcurrentModificationException` under load.
- **Do not touch:** `MIN_SAMPLES` (`:208`). "Under a third of a second is a mis-tap, not a thought"
  is a deliberate product rule and it is the lower bound to the upper bound being added.
- **Do not touch:** `stopAndTranscribe`'s `cancelAndJoin` at `:109`. It is what makes the drain
  safe, and it is easy to think it is redundant once the buffer is cheaper. It is not.
- **Watch for:** `appendSamples` is called from the IO thread and now *launches on
  `viewModelScope`* when the cap is hit. `viewModelScope.launch` from a background thread is safe,
  but `stopAndTranscribe` reads `_state.value !is VoiceState.Recording` and returns — so the cap
  path must not fire twice. `PcmBuffer.append` returning false repeatedly is the likely case;
  guard with a flag or make the launch idempotent via the state check, and **test it** (test 8
  should assert exactly one transcription).
- **Watch for:** `LifecycleEventEffect` requires `androidx.lifecycle:lifecycle-runtime-compose`,
  which is already present (`collectAsStateWithLifecycle` is used on all five screens).

## Correction to the finding

The three cited rows (E-02, I-10, E-03) are accurate and confirmed against the tree. Three
additions and one caveat:

1. **C-05 belongs on this row and is currently misfiled.** The plan attaches C-05 to **T-016**
   ("the Space is entered and left without a crash"), where it has nothing to do with the subject.
   C-05 is `AudioRecorder.kt:60-73` — the negative-`read` busy loop — and it is in the exact twelve
   lines this task rewrites. Fixing it anywhere else means touching those lines twice; leaving it
   where the plan put it means it is never fixed at all, because T-016 will not open that file.
2. **E-02 and I-10 are one defect seen from two sides**, which the merge notes but the task list
   does not: the boxing *is* the lock-hold time. Fixing the buffer closes both; there is no
   separate locking work.
3. **No row asks for a maximum recording length.** E-03 says "nothing bounds the recording length
   (E-03 makes an unbounded one reachable), so this is an OOM path" and proposes stopping on
   navigation — which is necessary and not sufficient: a person who sits still and keeps talking
   hits no navigation. The cap is this spec's addition and it is the part that needs an operator's
   number.
4. **One caveat on E-02's arithmetic**, stated so the test in step 1 is written honestly: the
   "~20 bytes per sample" figure assumes every sample misses `Short.valueOf`'s −128…127 cache. Near
   silence — and the leading and trailing silence of every dictation — samples *do* fall in that
   range and are interned, so the real retained figure for a quiet recording is lower than 19 MB
   per minute. It is still an order of magnitude over 1.9 MB for anything with speech in it, and
   the cache makes the memory usage *depend on the loudness of the room*, which is its own reason
   to be rid of it.
