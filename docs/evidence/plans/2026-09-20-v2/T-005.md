# T-005 — *Retry* on a failed transcription keeps the recording

> **IMPLEMENTED 2026-09-20 — with one correction to this spec's own text.**
>
> This spec said to wire *Retry* to `VoiceViewModel.retryLast()`. **`retryLast()` does not retry
> the last recording**: it calls `start()`, which begins a *new* one. The method that re-runs the
> stored audio is `retranscribe(language)`. Wiring *Retry* to `retryLast()` would have replaced
> "deletes the recording" with "throws it away by starting another" — the same loss with a
> friendlier name.
>
> What shipped: three methods for the three intents — `retryTranscription()` (same audio, current
> language), `dismissFailure()` (message away, recording kept), `cancel()` (unchanged: the one
> thing that deletes). The screen takes three parameters instead of one, so they cannot be bound
> to a single lambda by accident, plus `hasRecording` so *Discard* appears only when there is
> something to discard.
>
> One design change the spec did not anticipate: `lastPcm`/`lastAudioPath` became an injectable
> `LastRecording` holder. Without it the failure state could not be constructed in a test at all,
> and the alternative was a setter existing only for tests — a production API shaped by its test.
>
> `NoteEditorScreen` does **not** share the defect; its banner is about saving a note. It renders
> no voice failure whatsoever, which is B-11 and is now board row **B-083**.

- **Severity:** Blocker
- **Work package:** WP-1 (stop the data loss)
- **Closes:** A-03, B-06, D-08
- **Depends on:** nothing
- **Needs a headset:** no
- **Estimated blast radius:** 2 files changed, 1 test file, no contract moves

## What is wrong, in the person's terms

They dictate. Transcription fails — the model is missing, the engine errors, the cloud refuses the
key. The screen says:

> Couldn't transcribe that. The recording is kept.

There is one button, *Retry*. They press it. **The recording is deleted.** There is now nothing to
retry, nothing to re-transcribe with a different model, and nothing that can be recovered. The app
stated the opposite of what it did, and the loss is silent.

## Where it is

`app/src/main/kotlin/ai/passioncode/fabricvr/ui/TodayScreen.kt`, the `VoiceState.Failed` branch of
`RecordControl`:

```kotlin
is VoiceState.Failed -> ErrorBanner(
    message = current.message,
    onAction = { action ->
        when (action) {
            UiAction.GRANT_PERMISSION -> onGrantPermission()
            UiAction.DOWNLOAD_MODEL -> onDownloadModel()
            UiAction.OPEN_SETTINGS, UiAction.OPEN_APP_SETTINGS -> onOpenSettings()
            UiAction.RETRY -> onDismissFailure()     // <-- this
        }
    },
    onDismiss = onDismissFailure,
)
```

`onDismissFailure` is bound at the call site to `{ voiceViewModel.cancel() }`, and
`VoiceViewModel.cancel()` is:

```kotlin
fun cancel() {
    recordJob?.cancel(); recordJob = null
    clearBuffer(); lastPcm = null
    lastAudioPath?.let { path -> runCatching { File(path).delete() } }   // <-- the deletion
    lastAudioPath = null
    _state.value = VoiceState.Idle
}
```

The method that should be called already exists and is called by nobody:

```kotlin
fun retryLast() { … }   // VoiceViewModel
```

The string is `core-common/src/main/res/values/strings.xml` → `error_stt_failed`.

## The decision, and what was weighed

**Chosen: *Retry* re-runs the last recording; dismissing keeps the recording; a separate, explicitly
labelled control discards it.**

Three actions are being conflated by two handlers. Separate them:

| Intent | Today | After |
|---|---|---|
| try the same audio again | deletes it | `viewModel.retryLast()` |
| put the message away, keep the audio | deletes it | `viewModel.dismissFailure()` — new, does not touch the file |
| throw the recording away | same handler as the two above | `viewModel.cancel()`, behind a control that says *Discard recording* |

**Alternatives considered:**

- *Make `cancel()` stop deleting, and delete elsewhere.* Rejected: `cancel()` is also the Discard
  path from the recording state, where deleting is exactly right (`DEC-0011` has no confirmation
  step, so Discard is the only way to refuse a recording). Weakening it would leave rejected
  recordings on the headset forever — the failure `cancel()` was written to prevent.
- *Keep one handler and pass a `deleteAudio: Boolean`.* Rejected: a boolean at the call site is how
  this defect happened. Two named methods cannot be miswired silently.
- *Change the string to admit the deletion.* Rejected: the recording is the only thing that makes
  *Transcribe again* possible, and it is the expensive artefact. The text is right; the code is
  wrong.

## Decomposition

**Step 1 — write the failing tests first.**
`app/src/test/kotlin/ai/passioncode/fabricvr/ui/VoiceViewModelTest.kt` (new file; the class has no
test today — see T-017, which makes the rest of it testable, but these three need no injection):

1. `retryLast re-transcribes the same audio and does not touch the file` — put the view model in
   `Failed` with a `lastAudioPath` pointing at a real temp file, call `retryLast()`, assert the file
   still exists and the engine was asked again.
2. `dismissing a failure keeps the recording` — call the new `dismissFailure()`, assert the file
   exists and the state is `Idle`.
3. `cancel deletes the recording` — the existing behaviour, asserted so the next change cannot take
   it away.

Run them. **Watch 1 and 2 fail.** If they pass before the fix, they are testing the wrong thing.

**Step 2 — `VoiceViewModel`.** Add:

```kotlin
/**
 * Put the message away and keep the recording. Distinct from [cancel], which throws the recording
 * away: the two used to be one handler, and the banner that said "The recording is kept" was wired
 * to the one that deleted it.
 */
fun dismissFailure() {
    if (_state.value is VoiceState.Failed) _state.value = VoiceState.Idle
}
```

Leave `cancel()` exactly as it is. Confirm `retryLast()` re-runs `lastPcm`/`lastAudioPath` and does
not clear them on failure — if it does, fix that here and say so in the commit.

**Step 3 — `TodayScreen.RecordControl`.** Replace the single `onDismissFailure` parameter with
three, so the call site cannot bind them to one lambda by accident:

```kotlin
onRetry: () -> Unit,
onDismissMessage: () -> Unit,
onDiscardRecording: () -> Unit,
```

`UiAction.RETRY -> onRetry()`, `onDismiss = onDismissMessage`. Add a `TextButton` reading
`action_discard_recording` next to the banner **only when `lastAudioPath` is non-null** — a Discard
that discards nothing is a control that teaches the person the app is confused.

**Step 4 — the call site in `TodayScreen`.** Bind `onRetry = { voiceViewModel.retryLast() }`,
`onDismissMessage = { voiceViewModel.dismissFailure() }`,
`onDiscardRecording = { voiceViewModel.cancel() }`.

**Step 5 — the string.** Add to `app/src/main/res/values/strings.xml`:

```xml
<string name="action_discard_recording">Discard the recording</string>
```

**Step 6 — the same conflation in the editor.** `NoteEditorScreen` renders its own failure path;
check whether it binds the same way and fix it identically. If it does not render one at all, say
so in the commit — that is a separate finding (B-11), not this task's to fix.

## Blast radius, and what NOT to touch

- **Touches:** `VoiceViewModel` (one new method), `TodayScreen.RecordControl` (its signature and one
  call site), one string.
- **Do not touch:** `cancel()`'s body — the Discard path depends on it. `retryLast()`'s transcription
  logic — if it is wrong that is T-008's ground.
- **Watch for:** `RecordControl` is also rendered while `Downloading`; adding a parameter must not
  change that branch. `NoteEditorScreen` shares `VoiceViewModel` through the same activity, so a
  state change here is visible there.
