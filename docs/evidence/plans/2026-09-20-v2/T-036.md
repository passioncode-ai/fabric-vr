> **DECIDED 2026-09-20 — `DEC-0023`: the second headset is a test copy, not a second user.**
> Option A. The operator delegated this one; the author took it. v1 gains no account, no sync and

## What is wrong, in the person's terms

There is a second Quest 3 with this app on it, belonging to someone who is not the operator. The
repository does not know it exists, the app has no notion of who is using it, and there is no way
to learn that their build is failing.

Nothing in the tree mentions it:

```bash
grep -ril 'the tester\|second headset\|второй шлем' docs/ | grep -v 'evidence/audits'   # nothing
```

There is no account, no sync, no sharing, no identity of any kind in the codebase. There is also no
device register: no serial, no owner, no record of what version is installed where or when.

## Where it is — four facts that together define the problem

**1. Nobody can tell which build is on which headset.** `app/build.gradle.kts:18-21`:

```kotlin
// The build number comes from the caller (`-PversionCode=42`) so a release can be rebuilt
// from the same commit without editing a tracked file.
versionCode = (findProperty("versionCode") as String?)?.toInt() ?: 1
versionName = "0.1.0"
```

Every build ever made is `1`. `SettingsViewModel.kt:44-45` reads `BuildConfig.VERSION_CODE`, so the
Settings line (`strings.xml:87`, `Fabric VR %1$s (%2$d)`) reads `Fabric VR 0.1.0 (1)` on every APK.
`adb shell dumpsys package | grep version` gives the same `1`. **T-038 fixes this**, and every
option below assumes it has.

**2. The installer does not say which headset it installed on.** `scripts/install-on-quest.sh:12-15`:

```bash
if [ -z "${DEVICE:-}" ]; then
  DEVICE=$("$ADB" devices | awk '$2=="device"{print $1; exit}')
fi
DEVICE=${DEVICE:-192.168.0.253:5555}
```

The first device in the list wins, and with no device listed it falls back to one hard-coded
address. With two headsets reachable — the premise of this deployment — the script installs on an
arbitrary one, prints `connected.`, starts the activity and exits 0. `push-model-for-tests.sh:12`
has the identical pick. (H-30; **T-038** owns the fix.)

**3. There is no way to reach a headset that is not on this LAN.** The only delivery mechanism is
`adb connect` from this laptop. `git ls-remote --tags origin` is empty; `.github` does not exist;
there is no published artifact of any kind. (H-32; **T-041** owns it, and is blocked on this
answer.)

**4. Nothing would report a crash.** No crash capture, no log sink beyond a logcat ring that clears
on reboot. The one production crash in this project's history was found by a person running
`adb shell dumpsys activity exit-info` by hand. (H-01; **T-011** owns it, and its shape changes
with this answer.)

## The three answers

### Option A — it is a copy for testing *(recommended)*

The second headset runs the build so a second pair of eyes can use it. It is not a user account, it
holds notes that are the tester's own and nobody else's, and nobody promises it will keep them.

**What it implies:**

| Task | Shape under A |
|---|---|
| **T-011** (crash capture) | on-device is sufficient. A crash log written to `filesDir` and readable from Settings, which the tester reads out or the operator reads at the next meeting. No network sink, no crash service, no consent question. |
| **T-041** (updating off this LAN) | its cheapest honest option: a GitHub Release with the signed APK and a written install step, so the tester can update between meetings if they want to. Even if they never use it, the release is what makes "which build is the tester on" answerable by a version string rather than by memory. |
| **T-037** (the debug→release cut-over) | must be performed **on both headsets**, and the tester's notes must be exported first exactly as the operator's are. A testing copy is not a copy whose data may be destroyed without asking. |

**What must ship for A to be true rather than assumed:** a tracked `docs/deployment/devices.md`,
one row per headset — label, owner, serial (`adb shell getprop ro.serialno`), model
(`ro.product.model`), the installed `versionCode`, the date, and who installed it. Four columns and
a discipline, not a system. Updated by `install-on-quest.sh` itself once T-038 makes the
`versionCode` real and readable.

**Cost:** one document, plus the `DEVICE=` guard that T-038 is already specifying.

### Option B — it is a second user, and the product needs identity

The tester is a user. Their notes are theirs, the product owes them continuity, and the operator is
responsible for the build they are running.

**What it implies, and none of it is small:**

- **Identity.** Accounts, or at minimum a device identity that survives a reinstall. Nothing in the
  tree has one.
- **Sync.** `docs/product/product-definition.md` §3 puts CRDT sync in v2+, correctly. Under B that
  ordering is wrong and the roadmap moves.
- **A privacy boundary that is currently uncomputed.** The vault is app-private per device; under B
  there are two vaults and a question about whether they ever meet. Every disclosure decision in
  T-025 and T-035 acquires a second person.
- **T-011 must ship crashes off the device.** A crash log readable only from the headset's own
  Settings is useless when the person holding the headset is not the person who reads logs. That
  means a network sink, which means a consent string, which means the product's second undisclosed
  egress after the one T-033 is deciding whether to cut.
- **T-041 must be over-the-air.** A GitHub Release that requires a person to sideload by hand is
  not an update mechanism for a user; it is an update mechanism for a tester. The thing built for
  this is a Horizon Store release channel (Alpha): named testers, automatic updates, no `adb`. It
  needs a Meta developer organisation and a signed build with a stable `applicationId`.

**Cost:** a phase. This is not a task and should not be written as one.

### Option C — out of scope for v1

The second headset is not supported. Either the build is removed from it, or it is frozen and
explicitly unsupported until a later phase.

**What it implies:**

- **T-041 is closed as will-not-fix**, and H-32 is answered by scope rather than by mechanism —
  which is a legitimate answer, and the only one of the three that costs nothing.
- **T-011 stays on-device**, same as A.
- **T-037 still applies to that headset if the build stays on it.** "Unsupported" does not mean
  "its data may be destroyed silently"; if the app is there and someone has dictated into it, the
  export happens before the signed install, or the build comes off first.

**Rejected as a recommendation** for one reason: it is not what is happening. There is a build on
someone's headset and the operator cares whether it works — H-32's own framing (the second headset
can be updated only when its holder and the laptop are in the same room) is written from the
assumption that updating it matters. Choosing C means saying out loud that it does not, and if that
were true the build would already be off the device.

## Recommendation

**Option A — a copy for testing, with a device register.**

It is what is true today. It costs one tracked document and a guard in a script that T-038 is
already touching. It makes T-041 the cheapest of its three options and keeps T-011 on-device, with
no consent surface and no second egress. And it converts the deployment's state from one person's
memory into four columns, which is the whole of H-35.

The one thing A must **not** be allowed to mean: that the tester's notes are expendable. T-037
applies to both headsets, in full.

## Decomposition

**If A:**

1. `DEC` row: *the second headset is a test installation, not a second user; v1 ships no identity
   and no sync.* Its `Consequences / affects:` line names `T-011`, `T-037`, `T-041`,
   `docs/deployment/devices.md`, and `docs/product/product-definition.md` §3 (which stays as it is
   — this decision confirms its ordering rather than changing it). Read `docs/DECISIONS.md:7` for
   the free id.
2. Create `docs/deployment/devices.md`. One table:

   | Label | Owner | Serial | Model | versionCode | Installed | By |
   |---|---|---|---|---|---|---|

   Fill it by hand once, per headset, from `adb shell getprop ro.serialno` and
   `adb shell getprop ro.product.model`. **Do not put the network address in it as the identifier**
   — `192.168.0.253:5555` is a DHCP lease, and the serial is the device.
3. Tell T-011, T-037 and T-041 the answer: each spec names it in its *Depends on* line.
4. The `DEVICE=` guard and the serial/versionCode printing belong to **T-038**, not here — this
   task supplies the reason, T-038 supplies the code.

**If B:** stop. Write a phase brief, not a task. The first question it answers is whether sync
comes before or after the things v1 still cannot do (a text note cannot be created).

**If C:** the `DEC` row, a line in `docs/deployment/devices.md` recording that the second headset
is unsupported and at which `versionCode` it was abandoned, and T-041 closed as will-not-fix with
that row as its reason.

## Blast radius, and what NOT to touch

- **Touches (A):** one new document, one `DEC` row, three specs' dependency lines, one plan row.
- **Do not touch:** `scripts/install-on-quest.sh`. The device-pick fix is T-038's and doing it here
  puts one change in two tasks.
- **Do not touch:** `docs/product/product-definition.md`. Under A it is already correct — sync is
  marked v2+ — and editing it to say so again is the duplicate-source-of-truth failure the doc map
  exists to prevent.
- **Do not put a serial, an IP or a person's full name into a public surface.** The register is a
  tracked file in a repository; a serial is a device identifier, and the repository
  (`git@github.com:passioncode-ai/fabric-vr.git`) is where it will live for as long as the project
  does. Use a label and a role, not a name; keep the serial if the operator accepts it, and say in the
  file that they did.
