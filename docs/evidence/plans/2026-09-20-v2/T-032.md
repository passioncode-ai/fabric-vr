## What is wrong, in the person's terms

The first sentence the product says is wrong twice.

```xml
<!-- app/src/main/res/values/strings.xml:102 -->
<string name="today_empty">Nothing here yet. Hold Record and say something, or start a note.</string>
```

**Hold** — the hold gesture was deleted by DEC-0010; the button toggles.
**Or start a note** — there is no control that starts one (A-01), until T-028 puts it back.

In English an operator shrugs. In the `values-ru` that G-09 wants, a translator would have to invent
a gesture that does not exist, in the app's primary language.

Behind that sentence is a larger problem: **26 declared strings are referenced by nothing**
(B-26), and the reason they are dead splits two ways that must not be confused — some describe
features that were deleted, and some describe features that exist and were never wired up.

## The rule that keeps them true — and which half is T-003's

Two layers, because the problem has two halves and only one of them is mechanical.

### Layer 1 — mechanical: a string gate (this task's)

A new `scripts/check-strings.sh`, run in CI beside the existing three gates
(`README.md:115-117`). Three checks:

1. **Declared and unreferenced** → fail, with the key and its line.
2. **Referenced and undeclared** → fail. (The compiler catches `R.string.x` for a missing `x`, but
   not a key named only in a comment or a doc.)
3. **Declared in two modules** → fail, naming both. This is the `action_allow` case, and it is the
   one a human reviewer will never see.

**It must resolve references the way Android does, not the way `grep R.string.NAME` does.** The
naive grep was run for this spec and got three answers wrong out of twenty-seven:

| Reference form | Naive grep | Correct |
|---|---|---|
| `@string/app_name_space` in `AndroidManifest.xml` | unused | **used** |
| `R.plurals.settings_vault_out_of_sync` | unused | **used** |
| `action_allow` declared in `:app` **and** `core-common`, `R.string.action_allow` resolved from core | used | the **app copy is dead** |

So the check searches `R.string.`, `R.plurals.`, `R.array.` **and** `@string/`, `@plurals/` across
`*.kt` and `*.xml`, and attributes each hit to the module whose `R` it resolves against. In bash 3.2
(the constraint `scripts/check-docs.sh` documents in its own header: no `grep -P`, no `readarray`).

**First, check whether this already exists.** Android lint's `UnusedResources` detector reports
unused strings, and `./gradlew :app:lintDebug` is already a gate — reported as "0 errors" in
`README.md:115`, which means these 26 are **warnings** today, if lint sees them at all (it is
unreliable across module boundaries, which is exactly this project's shape). Run it and read the
report. **If lint already names them, the fix is one gradle block** —

```kotlin
lint { error += "UnusedResources" }
```

— **and no script is needed.** Do not write a script to detect what the toolchain already detects;
do write one for the cross-module duplicate, which lint will not find.

**Known false positive to design for:** a string added by a task whose UI lands in the same release
is momentarily unreferenced. The gate must fail loudly rather than be given a suppression list —
the suppression list is how 26 strings accumulated. Add the string in the same commit as its caller.

### Layer 2 — the part no script can check: does the sentence describe this build

`today_empty` was never *unreferenced*. It was rendered, on the first screen, every launch, saying
two false things. **No mechanical check would have caught it**, and pretending otherwise is the
failure mode this section exists to avoid.

The rule: **a string that makes a claim about behaviour carries a comment naming the code that
makes it true.**

```xml
<!-- true because: TodayScreen.kt RecordControl — one press starts, the next stops -->
<string name="action_record">Record</string>
```

Then:

- **Review rule:** changing the named file means re-reading the strings that point at it. It is
  cheap because only behaviour-claiming strings are annotated — labels like `action_copy` are not.
- **The resolver is T-003's.** T-003 builds the check that "every path, command and symbol named in
  prose exists". These annotations are `file:line` claims in a tracked file, so the same resolver
  validates them. **The split:** T-003 owns the *machinery* — a `file:line` that no longer resolves
  fails the build. **This task owns the convention and the annotations** — which strings carry one,
  what it names, and that a new behaviour-claiming string without one fails review. If T-003 has
  not landed, write the annotations anyway and hand it the format; they are readable without a
  tool, which is more than could be said for the strings today.
- **Record it as a DEC** in `docs/DECISIONS.md`. A CI step nobody can explain is deleted the first
  time it is inconvenient; a DEC is the sentence that stops that.

The `strings.xml` header already carries half of this — "Every word the person reads, in one file.
Kotlin holds none of them" (`:2-6`). It is a rule about *location* and it held. What was missing is a
rule about *truth*. Add it to the same header, in the same voice.

which owns the scenarios: T-042 would be the place to choose B, and choosing B is what this task
exists to stop.

## F-14 — a test that claims more coverage than it has

`docs/evidence/verification.md:159`, REQ-009:

> `UiStringsTest`, 2 tests: **every one of the 17 `AppError` shapes** resolves through the resource
> table to a non-blank sentence

`UiStringsTest.kt:19-37` lists **17 cases**, not 17 shapes. `AppError` (`AppError.kt:7-36`) has
**11** constructors, and `AppError.InsecureUrl` (`:25`) — a real shape, the one DEC-0005 created —
is **not among the cases**. So the row claims exhaustive coverage its evidence does not show, about
the one error class that exists to stop a person sending their voice to an address they did not
mean.

Two changes, both small:

1. `UiStringsTest.kt`: add `AppError.InsecureUrl("http://10.0.0.5:8080")` to `all`. It becomes 18
   cases over 11 shapes.
2. `verification.md:159`: "every one of the 17 `AppError` shapes" → "18 cases across all 11
   `AppError` shapes".

And make the claim **structural** rather than a count someone has to keep true by hand: assert that
every shape is covered, so adding a twelfth `AppError` fails this test rather than quietly widening
the gap.

```kotlin
@Test fun everyAppErrorShapeIsCovered() {
    val shapes = AppError::class.sealedSubclasses.map { it.simpleName }.toSet()
    val covered = all.map { it::class.simpleName }.toSet()
    assertEquals("an AppError shape with no case", emptySet<String>(), shapes - covered)
}
```

`AppError` is `sealed`, so `sealedSubclasses` is exhaustive by construction. **Watch it fail**
before step 1: it reports `[InsecureUrl]`.
