# T-007 — A dictation cannot be reverted by the autosave it interrupted

- **Severity:** Blocker
- **Work package:** WP-1 (stop the data loss)
- **Closes:** I-01, E-01 — and the *ordinary-navigation* half of I-03. See **What this leaves to
  T-012**.
- **Depends on:** nothing
- **Needs a headset:** no — the defect is deterministic on a test dispatcher. One on-device
  confirmation is named below and is not a gate.
- **Estimated blast radius:** 1 view model (~25 lines), 1 constructor parameter, 1 test file
  extended. No UI change, no schema change, no string.

## What is wrong, in the person's terms

They are typing into a note. Mid-sentence they press *Record* and speak the rest of it. The
dictation appears in the note, under what they typed. It looks saved — the header says *Saved*.

Half a second later the note silently reverts to what it was **before** they spoke. The dictation
is gone, the transcript is gone, the recording's path is gone, and the Markdown file in the vault
is rewritten to match. Nothing on screen changed colour. No error.

The window is 600 ms wide and it is open **exactly when someone dictates into a note they are
typing** — which is the product's own headline gesture.

## Where it is

`app/src/main/kotlin/ai/passioncode/fabricvr/ui/EditorViewModel.kt`. Three methods and one field.

`edit()` owns the pending write and cancels its predecessor (`:41-50`):

```kotlin
    fun edit(title: String? = null, body: String? = null) {
        val current = _state.value.note ?: return
        val updated = current.copy(title = title ?: current.title, body = body ?: current.body)
        _state.value = _state.value.copy(note = updated, saved = false)
        saveJob?.cancel()
        saveJob = viewModelScope.launch {
            delay(AUTOSAVE_DELAY_MS)
            save(updated)
        }
    }
```

`attachTranscript()` does not (`:58-71`) — it launches a **second, unrelated** job and never
touches `saveJob`:

```kotlin
    fun attachTranscript(transcript: Transcript, audioPath: String?) {
        val current = _state.value.note ?: return
        val body = listOf(current.body, transcript.text).filter { it.isNotBlank() }.joinToString("\n\n")
        val shown = current.copy(
            body = body,
            title = current.title.ifBlank { transcript.text.take(60) },
            transcript = transcript,
        )
        _state.value = _state.value.copy(note = shown, saved = false)
        viewModelScope.launch {
            val landed = vault.adoptOrKeep(shown, audioPath)
            save(shown.copy(audioPath = landed ?: current.audioPath))
        }
    }
```

And `save` takes the note **by value** (`:105-110`), so whatever each job captured at launch is
what it writes:

```kotlin
    private suspend fun save(note: Note) {
        repository.upsert(note).fold(
            onSuccess = { stored -> _state.value = _state.value.copy(note = stored, saved = true, message = null) },
            onFailure = { failure -> _state.value = _state.value.copy(saved = false, message = failure.toMessage()) },
        )
    }
```

The interleaving, from I.md:258-275, which I re-derived against these lines:

```
Main t+0    edit(body="hello")   -> state.note = A,  saveJob := launch { delay 600; save(A) }
Main t+100  VoiceState.Ready     -> LaunchedEffect -> attachTranscript(tx, path)
                                    state.note = B (body + transcript)
                                    launch { … }      <-- a NEW job; saveJob is NOT cancelled
IO   t+140  adoptOrKeep moves the .wav into the vault
Main t+150  save(B.copy(audioPath=…))  -> row = B.  state.saved = true
Main t+600  the ORIGINAL saveJob fires -> save(A)
                                       -> row = A: transcript gone, audioPath gone, body reverted
```

The caller is `app/src/main/kotlin/ai/passioncode/fabricvr/ui/NoteEditorScreen.kt:58-62`:

```kotlin
    LaunchedEffect(voiceState) {
        val ready = voiceState as? VoiceState.Ready ?: return@LaunchedEffect
        viewModel.attachTranscript(ready.transcript, ready.audioPath)
        voiceViewModel.consumed()
    }
```

**The loss reaches the person's own folder.** `repository.upsert` emits `NoteChange.Upserted`
(`core-notes/.../NotesRepository.kt:94`), `VaultMirror` collects it (`VaultMirror.kt:37-42`) and
rewrites the Markdown — so `save(A)` mirrors A over B on disk as well as in the database.

### The second half: `flush()` into a scope that is being cancelled (E-01, I-03)

`flush()` is the mechanism that is supposed to prevent exactly this class of loss, and it launches
on the scope that is about to die (`EditorViewModel.kt:88-93`):

```kotlin
    fun flush() {
        val pending = _state.value.note ?: return
        if (_state.value.saved) return
        saveJob?.cancel()
        saveJob = viewModelScope.launch { save(pending) }
    }
```

Both callers fire it as the screen goes away. `NoteEditorScreen.kt:67`:

```kotlin
    DisposableEffect(noteId) { onDispose { viewModel.flush() } }
```

and `NoteEditorScreen.kt:81`:

```kotlin
            TextButton(onClick = { viewModel.flush(); onBack() }) { Text(stringResource(R.string.action_back)) }
```

`Dispatchers.Main.immediate` starts the coroutine inline; `save` reaches its first suspension
inside Room and returns; `onBack()` then pops the back-stack entry, which clears that entry's
`ViewModelStore`, which calls `onCleared()`, which cancels `viewModelScope` **with the write
suspended inside it**.

In the immersive host it is not a race at all. `ImmersiveActivity.kt:63-66`:

```kotlin
    override fun onDestroy() {
        owners.onDestroy()
        super.onDestroy()
    }
```

`owners.onDestroy()` clears the ViewModelStore *before* `super.onDestroy()` lets the SDK dispose
the composition, so `onDispose { flush() }` always runs after `onCleared()`. **`flush()` is a
no-op on every exit from the Space** — I-03 upgraded E-01 from "a real risk, ≤600 ms" to a
deterministic loss for that reason.

## Correction to the finding

**I-01 and E-01 are both correct as written.** I re-derived each interleaving against the current
lines and found no error.

Two things the findings do not say that this task has to handle, and that a developer implementing
only what is written would get wrong:

1. **`saveJob` cannot simply be shared with `attachTranscript` without splitting the adoption out
   of it.** I's rule 4 (`I.md:492-495`) says "`attachTranscript`, `edit`, `flush` and `retry` all
   assign the same `saveJob` and cancel the previous one". Done literally, a keystroke arriving
   150 ms after a dictation would cancel the attach job — and that job is inside
   `vault.adoptOrKeep` → `FileVault.adoptAudio`, whose move is `renameTo`, falling back to
   `copyTo` + `delete` (`feature-vault/.../Vault.kt:69-72`). Cancelling between the copy and the
   delete leaves two copies; cancelling after a successful `renameTo` but before the path is
   recorded leaves the note pointing at a scratch file that has just stopped existing. That is a
   *new* loss shape introduced by the fix. The adoption must be uncancellable; only the write it
   leads to is `saveJob`.

2. **`save`'s success branch is a third revert path in the same function.** `onSuccess = { stored
   -> _state.value = _state.value.copy(note = stored, …) }` overwrites the state's note with
   whatever was sent, so keystrokes typed while an upsert was in flight are reverted too — a
   narrower window than I-01's, in the same nine lines. Reading `_state.value.note` at call time
   fixes the *input*; it does not fix the *output*. Both ends need doing or the fix is half.

## The decision, and what was weighed

**Chosen: one pending write per editor, owned by one job; the adoption is not part of it; the
final write outlives the view model.**

Four rules, all in `EditorViewModel`:

| Rule | Why |
|---|---|
| **`save()` takes no argument.** It reads `_state.value.note` when it runs. | A write must express the note as it is at the moment of writing, not as it was at the moment of scheduling. This alone kills I-01's revert. |
| **`save()`'s success does not overwrite a state that has moved.** | Correction (2). It marks `saved = true` only when the state still holds what was sent. |
| **Every path that schedules a write assigns `saveJob` and cancels the previous one** — `edit`, `attachTranscript`, `flush`, `retry`. | One pending write per editor. Two is how this happened. |
| **The adoption runs on an application scope and is not `saveJob`.** `flush()` runs there too. | Correction (1), and E-01. A move-and-record must not be cancellable by a keystroke, and the last write must not be cancellable by navigation. |

### Alternatives considered

- ***`attachTranscript` calls `flush()` first, then does its own thing.*** Rejected: `flush()`
  writes the *pre-dictation* note to the database before the dictation is attached. It replaces a
  revert with a redundant write and an extra `NoteChange`, and it still leaves two jobs in flight.
- ***Make `saveJob` a `Mutex` and serialise the writes.*** Rejected: serialising A then B still
  writes A; the problem is not ordering, it is that A is stale. A mutex would make the revert
  reliable instead of racy.
- ***Cancel the autosave in the screen, in the `LaunchedEffect`, before calling
  `attachTranscript`.*** Rejected: it puts the view model's invariant in a composable, where the
  next screen that dictates (`TodayScreen` already does) has to remember it independently. The
  rule belongs where the field is.
- ***Keep `save(note: Note)` and pass a fresh read at each call site.*** Rejected: four call sites,
  each of which has to remember. A parameter that must always be `_state.value.note` should not be
  a parameter.
- ***Put the whole view model on an application scope.*** Rejected: then nothing is ever
  cancelled, an abandoned editor keeps its autosave alive, and `onCleared` stops meaning anything.
  `viewModelScope` is right for the debounce; only the final write and the adoption need to
  outlive it.
- ***`GlobalScope.launch`.*** Rejected: untestable, unownable, and `Graph.scope` already exists
  (`Graph.kt:39`) and is exactly this — `SupervisorJob() + Dispatchers.Default`, one collector, never
  cancelled (I-29 notes that invariant is undocumented; leave a line at the declaration while you
  are there).

### The seam

`EditorViewModel` already takes its collaborators as constructor parameters with `Graph` defaults
(`:25-28`), which is the pattern `SettingsViewModel` established and wrote down (`:51-55`). Add one
more, in the same shape:

```kotlin
class EditorViewModel(
    private val repository: NotesRepository = Graph.notes,
    private val vault: Vault = Graph.vault,
    /**
     * Where a write that must not be cancelled runs. `viewModelScope` dies with the editor, and
     * both callers of [flush] fire it as the screen is going away — on the ordinary path
     * `onBack()` pops the back-stack entry and clears its store mid-write, and in the Space the
     * activity clears the store before the composition is disposed, so `onDispose { flush() }`
     * launched into a cancelled scope every time. A parameter, not `GlobalScope`, so a test can
     * supply its own.
     */
    private val appScope: CoroutineScope = Graph.scope,
) : ViewModel()
```

`Graph.scope` is `Dispatchers.Default`. Room's generated suspend DAOs dispatch onto their own
query executor, so the write does not land on a UI thread — but the dispatcher question for view
models as a whole is **T-019's rule 1**, and this task must not start adding `io:` parameters
across the class. One scope, one purpose, named for it.

## What this task does, and what it leaves to T-012

They overlap and neither subsumes the other. Stated explicitly, because the plan's chain has T-012
in a different work package and a developer could reasonably assume one waits for the other.

**T-007 makes the last write survive a cancelled view-model scope.** After it, `flush()` runs on a
scope nothing navigational cancels, so the write completes whatever order the host tears down in.
That covers **both** hosts, and it covers a case T-012 cannot: on the panel, `onBack()` pops a
`NavBackStackEntry` and clears *that entry's* `ViewModelStore` — nothing to do with the activity's
owners, and T-012 does not touch it.

**T-012 makes the scope not be cancelled at the wrong time.** It drops the three owners that
shadow the SDK's (I-15), so disposal and clearing both follow
`ComposeFeature.panelViewLifecycleOwner` and `onDispose` runs *before* the store is cleared. That
is the structural fix and it matters for everything else in the panel, not only for `flush` —
I-12 (no `ON_STOP`, so every `collectAsStateWithLifecycle` keeps collecting behind a stopped
Space) and I-17 (view models cleared while their composables still read them) are the same change.

**Do not defer this task to T-012, and do not let T-012's landing remove this task's fix.**
Belt and braces is the correct posture for the one path that loses a person's words: T-007 means
a wrong teardown order cannot lose the write, T-012 means the order is not wrong.

**T-007 explicitly does not touch:** `SpatialPanelOwners`, `ImmersiveActivity.onDestroy`, the
`CompositionLocalProvider` block, or any `LaunchedEffect` in `NoteEditorScreen`. It also does not
touch **I-02** (the Today screen commits a dictation on the composition's scope) — same family,
different screen, and `TodayScreen`'s rebuild is T-028/T-030's ground.

**Step 2 — `save()` reads at call time and does not overwrite a moved state.**

```kotlin
    /**
     * Writes whatever the note is **now**, not what it was when this write was scheduled.
     *
     * Taking the note by value is how a 600 ms autosave scheduled before a dictation came back and
     * wrote the pre-dictation note over it — body, transcript and audio path — and the mirror
     * copied the loss into the vault.
     */
    private suspend fun save() {
        val sending = _state.value.note ?: return
        repository.upsert(sending).fold(
            onSuccess = { stored ->
                // Only claim "saved" about the note that was sent. Keystrokes that arrived while
                // the upsert was in flight are newer than `stored` and must not be written back over.
                if (_state.value.note == sending) {
                    _state.value = _state.value.copy(note = stored, saved = true, message = null)
                } else {
                    _state.value = _state.value.copy(message = null)
                }
            },
            onFailure = { failure -> _state.value = _state.value.copy(saved = false, message = failure.toMessage()) },
        )
    }
```

`stored` differs from `sending` in `updatedAt` and `tags` (`NotesRepository.kt:89-92` re-derives
both), so the equality is on the note the *caller* composed — that is deliberate and worth a
comment, because `sending == stored` is never true.

**Step 3 — `edit`, `flush`, `retry`.** Drop the argument. `edit` stays on `viewModelScope` (a
debounce that outlived the editor would be wrong). `flush` and `retry` move to `appScope`:

```kotlin
    fun flush() {
        if (_state.value.note == null || _state.value.saved) return
        saveJob?.cancel()
        saveJob = appScope.launch { save() }
    }
```

**Step 4 — `attachTranscript`.** Cancel the pending autosave, run the adoption where nothing
cancels it, publish the final path, then write:

```kotlin
    fun attachTranscript(transcript: Transcript, audioPath: String?) {
        val current = _state.value.note ?: return
        val body = listOf(current.body, transcript.text).filter { it.isNotBlank() }.joinToString("\n\n")
        _state.value = _state.value.copy(
            note = current.copy(
                body = body,
                title = current.title.ifBlank { transcript.text.take(60) },
                transcript = transcript,
            ),
            saved = false,
        )
        // The autosave scheduled before the person spoke holds the pre-dictation note. It must not
        // outlive this call: it would write that note back 600 ms from now.
        saveJob?.cancel()
        // appScope, not viewModelScope, and one job for the whole of it: the move is renameTo with
        // a copy-then-delete fallback (Vault.kt:69-72), and a cancellation between the copy and the
        // delete leaves two files while a cancellation after the rename leaves the note pointing at
        // a scratch path that has just stopped existing.
        saveJob = appScope.launch {
            val landed = vault.adoptOrKeep(_state.value.note ?: return@launch, audioPath)
            if (landed != null) {
                _state.value.note?.let { latest ->
                    _state.value = _state.value.copy(note = latest.copy(audioPath = landed))
                }
            }
            save()
        }
    }
```

## Corrections made while implementing this, against this document

Both were found by the task's own tests and both change code this spec printed in full, so they
are recorded here rather than left as a silent divergence.

1. **The adoption is not assigned to `saveJob`.** Step 4's code reads
   `saveJob = appScope.launch { … adoptOrKeep … }`, which is exactly what the task's own test
   *`a keystroke during a dictation does not cancel the adoption`* forbids: the next `edit()`
   cancels `saveJob`, and on a queueing dispatcher it does so **before the coroutine's first
   dispatch**, so the body never runs at all and the file is never moved. `withContext(NonCancellable)`
   does not help — it protects a body that has already started, not one that has not. The adoption
   therefore runs as its own job on `appScope`, and `attachTranscript` still cancels the *previous*
   `saveJob`, which is the half of the DoD line that matters (killing the stale pre-dictation
   autosave). Confirmed by planting the spec's version: that one test, and only that test, goes red.
2. **`backgroundScope` is the wrong `appScope` for the tests.** `runTest` registers its
   `backgroundScope` coroutines as background work, and `advanceUntilIdle` deliberately does not
   wait for it — so every write this task moves off `viewModelScope` silently never ran and all
   seven writing tests failed reading an empty repository. The tests use a scope they own on the
   same scheduler, `CoroutineScope(dispatcher)`, cancelled in `@After`.

Two additions beyond the written scope, both cheap and both evidence rather than behaviour:

- **A-08 has a test now.** The DoD asks the commit to name A-08 as closed by mechanism; a claim of
  that shape with nothing driving it is what this project's own evidence rule refuses. The audit's
  suggested name was used verbatim — `flushing immediately after a dictation keeps the adopted
  audio path` — and it was watched failing against a planted `flush()` that captures the note at
  call time, which is A-08's exact shape.
- **A-08 has no board row to move.** The board carries the plan's `T-` rows, not the audit's
  per-axis ids; `B-043` closes naming all three findings instead.
