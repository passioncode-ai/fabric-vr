# T-040 — Dependencies are verified, not merely pinned

- **Severity:** High
- **Work package:** WP-7 (release engineering)
- **Closes:** H-13, C-19
- **Depends on:** T-002 (CI — the metadata is worth little if nothing checks it on a clean runner)
- **Needs a headset:** no
- **Estimated blast radius:** 1 new tracked file (`gradle/verification-metadata.xml`, expect
  several thousand lines), 1 CI step, 1 runbook section, 1 `DEC` row. No source code.

## What is wrong, in the person's terms

Every clean build of this project downloads about 120 artefacts from `mavenCentral()` and
`google()` and runs them, with **no checksum, no signature check and nothing pinned beyond a
declared version number**. One of them is `meta-spatial-sdk-0.14.0.aar`, a 47.8 MB proprietary
native blob loaded into the same process as the microphone and the Keystore.

If any one of those artefacts were republished or substituted, it would enter a build that ships to
a second person's headset, and nothing in the toolchain would notice.

## Where it is

**The absence, measured:**

```bash
$ ls gradle/
libs.versions.toml   wrapper/

$ git ls-files gradle/
gradle/libs.versions.toml
gradle/wrapper/gradle-wrapper.jar
gradle/wrapper/gradle-wrapper.properties
```

No `verification-metadata.xml`. No `gradle.lockfile` anywhere.

**The resolution configuration.** `settings.gradle.kts:14-20`:

```kotlin
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        google()
        mavenCentral()
    }
}
```

Note the asymmetry with `pluginManagement` above it (`:1-13`), which filters `google()` by group
regex. Here it does not — `google()` is declared first and is asked for everything (C-22, a Low,
and this task's metadata makes it harmless rather than requiring a change).

**What the version catalog actually pins.** `gradle/libs.versions.toml:1-19` declares 18 versions.
A version is not an identity: `spatialsdk = "0.14.0"` names a coordinate, not a set of bytes.

**What is already correct, and must not be re-litigated.** The Gradle wrapper itself **is** pinned
and validated — `gradle/wrapper/gradle-wrapper.properties:3,6`:

```
distributionSha256Sum=20f1b1176237254a6fc204d8434196fa11a4cfb387567519c61556e8710aed78
validateDistributionUrl=true
```

C-19 left this half "pinned-but-unverified" for want of network access; **H-14 records it as
resolved and verified**. This task does not touch it.

## The decision, and what was weighed

**Chosen: dependency verification metadata with SHA-256 checksums, generated from a known-good
tree, committed, and re-generated deliberately at every version bump.**

**Alternatives considered:**

- ***Dependency locking (`gradle.lockfile`) as well, or instead.*** Rejected as a second
  mechanism. Locking pins *versions*, and the version catalog already does that for every
  first-order dependency; what locking adds is pinning transitive versions, which the checksums
  make moot — a substituted transitive artefact fails verification whatever its version. Locking
  also writes one lockfile per configuration per module, which on six modules with debug/release
  variants is a large amount of churn for the smaller half of the problem. **Verification is the
  mechanism that closes the supply-chain gap; locking is the one that closes a reproducibility gap
  this project does not currently have.** If reproducible resolution is later wanted, it is its own
  row.
- ***PGP signature verification instead of checksums.*** Rejected for v1. Gradle supports it, and
  it is stronger in principle — but coverage across Maven Central and `google()` is uneven, keys
  have to be trusted individually, and the failure mode ("this artefact is unsigned") produces a
  large `<trusted-keys>` block that nobody reads. SHA-256 answers the actual threat: *these bytes,
  and not other bytes.* Adding `pgp` later is additive and does not invalidate the checksums.
- ***Vendor the dependencies.*** Rejected: 47.8 MB of proprietary AAR plus ~120 artefacts in git,
  for a guarantee the metadata gives in one file.
- ***Do nothing until there is a real release.*** Rejected because it inverts the order: the
  metadata must be generated **at a moment the build is known-good**, and every day that passes
  adds a version bump whose provenance nobody checked. H-13 calls this the highest-leverage
  supply-chain gap in the project and one command to close; both halves are true.

## Decomposition

**Step 1 — establish that the tree is known-good before capturing it.**

The metadata records what is there *now*. Generating it from a compromised or half-resolved tree
records the compromise. So, first:

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew --refresh-dependencies clean testDebugUnitTest lintDebug :app:assembleRelease
bash scripts/check-secrets.sh && bash scripts/check-docs.sh && python3 docs/ux/lint.py
git status --short        # clean
git rev-parse HEAD        # recorded in the DEC row and in the metadata's own comment
```

**Abort if** anything is red. A green tree is the precondition, not the goal.

**Step 2 — generate, with a task set that resolves the real graph.**

`--write-verification-metadata sha256 help` is the command H-13 and C-19 both quote, and it
**under-covers**: `help` resolves almost nothing, so the resulting file misses most of the
artefacts the real build pulls and the first real build then fails on hundreds of missing entries.
Use the tasks that actually resolve:

```bash
./gradlew --write-verification-metadata sha256 \
  clean :app:assembleDebug :app:assembleRelease testDebugUnitTest lintDebug \
  --refresh-dependencies
```

Add `:app:assembleDebugAndroidTest` so the instrumented suite's dependencies are covered too — a
verification failure that only appears when someone runs the device suite is the worst time to
discover it.

**Step 3 — deal with the artefacts that will fight this, before committing.**

Three categories, each with a known answer:

| Category | Symptom | Answer |
|---|---|---|
| IDE-only artefacts (`-sources.jar`, `-javadoc.jar`) | Android Studio fails to sync with verification errors for artefacts Gradle never downloads on the command line | a `<trusted-artifacts>` block trusting `**/*-sources.jar` and `**/*-javadoc.jar`, with a comment saying why |
| Gradle's own module metadata (`.module`, `.pom`) | entries multiply | keep them — they are part of resolution and substituting one changes what is resolved |
| the Gradle wrapper and plugin-management artefacts | may resolve before verification applies | already covered by `distributionSha256Sum`; do not duplicate |

**Do not turn verification off to make a sync work.** `--dependency-verification lenient` exists
and is the right tool *while generating*; it is not a state to leave the project in, because a
lenient build prints warnings that look exactly like a build with no verification at all.

**Step 4 — commit it, and say what it is.**

`gradle/verification-metadata.xml` goes in with a commit message naming the commit it was captured
at and the task set used. The file is large and its diff is unreadable by eye; the commit message
is the only place the human-readable fact lives.

**This file is also the project's SBOM** (H-19): it is the only tracked artefact that enumerates
every third-party component the build pulls. Say so in the commit and in the module README, so the
next person who needs a component inventory does not build a second one.

**Step 5 — wire it into CI (T-002).**

Verification runs automatically once the file exists; the CI step is about making its failure
visible and legible. Add to the workflow, after the build:

```bash
# A verification failure must not be reported as a generic build error.
./gradlew --no-daemon testDebugUnitTest || {
  echo "::error::if this names verification-metadata.xml, see docs/runbooks/dependencies.md"; exit 1; }
```

and a job that runs with `--refresh-dependencies` on a schedule, so a republished artefact is found
by a nightly rather than by the next person who clears their cache.

**Step 6 — the runbook, because this is the part that will be met at the wrong moment.**

`docs/runbooks/dependencies.md`, covering the only three things a person will need:

1. **Bumping a version.** Edit `gradle/libs.versions.toml`, run the generation command from step 2
   again, review the diff (it should touch only the artefacts of the thing you bumped — if it
   touches unrelated entries, *stop and find out why*), commit both files together.
2. **A verification failure on a clean machine.** What the message looks like, and the rule: it is
   never resolved by deleting the file or adding `--dependency-verification off`. Either the
   artefact changed (investigate) or the metadata is stale (regenerate deliberately, from a green
   tree).
3. **Adding a new dependency.** Same as (1).

**Step 7 — the `DEC` row.** *Dependencies are verified by SHA-256 against committed metadata;
locking is deliberately not used and why.* Read `docs/DECISIONS.md:7` for the free id.

## What it costs on a normal change

This is the question that decides whether the mechanism survives, so it is answered with numbers
rather than reassurance.

| Change | Cost |
|---|---|
| editing Kotlin, adding a test, changing a string | **nothing.** Verification runs against the resolution cache and adds no measurable time |
| a clean build on a fresh machine | one SHA-256 per artefact over ~120 artefacts, most of them small; the 47.8 MB AAR dominates and it is hashed once |
| **bumping any version in `libs.versions.toml`** | the build **fails** with a verification error naming the artefact, until the metadata is regenerated: one command, then a diff to review. **This is the point, not a side effect** — an unreviewed change in what the build pulls is exactly what the file exists to surface |
| a transitive dependency changing under a first-order bump | the same failure, naming an artefact nobody edited — which is the case this is really for |
| Android Studio sync | unaffected once the `<trusted-artifacts>` block of step 3 is in |

The file is large and its diffs are noisy. That is the honest cost, and the mitigation is the
review rule in the runbook: **a verification diff that touches artefacts unrelated to the version
you bumped is a finding, not noise.**

## Tests

There is no application code here. The checks are the mechanism proving it can fail:

| Check | Where | Asserts |
|---|---|---|
| `a tampered artefact is refused` — **planted, watched failing** | locally, once | corrupt one byte of a cached artefact (or edit one checksum in the metadata), run `./gradlew testDebugUnitTest`, see it refuse, restore |
| `a clean machine builds` | CI (T-002), fresh runner, cold cache | green — proves the metadata's coverage is complete, which a warm local cache cannot |
| `the instrumented suite's dependencies are covered` | `./gradlew :app:assembleDebugAndroidTest` on that runner | green |
| `the metadata is not lenient` | `grep -c 'dependency-verification' gradle.properties` | 0 — no global escape hatch was left behind |

The first row is not optional. The project's own retro carries the reason: **a gate is not a gate
until a violation has been planted and watched failing it** — `check-secrets.sh` printed `ok`
while reading nothing, and ten planted credentials passed (`f7d656d`). The same standard applies
here, and it takes two minutes.

## Definition of Done

- [ ] `gradle/verification-metadata.xml` is committed, generated from a green tree whose commit is
      named in the commit message.
- [ ] A tampered artefact was **planted and watched failing** the build.
- [ ] A clean CI runner with a cold cache builds green — debug, release, JVM suite, lint, and the
      androidTest compile.
- [ ] Android Studio syncs without verification errors, via `<trusted-artifacts>` and not via
      disabling verification.
- [ ] `docs/runbooks/dependencies.md` exists; every command in it resolves (T-003's gate).
- [ ] The commit says the file is also the SBOM.
- [ ] A `DEC` row records the decision and the rejected alternative (locking), so it is not
      re-litigated.
- [ ] Four gates green.

## Blast radius, and what NOT to touch

- **Touches:** `gradle/verification-metadata.xml` (new), the CI workflow, one runbook, one `DEC`
  row. Possibly one comment in `settings.gradle.kts`.
- **Do not touch:** `gradle/wrapper/gradle-wrapper.properties`. `distributionSha256Sum` and
  `validateDistributionUrl=true` are already right and H-14 records them verified. Re-deriving or
  "tidying" them here risks replacing a verified pin with an unverified one.
- **Do not touch:** `gradle/libs.versions.toml` in the same commit. A version bump and a metadata
  regeneration in one diff is unreviewable — the whole value of the file is that its diff can be
  read against a known cause.
- **Do not touch:** the `pluginManagement` repository filters in `settings.gradle.kts:1-13`. They
  are correct and unrelated; C-22's asymmetry in `dependencyResolutionManagement` becomes harmless
  once bytes are pinned, and changing repository order during this task would change what resolves
  at the moment you are trying to record what resolves.
- **Never commit with `--dependency-verification off` or `lenient` set anywhere persistent.** A
  lenient build and an unverified build produce the same green.
- **Watch for:** `third_party/whisper.cpp` is a submodule and its native build is not a Gradle
  dependency — this task does nothing for it. Its integrity is the submodule pin's job
  (`.gitmodules`, H-20: `branch = master` invites `git submodule update --remote`, and master is
  83 commits ahead). That is a separate row and this task must not be read as having covered it.
