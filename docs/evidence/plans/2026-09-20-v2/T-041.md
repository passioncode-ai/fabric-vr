# T-041 — A headset that is not on this LAN can be updated

- **Severity:** High
- **Work package:** WP-7 (release engineering)
- **Closes:** H-32
- **Depends on:** **T-036 — this task's answer is decided by that one**; T-037 (a signed build that
  installs), T-038 (a version a person can name), T-039 (a key to sign with), T-002 (CI, if the
  release is published automatically)
- **Needs a headset:** yes, once, to prove the install path works from the other end
- **Estimated blast radius:** Option 1 — 1 CI workflow step, 1 runbook, 1 `docs/deployment` row.
  Option 2 — the same minus CI. Option 3 — 1 document.

> **T-036 decides what a second person's headset is, and this task's right answer changes with
> that decision.** Do not build a delivery mechanism for a user if the register says the device is
> a test copy, and do not close this as will-not-fix if the register says the device is a user's.
> The mapping is in *Recommendation*.

## What is wrong, in the person's terms

The only way a build reaches a headset is `adb connect` from this laptop. So the second headset can
be updated only when it and the laptop are in the same room. Between visits its build drifts
arbitrarily far from the operator's, and — with no crash capture (H-01) and no usable version
string (H-31) — nobody knows how far, or what it is doing.

Every Blocker in the 2026-09-20 audit is live on that device until the next physical meeting. That
includes the two that lose data: *Retry* deleting the recording it promises to keep (A-03), and
*Undo* restoring a note whose audio is gone (A-02).

## Where it is

**The whole delivery mechanism.** `scripts/install-on-quest.sh` — the file quoted in T-038, which
waits for a device, runs `adb install -r`, starts the activity and prints some logcat. It requires
a live `adb` link to the device, which in practice means the same LAN or a USB cable.

**What does not exist:**

```bash
$ git ls-remote --tags origin        # empty
$ ls .github                          # No such file or directory
$ grep -rn 'release' scripts/         # nothing
```

No GitHub Release, no artefact attached to anything, no Horizon release channel, no SideQuest
listing, no tag of any kind. The remote is `git@github.com:passioncode-ai/fabric-vr.git`.

**What makes any of this moot today:** the release variant has never been signed and never been
installed (the audit's verification table), `versionCode` is `1` on every APK (H-31), and there is
no signing key (H-34). So this task cannot be the first one done — it is the last of WP-7 for a
reason.

## The three answers

### Option 1 — a GitHub Release with the APK and a written install step

On a tag, CI (T-002) builds the signed release and attaches `app-release.apk` to a GitHub Release
named `v0.1.0+<sha>`. The other person downloads it in the headset's own browser and installs it,
or pulls it to a computer and uses Meta Quest Developer Hub over USB.

**What it costs:** an afternoon, once T-037/T-038/T-039 exist. One workflow job, one runbook page,
one `docs/deployment/devices.md` row updated per install.

**The consequence nobody mentions until it bites:** `passioncode-ai/fabric-vr` is a repository
whose release assets are only downloadable without authentication if it is public. If it is
private, the download URL requires a token — and handing a second person a GitHub token so they
can update a notes app is worse than the problem. **Check this before choosing Option 1**, and if
the repository is private, the honest variants are: make the release public while the repository
stays private (GitHub does not allow that — releases inherit repository visibility), publish the
APK to a different location the person can reach, or accept Option 2.

**What it does even if the link is never used:** it creates a durable, named, dated artefact. "Which
build is the tester on?" becomes answerable by comparing a version string to a release page instead of by
comparing APK bytes. That is most of H-32's harm gone, for the cost of the tag.

**What it does not do:** nothing tells the person a new build exists. The app never checks (H-33,
a separate Medium row, explicitly out of this task's scope and blocked on C-01 being fixed because
it would be a new outbound call on the URL parser T-010 is repairing).

### Option 2 — sideload via a link

Put the signed APK somewhere with a plain URL the person can open in the headset browser — a
static host, a shared drive with direct download, a short-lived link sent at each release. No CI, no
tags, no release page.

**What it costs:** almost nothing per release, and it costs the record. There is no dated artefact,
no version history, and no answer to "which build is that link?" six weeks later. It is Option 1
with the part that makes it auditable removed.

**Rejected as the primary recommendation** for that reason: the harm in H-32 is half "cannot
update" and half "cannot know", and Option 2 addresses only the first half. It is the right answer
only if Option 1 is blocked by repository visibility and no other host is acceptable.

### Option 3 — leave it manual, and document it

Write down that the second headset is updated in person, name the procedure, and record in
`docs/deployment/devices.md` what build it is on and when it was last touched.

**What it costs:** one document. **What it buys:** the state of the deployment stops living in one
person's memory, which is H-35's whole finding and T-036's whole output.

**Rejected as the primary recommendation, but not absurd.** For a two-headset test deployment
where both people meet regularly, a documented manual procedure is honest and complete. It becomes
dishonest the moment someone says "the tester can just update it" without a mechanism behind the
sentence.

### Named but out of scope — the Horizon Store release channel

Meta's Alpha channel is the mechanism built for exactly this: named testers, over-the-air,
automatic updates, no `adb`. It needs a Meta developer organisation, a signed build with a stable
`applicationId`, and store-side setup. **It is the correct answer if T-036 answers "second user"**,
and it is disproportionate for two testers. It is named here so that choosing Option 1 is a choice
rather than an omission.

## Recommendation

**It depends on T-036, and here is the mapping, so the decision does not have to be made twice:**

| T-036's answer | This task |
|---|---|
| **A — a copy for testing** *(T-036's own recommendation)* | **Option 1**, if the repository's visibility allows an unauthenticated download; **Option 3** if it does not and no other host is acceptable. Either way `docs/deployment/devices.md` gets the row — that is the part that closes the "cannot know" half. |
| **B — a second user** | Nothing below the Horizon Alpha channel is honest. Option 1 is a stopgap and must be recorded as one, with the channel as the next row. |
| **C — out of scope** | **Close as will-not-fix**, with the `DEC` row and the `devices.md` line recording the `versionCode` at which the device was abandoned. H-32 is answered by scope. |

**The smallest honest improvement, under the recommended path (A + Option 1):** a tag produces a
signed APK attached to a dated release, and the device register records what went where and when.
That is two mechanisms — one that can deliver and one that can answer — and neither of them
requires the other person to have a computer or a token if the repository is public.

## Decomposition — under Option 1

**Step 0 — the prerequisites, checked rather than assumed.**

```bash
gh repo view passioncode-ai/fabric-vr --json visibility   # decides whether Option 1 is viable at all
ls "$(grep storeFile keystore.properties | cut -d= -f2)"  # T-039
git ls-remote --heads origin                               # T-037's branch is pushed
./gradlew -q :app:assembleRelease && \
  apksigner verify --print-certs app/build/outputs/apk/release/app-release.apk   # signed, T-037/T-039
```

**Abort if** the repository is private and no alternative host is agreed — that is a decision, not
an obstacle to work around by embedding a token in a workflow.

**Step 1 — tags become the release trigger.** There are none today (`git ls-remote --tags origin`
is empty). Adopt `v<versionName>` — which, after T-038, is `v0.1.0+<short sha>`. Note that `+` is
legal in a git tag and in a GitHub release name; confirm it survives the workflow's own
interpolation before relying on it, and fall back to `v0.1.0-<sha>` if it does not.

**Step 2 — the workflow job.** In the CI T-002 creates, a job that runs on `push: tags: ['v*']`:

1. checks out with submodules (`third_party/whisper.cpp` — the NDK build needs it);
2. accepts SDK licences (H-38: `sdkmanager --licenses` appears nowhere in the repository and is the
   most common fresh-machine failure);
3. builds `:app:assembleRelease` with the signing passwords injected from repository secrets whose
   **names** mirror T-039's vault names (`FABRICVR_KEYSTORE_PASSWORD`, `FABRICVR_KEY_PASSWORD`) and
   the keystore itself supplied as a base64 secret decoded to a runner-local path;
4. runs `apksigner verify --print-certs` and **fails if the fingerprint does not match the one
   recorded in `docs/deployment/signing.md`** — otherwise a misconfigured runner silently publishes
   an unsigned or differently-signed APK, which is H-23 again with a download link on it;
5. attaches the APK to the release.

**No secret value in the workflow file, in a log, or in a release note.** The fingerprint is public
and belongs in the check; nothing else from the signing path does.

**Step 3 — the install note, written for the person who is not in this repository.** Three lines,
in the release body itself rather than only in `docs/`:

> Open this page in the headset browser, download the APK, and open it from Downloads. Horizon OS
> will ask you to allow installing from this source once. If it refuses to install over the
> existing app, stop and message me — do not uninstall it, that deletes your notes.

The last sentence is the important one and it is why this task depends on T-037. A person told to
"just uninstall it" is one message away from the exact loss T-037 exists to prevent.

**Step 4 — the register.** `docs/deployment/devices.md` (T-036) gains the `versionCode` and the
date after every install, taken from the script's own output (T-038) rather than from memory.

**Step 5 — the runbook.** `docs/runbooks/release.md`: tag, watch the workflow, verify the
fingerprint, update the register, tell the person. Every command in it must resolve — T-003's gate
will check.

**Step 6 — the `DEC` row.** *Builds reach a headset that is not on this LAN as a signed APK
attached to a tagged GitHub Release; the app does not check for updates itself.* The second clause
matters: without it, H-33 reads as an oversight rather than as a scoped-out decision. Read
`docs/DECISIONS.md:7` for the free id.

## Tests

| Check | Where | Asserts |
|---|---|---|
| `the published APK is signed by our key` | the workflow, step 2.4 | `apksigner verify --print-certs` fingerprint equals the recorded one — **planted failure watched**: run it once with the debug key and see it refuse |
| `the release artefact is downloadable by someone who is not the operator` | by hand, once | a logged-out browser (or the second person) reaches the file |
| `the APK on the release page installs over the installed build` | on the second headset, once | `install -r` equivalent succeeds — this is T-037's rotation proven from the other end |
| `the tag and the version agree` | the workflow | the tag's suffix equals `BuildConfig.GIT_SHA` in the built APK |

The third row is the one that proves the whole task. Until an APK from the release page has gone
onto a headset that was not plugged into this laptop, H-32 is not closed — it is only prepared for.

## Blast radius, and what NOT to touch

- **Touches:** one CI job, one runbook, one register row, one `DEC` row, and the release body
  text. No application source.
- **Do not touch:** `scripts/install-on-quest.sh`. It is the LAN path and it stays; T-038 owns its
  changes. Two tasks editing one script is how a device-pick guard gets reverted by a merge.
- **Do not build an in-app update check.** That is H-33, it is a new outbound call, and it is
  blocked on T-010 (C-01 — `NetworkPolicy` reads a URL's userinfo as its host). Adding it here
  would route a new request through a parser that is currently exploitable.
- **Do not put the keystore or its passwords in the repository, in a workflow file, or in a log.**
  The keystore reaches CI as an encrypted repository secret and is decoded to a runner-local path
  that is deleted with the runner; the passwords reach it by name (T-039). If that is not
  acceptable, release from the laptop by hand and say so in the runbook — a manual release with a
  safe key is better than an automated one with an exposed key.
- **Do not publish a release before T-037 has completed on both headsets.** A download link to a
  differently-signed APK, in the hands of someone who will hit
  `INSTALL_FAILED_UPDATE_INCOMPATIBLE` and reach for `uninstall`, is a data-loss mechanism with a
  friendly URL.
- **Watch for:** the APK is ~150 MB. A headset-browser download over the other person's Wi-Fi is
  minutes, and Horizon OS's download manager and "install from unknown source" prompt are the two
  places the procedure will actually fail. Walk it once yourself before sending the link.
