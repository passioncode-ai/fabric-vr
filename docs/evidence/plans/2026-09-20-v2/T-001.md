# T-001 — Make the instrumented suite green for the right reason

- **Severity:** Blocker
- **Work package:** WP-0 (honest build)
- **Closes:** F-02, F-03, E-18
- **Depends on:** nothing
- **Needs a headset:** partly — the *fix* is written and reviewed off-device; the *observation* that
  `PanelSmokeTest` is now green needs a Quest. The named observation is in **Tests** below.
- **Estimated blast radius:** 2 test files changed, 1 test file deleted, 1 test file added, 1 new
  tracked ledger, 1 string corrected. No production behaviour changes.

## What is wrong, in the person's terms

Nobody reading this repository can tell a broken app from a broken test.

The handoff says, at `docs/handoff/2026-09-19-v1-build-handoff.md:115-118`:

> **The instrumented suite has now run.** 13 tests on a Quest 3, 0 failures, 0 skipped

Two of the fifteen instrumented tests that exist today cannot pass, for two completely different
reasons, and the document distinguishes neither:

- **`PanelSmokeTest` asserts two sentences no screen renders.** It will be red on any device, in
  any room, forever. It is a stale assertion.
- **`ImmersiveLaunchTest` fails when nobody is wearing the headset.** The shell defers the
  immersive launch behind a Guardian dialog and the panel never composes. It is an environmental
  condition, and the code under test may be perfectly correct.

And a third file, `VoiceViewModelStateTest`, is **green and proves nothing** — it re-types the rule
it claims to check and asserts against its own copy. It occupies the name a real test would be
found under, so an absence reads as a presence.

The consequence is the one F-03 names: the next agent runs the suite, sees red, and bisects for a
regression that is not there — or, worse, "fixes" the red by weakening the assertion.

## The decision, and what was weighed

### 1. `PanelSmokeTest` — it asserts the control that exists, by resource id, not by literal

**Chosen:** the test keeps its name and its job (the panel's Compose tree stands up and draws the
Today screen), and its two assertions become one assertion against `R.string.action_record`
resolved through the activity's own resources, plus one against `R.string.app_name` in the header
(`TodayScreen.kt:122-126`) — a node that is present in **every** `VoiceState`, which the record
button's label is not.

The question the plan asked — *does it assert the new control, or is it replaced?* — has an answer
that is not "either": **it asserts the new control, but never as a literal.** A literal assertion
is how this defect happened, and it will happen again the first time `copywriting` touches the
string. Resolve the id.

**Alternatives considered:**

- *Delete `PanelSmokeTest`.* Rejected: it is the only machine evidence that the 2D panel composes
  at all, and `docs/evidence/verification.md:161` cites it for REQ-001. Deleting it silently
  removes a requirement's only evidence.
- *Relax to `assertExists()` instead of `assertIsDisplayed()`.* Rejected: the node exists in the
  semantics tree before it is laid out, so this passes over a panel that drew nothing — the exact
  class of vacuous pass the retro's second standing instruction (F.md:216) was written about.
- *Assert `R.string.today_empty` instead.* Rejected on inspection, and this is worth recording:
  `strings.xml:102` reads *"Nothing here yet. Hold Record and say something, or start a note."* —
  it names the deleted hold gesture **and** a *New note* control that does not exist. Pinning a
  test to it would make the suite enforce a lie. That string is corrected in this task (step 5);
  it is not what the test asserts.
- *Assert the literal again, but the right literal.* Rejected: same failure, one commit later.

### 2. `ImmersiveLaunchTest` — it stays red, and the red is recorded as environmental

**Chosen:** the test is **not** changed, **not** `@Ignore`d, and **not** weakened. What changes is
that its red becomes *attributable*: a tracked `docs/evidence/device-gate.md` records every
instrumented run with the date, the commit, the device serial, the environment (headset worn or
not) and the per-test outcome, and this test's row carries `expected red — headset unworn` with
the observation that would flip it.

**What to do about a test that fails when nobody is wearing the headset:** make the failure say
which of the two it is, and write down which one was seen. The test already does the first half —
its message names the cause. The second half is the ledger, which does not exist.

**Alternatives considered:**

- *`@Ignore("needs a worn headset")`.* Rejected: an ignored test is invisible. The suite would
  report 14 green and the Space's launch — the one claim in this tree with no device evidence
  behind it — would have no failing signal at all. `@Ignore` converts a known unknown into an
  unknown unknown.
- *`Assume.assumeTrue(composedAtLeastOnce)` so it reports *skipped* rather than *failed*.*
  Rejected, and this is the tempting one. The assumption's condition is identical to the
  assertion, so it would turn the test's entire subject into its precondition: the test would
  report "skipped" whenever the Space did not compose, which is precisely the case it exists to
  catch. `421377e` added that assertion because the previous test passed over a Space that never
  opened; an assumption on the same predicate re-creates that hole with a nicer colour.
- *Detect the Guardian dialog and assume on that instead.* Rejected as unbuildable here: nothing
  in the app can observe the shell's dialog, and an approximation ("was a proximity sensor
  triggered") would be an assumption about the thing we cannot measure. If a later platform
  assertion for "the scene composed" appears, the retro instruction at `F.md:216` names that as
  the retirement condition.
- *Run it only under a `-PdeviceGate` flag.* Rejected for now: it hides the test behind a flag
  nobody will set, and `connectedDebugAndroidTest` is already manual. Revisit if the ledger proves
  the noise is real.

**This one has an operator-facing half.** Whether the two headsets are worn during a device gate
run is a person's choice, not a developer's. The ledger row therefore has an `Environment` column
with the vocabulary `device-worn` / `device-unworn`, and **the person running the gate fills it**.
Do not invent a code-side detection for it.

### 3. `VoiceViewModelStateTest` — deleted, and replaced by a test of the real class

**Chosen:** delete `VoiceViewModelStateTest.kt` and add
`app/src/test/kotlin/ai/passioncode/fabricvr/ui/VoiceViewModelTest.kt`, which constructs the real
`VoiceViewModel` and asserts the guard at `VoiceViewModel.kt:100` through the public API.

**The scope limit, stated because it is not obvious.** The full record → stop → transcribe path
**cannot** be tested in this task. `VoiceViewModel`'s `recorder` parameter
(`VoiceViewModel.kt:40`) is typed as the concrete, final class
`ai.passioncode.fabricvr.stt.AudioRecorder` (`feature-stt/.../AudioRecorder.kt:21`), which takes a
`Context` and talks to `AudioRecord`. There is no seam to fake it through. Making one is a
signature change to `AudioRecorder.record`, which is **T-020**'s change (it rewrites that callback
to `ShortArray` for E-02). Doing it here would mean doing it twice.

What *is* reachable today, with no new seam: `onPermissionResult`, `consumed()`, `cancel()`, and —
crucially — the guard, because a `Failed` state is reachable without ever recording. That is the
one this task must land, because it is the one the deleted file pretended to cover.

**Alternatives considered:**

- *Leave `VoiceViewModelStateTest` and add a real test beside it.* Rejected: two files, one of
  which is a decoy. The next reader greps for `VoiceViewModel` tests and finds the wrong one first.
- *Make `AudioRecorder` an interface now.* Rejected: T-020 changes the same signature for a
  different reason. Two churns of one seam, and the second one would have to redo the first one's
  fakes.
- *Keep the file, fix it in place.* Rejected: the file's KDoc (`:10-14`) describes a hold gesture
  that does not exist, both test names say "release", and neither name is true of the product.
  Nothing in it survives.

## Decomposition

**Step 1 — write the failing test first, and watch it fail.**
New file `app/src/test/kotlin/ai/passioncode/fabricvr/ui/VoiceViewModelTest.kt`. Robolectric, which
`:app` already has (`app/build.gradle.kts:107`) though no `:app` test uses it yet; follow the
pattern in `core-notes/src/test/.../NotesRepositoryTest.kt:26,34`.

```kotlin
@RunWith(RobolectricTestRunner::class)
class VoiceViewModelTest {
    private fun viewModel() = VoiceViewModel(
        recorder = AudioRecorder(ApplicationProvider.getApplicationContext()),
        modelStore = { FakeModelStore(present = true) },
        engine = { FakeEngine() },
        language = { "auto" },
        serverUrl = { null },
        audioDir = { tempDir() },
    )
```

Three tests:

1. `stopping after a refused microphone keeps the failure on screen` — `onPermissionResult(granted
   = false, permanent = true)`, then `stopAndTranscribe(true)`, assert the state is still
   `VoiceState.Failed` and its `message.action` is still `UiAction.OPEN_APP_SETTINGS`.
2. `stopping when nothing is recording changes nothing` — from `Idle`, `stopAndTranscribe(true)`,
   assert the state is still `Idle` and that no engine call was made.
3. `granting the microphone leaves a state the screen can act on` — `onPermissionResult(true,
   false)`, assert `VoiceState.Allowed`. **This test is expected to pass today.** It exists to pin
   the current behaviour so that A-07's fix (T-030's ground — `Allowed` renders nowhere) is a
   deliberate change with a failing test, not a silent one. Mark it in a comment as a
   pinning test, not a regression test.

**Watch 1 and 2 fail** by deleting `VoiceViewModel.kt:100` before running them. If they pass with
that line gone, they are testing something else. Then restore the line.

**Step 2 — delete `VoiceViewModelStateTest.kt`.** Whole file. Do not port its names.

**Step 3 — `PanelSmokeTest`.** Resolve ids against the activity's resources rather than asserting
sentences:

```kotlin
    @Test
    fun the_panel_renders_the_today_screen() {
        val context = compose.activity
        compose.onNodeWithText(context.getString(R.string.app_name)).assertIsDisplayed()
        compose.onNodeWithText(context.getString(R.string.action_record)).assertIsDisplayed()
    }
```

`R` here is `ai.passioncode.fabricvr.R`. Note `app_name` is also the activity label and may match
more than one node in a future layout — if `onNodeWithText` throws on ambiguity, use
`onAllNodesWithText(...).onFirst()` and say so in a comment rather than switching to a weaker
assertion.

Add a comment above the assertions recording *why* they resolve ids: the literal form of this test
was red for three commits and nothing said so.

**Step 4 — `docs/evidence/device-gate.md`, new tracked file.** One row per instrumented run:

| Date | Commit | Device | Environment | `connectedDebugAndroidTest` | Red, and why |
|---|---|---|---|---|---|

`Environment` vocabulary: `device-worn`, `device-unworn`. Declare it in the file, the way
`verification.md:88-96` declares its own — F-24 exists because a value was used and never declared.
Seed the file with one row describing the last known state (`421377e`, `ImmersiveLaunchTest` red,
`device-unworn`) and mark it as reconstructed from `421377e`'s commit message, not observed.

**T-002 consumes this file** (H-10): a push that touches `*/src/androidTest/**` with no ledger row
whose commit is an ancestor of `HEAD` fails CI. This task creates the file and its shape; T-002
writes the check. Do not build the check here.

**Step 5 — the one string that makes the suite's subject false.** `strings.xml:102`:

```xml
<string name="today_empty">Nothing here yet. Hold Record and say something, or start a note.</string>
```

Change to text that is true of this build — it names a gesture deleted in `732c92b` and a control
that does not exist. Suggested: `Nothing here yet. Press Record and say something.` **This is the
only production-facing change in this task**, and it is here because a test that asserts against
the empty state (a reasonable next step) would otherwise pin the lie. The full string sweep is
T-032's; take only this one.

**Step 6 — do NOT delete the dead strings.** `action_hold_to_record` and `action_new_note` are
E-13's and T-032's. They stop being load-bearing once step 3 lands, and that is all this task
needs to be true.

## Blast radius, and what NOT to touch

- **Touches:** `PanelSmokeTest.kt`, `VoiceViewModelStateTest.kt` (deleted),
  `VoiceViewModelTest.kt` (new), `strings.xml` (one string), `docs/evidence/device-gate.md` (new).
- **Do not touch:** `ImmersiveLaunchTest.kt` — including its `SETTLE_MS`. Lengthening the wait to
  make it pass would be the "fix" F-03 warns about. `ImmersiveActivity.composedAtLeastOnce` — I-27
  notes it is never reset between runs in one process; that is T-016's.
  `AudioRecorder`'s signature — T-020 owns it. The 25 dead strings — T-032 owns them.
  `VoiceViewModel.retryLast()` — T-005 owns it.
- **Watch for:** `:app` has no Robolectric test today, so this is the first one. If the runner needs
  an SDK level pinned, add `app/src/test/resources/robolectric.properties` with `sdk=34` (matching
  `minSdk`) rather than annotating each class — and say so in the commit, because a new
  `robolectric.properties` changes how every future `:app` JVM test runs.
- **Neighbouring breakage:** `docs/evidence/verification.md:161` cites `PanelSmokeTest` as REQ-001's
  evidence. Its wording survives this change, but the row is stale for other reasons (F-33) and is
  T-044's to correct — do not edit it here beyond nothing.
