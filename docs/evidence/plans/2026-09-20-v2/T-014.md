## What is wrong, in the person's terms

They put on the headset, enter the Space, and tap *Search*. The field takes focus on its own and
the keyboard comes up. They type two letters, then reach out to tap the first result.

Nothing happens. They tap again. Nothing. They tap *Back*. Nothing. They tap the ✕ that clears the
query. Nothing. Every target on the panel is dead, and the only thing still working is the keyboard
itself. There is no message, no visual change, nothing that distinguishes this from the app having
frozen. The way out is to take the headset off or to use the system menu.

This is not a bug in this app's code. The Spatial SDK drops the touch event before it reaches our
view, and it says so in the log while it does it.

Three things follow that are not in the audit rows and that change what is buildable:

**1. The guard covers all three dispatch routes, not just ours.** Activity-backed panels
(`TaskContainer`), virtual-display panels and view panels are gated by the same `ifeq 106`. Moving
our text entry to an activity-backed panel does not escape it.

**2. `isAcceptingText()` is *our* process's IME state, and we can change it.** It answers "is the
currently served view accepting text", and the served view is our `OutlinedTextField` inside our
`ComposeView`. `focusManager.clearFocus()` plus `keyboardController?.hide()` makes it false and the
panel becomes live again. The problem is purely that the only input channel we normally have —
a tap — is the one thing that is blocked. **We need a channel that is not a tap.**

**3. There is one, and it is public API.** `SceneObject.addInputListener(InputListener): Long` is
public, and `SceneObject.onClick` / `SceneObject.onInput` iterate **every** registered listener
with no short-circuit:

```
SceneObject.onClick(HitInfo, Entity):
  12: getfield #81   // inputListeners:Ljava/util/HashMap;
  23..103: for each entry -> InputListener.onClick(this, hitInfo, sourceOfInput)
```

`SceneObject.onInput` is the same shape — it maps every listener to a `Boolean` and *then* folds
with `any`, so no listener can prevent a later one running. The SDK's own `PanelInputListener`
(held on `PanelSceneObject.PanelInputListenerId`) is just one entry in that map, and it is the one
that calls `dispatchEvent`. **A second listener we register receives the pointer event before and
independently of the IME guard.** That is the escape hatch, and it exists in 0.14.0.

**4. The SDK offers no keyboard API of its own.** Searched all five AARs:

```bash
for j in ~/.gradle/caches/modules-2/files-2.1/com.meta.spatial/*/0.14.0/*/*.aar; do
  unzip -p "$j" classes.jar > /tmp/c.jar && unzip -l /tmp/c.jar | \
    grep -E 'Keyboard|Ime[A-Z$.]|IME|TextInput|Soft'
done
```

→ **no matches.** No `VirtualKeyboard`, no IME helper, nothing named for text input anywhere in
`com.meta.spatial.*`. The Spatial SDK release notes through 0.14.0 (11 September 2026, the newest
release that exists — axis H) contain no keyboard entry either. So there is nothing to adopt and
nothing to upgrade to; whatever is done here is ours.

**Our side of it:**

- `SearchScreen.kt:43-46` focuses the field on entry:
  ```kotlin
  val focus = remember { FocusRequester() }
  // Focused on entry: the person came here to type, and a raycast to a text field costs a second.
  LaunchedEffect(Unit) { runCatching { focus.requestFocus() } }
  ```
  So Search does not merely risk the trap — it enters it on arrival, before the person has done
  anything.
- `grep -rn "SoftwareKeyboardController\|LocalFocusManager\|clearFocus\|imeAction" app/src/main
  core-common/src/main` → **nothing**. No field in the app sets an IME action, and nothing anywhere
  hides the keyboard or clears focus.
- Text fields exist on Search (`SearchScreen.kt:50`), the editor (`NoteEditorScreen.kt`, title and
  body), Chat (multi-line, so its IME has no *Done*), and Settings (six `rememberSaveable` fields:
  server URL, cloud URL, cloud key, cloud model, OpenRouter key, vault path).

## What nobody has established, and why the task cannot start without it

B-01 proves what happens **while the IME is accepting text**. It does not prove that the IME ever
appears for a Spatial panel. D-19 says the same from the scenario side and marks it unproven; the
merge lists it first under *What no reader could settle*. There are three possible worlds and they
need different code:

| World | What is observed | What this task becomes |
|---|---|---|
| **W1** | The IME appears; typed text lands in the field; taps are swallowed while it is up | Route 1 below — make the trap escapable |
| **W2** | No IME appears at all; the field takes focus and nothing can be typed | Route 2 below — the Space is read-plus-dictate, and six scenarios become panel-only |
| **W3** | The IME appears but text does not reach the field | Route 2, and a separate defect report to Meta; do not build around it |

## The measurement that decides it

**On a Quest 3, one session, about fifteen minutes. This is the exact observation, and no other
evidence substitutes for it.**

Preparation — one debug-only listener so question 4 can be answered at the same time as 1–3. In
`ImmersiveActivity.onSceneReady()`, after `Entity.create(...)`:

```kotlin
if (BuildConfig.DEBUG) {
    SpatialActivityManager.getAppSystemActivity()   // or the entity's own SceneObject
        .let { /* resolve the PanelSceneObject for PANEL_ID */ }
        ?.addInputListener(object : InputListener {
            override fun onClick(so: SceneObject, hit: HitInfo, source: Entity) {
                val imm = getSystemService(InputMethodManager::class.java)
                Log2.i("space.rawclick", "acceptingText" to imm.isAcceptingText)
            }
        })
}
```

Then, in the Space:

1. **Does an IME appear?** Tap *Search*. Field auto-focuses.
   `adb shell dumpsys input_method | grep -E "mInputShown|mServedView|mCurFocusedWindow"`.
   `mInputShown=true` is the answer to W1-vs-W2.
2. **Does typed text land?** Type `ор` on whatever keyboard appeared.
   `adb logcat -s FabricVR:*` and watch the search query state, or read the panel through
   `adb exec-out screencap`.
3. **Are taps swallowed?** With the keyboard still up, tap *Back* five times.
   `adb logcat | grep "Software Keyboard was shown"` — five lines means the guard fired five times
   and this is exactly B-01.
4. **Does the raw listener still fire?** Same five taps: `adb logcat -s FabricVR:* | grep
   space.rawclick` — five lines with `acceptingText=true` means **route 1 is buildable**; zero lines
   means the scene-level input is also gated somewhere this disassembly did not reach, and route 1
   is off the table regardless of which world we are in.
5. **Does clearing focus restore the panel?** From the listener, call
   `keyboardController.hide()` + `focusManager.clearFocus()` on the next tap, then tap *Back* again
   and see whether it works. This is the end-to-end proof of route 1 in one gesture.

**Record all five answers in `docs/evidence/verification.md`** with the date, the device serial and
the SDK version. That file is where the plan's *"the first thing to measure on the headset"* is
discharged. **This task's board row does not move until those five lines exist.**

## The decision, and what was weighed

**Chosen, conditionally: route 1 — an input escape hatch plus the ordinary IME hygiene — if
observation 4 fires. Route 2 — the Space is read-plus-dictate, stated in the interface — in every
other case. Route 2 is also the fallback if route 1 is built and the observation at step 5 of its
own verification does not hold.**

### Route 1 — the trap is escapable (build if W1 **and** observation 4 fires)

Three pieces, in order of how much they carry:

1. **A panel-level escape listener.** One `InputListener` registered on the panel's `SceneObject`
   for the life of the panel. On `onClick`, if `imm.isAcceptingText()`, it hides the keyboard and
   clears focus and consumes that tap. Cost to the person: the first tap after typing dismisses the
   keyboard instead of pressing what they aimed at. That is the behaviour of every phone with a
   full-screen IME, and it is infinitely better than a dead panel.
2. **IME hygiene on every field** (B-01's own proposal): `KeyboardOptions(imeAction = ImeAction.Done)`
   plus `KeyboardActions { focusManager.clearFocus(); keyboardController?.hide() }` on Search,
   Settings' six fields and the editor's title. Chat's input is multi-line and gets `ImeAction.Send`
   bound to `ask()` rather than `Done`, or it is made single-line — a `super-ux` question, flagged,
   not decided here.
3. **Search stops auto-focusing.** `SearchScreen.kt:46`'s `LaunchedEffect(Unit) { focus.requestFocus() }`
   is deleted **in the immersive host**. Its comment is right about the panel and wrong about the
   Space: a raycast to a field costs a second, and being unable to leave costs the session. Pass
   `autoFocus: Boolean` down from the host (`FabricApp` already distinguishes them by
   `onLeaveSpace != null`), or better, add an explicit `isImmersive` to `FabricApp` so the reason is
   named rather than inferred from an unrelated lambda.

### Route 2 — the Space is read-plus-dictate (build if W2, W3, or observation 4 is silent)

- Search, Assistant and Settings are **not reachable** from the Space's header. The three actions
  are absent, not disabled-with-a-tooltip: a control that cannot work is worse than no control.
- The editor in the Space is **read plus dictate**: the body is rendered, the *Record* button works
  (dictation needs no keyboard, which is the whole point of this product), and the text fields are
  read-only with one line under them — `space_text_is_panel_only` — saying where to type.
- Today keeps Record, the note list, Copy, *Transcribe again*, delete and undo. Everything the
  product's headline gesture needs, in the room.
- `docs/ux/screens.md` and `docs/ux/scenarios.md` record that SCN-001, SCN-003, SCN-008, SCN-010,
  SCN-011 and SCN-014 are panel-only, with the bytecode as the reason.

**This is a real loss and the spec should not soften it.** `docs/ux/foundation.md`'s access
principle says the same notes are reachable from both surfaces. Route 2 keeps *reading* and
*dictating* in both and moves *typing* to one. The honest sentence is: **the Space is where you
speak and read; the panel is where you type.** That is defensible for this product in a way it
would not be for a general note-taker, because dictation is the primary path and typing is the
repair path — but it must be written down as a decision with that reasoning, not left as an
absence.

### Alternatives considered

- *Subclass `PanelDisplay` and override `dispatchEvent`, or call the protected `setImm(null)` so
  the guard can never fire.* Both are reachable: `PanelDisplayBase` and `PanelDisplay` are open,
  `dispatchEvent` is `public` and not `final`, `getImm`/`setImm` are `protected`, and
  `PanelRegistration.panelCreator(Scene, SpatialContext)` is public and open, so a subclass could
  build its `PanelSceneObject` with a custom `Function4<…, PanelDisplay>` factory and still use
  `composePanel` for the view. **Rejected.** The guard is not a bug the SDK forgot to remove — the
  two non-`rootView` paths inject a `MotionEvent` into a *virtual display* through reflected
  `InputManager.injectInputEvent`, while the IME window lives on the real display and owns focus.
  Defeating the guard sends input into a display whose focus the system believes is elsewhere; the
  outcome is undefined and untestable without a headset, and if it misbehaves it will misbehave as
  "taps land on the wrong thing", which is worse than "taps do nothing". It also puts us in the
  business of reimplementing `panelCreator` against a surface that moved twice in the last four
  SDK releases. The escape listener gets the same result through API the SDK means us to use.
- *Move text entry to an activity-backed panel (`ActivityPanelRegistration` / `IntentPanelRegistration`),
  on the theory that the shell handles the IME for a contained task.* Rejected: the `TaskContainer`
  branch is at offset 106, *after* the same `ifeq`. It is behind the identical guard. It is also a
  second Compose host with its own owners, which is the problem T-012 exists to reduce.
- *Upgrade the SDK.* Not available. 0.14.0 is the newest release (axis H, and confirmed against the
  release notes index while writing this spec); no release note in the series mentions a keyboard.
- *Add an in-panel software keyboard of our own — a Compose key grid.* Rejected for v1, and it is
  worth saying why it is not absurd: it would sidestep the IME entirely, because a Compose button
  grid raises no `InputMethodManager` and `isAcceptingText()` stays false. It is also several
  hundred lines, two layouts (Latin and Cyrillic — see G-09), and a worse typing experience than
  the system keyboard on a device whose system keyboard is good. If route 2 is taken and typing in
  the Space later turns out to be load-bearing, **this is the thing to build**, and that sentence
  belongs in the decision record so the option is not rediscovered from scratch.
- *Show a message when the keyboard is up ("tap the keyboard's ✓ to continue").* Rejected as the
  whole answer: the message would have to be drawn by a recomposition, which works, but the person
  still cannot act on it with a tap. It is a good **addition** to route 1 and is specified there as
  the label on the escape.

### If route 1

**Step 1 — write the failing test first.** Two tests, in two places, because the seam is split:

`app/src/test/kotlin/ai/passioncode/fabricvr/ImeEscapeTest.kt` (JVM, Robolectric) over the *policy*
object, not the SDK:

```kotlin
class ImeEscape(
    private val isAcceptingText: () -> Boolean,
    private val dismiss: () -> Unit,
) {
    /** @return true when the tap was spent dismissing the keyboard and must not be forwarded. */
    fun onPanelTap(): Boolean = if (isAcceptingText()) { dismiss(); true } else false
}
```

1. `a tap while the keyboard is up dismisses it and is consumed`
2. `a tap while the keyboard is down is not consumed and does not dismiss`

`app/src/androidTest/.../SpaceImeTest.kt` (instrumented):

3. `search does not open the keyboard on entry in the Space` — enter, assert
   `dumpsys`-equivalent state or simply that the field is not focused.

Run them. **Watch 1 and 3 fail**; 2 passes trivially and exists so the escape cannot regress into
"always dismiss", which would make the panel unusable in the opposite direction.

**Step 2 — the escape listener.** In `ImmersiveActivity.onSceneReady()`, after `Entity.create`,
resolve the panel's `PanelSceneObject` and `addInputListener` an object that calls the `ImeEscape`
policy. Keep the returned id and `removeInputListener` in `onDestroy` — the map lives on the
`SceneObject`, which outlives a recomposition. The dismissal itself is a Compose concern, so the
listener sets a `MutableStateFlow<Long>` tick that a `LaunchedEffect` in `FabricApp` collects and
answers with `keyboardController?.hide(); focusManager.clearFocus()`. **Do not** call
`InputMethodManager.hideSoftInputFromWindow` directly from the listener: the listener runs on the
SDK's input thread, and the IMM call must be on Main.

**Step 3 — IME hygiene.** Every `OutlinedTextField` in `app/src/main/.../ui/` and
`core-common/.../ui/` gets `keyboardOptions` and `keyboardActions`. There are enough of them that a
shared `fabricTextField()` modifier-plus-defaults in `core-common/ui` is cheaper than nine edits and
stops the tenth field shipping without it. Chat's *Send* mapping is flagged to `super-ux` in the
commit, not decided here.

**Step 4 — Search stops auto-focusing in the Space.** Add `isImmersive: Boolean = false` to
`FabricApp`, pass `autoFocus = !isImmersive` into `SearchScreen`, and set it from
`ImmersiveActivity.kt:117`. Do **not** key it off `onLeaveSpace != null` — that lambda means
"this host can return to the panel", and reusing it as "this is the Space" is how the next
behavioural difference gets attached to the wrong condition.

**Step 5 — say it on screen.** One string, shown in the Space only, above a focused field:
`<string name="space_keyboard_hint">Tap anywhere to close the keyboard.</string>`. It is the
message that makes the first wasted tap intelligible instead of mysterious.

## Blast radius, and what NOT to touch

  class with its test, `FabricApp` (`isImmersive`), `SearchScreen` (`autoFocus`), the text fields
  across five screens, two strings.
- **Touches, route 2:** `FabricApp` (graph), `TodayScreen` (header), `NoteEditorScreen`
  (read-only mode), six strings, six scenario rows, two docs.
- **Do not touch:** `PanelActivity` or anything that changes the 2D panel's behaviour. The panel
  works; every change here is conditional on the immersive host, and a test asserts the panel is
  unaffected in both routes. **This is the single largest risk in this task** — it is very easy to
  make Search read-only for everyone.
- **Do not touch:** `PanelDisplayBase`, `PanelDisplay`, `PanelRegistration.panelCreator`, or any
  reflection into the SDK's input path. The rejected alternative is rejected; a later agent must
  not reach for it because it looks shorter.
- **Do not touch:** `SearchViewModel`'s debounce or query handling. If Search is removed from the
  Space (route 2) the view model stays exactly as it is — it is the panel's.
- **Watch for:** route 1's listener holds a reference to the activity through the tick flow. Remove
  it in `onDestroy` or the `SceneObject`'s map keeps it past teardown.
- **Watch for:** `isAcceptingText()` is per-process, and the panel and the immersive activity are
  two activities in **one** process. If both are alive (the panel in the background while the Space
  is open), a focused field in the backgrounded panel could make the Space's guard fire. The
  measurement should be repeated once with the panel left open behind the Space; if that reproduces,
  it is a second finding and belongs on the board, not silently inside this fix.

## Correction to the finding

Both cited rows are correct as to fact. Three things are missing from them, and each changes what
gets built:

1. **B-01 says "no tap reaches the panel"; it does not say that *typing* still works.** The IME
   delivers text through the input connection, not through panel touch, so in world W1 the person
   can type — they simply cannot do anything else. The finding reads as "text entry is impossible",
   and the measurable claim is narrower and worse: *text entry works and then locks the panel*.
   Route 1 exists because of that distinction.
2. **Neither row knows that `SceneObject.addInputListener` is an unguarded channel.** Axis I's
   *Not covered* section explicitly leaves `PanelDisplayBase.dispatchEvent`'s threading and any
   workaround unestablished, and says "this axis did not establish … whether an IME-dismiss
   workaround can be written at all". It can: the listener map is public, the dispatch loop
   short-circuits nothing, and the SDK's own `PanelInputListener` is one entry in that map. That is
   new and it is the reason this task has a route 1 at all.
3. **The SDK has no keyboard API whatsoever**, which is stronger than "the SDK cannot be upgraded
   out of the keyboard trap". A class-name search across all five 0.14.0 AARs returns zero matches
   for `Keyboard`, `IME`, `TextInput` or `Soft`. There is nothing to call, so "raise the Horizon
   system keyboard explicitly" (D-19's proposed fix) is not implementable through this SDK; it
   would mean the OpenXR `XR_META_virtual_keyboard` extension from native code, which is a
   different project.
