## What is wrong, in the person's terms

In the Space they press the controller's **B** button, or make the back gesture, expecting to go
back a screen the way every other Horizon app does. Nothing happens. Not "nothing visible" —
nothing at all: the key event is discarded three frames before anything in this app could see it.

That on its own would be a missing convenience. What makes it a defect is that the code says
otherwise. `ImmersiveActivity.kt:46` reads:

```kotlin
private val owners = SpatialPanelOwners(onUnhandledBack = { returnToPanel() })
```

and `SpatialPanelOwners.kt:32` documents it as "What Back does when nothing in the composition has
consumed it." Back does nothing, the lambda has never run, and the next person to read that line
will believe there is an exit path there and build on it.

## Where it is

`com.meta.spatial.runtime.VrActivity.dispatchKeyEvent` — the class `AppSystemActivity` extends
(`public class AppSystemActivity extends com.meta.spatial.runtime.VrActivity`) — is 65 bytes and
contains no call to `android.app.Activity.dispatchKeyEvent`:

```
public boolean dispatchKeyEvent(android.view.KeyEvent);
   7: getfield      #142  // gameControllerDeviceIds:Ljava/util/Set;
  12: invokevirtual #1093 // KeyEvent.getDeviceId()
  18: invokeinterface #1079 // Set.contains(Integer)
  23: ifeq 63
  26..51: pinnedControllers[deviceId]?.invoke(null, event)
  61: iconst_1 / 62: ireturn    // a pinned game controller: consumed, super never called
  63: iconst_0 / 64: ireturn    // everything else: "not handled", super never called
```

`dispatchGenericMotionEvent` has the identical shape. Reproduce:

```bash
JAVAP="/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/javap"
cd "$(mktemp -d)" && unzip -q ~/.gradle/caches/modules-2/files-2.1/com.meta.spatial/\
meta-spatial-sdk/0.14.0/*/meta-spatial-sdk-0.14.0.aar && unzip -q classes.jar
"$JAVAP" -p -c com/meta/spatial/runtime/VrActivity.class | \
  sed -n '/public boolean dispatchKeyEvent/,/^$/p'
```

`Activity.dispatchKeyEvent` is what routes `KEYCODE_BACK` into `onKeyUp` → `onBackPressed` →
`onBackPressedDispatcher`. It is never reached, so:

- `grep -rn "onBackPressed" app/src/main` → two hits, both in `SpatialPanelOwners.kt` (`:21` the
  KDoc, `:42` the field). **No call site.**
- `grep -rn "setOnBackInvokedDispatcher\|enableOnBackInvokedCallback" app/ ` → nothing. The
  Android 13+ predictive-back route (`ComponentActivity` registers the platform dispatcher; a
  plain `Activity` does not) is not wired either.
- `grep -rn "BackHandler" app/src/main core-common/src/main` → **zero**. The app contains no
  `BackHandler` at all; the only callback in the dispatcher is navigation-compose's own
  `PredictiveBackHandler`, and it is fed nothing.

So the dispatcher exists for exactly one reason: to stop `PredictiveBackHandler` throwing at
composition. That is a real reason (T-012 keeps it for that). It is not the reason the code states.

## The decision, and what was weighed

**Chosen: accept that a Back *key* does not exist in the Space, delete the fallback that pretends
otherwise, and make the on-screen exit reach the Space boundary from every screen — after one
on-device observation that could still overturn the first half.**

The premise most of this discussion rests on is wrong and has to be corrected before the options
are weighable: **the Space is not a trap for want of an exit control.** Every screen already
renders one:

| Screen | Its own Back | Reaches |
|---|---|---|
| Today | — | `onLeaveSpace` icon, `TodayScreen.kt:135-137` → `returnToPanel()` |
| Search | `SearchScreen.kt:49` | `nav.popBackStack()` → Today |
| Note editor | `NoteEditorScreen.kt:81` | Today |
| ~~Assistant~~ VOID | ~~`ChatScreen.kt:49`~~ | deleted by `DEC-0020` |
| Settings | `SettingsScreen.kt:71` | Today |

So leaving the Space from Search is two taps, not zero. What is missing is a **key**, and a
*one*-tap exit from a screen that is not Today. (Search is still a trap while the keyboard is up,
but for B-01's reason — no tap reaches the panel at all — which is T-014's, not this task's.)

**Alternatives considered:**

- *Override `dispatchKeyEvent` in `ImmersiveActivity` to feed the dispatcher on `KEYCODE_BACK`
  `ACTION_UP` (I-13's and B-15's first proposal).* **Rejected as written, pending the observation
  below.** It is eight lines and it is the right shape — `dispatchKeyEvent` is `public` and not
  `final`, `super` is unreachable so the override is the whole mechanism, and the SDK's game-pad
  branch can be preserved by delegating to `super.dispatchKeyEvent` for everything that is not
  Back. The problem is that **nobody has established that a Back key event reaches an immersive
  `VrActivity` on Horizon OS at all.** In an OpenXR immersive session the runtime consumes
  controller input; the B button is not an `InputDevice` key to the app unless the shell sends it,
  and there is no navigation bar. Shipping the override without that evidence produces the exact
  defect this task closes: a plausible path nobody can show firing. Write it *after* the log says
  the events arrive, not before.
- *Register the platform dispatcher with `setOnBackInvokedDispatcher` (C-02's proposal) and set
  `android:enableOnBackInvokedCallback="true"`.* Rejected on its own: it is the correct thing to do
  in a `ComponentActivity`, and here it changes nothing, because `VrActivity` swallows the key
  before the platform's own callback path is reached and the immersive activity has no system back
  affordance to invoke the platform dispatcher from. It becomes worth doing only if the
  observation shows the system *is* sending back invocations, in which case it replaces the
  `dispatchKeyEvent` override rather than joining it.
- *Keep the fallback and correct only the comment (B-15's second proposal).* Rejected. "This
  dispatcher's fallback is unreachable" documented next to a live-looking `onUnhandledBack =
  { returnToPanel() }` is a footnote against a signature; the next reader takes the signature. A
  lambda that has never run and cannot run is deleted, not annotated.
- *Put `onLeaveSpace` on every screen as a header icon, like Today's.* **Partly chosen, with a
  caveat.** Today's exit is `Icons.Filled.ViewInAr` — the same glyph as the *enter the Space*
  action, unlabelled (B-25). Copying it to four more screens copies the confusion four times.
  Reaching the Space boundary from every screen is right; doing it with that icon is not. The
  control is specified below with a word on it.
- *Make the person's own Back control the only story and do nothing else.* Rejected: it leaves
  `onUnhandledBack` in the tree.

**Open to the operator, one line, answer before step 3:** should the exit from a non-Today screen
*leave the Space* (`returnToPanel()`) or *go back one screen* (`popBackStack()`)? They are
different intentions and the interface currently offers only the second.
Trade-off: one control that always leaves is predictable and loses the person's place in the nav
stack; two controls is honest and costs 72 dp of a 1024 dp header that already holds five actions
on Today. **This spec assumes "go back one screen, and Today keeps the only leave-the-Space
control", because that is what the code does today and changing it is a `super-ux` question, not a
platform one.** If the answer is the other one, step 3 changes and nothing else does.

## The observation that settles the first half

**On a Quest 3, one run, five minutes.** Add to `ImmersiveActivity`, behind `BuildConfig.DEBUG`:

```kotlin
override fun dispatchKeyEvent(event: KeyEvent): Boolean {
    if (BuildConfig.DEBUG) {
        Log2.i("space.key", "code" to event.keyCode, "action" to event.action,
               "device" to event.deviceId, "source" to event.source)
    }
    return super.dispatchKeyEvent(event)
}
```

Then, in the Space, on the Today screen: press **B** on each controller, make the system back
gesture, and if a Bluetooth keyboard is paired press Escape and Backspace.

```bash
adb logcat -c && adb logcat -s FabricVR:* | grep space.key
```

- **Any line with `code=4` (`KEYCODE_BACK`) and `action=1`** → the key reaches the activity. The
  override is real; write it (step 5) and this task gains a working Back.
- **No line at all** → the runtime consumes controller input and no key is delivered. Back does not
  exist in the Space, the override would be dead code, and step 5 is deleted from this spec rather
  than implemented.
- **Lines for some other code but not 4** → record which, in the commit and in
  `docs/evidence/verification.md`. That is a third answer and it changes the mapping, not the shape.

Record the result in `docs/evidence/verification.md` with the date and the device serial. **This
task's row stays open until that line exists** — it is the only claim here that code cannot settle.

## Decomposition

**Step 1 — write the failing test first.**
`app/src/androidTest/kotlin/ai/passioncode/fabricvr/SpaceBackTest.kt` (new):

1. `pressing back in the Space does not silently do nothing` — launch `ImmersiveActivity`, wait for
   `composedAtLeastOnce` (T-016 replaces the marker; use whatever it leaves), then
   `instrumentation.sendKeyDownUpSync(KeyEvent.KEYCODE_BACK)` and assert the documented outcome.
   **Write the assertion for the behaviour the observation reports**, and if the answer is "no key
   arrives", the test asserts that instead — `assertFalse(activity.backWasDispatched)` with a
   comment naming the bytecode — so that a future SDK that *starts* delivering keys turns this test
   red and forces the decision to be re-made rather than drifting.
2. `the exit control is present on every screen in the Space` — Compose test over `FabricApp`,
   navigate to each of the five routes and assert a node with a click action and the text
   `action_back` (or `action_leave_space`) exists.

Run them. **Watch 2 fail** on Search/Chat/Settings/editor only if step 3 changes their contract; if
it does not, watch it pass and say so — a test that was green before the change is evidence the
premise was wrong, and that belongs in the commit (see *Correction to the finding*).

**Step 2 — delete the dead fallback.** In `ImmersiveActivity.kt:46`, `SpatialPanelBackOwner` (T-012's
reduced class) no longer takes `onUnhandledBack`:

```kotlin
private val owners = SpatialPanelBackOwner(this)
```

and its dispatcher is constructed with no fallback: `OnBackPressedDispatcher()`. The class doc gains
the sentence that replaces the deleted lambda:

```
 * Nothing feeds this dispatcher. VrActivity.dispatchKeyEvent (0.14.0, 65 bytes) never calls
 * super, so no key event reaches Activity's back path; this exists so navigation-compose's
 * PredictiveBackHandler can compose, and for nothing else. Measured <date>, see
 * docs/evidence/verification.md. Exit from the Space is the control on Today.
```

Delete `returnToPanel()`'s only other reference? No — it is still called from
`onLeaveSpace = { returnToPanel() }` at `ImmersiveActivity.kt:119`. Leave the function alone.

**Step 3 — make the exit reachable without leaning on a keyboard-blocked tap.** Per the assumption
above, no route change: every screen keeps its own Back and Today keeps `onLeaveSpace`. What does
change is the **label**, because the current one cannot be told from its opposite:

- `TodayScreen.kt:136` renders `SmallAction(stringResource(R.string.action_space),
  Icons.Filled.ViewInAr, …)` for *enter* and `:142` renders `SmallAction(stringResource(
  R.string.action_back), Icons.Filled.ViewInAr, leave)` for *leave* — the same glyph, and the leave
  one is labelled "Back", which in this app already means "pop one screen".
- Add `<string name="action_leave_space">Leave the Space</string>` to
  `app/src/main/res/values/strings.xml` and use it at `:142`, with a different glyph
  (`Icons.Filled.CloseFullscreen` or `Icons.AutoMirrored.Filled.ExitToApp`).

This is one string and one icon; it is in this task rather than T-030 because it is the control the
whole *"can the person get out"* question rests on, and leaving it ambiguous makes T-013's Definition
of Done unverifiable by a person.

**Step 4 — say it in the scenarios and the screens doc.** `docs/ux/screens.md` → *Panel geometry* is
not the place; add one line under the Space's screen entries: "In the Space, the system Back key
does nothing — `VrActivity` discards key events. Every screen carries its own Back control and Today
carries *Leave the Space*." `docs/ux/scenarios.md` gets the same sentence wherever a scenario says
"press Back". T-042 owns the scenario sweep; this task owns the one sentence that is now true.

**Step 5 — ONLY IF the observation says keys arrive.** Add to `ImmersiveActivity`:

```kotlin
/**
 * VrActivity.dispatchKeyEvent never calls super (0.14.0, 65 bytes), so this override IS the back
 * path — there is no platform one underneath it to fall through to. Delegating everything else
 * to super preserves the SDK's pinned-game-controller branch, which is the only thing it does.
 */
override fun dispatchKeyEvent(event: KeyEvent): Boolean {
    if (event.keyCode == KeyEvent.KEYCODE_BACK &&
        event.action == KeyEvent.ACTION_UP &&
        event.repeatCount == 0
    ) {
        owners.onBackPressedDispatcher.onBackPressed()
        return true
    }
    return super.dispatchKeyEvent(event)
}
```

and restore a fallback on the dispatcher — `OnBackPressedDispatcher { returnToPanel() }` — because
now it can fire. Change the class doc from "nothing feeds this dispatcher" to what does.
Do **not** also call `super.onBackPressed()` anywhere: `returnToPanel()` already calls `finish()`,
and a second finish after the PendingIntent has been sent is the redundant-finish shape C-02
describes.

  `ImmersiveLaunchTest` has — the shell can defer the launch behind a Guardian dialog. Use whatever

## Correction to the finding

**The plan cites B-14. That row is something else.** `B.md:39` — B-14 is "`copied` is never reset,
so the row's button reads *Copied* for the rest of the screen's life" (`TodayScreen.kt:370,446,452`).
The Back row is **B-15** (`B.md:40`): "`Activity.onBackPressed()` is never invoked in the immersive
activity, so nothing ever dispatches to `owners.onBackPressedDispatcher`". Cite B-15. B-14 is a real
Medium finding with no task; fold it into T-030, which touches the same file.

**Two claims in I-13 are overstated, and the overstatement matters because it is what makes this
look like a Blocker.**

1. *"in the Space the only exit is the `onLeaveSpace` icon on Today … so the only way out is the
   system menu."* False. Search, Chat, Settings and the editor each render a `TextButton` bound to
   `nav.popBackStack()` (`SearchScreen.kt:49`, `ChatScreen.kt:49`, `SettingsScreen.kt:71`,
   `NoteEditorScreen.kt:81`) which reaches Today, where the exit is. Two taps, not zero. What is
   true is that no *single* control leaves the Space from a non-Today screen, and that `onLeaveSpace`
   is only passed to `TodayScreen` (`FabricApp.kt:43-51`).
2. *"every `BackHandler` inside the tree is inert."* Vacuous: `grep -rn "BackHandler" app/src/main
   core-common/src/main` returns nothing but the KDoc mention in `SpatialPanelOwners.kt:21`. The app
   has no `BackHandler`. The only registered callback is navigation-compose's internal
   `PredictiveBackHandler`. Saying "inert handlers" implies there is app behaviour being lost; there
   is not. What is lost is the *ability to add one* and have it work — which is the finding worth
   keeping.

Both corrections lower this task's user-visible severity and raise its documentation severity: the
defect that survives is a stated behaviour the platform does not deliver, sitting one line above the
code a future agent will extend.
