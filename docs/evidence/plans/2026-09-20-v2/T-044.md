## What is wrong, in the person's terms

`docs/evidence/verification.md` is the file that answers "what do we actually know is true?". All
eighteen of its rows were observed against trees that are now **twelve to thirty-one commits old**,
none of them says so, and the mechanism the file describes for saying so does not exist.

The file spends `:48-73` defining four staleness states — `current`, `behind`, `unresolvable`,
`unanchored` — and delegates computing them to `scripts/exposure.sh`. There is no
`scripts/exposure.sh`. Its producer block at `:14-16` instructs
`python3 scripts/graph.py producer`. There is no `scripts/graph.py`.

```bash
$ ls scripts/
check-docs.sh   check-secrets.sh   install-on-quest.sh   push-model-for-tests.sh
```

So the four states have never been computed once, and no row has ever been marked `behind` despite
every row being behind.

## Correction to the finding

**Two corrections. One is a mis-citation in the plan; the other is a wrong number in the audit.**

**1. The plan's `Closes` range is wrong.** — **applied 2026-09-21; the plan's own row now reads
`F-14, F-15, F-24, F-33`.** The line number this paragraph used to cite has drifted since, so it is
dropped rather than left pointing at unrelated prose; the row is `T-044`'s in the task table.
As found, the plan cited `F-20…F-26` for this task. Of that range,
only **F-24** is about the verification ledger. F-20 is `docs/modules/core-notes.md`, F-21 is
`docs/modules/core-common.md`, F-22 is `README.md`, F-23 is the build handoff, F-25 and F-26 are
`docs/DOCMAP.md` — all of them **T-045's**. The ledger findings are **F-14** (the REQ-009
overclaim), **F-15** (the two missing scripts) and **F-33** (every row behind). The `Closes` line
at the top of this spec is the corrected set.

**2. F-33's own staleness numbers are wrong, by a factor of two on three of its five rows.**
F.md's table states REQ-001 is 13 commits behind, the `325e100` rows 12, the `e235a81` rows 11, the
`830ad0a` rows 10 and the `f770049` row 9 — measured, per its header, at `421377e`. Recomputed at
that same commit:

```bash
$ for c in d9967a3 325e100 e235a81 830ad0a f770049; do
    echo "$c..421377e = $(git rev-list --count $c..421377e)"; done
d9967a3..421377e = 21
325e100..421377e = 27
e235a81..421377e = 26
830ad0a..421377e = 9
f770049..421377e = 8
```

The first three are off by 8, 15 and 15. The last two are off by one, consistent with an inclusive
count. **The range "9–13 commits behind" is wrong; at `421377e` it was 8–27, and at `8c5ff9e` it is
12–31.** F-33's *direction* is right and its per-row invalidation analysis is sound and is used in
full below — only its arithmetic moves, and it moves the wrong way: the ledger is staler than the
audit said.

This is itself an instance of what the file exists to prevent. A number restated rather than
computed is the class F-21 and F-22 also belong to, and it is the argument for step 1 below:
**write the script, then the number is never typed again.**

## The decision, and what was weighed

### The two missing scripts get different answers, and the reason is what each one can know

**`scripts/exposure.sh` — write it.** Everything it needs is in the repository: an `Observed at`
commit and `git rev-list --count <sha>..HEAD`. It is about twenty lines and it makes F-33
uncomputable-by-hand rather than merely unfixed.

**`scripts/graph.py producer` — remove the citation.** Look at what the producer block actually
prints (`verification.md:19-26`):

```
actor: unavailable: TASK_PIPELINE_ACTOR is not set by this harness
model: unavailable: TASK_PIPELINE_MODEL is not set by this harness
runtime: unavailable: TASK_PIPELINE_RUNTIME is not set by this harness
skill: task-pipeline@1.69.0
config: sha256:3bb638e189c9ef46
commit: fbd8a67e…
trace: unavailable: TASK_PIPELINE_TRACE is not set by this harness
```

Four of the seven fields are harness environment variables **this harness does not export**, and
the file's own rule (`:34-38`) is that such a field says so by name. Three are resolvable from the
tree. A script that printed four "unavailable" lines and three `git`/version lookups is not worth
vendoring, and vendoring it would be importing a tool from another project to satisfy a citation.

So: replace `:14-17` with the two commands this project can actually run
(`git rev-parse HEAD`, and the skill version read from where it is recorded), keep the field
vocabulary and the "a field is never deleted and never guessed" rule verbatim — **that rule is the
valuable part and it survives the script's removal.**

**Alternatives considered:**

- ***Vendor both scripts from the skill that wrote this file.*** Rejected for `graph.py`, as
  above. Rejected for `exposure.sh` too, in favour of writing it here: a twenty-line script tuned
  to this file's own column layout is cheaper to maintain than a vendored one whose contract can
  drift, and it can be given the planted-failure test this project requires of a gate.
- ***Delete both sections and stop describing staleness.*** Rejected: the staleness model at
  `:48-73` is correct and is the file's best idea. The defect is that it was never computed, not
  that it was wrong.
- ***Edit the eighteen rows in place to say `behind`.*** Rejected, and forbidden by the file's own
  header (`:1-3`, append-only; `:68` "Invalidation is not deletion. An overtaken row is not wrong —
  it is true about the tree it observed, and it stays"). Staleness is **computed and printed**, not
  written into a row. Re-observing **appends**.

## Decomposition

**Step 1 — `scripts/exposure.sh`, first, because everything else is measured with it.**

Twenty lines. It reads every `Observed at` cell in `docs/evidence/verification.md`, resolves each
commit, and prints the four states with a total:

```
current 0 · behind 18 · unresolvable 0 · unanchored 0
```

per-row detail behind a flag. The file's rule at `:74-76` is explicit and must be honoured: **state
zero prints out loud** — `current 12 · behind 0 · …` is a measurement, and printing nothing when
everything is fresh is what makes freshness indistinguishable from a check that never looked.

It is a **disclosure, not a gate**: no floor, no direction, never a target, for the same reason
`Human` has none. It exits 0 whatever it finds, and it exits non-zero only when it cannot parse the
file — a script that cannot read the ledger must not report `behind 0`.

**Step 2 — plant a failure and watch it.** Add a row with a commit that does not resolve; the
script must print `unresolvable 1`, not skip it. Add a row with an empty `Observed at`; it must
print `unanchored 1`. Remove both. This is the project's own standard (`f7d656d`: `check-secrets.sh`
printed `ok` having read nothing, and ten planted credentials passed).

**Step 3 — wire it into CI** (T-002) as an informational step whose output is in the log, and into
`scripts/check-docs.sh` as a **printed line**, not a failure condition.

**Step 4 — fix the two prose defects.**

- `verification.md:88-96` — declare `device` in the Environment table: *a real Quest 3, named by
  `ro.serialno`; accumulated state, like `local`, but on the target hardware*. F-24's point is not
  that `device` is wrong; it is the right value. The rule it broke is that it was never declared.
- `verification.md:14-17` — replace the `scripts/graph.py producer` instruction with the commands
  this project can run. Keep `:28-38` verbatim — the "paste one block per run" rule and "a field is
  never deleted and never guessed" are the valuable half.

**Step 5 — append the new observations.** A new dated section with its own producer block, below
the existing rows, under a heading naming the commit. **Nothing above it is edited.** F-14's
correction appears as a *new* REQ-009 row whose note says "17 cases, not 17 shapes; `InsecureUrl`
now covered" — the old row at `:159` stays, because it is true about the tree it observed and
because editing it would hide that the overclaim was ever made.

**Step 6 — the rows this run itself owes.** The file's rule at `:205-207` is that stage 8 writes
one row per REQ the run shipped. The run that produced `4bddfcc`…`421377e` touched REQ-001, 003,
004, 007 and 010 and wrote **nothing**. Write them now, retroactively and marked as such, or the
gap is permanent.

**Step 7 — a `DEC` row** recording that `exposure.sh` is this project's staleness instrument and
that `graph.py` was deliberately not vendored, with the reason. Without it, the next agent reads
the removed citation as an accident and re-adds it. Read `docs/DECISIONS.md:7` for the free id.

## Blast radius, and what NOT to touch

- **Touches:** `scripts/exposure.sh` (new), `docs/evidence/verification.md` (two prose sections and
  an appended block), `scripts/check-docs.sh` (one printed line, one vocabulary check), the CI
  workflow, one `DEC` row.
- **Do not edit any existing row.** The file is append-only by its own header and the reason is
  load-bearing: an overtaken row is true about the tree it observed. This includes `:159`'s
  overclaim — it is corrected by a new row saying so, not by a silent fix.
- **Do not fill `Human`.** `:184-190` — it is the one column in the pipeline a machine may not
  write, and the one signal the project has about the world outside its own checks. If the operator
  walks the device gate (T-043), **they** write the date.
- **Do not give `exposure.sh` a threshold, a floor or a non-zero exit on `behind`.** `:74-76` and
  `:192-196` both say why: the moment `behind` becomes something to avoid printing, rows stop being
  re-observed and start being re-worded.
- **Do not vendor `scripts/graph.py`** to satisfy the citation. Removing the citation is the
  decision; re-adding the script is re-opening it without the `DEC` row that closed it.
- **Watch for:** `exposure.sh` parses a markdown table. It will break the first time a row's note
  contains a `|`. Either escape-tolerate it or parse by column index from the right; a staleness
  tool that silently drops a row it could not parse is a tool that reports `behind 0` for the wrong
  reason — which is the entire finding this task closes.
