## What is wrong, in the person's terms

The app stutters at exactly the moments it must not.

Tapping *Record* does three Keystore decrypts and two filesystem `stat` calls before the meter
appears. Letting go writes about two megabytes of WAV on the drawing thread. The first *Ask*
builds an HTTP client, renders up to sixty notes into a twelve-kilobyte string and encodes it to
JSON, all before the first token. On the very first run of a fresh install, generating the
Keystore key — which the code politely asks StrongBox for first — happens inside a lock that the
click handler is waiting on.

In the 2D panel that reads as jank. In the Space it is worse: the panel's texture is redrawn from
the same main thread that composes it, so a stall there is a frozen rectangle hanging in the room
while the passthrough world behind it moves normally. The person's own room keeps working and the
app does not.

## The decision, and what was weighed

The findings are fourteen `withContext` patches. A list of fourteen patches is not a fix, because
the fifteenth call site is written next week by somebody reading the file, not the audit. **What
this task lands is a rule about which layer owns a dispatcher, and the patches are what the rule
costs today.**

### The rule

> **R1 — A function that touches the Keystore, the filesystem, JNI or the network is `suspend` and
> switches its own thread.** Its caller needs no knowledge of dispatchers. `FileVault`,
> `AudioRecorder`, `ModelDownloader`, `RemoteWhisperClient` and `CloudTranscriptionClient` already
> obey this. `Graph`'s settings-reading accessors and `OpenRouterClient.stream` do not, and this
> task brings them in.
>
> **R2 — A view model's `viewModelScope.launch { … }` body may read a `StateFlow`, assign one, and
> call suspend functions. Anything else it does itself — JSON, rendering, a loop over the note
> base — goes in `withContext(io)`, where `io` is an injected
> `CoroutineDispatcher = Dispatchers.IO`.** The parameter exists for testability, not for taste:
> `SettingsViewModel.kt:69-71` records that a hard-coded `Dispatchers.IO` cannot be waited for from
> a test.
>
> **R3 — A composable never calls a `suspend` function that writes.** `LaunchedEffect` and
> `rememberCoroutineScope` observe and invoke non-suspend view-model entry points; the view model
> owns the scope the work runs on. A commit scoped to a composition is cancelled by navigation
> (I-02), which is a data-loss defect, not a threading one — but it is the same rule.

R1 is the load-bearing one. R2 alone is what the findings propose, and it fails the same way the
current code failed: it puts the obligation at every call site. With R1, forgetting `withContext`
in a view model costs nothing, because there is nothing left in `Graph` that blocks.

### The mechanical check that keeps it

```bash
# R1: no blocking primitive in main source outside a component that owns its dispatcher.
grep -rn "runBlocking" app/src/main core-*/src/main feature-*/src/main   # must be empty (T-018)

# R2: inside any viewModelScope.launch that has no withContext, nothing may reach a blocking seam.
python3 tools/check_main_thread.py   # see step 6
```

Axis I states the grep heuristic — *"`grep -n "Graph\.\|File(\|WavWriter\|settings.get"` inside
any `viewModelScope.launch {` that has no `withContext`"* — and says it matches eleven sites today.
A one-line grep cannot see block structure, so step 6 makes it a small script. Without it this task
decays.

### Alternatives considered

- *Make `SecureSettings.get`/`put` `suspend`.* The purest version of R1, and **rejected for this
  task**. `SecureSettings` is an interface with two implementations, six `KEY_*` constants, callers
  in `Graph` (seven), `SettingsViewModel` and `OpenRouterClient`'s `apiKey` lambda, plus
  `InMemorySecureSettingsTest` and the instrumented `SecureSettingsTest`. Making it suspend is a
  correct, large, separate change. Putting the boundary one layer out — at `Graph`'s accessors,
  which every app-side caller already goes through — buys the same property for this app at a
  tenth of the diff. **Say this in the commit**: the boundary is at `Graph`, not at
  `SecureSettings`, and the reason is the size of the blast radius, not a belief that
  `SecureSettings` is safe to call from Main.
- *Wrap each of the fourteen in `withContext(Dispatchers.IO)` where it stands.* Rejected: it is
  what the findings say and it leaves `Graph.whisperModel()` callable from Main by the next
  feature.
- *Move everything to `Dispatchers.Default` instead of `IO`.* Rejected. Most of the fourteen are
  genuine blocking IO (Keystore, files, `SharedPreferences`); `Default` is sized to the core count
  and would starve. The two that are CPU — the 12 KB render (#9) and `json.encodeToString` (#10) —
  are small enough that splitting the pool for them is premature. One `io` per view model, and a
  note in the rule that a future CPU-heavy path takes `Dispatchers.Default` explicitly.
- *Generate the Keystore key lazily and accept the first-run cost (#14).* Rejected: it is a
  one-time cost paid at the worst possible moment — the person's first tap on a new install, which
  is also the moment D-05 and G-17 say the first run must reach a dictation without reading a
  document. Generating it eagerly and off Main in `Graph.init` costs nothing anyone will notice.
- *Add `StrictMode` with `penaltyDeath` to the debug build permanently.* **Chosen in part**:
  `penaltyLog` permanently in debug, `penaltyDeath` behind a build flag used for the measurement
  below. Permanent `penaltyDeath` turns any third-party disk read — Room's, the SDK's, Compose's
  font loading — into a crash on someone else's schedule, and the suite would be red for reasons
  nobody here can fix (H-08's ground again).

## Decomposition

The rule is the change. The list below is what obeying it costs today, in the order that keeps each
commit reviewable.

**Step 1 — write the failing tests first.** Threading is the one subject where an assertion is
easy to write and easy to write uselessly. Three shapes, all of them real:

`app/src/test/kotlin/ai/passioncode/fabricvr/ui/VoiceViewModelThreadTest.kt`:

1. `recording work does not run on the calling thread` — construct `VoiceViewModel` with
   `io = StandardTestDispatcher(scheduler)` and fakes that **record the thread name** they were
   called on; call `start()` and `stopAndTranscribe()`; assert the WAV writer and the settings
   readers were not called on the test's main dispatcher thread.
2. `the WAV is written before the transcription starts` — ordering, which the `withContext` must
   not break.

`feature-assistant/src/test/kotlin/.../StreamDispatcherTest.kt`:

3. `stream's prologue does not run in the collector's context` — collect `stream(...)` from a
   known dispatcher and assert `apiKey()` was invoked on another. Today it is invoked on the
   collector's, because `callbackFlow` has no `flowOn`.

`app/src/test/kotlin/ai/passioncode/fabricvr/MainThreadPolicyTest.kt`:

4. `no viewModelScope.launch touches a blocking seam without withContext` — run the step-6 script
   over the source tree as a JVM test and assert the finding count is zero. **This is the test that
   outlives the fourteen patches**, and it is the one to write first: today it reports eleven
   sites, which is the failing baseline the commit should quote.

**Watch 1, 3 and 4 fail.** 2 passes today and exists to stop the fix reordering the write.

**Step 2 — `Graph`'s accessors become `suspend` (R1).** Add a private
`private val io = Dispatchers.IO` and wrap:

```kotlin
suspend fun whisperModel(): WhisperModel = withContext(io) { WhisperModel.byKey(settings.get(KEY_STT_MODEL)) }
suspend fun sttProvider(): SttProvider  = withContext(io) { … }
suspend fun sttLanguage(): String       = withContext(io) { … }
suspend fun model(): String             = withContext(io) { … }
suspend fun modelStore(model: WhisperModel? = null): ModelStore = …
```

`sttEngine()` (`:85-101`) is already becoming `suspend` in T-018; its five decrypts move inside one
`withContext(io)` **as a single hop, not five** — five `withContext` calls to the same dispatcher
is five context switches for work measured in microseconds each.

`Graph.assistant`'s `by lazy` (`:155-161`) stops being a `by lazy`: its initialiser builds an
`OkHttpClient` and runs `NetworkPolicy.requireReachable`, so first touch is blocking. Make it
`suspend fun assistant(): Assistant` behind a `Mutex`-guarded nullable, or build it eagerly in
`Graph.init`'s off-Main block (step 5). **Prefer the suspend accessor**: eager construction makes
every launch pay for a feature most sessions never use.

**Step 3 — `VoiceViewModel` (#1–#6, I-11).** Add `private val io: CoroutineDispatcher =
Dispatchers.IO` as the last constructor parameter, matching `SettingsViewModel.kt:72` including its
KDoc's reasoning. Then:

- `start()` (`:74-91`) — `needsPermission()` is a cheap permission check and stays; `modelMissing()`
  and `serverUrl()` are disk and Keystore, so the guard at `:80-83` moves inside the launch:
  ```kotlin
  fun start() {
      if (needsPermission()) { _state.value = VoiceState.NeedsPermission; return }
      viewModelScope.launch {
          val blocked = withContext(io) { modelMissing() && serverUrl().isNullOrBlank() }
          if (blocked) { _state.value = VoiceState.Failed(...); return@launch }
          clearBuffer()
          _state.value = VoiceState.Recording(0f, 0)
          recordJob = launch { recorder.record(::appendSamples)… }
      }
  }
  ```
  **Note the behaviour change and test it:** `start()` was synchronous and now the state moves a
  frame later. `TodayScreen`'s record button must not depend on `_state` being updated by the time
  `start()` returns. Check it; if it does, that is a finding, not a licence to keep the blocking
  read.
- `stopAndTranscribe()` (`:97-121`) — wrap the WAV write and the language read:
  ```kotlin
  val pcm = drainBuffer()
  …
  lastAudioPath = withContext(io) {
      runCatching { WavWriter.write(File(audioDir(), "${System.currentTimeMillis()}.wav"), pcm).absolutePath }
  }.getOrNull()
  val lang = language()          // suspend after step 2
  transcribe(pcm, lang)
  ```
  `audioDir()` is `File(Graph.appContext.filesDir, "audio")` — a path construction, not IO — but it
  goes inside the same block anyway because it is one line and splitting it invites the next reader
  to split more.
  **While here:** G-05 says a failed WAV write is swallowed and the note is created with
  `audioPath = null` and no message. That is not this task's to fix, but the `runCatching` above is
  the exact line. Name it in the commit.
- `transcribe()` (`:130-141`) — after T-018 this is `withStt { … }`, which owns its own thread.

**VOID (DEC-0020, re-audit 2026-09-20 — the class does not exist):** only its `feature-assistant` half survives, as a latent defect in a module the APK does not link.

**Step 4 — `ChatViewModel` and the assistant path (#7–#10, I-09).** `ask()` (`:57-92`):
`Graph.model()` at `:66` is now suspend and cannot be called inside the state `copy(...)` — move it
into the launch, and keep the already-loaded `_state.value.model` for the optimistic update so the
screen does not flicker. `Graph.assistant` at `:72` becomes `assistant()` inside the launch. And in
`feature-assistant`:

- `OpenRouterClient.stream` (`:50`) gains `.flowOn(Dispatchers.IO)` at the end of the
  `callbackFlow`. **Read the KDoc at `:45-49` before doing it**: tokens are sent with
  `trySendBlocking` deliberately, because "with a bounded buffer and a non-blocking send, 335 of
  400 tokens were measured lost". `flowOn` inserts a channel between producer and collector; the
  existing back-pressure test (`StreamBackpressureTest`) must be re-run and must still pass. If it
  does not, the fix is a buffer size on the `flowOn`, not the removal of `trySendBlocking`.
- `NotesContextBuilder.build` (`Assistant.kt:14`) — the DAO calls already suspend off-Main; the
  rendering does not. Wrap the render in `withContext(Dispatchers.Default)` inside
  `NotesContextBuilder`, per R1, so `Assistant.ask` stays a plain suspend call. This is the one
  place `Default` is right: it is pure CPU over an in-memory list.

**Step 5 — startup (#13, #14, I-21).** `FabricVrApp.onCreate` → `Graph.init(this)` → `vaultMirror`
→ `notes` → `NotesDatabase.open`. `Room…build()` does no disk IO, so that chain is cheap; what is
not cheap is `Graph.settings`'s `SharedPreferences` construction and the first `secretKey()`. Add
to `Graph.init`:

```kotlin
fun init(context: Context) {
    appContext = context.applicationContext
    vaultMirror.start(scope)
    // The Keystore key is generated on first use, inside a monitor, and the first attempt asks
    // StrongBox (which most headsets lack) and falls back — so the first `get()` from a click
    // handler blocked for two key generations. Warm it here, off Main, where nobody is waiting.
    scope.launch { runCatching { settings.get(SecureSettings.KEY_STT_MODEL) } }
}
```

`Graph.scope` is `Dispatchers.Default` + `SupervisorJob` (`:39`) and currently carries exactly one
coroutine. Adding a second makes I-29's "never cancelled, one coroutine, undocumented" worse, so
write the invariant at the declaration in the same commit: what the scope is for, that it is
process-lifetime, and that nothing long-running may join it.

**Step 6 — the checker.** `tools/check_main_thread.py`, run as a JVM test and by the doc gate:

## Blast radius, and what NOT to touch

- **Touches:** `Graph.kt` (five accessors, `init`) **and `app/.../SttRouting.kt`, where four of the
  five decrypts now live** — see the banner; `VoiceViewModel.kt` (one parameter, three methods), `NotesViewModel.kt` (`retranscribe`'s
  two lines, already parameterised by T-017), `OpenRouterClient.kt` (one `flowOn`),
  `NotesContextBuilder.kt` (one `withContext`), `FabricVrApp.kt` (StrictMode in debug), one new
  checker, three test files, `docs/modules/app.md`.
- **Do not touch:** `AudioRecorder.kt` or `ModelDownloader.kt`'s `flowOn(Dispatchers.IO)`. They are
  the examples R1 is generalised from. `AudioRecorder`'s other defects — the boxed `ArrayList<Short>`
  (E-02) and the negative-`read` busy loop (C-05) — are **T-020's**, and both live in the twelve
  lines this task would otherwise be tempted to tidy.
- **Do not touch:** `SecureSettings`. The boundary is at `Graph` by decision, not by oversight, and
  moving it is its own task. In particular do not "just make `get` suspend while I'm here" — it
  would change `OpenRouterClient`'s `apiKey: () -> String?` parameter, which is in another module
  with its own tests.
- **Do not touch:** `EditorViewModel`. Its autosave is already off the critical path and its two
  real defects (I-01's uncancelled `saveJob`, I-03's dead-scope flush) are T-007's and T-012's. A
  dispatcher change here would collide with both.
- **Do not touch:** `TodayScreen.kt:105`'s `LaunchedEffect` (#12). R3 says a commit must not be
  scoped to a composition, and that is **I-02**, a Blocker with its own data-loss mechanism and no
  task in this plan (see T-012's *Correction*). Fixing it inside a threading commit hides it. State
  R3 here; leave the call site to the row that owns it.
- **Watch for:** making `start()` asynchronous (step 3) is a real behaviour change at a control the
  person taps constantly. If `TodayScreen` reads `voiceViewModel.state` immediately after calling
  `start()`, or disables the button on a synchronous state read, it will flicker. Check
  `TodayScreen.kt:127-138` and the record control before assuming it is safe.
- **Watch for:** `withContext` inside `callbackFlow` is not the same as `flowOn`. The prologue in
  `OpenRouterClient.stream` runs in the flow's collection context; only `flowOn` moves it. A
  `withContext` around the prologue inside `callbackFlow` is a compile error
  (`ProducerScope` is not re-entrant that way) or a subtle mistake — use `flowOn`.
- **Watch for:** five separate `withContext(io)` calls where one would do. Each one is a dispatch;
  the Keystore reads in `sttEngine()` are microseconds apart and must share a hop.

## Correction to the finding

The four cited rows (I-09, I-11, I-14, C-03) are all accurate and all confirmed against the tree.
Four additions:

1. **I-21 belongs on this row.** `secretKey()` is `@Synchronized` and may generate a StrongBox key
   inside the monitor, so the first `get()` from a click handler blocks for a key generation — and
   on a headset without StrongBox for **two**, because `generate()` (`SecureSettings.kt:127-139`)
