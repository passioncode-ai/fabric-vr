# T-012 — The panel keeps the SDK's owners and adds only the one it lacks

- **Severity:** Blocker
- **Work package:** WP-2 (the immersive host)
- **Closes:** I-15, I-16, I-17, I-12, I-03, C-11, B-16 — see *Correction to the finding*; the plan
  row reads "I-02, I-03, I-12, C-04"
- **Depends on:** nothing
- **Needs a headset:** for the final confirmation only (the unit and instrumented assertions run on
  a Quest but not by hand); the change itself is settled by bytecode
- **Estimated blast radius:** 2 files changed (one may be deleted), 1 instrumented test file, 1
  decision superseded, 1 module doc line

## What is wrong, in the person's terms

They are in the Space, typing into a note. They take the headset off, or open another app, or press
the exit control. Two things happen that should not.

**The last thing they typed is gone.** Not sometimes — every time. Leaving the Space destroys the
view model that holds the unsaved text *before* the screen that would have flushed it is disposed,
so the flush runs into a scope that is already cancelled and writes nothing. It fails silently:
the editor said *Saving…* and then the Space closed.

**And while the headset sits on the desk, the app keeps working.** Room re-runs its queries on
every write, the search debounce keeps ticking, and a chat answer keeps streaming down an OkHttp
connection with a ten-minute call timeout. Nothing on the headset is showing. The battery does not
know that.

Both come from one cause: the app hands the Space's Compose tree four "owners" — a lifecycle, a
view-model store, a saved-state registry and a back dispatcher — and three of those four were
already provided, better, by the Spatial SDK.

## Where it is

`app/src/main/kotlin/ai/passioncode/fabricvr/SpatialPanelOwners.kt`, the whole class:

```kotlin
class SpatialPanelOwners(
    /** What Back does when nothing in the composition has consumed it. */
    onUnhandledBack: () -> Unit,
) : LifecycleOwner, ViewModelStoreOwner, SavedStateRegistryOwner, OnBackPressedDispatcherOwner {

    private val registry = LifecycleRegistry(this)                       // :36
    private val savedState = SavedStateRegistryController.create(this)   // :37

    override val lifecycle: Lifecycle get() = registry                   // :39
    override val viewModelStore: ViewModelStore = ViewModelStore()       // :40
    override val savedStateRegistry: SavedStateRegistry get() = savedState.savedStateRegistry
    override val onBackPressedDispatcher: OnBackPressedDispatcher =      // :42-43
        OnBackPressedDispatcher { onUnhandledBack() }

    fun onCreate() {                                                     // :45-48
        savedState.performRestore(null)
        registry.currentState = Lifecycle.State.CREATED
    }

    fun onResume() { registry.currentState = Lifecycle.State.RESUMED }   // :50
    fun onPause() { registry.currentState = Lifecycle.State.STARTED }    // :52

    fun onDestroy() {                                                    // :54-57
        registry.currentState = Lifecycle.State.DESTROYED
        viewModelStore.clear()
    }
}
```

`getPanelViewLifecycleOwner(AppSystemActivity)` is
`activity.findFeature(ComposeFeature::class).panelViewLifecycleOwner` (offsets 6–21). That lookup
resolves because `ImmersiveActivity.kt:91` registers `ComposeFeature()`.

`PanelViewLifecycleOwner` is `final` and implements exactly
`LifecycleOwner, ViewModelStoreOwner, SavedStateRegistryOwner` — **not**
`OnBackPressedDispatcherOwner**.** `ComposeFeature` forwards the activity's whole lifecycle into it,
`onStop` included:

```
ComposeFeature.onStart()       -> panelViewLifecycleOwner.onStart()
ComposeFeature.onStopActivity() -> panelViewLifecycleOwner.onStop()
ComposeFeature.destroyLifecycleOwner() -> guarded by lifecycleOwnerDestroyed, then onDestroy()
```

and `VrActivity` dispatches those: `onPause` offset 190 → `FeatureManager.onPauseActivity()`,
`onStop` offset 125 and `onDestroy` offset 139 → `FeatureManager.onStopActivity()`.

**So the SDK's owner receives `ON_STOP`. Ours never does** — `ImmersiveActivity` overrides
`onCreate`, `onResume`, `onPause`, `onDestroy`, and no `onStop`. Our registry rests at `STARTED`
while the activity is stopped.

### Three consequences, stated exactly, because two of the three guesses are wrong

- **The view-model store.** Shadowing it is nearly harmless *for screens*: `NavHost` reads
  `LocalViewModelStoreOwner.current` only to hold its own `NavControllerViewModel`, and each
  `composable {}` then re-provides the `NavBackStackEntry` as the owner — so
  `TodayScreen.kt:83-84`, `NoteEditorScreen.kt:50-51` and the rest already resolve against the
  back-stack entry. What is *not* harmless is **when** the store is cleared, which is I-03 below.
- **The saved-state registry.** Shadowing it is inert, and `SpatialPanelOwners.kt:26`'s reason
  ("`rememberSaveable` across a panel rebuild needs the saved-state registry") names the wrong
  mechanism: `rememberSaveable` reads `LocalSaveableStateRegistry`, which
  `ProvideAndroidCompositionLocals` builds from the **view-tree** owner *before* our provider runs.
  Neither owner ever calls `performSave`, so nothing survives a rebuild either way. Deleting ours
  changes nothing here; the comment is what has to go.
- **The lifecycle.** This is the regression, and it is the opposite of the intuitive one. Our
  registry *is* driven, so "stuck at CREATED" never happens. It is stuck at **STARTED**, and every
  `collectAsStateWithLifecycle` in the app defaults to `minActiveState = STARTED`, so the Space
  keeps collecting after it is gone (I-12).

### The destroy ordering, I-03, and why it is not a race

`ImmersiveActivity.kt:63-66` runs `owners.onDestroy()` before `super.onDestroy()`. The order that
follows is fixed:

```
Main  owners.onDestroy()   -> registry = DESTROYED; viewModelStore.clear()
                           -> NavControllerViewModel.onCleared -> every back-stack entry's store cleared
                           -> EditorViewModel.onCleared -> viewModelScope CANCELLED
Main  super.onDestroy()    -> AppSystemActivity -> FeatureManager.onStopActivity/onDestroy
                           -> ComposeFeature.destroyLifecycleOwner -> SDK owner DESTROYED
                           -> DisposeOnViewTreeLifecycleDestroyed disposes the composition
Main  NoteEditorScreen.kt:67  onDispose { viewModel.flush() }
                           -> EditorViewModel.kt:88-93: saveJob = viewModelScope.launch { save(…) }
                           -> the scope is cancelled. The body never runs. Nothing is logged.
```

The composition strategy the SDK installed (`composePanel$lambda$1` offset 34) keys disposal to the
**SDK's** owner, which we destroy ours ahead of. E-01 graded this "a real risk, ≤600 ms"; in the
immersive host it is not a risk, it is the order on every exit. **Removing our lifecycle and store
removes it entirely** — there is then only one owner, destroyed by the SDK after the composition is
disposed, so `onDispose` runs on a live scope.

## The decision, and what was weighed

**Chosen: keep `OnBackPressedDispatcherOwner`, delegate its `lifecycle` to the SDK's owner, delete
the other three, and delete the hand-driven lifecycle callbacks with them.**

| Owner | Today | After |
|---|---|---|
| `LocalLifecycleOwner` | our `LifecycleRegistry`, never stopped | the SDK's, stopped by `VrActivity.onStop` |
| `LocalViewModelStoreOwner` | our store, cleared before disposal | the SDK's, cleared after |
| `LocalSavedStateRegistryOwner` | ours, never saved, read by nobody | the SDK's, also never saved |
| `LocalOnBackPressedDispatcherOwner` | ours — **the only one that was missing** | ours, `lifecycle` delegated |

**Alternatives considered:**

- *Keep all four and add `onStart`/`onStop` to the activity (C-11's proposal).* Rejected. It fixes
  I-12 and leaves I-03, I-15, I-16 and I-23 standing: two lifecycles still have to be kept in step
  by hand, forever, and the second one is strictly less complete than the first. The SDK already
  drives an owner correctly; a second one is a maintenance obligation bought for nothing.
- *Keep all four and move `owners.onDestroy()` after `super.onDestroy()` (C-11(c)).* Rejected as
  the whole fix: it corrects the ordering but leaves `ON_STOP` missing and leaves a `Popup` or
  `AndroidView` subtree resolving a different `ViewModelStore` from its parent composition (B-16).
  It is the right *shape* of correction and it becomes unnecessary once the owner is gone.
- *Drop `SpatialPanelOwners` entirely and let the SDK provide everything.* Rejected: the SDK sets
  **no** `OnBackPressedDispatcherOwner` anywhere in the compose module — five classes, none
  mentions `OnBackPressedDispatcher` — and navigation-compose's `PredictiveBackHandler` throws
  `No OnBackPressedDispatcherOwner was provided via LocalOnBackPressedDispatcherOwner` without one.
  That is the crash that took the activity down on every entry into the Space on 2026-09-19.
- *Give the remaining owner its own `LifecycleRegistry`, since `OnBackPressedDispatcherOwner`
  extends `LifecycleOwner` and has to answer `lifecycle` somehow.* Rejected, and this is the trap
  in the obvious version of this change. `OnBackPressedDispatcher.addCallback(owner, callback)`
  uses that lifecycle to **unregister** the callback. A registry nobody drives to `DESTROYED` never
  unregisters anything, so every `BackHandler` the app ever composed stays in the dispatcher's
  list. Delegating to the SDK's owner is not a convenience, it is the requirement.
- *Set our owners on the `ComposeView` with `setViewTreeLifecycleOwner` so view tree and
  composition agree (B-16's second option).* Rejected: it makes the two answers consistent by
  replacing the good answer with the worse one, and it fights `attachLifecycleToRootView`, which
  runs *after* our `setContent` lambda returns (offset 56, vs our lambda at offset 27) and would
  overwrite whatever we set.

**What this change does NOT fix, stated so nobody claims it does:** Back still delivers nothing in
the Space. The dispatcher we keep is fed by nobody — `VrActivity.dispatchKeyEvent` never calls
`super`. That is T-013, and T-013 depends on this task.

## Decomposition

**Step 1 — write the failing test first.**
`app/src/androidTest/kotlin/ai/passioncode/fabricvr/PanelOwnersTest.kt` (new). It must assert
identity, not absence:

```kotlin
// inside the panel composition, reached through a test hook on ImmersiveActivity
assertSame(activity.panelViewLifecycleOwner, capturedLifecycleOwner)
assertSame(activity.panelViewLifecycleOwner, capturedViewModelStoreOwner)
assertNotNull(capturedBackDispatcherOwner)
assertSame(activity.panelViewLifecycleOwner.lifecycle, capturedBackDispatcherOwner.lifecycle)
```

`panelViewLifecycleOwner` is the public extension on `AppSystemActivity` from
`com.meta.spatial.compose`. Capture the three locals by writing them into the same
`@Volatile companion` slot `composedAtLeastOnce` already uses (T-016 replaces that mechanism; until
then, follow it rather than inventing a second one).

Run it. **Watch all four assertions fail** — today the first two compare our object against the
SDK's and the fourth compares two different registries. If they pass before the change, the hook is
reading the wrong composition.

**Step 2 — reduce `SpatialPanelOwners.kt` to one owner.** The class becomes, in full:

```kotlin
/**
 * The one Compose host owner the Spatial SDK does not supply.
 *
 * `composePanel` calls `attachLifecycleToRootView`, which sets ViewTreeLifecycleOwner,
 * ViewTreeViewModelStoreOwner and ViewTreeSavedStateRegistryOwner on the panel's ComposeView to
 * `ComposeFeature.panelViewLifecycleOwner` — an owner the activity drives, `ON_STOP` included.
 * Verified against the 0.14.0 bytecode; see docs/evidence/audits/2026-09-20-v2/I.md, Job 1.
 * Providing our own shadowed three owners the SDK drives better than we did.
 *
 * It sets no OnBackPressedDispatcherOwner, and navigation-compose's PredictiveBackHandler needs
 * one; its absence crashed every entry into the Space on 2026-09-19.
 *
 * `lifecycle` delegates to the SDK's owner on purpose. OnBackPressedDispatcher.addCallback uses it
 * to unregister callbacks, so a registry nobody destroys leaks every BackHandler ever composed.
 *
 * Back is not delivered in the Space at all — see T-013 and I-13. This dispatcher exists so the
 * composition can be built; what reaches it is that task's subject, not this file's.
 */
class SpatialPanelBackOwner(
    private val host: AppSystemActivity,
    onUnhandledBack: () -> Unit,
) : OnBackPressedDispatcherOwner {
    override val lifecycle: Lifecycle get() = host.panelViewLifecycleOwner.lifecycle
    override val onBackPressedDispatcher: OnBackPressedDispatcher =
        OnBackPressedDispatcher { onUnhandledBack() }
}
```

Nine lines of code and a doc comment that is longer, which is the right ratio here. **It may
instead become a private class inside `ImmersiveActivity`** — it has one construction site, one
consumer, and it now needs the activity anyway. Either is acceptable; a separate file is preferred
only if T-013 grows it. The class name changes because the old one is a lie once it owns one
thing; `git mv` the file and rename in the same commit so review sees a rename, not a rewrite.

**Step 3 — `ImmersiveActivity`.** Delete `onCreate`'s `owners.onCreate()`, delete the whole
`onResume`, `onPause` and `onDestroy` overrides (they now do nothing but call `super`), and reduce
the provider at `:107-112` to one entry:

```kotlin
CompositionLocalProvider(LocalOnBackPressedDispatcherOwner provides owners) {
```

Delete the four now-unused imports (`LocalLifecycleOwner`, `LocalViewModelStoreOwner`,
`LocalSavedStateRegistryOwner`, plus whichever of `Lifecycle*` moved). `owners` becomes
`SpatialPanelBackOwner(this) { returnToPanel() }`. **Do not** make it `by lazy` with a
`panelViewLifecycleOwner` read at construction — the feature is registered in `registerFeatures()`,
so resolve the owner inside the `get()`, as written above.

**Step 4 — say what the panel rebuild now costs, and check it is not worse.** `PanelDisplayBase`
recreates the `ComposeView` on `recreateVirtualDisplay`/`resize` (B-29). Before this change, view
models survived a rebuild in *our* store while the composition was thrown away; after it they
survive in the SDK's, which is also activity-scoped (`ComposeFeature` holds one
`PanelViewLifecycleOwner` for the activity). **Survival is unchanged.** What is thrown away in both
cases is the `NavController` and its back stack, because `rememberNavController()` lives inside the
composition (`FabricApp.kt:40`) — that is B-29 and it is not this task's to fix. Record the finding
as unchanged in the commit rather than implying the rebuild got better.

**Step 5 — the second-panel hazard, written down rather than fixed.** Both the SDK's owner and ours
are **activity**-scoped. With one panel that is invisible. A second `composePanel` registration
would give two `NavHost`s one `SavedStateRegistry` and collide on its key. `attachLifecycleToRootView`
accepts a per-panel owner as its third argument and `composePanel` passes `aconst_null` (offset 53),
so the escape exists and is unused. Put that sentence in the class doc; do not build it (I-23).

**Step 6 — the decision record.** `DEC-0018 (retired, superseded by DEC-0028)` says all four owners are supplied and carries a
**Contested** note pointing at exactly this question. Reserve the next free id in
`docs/DECISIONS.md` (`Next free ID:` reads the register's next free id; read-then-reserve, per that file's own rule),
write the new decision, and set `DEC-0018`'s status to `Superseded by a new decision at the register's next free id`. The new record must
name the bytecode as its source, not an argument. Update `docs/modules/app.md`'s mention of
`SpatialPanelOwners` in the same commit.

## Correction to the finding

**The plan's `Closes` column for this row is wrong in two of its four ids.** They are not the rows
the axis reports carry:

| Plan says | Axis report actually says | The row that belongs here |
|---|---|---|
| I-02 | "a dictation committed on the composition's scope, cancelled by leaving the screen" — a `LaunchedEffect` defect on Today, nothing to do with owners | **I-15** ("three of the four provided owners shadow owners `attachLifecycleToRootView` already set") and **I-16** (the wrong reason in the doc comment) |
| C-04 | `SecureSettings.get()` deletes stored ciphertext on any throwable — a Keystore defect | **C-11** ("three gaps in the hand-rolled owners: no `onStop`; `performRestore(null)` with no `performSave`; `viewModelStore.clear()` before `super.onDestroy()`") |

I-03 and I-12 are correct as cited. **B-16** should also be listed — it is axis B's independent
finding of the same thing, and the merge's "where the reports disagreed" section is about that row.
**I-17** (destroy ordering) is closed by this change too and is not listed anywhere.

I-02 and C-04 are real Blocker/High findings that still need owners: I-02 belongs with T-028 or a
row of its own in WP-1 (it is the same class as A-03 and it is *not* closed by anything in WP-2),
and C-04 has no task in the plan at all. **Say so when this task's board row is written; do not let
citing them here mark them closed.**

One smaller correction: axis C's C-11(b) says the saved-state registry being providable "buys
nothing but the absence of a crash". It does not buy even that — `rememberSaveable` never reads it
(it reads `LocalSaveableStateRegistry`, built upstream from the view-tree owner), and nothing in
this app reads `LocalSavedStateRegistryOwner` directly. Removing it is a no-op at runtime. That is
worth stating because it is the one of the three removals with zero observable effect, and a
reviewer looking for one will not find it.
