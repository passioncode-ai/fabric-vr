# T-039 — The signing key has a custodian and a written procedure

- **Severity:** High
- **Work package:** WP-7 (release engineering)
- **Closes:** H-34
- **Depends on:** nothing. **T-037 cannot start until this is done.**
- **Needs a headset:** no
- **Estimated blast radius:** 3 files changed (`.gitignore`, `scripts/check-secrets.sh`,
  `README.md`), 1 file rewritten (`keystore.properties.sample`), 1 new runbook, 1 `DEC` row.
  No source code.

> **No secret value appears in this spec, in the runbook it produces, in a commit message, or in
> any chat message.** What is recorded is a *location* and a *custodian*. The maintainer's rule is
> explicit and it is not advisory: a value travels by stdin into
> the maintainer's local secret store, and a command that needs a value is run through
> the store's run wrapper, never by opening the file to look. This spec follows that rule and so
> must the work it describes.

## What is wrong, in the person's terms

The Android signing key is the only artefact in this project with **no recovery path**. Once a
signed build is on a headset, losing the key means no future build will ever install over it:
every upgrade becomes uninstall-plus-total-data-loss (H-23, T-037), permanently, for everyone who
has the app.

The entire written guidance on it is six lines:

```
# Copy to keystore.properties (untracked, and refused by scripts/check-secrets.sh if tracked).
# Paths are relative to the repository root.
storeFile=release.keystore
storePassword=
keyAlias=fabricvr
keyPassword=
```

It names a file and stops. Nothing anywhere says how to create the keystore, where the real one
lives, who holds it, or how it is backed up. Nothing verifies any of that.

**No release keystore exists on this machine**, and `keystore.properties` is absent — which is
precisely why this is the moment to decide. Nothing is lost yet. A `.keystore` on one laptop with
no backup is the default outcome of doing nothing, and it is the outcome the project will reach in
the next few days if this task does not run before T-037.

## Where it is

**The sample.** `keystore.properties.sample`, six lines, quoted in full above.

**What reads it.** `app/build.gradle.kts:25-40`:

```kotlin
val keystoreProperties = Properties().apply {
    val file = rootProject.file("keystore.properties")
    if (file.exists()) file.inputStream().use { load(it) }
}
signingConfigs {
    if (keystoreProperties.getProperty("storeFile") != null) {
        create("release") {
            storeFile = rootProject.file(keystoreProperties.getProperty("storeFile"))
            …
        }
    }
}
```

Note `rootProject.file(...)` on `storeFile`: the sample's `release.keystore` resolves **inside the
repository**. That is the wrong default and it is fixed below.

**What the gate covers, and what it does not.** `scripts/check-secrets.sh:46-52`:

```bash
for f in local.properties keystore.properties .env; do
  if git ls-files --error-unmatch "$f" >/dev/null 2>&1; then
    say "ERR:" "$f is tracked and must not be"
```

`keystore.properties` is covered. **The keystore file itself is not** — `*.keystore` and `*.jks`
appear in neither `scripts/check-secrets.sh` nor `.gitignore` (which lists `/local.properties` and
`/keystore.properties` at lines 12-13 and no key material). Combined with the sample's
repository-relative `storeFile`, the shortest path a person can take from the sample to a working
build puts a private key in a directory that is not ignored and not checked.

**What the maintainer's setup requires.** A local secret store and its run wrapper
both exist on the maintainer's machine. The rule they enforce: a value never enters a
chat message; values go in by stdin; a command that needs one is run through
the wrapper (`<secret-run> <project> <NAME> -- <cmd>`) so the value is never read into a transcript. This is
not optional here — a session-memory database on that machine has been measured holding
credential values because sessions said them out loud.

## The decision, and what was weighed

**Chosen: the keystore lives outside the repository, in the operator's credential store, with two
backups; its passwords live in the vault under names; and the build reads them through
the store's run wrapper, never from a file a person edited by hand.**

Five things get decided, and each has a rejected alternative.

### 1. Where the keystore file lives

**Chosen:** outside the worktree entirely — a path the operator chooses, recorded in
`docs/deployment/signing.md` as a *location*, not a value. The repository never contains key
material; `storeFile` in `keystore.properties` is an absolute path.

- ***Rejected: `release.keystore` in the repository root, as the sample implies.*** One
  `git add -A` and the project's unrecoverable secret is in a GitHub repository forever. `.gitignore`
  does not currently cover it. The sample's own wording — "Paths are relative to the repository
  root" — is what makes this the path of least resistance, and it is changed by this task.
- ***Rejected: inside `~/.android/` beside the debug keystore.*** Convenient, and it is exactly
  where a person looks when cleaning up Android tooling. A key with no recovery path does not live
  in a cache directory.

### 2. Who holds it

**Chosen:** the operator, named in the record, as the single custodian. One custodian and two
copies is the right shape for a two-person project; a second custodian without a second person who
can actually reach the backup is a name in a document.

- ***Rejected: "whoever has the laptop".*** That is the current state and it is what this task
  exists to end.

### 3. How it is backed up

**Chosen: two copies, at least one not on this laptop.** The minimum that survives the failure this
protects against — the laptop dying, being reset, or being tidied.

The backup must cover **three artefacts together**, because any one of them alone is useless:

| Artefact | Why |
|---|---|
| the `.keystore` file | the key |
| the store password, key password and alias | the key without them is a file |
| `release-lineage.bin` (T-037) | without it a rotated build cannot prove its descent from the debug key, and every headset needs an uninstall again |

The maintainer's machine already has a local credential store with its own daily backup
(a scheduled job kept independent of every other service, so the store's backup outlives
them). Passwords go there by stdin. The `.keystore` and the lineage are
binary files, not vault values: they go wherever the operator keeps things that must survive the
laptop, and the record says where without saying what is inside.

- ***Rejected: backing up only the passwords.*** The file is the irreplaceable half.
- ***Rejected: a copy on the second headset / in the repository / in a chat.*** Each of these has
  been somebody's idea before. None of them is a backup; all three are disclosures.

### 4. How a build uses it

**Chosen: `keystore.properties` stays untracked and holds `storeFile` and `keyAlias` only. The two
passwords come from the environment, supplied by the store's run wrapper.**

```kotlin
// app/build.gradle.kts — shape, not the final diff
storePassword = keystoreProperties.getProperty("storePassword")
    ?: System.getenv("FABRICVR_KEYSTORE_PASSWORD")
keyPassword = keystoreProperties.getProperty("keyPassword")
    ?: System.getenv("FABRICVR_KEY_PASSWORD")
```

and the release build is invoked as:

```bash
<secret-run> fabric-vr \
  FABRICVR_KEYSTORE_PASSWORD FABRICVR_KEY_PASSWORD -- ./gradlew :app:assembleRelease
```

*(Confirm the exact argument form against the wrapper's `--help` before writing it into the
runbook — a runbook that names a flag that does not exist is F-15's failure in a new file.)*

The file-first, env-second order keeps a plain `keystore.properties` working for whoever prefers
it, while making the documented path one where the value is never typed, never pasted, and never
in a transcript.

- ***Rejected: passwords in `keystore.properties`, as the sample implies.*** It works, and it puts
  two irreplaceable values in a plaintext file in the working directory, which is the file most
  likely to be opened, screenshotted or pasted while debugging a signing error.
- ***Rejected: a Gradle property in `~/.gradle/gradle.properties`.*** Same plaintext problem, in a
  file with an even wider blast radius (every project on the machine).
- ***Rejected: prompting interactively.*** It breaks CI (T-002) and it breaks the unattended
  release path T-041 may need.

### 5. What the gate must refuse

**Chosen:** extend `scripts/check-secrets.sh` section 2 and `.gitignore` to cover key material, and
give the addition a planted-violation self-test — because a gate that greps nothing prints the same
`ok` as a gate that found nothing, which is this project's own measured failure (`f7d656d`, ten
planted credentials passed).

## Decomposition

**Step 1 — close the gate first, before a keystore exists to leak.**

`.gitignore`, below the existing `/keystore.properties`:

```
# Signing material — never committed, and there is no recovery if it is lost.
*.keystore
*.jks
release-lineage.bin
```

`scripts/check-secrets.sh` section 2 — extend the untracked-files loop to refuse any tracked
`*.keystore`, `*.jks` or `release-lineage.bin`, by pattern rather than by name:

```bash
KEYMATERIAL=$(git ls-files -- '*.keystore' '*.jks' 'release-lineage.bin')
[ -n "$KEYMATERIAL" ] && { say "ERR:" "signing material is tracked:"; printf '%s\n' "$KEYMATERIAL"; FAIL=1; }
```

**Plant it and watch it fail:** `touch /tmp/x.keystore && git add -f /tmp/x.keystore` in a scratch
clone, run the gate, see it refuse, `git reset`. A gate whose new branch has never been seen
failing is not yet a gate.

**Step 2 — generate the keystore, once, by the operator.**

```bash
keytool -genkeypair -v \
  -keystore <absolute path outside the repository>/fabric-vr-release.keystore \
  -alias fabricvr -keyalg RSA -keysize 4096 -validity 10000 \
  -storetype PKCS12
```

`-validity 10000` is ~27 years; a key that expires is a key that ends the app. `PKCS12` rather than
the legacy JKS, which `keytool` warns about on every use.

**The passwords are chosen and entered by the operator at the prompt and go straight into the
vault by stdin.** They are not generated in a session, not echoed, not written into a file first.

```bash
# names, never values
<secret-store> put fabric-vr FABRICVR_KEYSTORE_PASSWORD
<secret-store> put fabric-vr FABRICVR_KEY_PASSWORD
```

**Step 3 — `keystore.properties.sample`, rewritten.** It currently teaches the wrong thing in four
of its six lines. It should say: the path is absolute and outside the repository; the passwords are
**not** put here; the vault names to use; and a pointer to the runbook.

**Step 4 — `app/build.gradle.kts`.** Add the environment fallback for the two passwords
(shape above). Leave everything else in `signingConfigs` and the `release` build type as it is —
in particular the lifecycle message on an absent keystore, which is a good behaviour and is what
makes an unsigned release build a clear message rather than a broken build.

**Step 5 — the custody record.** `docs/deployment/signing.md`, tracked, containing:

- the keystore's **location** (the path, and which machine), the alias, the algorithm and the
  expiry date;
- the **custodian** — a name;
- the **backup**: how many copies, where they are (described, not addressed with credentials),
  when each was last verified;
- the **vault names** of the two passwords, and the run-wrapper invocation;
- `release-lineage.bin`'s location, once T-037 creates it;
- **what happens if the key is lost**, in one paragraph, because the honest answer — every
  installed copy becomes unupgradable and must be uninstalled with its data — is the thing that
  makes the backups get made;
- the fingerprint, so a build can be checked against the record:
  `keytool -list -v -keystore <path> -alias fabricvr | grep SHA256`. **The fingerprint is public
  information and belongs in the record; nothing else from that command does.**

**Step 6 — `README.md`.** The §"The wrapper, and a release build" section currently jumps from
"copy the sample" to "fill it in". Insert the `keytool` line and a pointer to
`docs/deployment/signing.md`, and say that the passwords are not filled into the file.

**Step 7 — the `DEC` row.** *The release signing key is held outside the repository by a named
custodian, backed up in two places, and its passwords travel only through the machine's credential
store.* Its `Consequences / affects:` line names `T-037`, `README.md`,
`docs/deployment/signing.md`, `scripts/check-secrets.sh`. Read `docs/DECISIONS.md:7` for the free
id — it says the register's next free id today, and reading it is not reserving it.

## Definition of Done

- [ ] `.gitignore` and `scripts/check-secrets.sh` refuse tracked key material, and the refusal was
      **watched firing** on a planted file.
- [ ] A release keystore exists, at an absolute path outside the worktree, PKCS12, 4096-bit,
      validity ≥ 10 000 days.
- [ ] Its two passwords are in the vault under `FABRICVR_KEYSTORE_PASSWORD` and
      `FABRICVR_KEY_PASSWORD`, entered by stdin. **Neither value appears in any file, commit,
      transcript or log.**
- [ ] At least one backup copy of the `.keystore` exists somewhere that is not this laptop, and the
      record says when it was last verified.
- [ ] `docs/deployment/signing.md` exists, names a custodian, and contains the fingerprint and no
      other output of `keytool -list`.
- [ ] `keystore.properties.sample` no longer implies a repository-relative path or passwords in the
      file.
- [ ] `apksigner verify --print-certs` on a release build matches the recorded fingerprint.
- [ ] A `DEC` row is written.
- [ ] Four gates green, including the extended secrets gate.

## Blast radius, and what NOT to touch

- **Touches:** `.gitignore`, `scripts/check-secrets.sh`, `keystore.properties.sample`,
  `app/build.gradle.kts` (two lines), `README.md`, one new document, one `DEC` row.
- **Do not touch:** `~/.android/debug.keystore`. T-037's rotation lineage depends on it being
  byte-identical to the key that signed what is on the headsets. **CORRECTION (`B-166`,
  2026-09-22):** `44f3efe6…83fd` is the **certificate** digest that `apksigner verify
  --print-certs` prints — confirmed with `keytool` on 2026-09-21 — and NOT the file's hash, which
  is `b592817d…307e`. The sentence this replaces told a reader to verify byte-identity against a
  number computed from the certificate inside the file, so they would have got a mismatch they
  could not explain. `docs/deployment/signing.md` carries both numbers and says which is which;
  verify the FILE with `shasum -a 256`, and the CERTIFICATE with `apksigner`. Do not regenerate it, do not move it, do not let a tool "clean" it. **Back it
  up alongside the release keystore until T-037 has completed on every headset.**
- **Do not touch:** `scripts/check-secrets.sh`'s pattern list or its canary. The new section is
  additive; changing the existing patterns re-opens the exact class the canary was added to close.
- **Do not put any secret value anywhere:** not in `docs/deployment/signing.md`, not in a commit
  message, not in a test fixture, not in a `.sample`, not in an answer in chat. If a value must be
  shown to a person, it is wrapped in `<private>…</private>`, which the session memory store does
  not retain.
- **Do not generate the passwords inside an agent session.** A value that exists in a session
  transcript has already left the vault. The operator enters them at `keytool`'s prompt and into
  the secret store by stdin.
- **Watch for:** `keytool` prints the alias and fingerprint happily and also prints nothing secret —
  but `keytool -importkeystore` and some `-list` variants echo paths and, on failure, password
  hints. Pipe through `grep` for the fields you want rather than pasting whole output.
