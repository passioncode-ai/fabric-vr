# T-037 — A release build installs over a debug build without destroying data

- **Severity:** Blocker
- **Work package:** WP-7 (release engineering)
- **Closes:** H-23
- **Depends on:** **T-023 (export) — absolutely**; T-039 (the keystore exists and has a custodian);
  T-038 (a build can be identified, so "did it install?" has an answer); T-036 (whether the second
  headset is in scope)
- **Needs a headset:** yes — two of them, and this is the whole task
- **Estimated blast radius:** 2 files changed (`app/build.gradle.kts`,
  `scripts/install-on-quest.sh`), 1 new runbook, 1 `DEC` row. **Plus an irreversible operation on
  two devices holding the only copy of a person's notes.**

> **This is the most dangerous task in the plan.** Everything below is ordered so that no
> destructive command runs before the thing that makes it survivable. Read the whole spec before
> running the first line. If any check in the procedure fails, **stop** — the abort condition is
> written for each step and the device is left in its working state by not continuing.

## What is wrong, in the person's terms

Both headsets are running a debug build. The next planned step is a signed release build. A release
APK is signed with a different key, so `adb install -r` refuses it with
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`, and the way every guide (and this repository's own README)
gets past that is `adb uninstall`.

`adb uninstall` deletes `filesDir`. That is:

- the notes database,
- the entire vault — every `.md` and every `.wav` ever written,
- the 190 MB whisper model,
- every value in the Keystore, because the alias `fabricvr_settings_v1`
  (`core-common/.../SecureSettings.kt:143`) is scoped to the app's uid and dies with it —
  the OpenRouter key and the cloud-STT key.

`android:allowBackup="false"` (`app/src/main/AndroidManifest.xml:29`), so `adb backup` does not
save it either. And until T-023 ships, the app has no export of any kind.

The person loses everything, silently, to a routine-looking command.

## Where it is

**The signing configuration.** `app/build.gradle.kts:25-55`:

```kotlin
// Signing comes from an untracked keystore.properties. Absent, the release build still runs and
// produces an unsigned APK — an absent keystore must be a clear message, not a broken build.
val keystoreProperties = Properties().apply {
    val file = rootProject.file("keystore.properties")
    if (file.exists()) file.inputStream().use { load(it) }
}

signingConfigs {
    if (keystoreProperties.getProperty("storeFile") != null) {
        create("release") { … }
    }
}
```

`keystore.properties` does not exist on this machine and `release.keystore` does not exist. So the
release variant today produces an **unsigned** APK with a lifecycle warning, and has never been
installed anywhere (the audit's own verification table records the release build as "structurally
sound, and remains unsigned and never run").

**What is installed now, measured rather than assumed:**

```
$ apksigner verify --print-certs app/build/outputs/apk/debug/app-debug.apk
V2 Signer: certificate DN: C=US, O=Android, CN=Android Debug
V2 Signer: certificate SHA-256 digest: 44f3efe6c08c71542cefafa687c48b9e75dd1f80a97f1e22710b6841159083fd

$ keytool -list -v -keystore ~/.android/debug.keystore -storepass android -alias androiddebugkey
Owner: C=US, O=Android, CN=Android Debug
	 SHA256: 44:F3:EF:E6:…:83:FD
```

The digests match. **The key that signed the build on both headsets is on this machine**, at
`~/.android/debug.keystore`, alias `androiddebugkey`.

## Correction to the finding

**H-23 says the only way forward is `adb uninstall` — which deletes `filesDir` entirely: the
database, the vault with every recording, the model and every Keystore value. There is a second
way, and it must be tried first, because trying it costs nothing.**

Android's APK Signature Scheme v3 supports **signing-key rotation**: a new key may sign an update
if the APK carries a *proof-of-rotation lineage* signed by the old key. It is honoured from API 28;
these headsets are API 34.

Rotation needs both keys. We have both: the old one is `~/.android/debug.keystore`, verified above
against the bytes actually installed, and the new one is the release keystore T-039 creates.

**The decisive property, and the reason this is not a gamble:** a rejected
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` **changes nothing on the device**. The install is refused
before anything is written. So the rotated install is a free attempt, and if it fails the
destructive path is exactly where it was.

This does not remove the export. It changes the export from *the thing that makes recovery
possible* into *the thing that makes the attempt safe to make* — and the export is required either
way, because the debug keystore is one file on one laptop with a published password, and the day it
is gone the rotation option is gone with it.

**What rotation costs, stated so it is a decision and not a trick:** the release key's lineage
permanently records that this app was once signed by a well-known debug key. Configure the old
signer's capabilities explicitly when creating the lineage (`apksigner rotate` exposes
`--set-installed-data`, `--set-shared-uid`, `--set-permission`, `--set-rollback`); the default of
granting the old key nothing beyond what is needed is the right default. The operator should be
told this is being written into the app's identity for good.

## The decision, and what was weighed

**Chosen: export first, always; then attempt the rotated install; fall back to uninstall-and-restore
only if the rotated install is refused.**

| Path | Data outcome | When it is used |
|---|---|---|
| Rotated `install -r` | nothing is touched; the app keeps `filesDir` whole | first attempt, on a scratch device if one exists, then the operator's, then the tester's |
| `adb uninstall` → `install` → import | everything is destroyed and rebuilt from the export | only after the rotated install is refused, and only with a verified export in hand |

**Alternatives considered:**

- ***Sign the release with the debug key.*** Rejected: it makes the release build unshippable
  anywhere (Play and Horizon both refuse a debug certificate), and it would postpone this exact
  problem to the first real release, at which point the vault is a year larger.
- ***Set `allowBackup="true"` and use `adb backup`.*** Rejected on three grounds: `adb backup` is
  deprecated and unreliable on modern Android and was never tested on Horizon OS; it would make
  every app's data on the device extractable by anyone with `adb`, which is a privacy regression
  the product has not decided to take; and it does not restore across a signature change reliably
  either. If `allowBackup` is ever revisited it is a separate `DEC`, not a step in a migration.
- ***Pull `filesDir` with `adb pull` instead of building an export.*** Rejected as the *primary*
  path: `run-as` is unavailable for a release build, and for a debug build `adb pull
  /data/data/<pkg>` is blocked on Horizon OS unless the app is debuggable **and** the shell can
  reach it — it is exactly the mechanism nobody has tested. It is kept below as the belt-and-braces
  step 2b, because if it happens to work it is a byte-exact copy and it costs one command.
- ***Do the migration and accept the loss, "it's only test data".*** Rejected: the operator has
  been dictating into this build since 2026-09-19 and the second headset holds someone else's
  notes. T-036 decides what that headset is; no answer to T-036 makes another person's notes
  expendable.

## Decomposition

### Step 0 — prerequisites, verified rather than assumed

```bash
# The export exists and is shipped, not a branch.
git log --oneline -1 -- app/src/main/kotlin/ai/passioncode/fabricvr/ui/SettingsScreen.kt
grep -rn 'ACTION_CREATE_DOCUMENT\|MediaStore' --include='*.kt' app/src/main   # must be non-empty (T-023)

# The release keystore exists and has a custodian record (T-039).
ls -l "$(grep storeFile keystore.properties | cut -d= -f2)"
grep -rn 'keytool\|custodian' docs/deployment/ docs/DECISIONS.md              # must be non-empty

# The build identifies itself (T-038).
./gradlew -q :app:assembleDebug && adb shell dumpsys package ai.passioncode.fabricvr | grep version
```

**Abort if:** any of these is empty. This task does not begin before T-023 and T-039.

### Step 1 — export, on each headset, and verify the export before touching anything

On the device, through the app's own Settings export (T-023). Then, from the laptop:

```bash
adb -s "$DEVICE" pull /sdcard/Download/fabric-vr-export-<date>.zip ./backups/
unzip -l ./backups/fabric-vr-export-<date>.zip | tail -3
```

**Checks, all of them, before continuing:**

| Check | Expected |
|---|---|
| `unzip -t <zip>` | `No errors detected` |
| `unzip -l <zip> \| grep -c '\.md$'` | equals the note count the app's own Settings reports |
| `unzip -l <zip> \| grep -c '\.wav$'` | equals the recording count Settings reports (T-035's line) |
| total uncompressed size | within a few percent of `du -sh` on the vault |
| one `.md` opened by eye | is a real note with its front matter |

**Abort if:** any count differs, the archive fails `-t`, or the export is missing entirely. A
count that is close but not equal is a failed export, not a rounding difference.

### Step 1b — the free second copy

```bash
adb -s "$DEVICE" exec-out run-as ai.passioncode.fabricvr tar c files 2>/dev/null > ./backups/$DEVICE-filesDir.tar
tar tf ./backups/$DEVICE-filesDir.tar | head
```

This will probably fail (`run-as` needs a debuggable build and Horizon OS may refuse). **Its
failure is not an abort condition** — step 1 is the real export. Its success is a byte-exact
fallback including the model, and it costs one command.

### Step 2 — build the signed release, with the rotation lineage

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:assembleRelease

APKSIGNER=~/Library/Android/sdk/build-tools/37.0.0/apksigner

# Create the lineage: old signer = the debug key that is on the headsets, new signer = the release key.
# Verify the exact flag names against `$APKSIGNER rotate --help` on this build-tools version before
# running; the capabilities of the OLD key are set here and are not changeable afterwards.
"$APKSIGNER" rotate --out release-lineage.bin \
  --old-signer --ks ~/.android/debug.keystore --ks-key-alias androiddebugkey \
  --new-signer --ks <release keystore> --ks-key-alias fabricvr
```

Then sign the release APK with the new key **and** the lineage, and confirm the lineage is in the
APK:

```bash
"$APKSIGNER" verify --print-certs --verbose app/build/outputs/apk/release/app-release.apk
"$APKSIGNER" lineage --print-certs --in release-lineage.bin
```

**Abort if:** the lineage does not name the debug certificate SHA-256
`44f3efe6…83fd` — the **certificate** digest, which is the right number for this check and the
wrong one for byte-identity (`B-166`; the file's own hash is `b592817d…307e`). A lineage built from the wrong old key is indistinguishable from no lineage at the
install, and the only symptom is the failure in step 3.

**Keep `release-lineage.bin`.** It is now part of the app's identity and must be backed up with the
keystore (T-039).

### Step 3 — attempt the non-destructive install, on the operator's headset first

```bash
adb -s "$DEVICE" shell dumpsys package ai.passioncode.fabricvr | grep -E 'versionCode|versionName'   # before
adb -s "$DEVICE" install -r app/build/outputs/apk/release/app-release.apk
```

- **Success** → go to step 5. Nothing was destroyed.
- **`INSTALL_FAILED_UPDATE_INCOMPATIBLE`** → the rotation was not accepted. **Nothing was written
  to the device.** Go to step 4.
- **Any other failure** → stop and diagnose. Do not proceed to step 4 on an error you have not
  read; an `INSTALL_FAILED_INSUFFICIENT_STORAGE` answered with an uninstall is data loss caused by
  misreading a message.

### Step 4 — the destructive path, only if step 3 was refused

```bash
# Say out loud what is about to happen, and confirm the export one more time.
unzip -t ./backups/fabric-vr-export-<date>.zip && echo "export verified"

adb -s "$DEVICE" uninstall ai.passioncode.fabricvr        # THIS DESTROYS filesDir
adb -s "$DEVICE" install app/build/outputs/apk/release/app-release.apk
adb -s "$DEVICE" shell am start -n ai.passioncode.fabricvr/.PanelActivity
```

Then **import** (T-023's other half) and verify before declaring it done:

| Check | Expected |
|---|---|
| note count in the app | equals the pre-migration count recorded in step 1 |
| a specific note, named in step 1, opened by eye | present, with its text |
| a note with a recording | *Transcribe again* present and working |
| `du -sh` on the vault | within a few percent of step 1 |
| Settings | the model is absent — it is 190 MB and it is **not** in the export |

**The model must be re-downloaded or re-pushed** (`scripts/push-model-for-tests.sh`). Say so in the
runbook; a person who reaches a working app with no model will report the migration as broken.

**The Keystore values are gone and cannot be restored.** The OpenRouter key (if T-033 kept the
assistant) and the cloud-STT key must be re-entered by the operator from
the maintainer's local secret store. They are **not** in the export and must never be —
see T-039. Put this in the runbook as a *Human step*.

### Step 5 — the second headset

Repeat steps 1–4 in full. Do not carry the outcome of the first headset over: if rotation worked on
the operator's device it will almost certainly work on the second, but the export is performed
again regardless, because the second headset holds notes nobody else has a copy of.

**If T-036 answered "out of scope",** the build comes off that headset after its export, and that
is the whole of step 5.

### Step 6 — what changes so this never happens again

This is the half of the task that outlives the migration.

1. **One key from now on, for every build that reaches a headset.** Add a `debug` signing config
   pointing at the release keystore (or a stable, backed-up dev keystore recorded alongside it in
   T-039), so a debug install and a release install are signature-compatible forever. The cut-over
   happens once, here, and never again.
2. **`scripts/install-on-quest.sh` refuses to be the destructive path.** It does not call
   `adb uninstall`, and on `INSTALL_FAILED_UPDATE_INCOMPATIBLE` it prints the export procedure's
   path rather than a suggestion to uninstall. It also prints the installed `versionCode` before
   and after (T-038, H-11) so "did it install?" is answered by a number.
3. **`README.md` gains a line next to every `adb uninstall` it prints**, saying exactly what that
   command destroys. Today the README hands the reader `adb uninstall` as routine.
4. **A `DEC` row** recording the signing decision, the rotation lineage, and the rule that no
   signature change reaches a headset without an export first. Read `docs/DECISIONS.md:7` for the
   free id.
5. **A runbook** at `docs/runbooks/signature-change.md` carrying steps 0–5 above, so the next
   signature change — and there will be one, at the first store submission — is a procedure rather
   than a rediscovery.

## Tests

Most of this is a procedure, not code, and its proof is the checks inside each step. Two things
are testable:

| Test | File | Asserts |
|---|---|---|
| `the export round-trips` | `feature-vault/src/test/.../ExportImportTest.kt` (T-023's) | export → wipe → import reproduces every note, its tags, its front matter and its `audioPath` |
| `the installer never uninstalls` | `scripts/` self-check, run in CI (T-002) | `grep -c 'adb.*uninstall' scripts/install-on-quest.sh` is 0 |

The first is T-023's test and this task **depends on it having been watched failing**. An export
that has not had its restore half proven is a file, not a backup.

## Blast radius, and what NOT to touch

- **Touches:** `app/build.gradle.kts` (a `debug` signing config), `scripts/install-on-quest.sh`,
  `README.md`, one new runbook, one `DEC` row. And two devices.
- **Do not touch:** `android:allowBackup="false"` (`AndroidManifest.xml:29`). Flipping it looks like
  a solution to this problem and is not one; it is a separate privacy decision with its own `DEC`
  row, and it does not survive a signature change anyway.
- **Do not touch:** `SecureSettings` or `KEY_ALIAS` (`core-common/.../SecureSettings.kt:143`).
  Changing the alias would invalidate every stored value on a device that survived the migration —
  turning a successful rotation into the data loss the rotation avoided. Its own comment at `:107`
  warns about exactly this.
- **Do not put secrets in the export.** The Keystore values must not be exportable: an export
  that carries a decrypted API key is a file on `/sdcard` that any app can read. Their loss on
  uninstall is the correct behaviour, and re-entering them is a Human step.
- **Do not force it.** If `install -r` fails for a reason you have not read, stop. There is no
  version of this task in which guessing at an install error is cheaper than reading it.
- **Watch for:** the APK is ~150 MB and a streamed install over Wi-Fi needs a live link for about a
  minute; the Quest drops `adb` within seconds of sleeping. Keep the headset on the head or awake
  for the whole of steps 3 and 4 — an install interrupted between `uninstall` and `install` leaves
  a device with no app and no data, and only the export saves it.
