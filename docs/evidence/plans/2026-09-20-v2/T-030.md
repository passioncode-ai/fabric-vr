## This is the task that rebuilds the screen once

`TodayScreen.kt` is where nine findings and four other tasks land. **This spec is the structure
they all land in.** Read it before touching the file for any WP-5 reason.

The layout after this task, top to bottom:

```
Column(fillMaxSize, padding l = 24dp)            <- does NOT scroll; it is the frame
 ├ header Row            labelled actions, collapses to icons below 420dp   (B-25, T-028)
 ├ DayCard               date + today's note                                (T-028)
 ├ tag chips  FlowRow    only when tags exist                               (T-029)
 ├ statusSlot Box        FIXED height, sized for the tallest state          (B-13)
 │    └ banner / meter+seconds / download rows / provider line / nothing
 ├ Button                128dp, ALWAYS at the same y                        (B-13)
 └ LazyColumn(weight(1f))                                                   (B-11)
      ├ item { justCopied line }         transient rows live INSIDE the list
      ├ item { justDeleted + Undo }
      ├ items(notes) { NoteRow }
      └ item { "and N more" + Show all }                                    (T-026)
```

Two structural rules, and every finding below follows from them:

1. **Nothing above the button may change the button's height allocation.** The status area is a
   fixed-height `Box`; its contents swap inside it.
2. **Everything that can grow lives in the `LazyColumn`, which has `weight(1f)`.** The transient
   rows are `item {}`s, not siblings of the list.

## B-11 — the arithmetic, at the manifest's own minimum

`AndroidManifest.xml:47-51` declares `minWidth 480dp`, `minHeight 360dp`. The person can shrink the
panel to that from the Horizon shell. `Tokens.Space`: `l = 24`, `m = 16`, `s = 8`,
`iconButton = 64`, `controlHeight = 72`, `holdButtonHeight = 128`.

```
360  panel height
-48  outer padding (24 top + 24 bottom)
=312 usable

 64  header (IconButton is 64dp)
 16  spacedBy(m)
128  record button
 16  spacedBy(m)
----
224  before anything transient
 88  remaining
```

Then, all of which are siblings of the list today, not items in it:

```
~56  ErrorBanner
 16  spacing
~30  "Saved, and copied." line
 16  spacing
 72  Undo row (Button is controlHeight = 72)
 16  spacing
----
206  wanted, against 88 available
```

The `LazyColumn` at `TodayScreen.kt:204` is the **last, unweighted** child of a `Column` with no
`verticalScroll` (`:110-116`). It is measured with what is left, which is nothing, so **the notes
vanish and there is no scroll to reach them.** Adding T-028's day card (≥72 dp) and T-029's chip row
(≥72 dp) makes it worse, which is why those two tasks were told to hand their heights here.

**This is not a hypothetical resize**: the same arithmetic explains the panel at its *default*
640 dp too, once a banner and an Undo row are both up.

## The decision, and what was weighed

### The frame (B-11, B-13)

**Chosen: the outer `Column` stays non-scrolling; the status area is a fixed-height `Box`; the
`LazyColumn` takes `weight(1f)` and swallows the transient rows.**

- *Make the outer `Column` `verticalScroll`.* **Rejected, and it is the obvious wrong answer.** A
  `verticalScroll` `Column` gives its children infinite height, so a `LazyColumn` inside it either
  crashes or is forced to a fixed height and stops being lazy. It also means the record button
  scrolls away — the one control the product exists for.
- *Give the `LazyColumn` a fixed height.* Rejected: it hard-codes a number that is wrong at every
  size but one, and the panel is resizable by design (`resizeableActivity="true"`, manifest `:44`).
- *Put the transient rows in a `Scaffold` snackbar.* Rejected: a snackbar floats over the content
  and auto-dismisses; the Undo row must be reachable and aimed at with a ray, and B-18's 72 dp floor
  applies to it.
- *Reserve the status slot vs. anchor the button to the bottom.* B-13 offers both. **Reserve**,
  because anchoring puts the button below the list and a person scrolling the list would then push
  their thumb-equivalent past it. The slot's height is the tallest state — the download state:
  text (~30) + progress bar (~4 + padding) + a 72 dp Cancel + two 8 dp gaps ≈ **130 dp**. Declare it
  as `Tokens.Space.statusSlot = 130.dp` with the derivation in a comment, so the next person who
  adds a state has to update the token rather than silently overflow it.
- *Collapse the header below ~420 dp*, as B-11 suggests. **Adopted**: below 420 dp of height the
  header drops its labels and renders icons only. Below that the slot and the button alone are
  312 - 64 - 130 - 32 = 86 dp for the list, which is one row. That is degraded but usable, and it is
  honest: at the manifest's minimum this screen shows one note.

### B-09 — the dropdown in the Space

**Chosen: measure it, then replace it if it fails. The replacement is designed now, so the
measurement is cheap.**

`DropdownMenu` (material3 1.3.0) is a `Popup` with `PopupProperties(focusable = true)`, i.e. a
second window added through `WindowManager` on a `VirtualDisplay` created with flags `11`
(`PUBLIC | PRESENTATION | OWN_CONTENT_ONLY` — no `SUPPORTS_TOUCH`, no `TRUSTED`). Whether it is
composited into the panel texture **and** receives injected input is unverified, and B-09 names the
two failure shapes: it never appears, or it appears and cannot be dismissed — the second being a
trap that swallows the next tap.

The observation, in the Space, on a headset:
tap *Transcribe again* on a note row. Then (a) does the menu draw? (b) does tapping an item work?
(c) does tapping outside dismiss it?

**If any answer is no**, replace it with an **inline expansion**: tapping *Transcribe again*
expands the row to show the five `SpeechChoice.all()` options as a `FlowRow` of chips within the
row itself, and tapping one collapses it. No second window, no focus, and it works identically in
both hosts. That is ~20 lines and it is the safe default — **if the headset is unavailable when this
task runs, build the inline version and skip the measurement.** A feature that is the whole of
SCN-005's recovery path must not depend on an unproven widget.

The same reasoning applies to every `Popup` in the product; note in the commit that there are no
others today, so the rule is cheap to hold.

### B-12 — the clearing secret fields

`SettingsScreen.kt:65`: `LaunchedEffect(state.savedTick) { if (savedTick > 0) { key = ""; cloudKey = "" } }`,
and `SettingsViewModel.kt:241` increments `savedTick` on **every** successful `put` — language,
provider, model, whisper model, server URL, cloud URL. Paste a 70-character OpenRouter key, tap a
language chip before pressing *Save key*, and the key is gone with no message. In a headset,
re-pasting that is not a small cost.

**Chosen: the tick carries what was saved.** `savedTick: Long` becomes
`lastSaved: SavedField?` (an enum: `API_KEY`, `CLOUD_KEY`, `OTHER`) plus the tick, and each
`LaunchedEffect` clears only its own field.

- *A per-field boolean.* Rejected: two flags today, four the next time a secret is added.
- *Never clear the fields.* Rejected: leaving a secret in a `TextField` after it has been committed
  to the Keystore is the one behaviour the current code gets right.

While in this file, **B-24** is the same bug in a different costume (`:60-62`: the seeding effects
re-fire on every `reload()`, reverting an unsaved edit in a neighbouring field). It is not in this
task's list but it is three lines from it and shares the root cause. Fix it and say so, or leave it
and say so — do not leave the reader guessing whether it was seen.

### B-10 — the discarded result

`TodayScreen.kt:212-214` does `scope.launch { notesViewModel.retranscribe(...) }` and throws the
return value away. `RetranscribeResult` (`NotesViewModel.kt:52`) exists precisely so the screen can
distinguish *Replaced* from *TranscriptOnly*, and `state_retranscribed` / `state_retranscribed_kept`
(`strings.xml:110-111`) are written and unused. **Chosen:** collect the result and render it in the
same slot as the "Saved, and copied" line, with the same `CONFIRMATION_MS` timeout.
`NoRecording`/`Failed` already reach the banner through the view model, so only the two success
cases need a home.

### B-14 — `copied` never resets

Not in the plan's range for this task, and it is four lines from B-10 in the same composable, so it
is here. `NoteRow` at `:370` declares `var copied by remember { mutableStateOf(false) }` and `:446`
sets it true on click. **Nothing ever sets it false**, so the button reads *Copied* for the rest of
the screen's life — and because `items(state.notes, key = { it.id })` keys by id, the state survives
recomposition and list updates. Mirror the `justCopied` pattern the same file already uses at
`:93-98`:

```kotlin
LaunchedEffect(copied) { if (copied) { delay(CONFIRMATION_MS); copied = false } }
```

### `justCopied` and the `LaunchedEffect(voice)` race

`TodayScreen.kt:102-108`:

```kotlin
LaunchedEffect(voice) {
    val ready = voice as? VoiceState.Ready ?: return@LaunchedEffect
    clipboard.setText(AnnotatedString(ready.transcript.text))
    notesViewModel.createVoiceNote(ready.transcript, ready.audioPath)
    voiceViewModel.consumed()
    justCopied = true
}
```

Three problems, in increasing severity:

1. **`justCopied = true` is set after two suspending calls.** If `voice` changes while
   `createVoiceNote` is in flight, the effect is cancelled and **the note is saved with no
   confirmation shown** — the person sees nothing happen. Set `justCopied = true` before the
   suspending work, or after it in a `NonCancellable`-guarded block; setting a UI flag is not the
   thing that should lose the race.
2. **`LaunchedEffect(voice)` keys on the whole state object.** `VoiceState.Recording` carries
   `level` and `samples` (`TodayScreen.kt:253-262`), which change continuously, so this effect is
   **cancelled and relaunched on every audio frame while recording**. It returns immediately on the
   `as?` so nothing visible breaks, but it is churn in the hot path and it is why problem 1 is
   reachable at all. Key on something stable — `(voice as? VoiceState.Ready)?.audioPath` or a
   dedicated one-shot event.
3. **`consumed()` is called after `createVoiceNote`.** If the effect is cancelled between them, the
   state stays `Ready` and the *next* composition runs the whole body again — **a second note from
   one dictation.** `consumed()` must be reached whatever happens, or `createVoiceNote` must be
   idempotent. This is the same class of defect as T-007 (a dictation reverted by the autosave it
   interrupted) and the two should be read together.

**Chosen:** turn this into a one-shot the view model owns — `VoiceViewModel` emits a `Ready` event
through a `Channel`/`SharedFlow` that is consumed exactly once, and the screen collects it. That
removes the key, the race and the double-commit together. If that is too large for this task,
minimum viable: key on `audioPath`, set `justCopied` first, and wrap the commit so `consumed()`
always runs. **Say in the commit which of the two was done.**

## Decomposition

**Step 1 — write the failing tests first**, in `app/src/androidTest/.../TodayScreenTest.kt`
(created by T-028) unless marked otherwise:

1. `the first note is visible at the manifest's minimum size` — `DeviceConfigurationOverride.ForcedSize(DpSize(480.dp, 360.dp))`,
   with a message, a `justCopied` and a `justDeleted` all present; assert the first `note-row` is
   displayed. **Watch it fail** — this is B-11 and it fails today.
2. `the record button does not move between states` — capture `getBoundsInRoot()` of the button in
   Idle, Recording, Transcribing, Downloading and Failed; assert all five are identical.

3. `Copied reverts to Copy` — click Copy, advance the clock past `CONFIRMATION_MS`, assert the label

a ray on a target, and B-13's failure is the target moving out from under it twice per dictation.

## Correction to the finding

**B-13's claim that the button "keeps its place and its size through all of them" is false** — that
is the finding, and it is right. What the finding does not say is that **the doc comment asserting
it is still in the file** (`TodayScreen.kt:233-238`). Fixing the layout without fixing the comment
would leave a paragraph that has been false since `732c92b` looking like a freshly verified claim.
The comment is part of this change.

**B-11's arithmetic uses "Header 64 + 16".** Correct, and the derivation is `Tokens.Space.iconButton = 64`
(`Tokens.kt:44`) rather than a Material default — worth stating, because a reader who assumes 48 dp
concludes there is 16 dp more room than there is.
