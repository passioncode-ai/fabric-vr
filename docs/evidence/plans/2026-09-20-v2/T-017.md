## What is wrong, in the person's terms

Nothing, directly. This is the task that makes the other four in WP-3 possible, and it is here
because of a correlation nobody can argue with.

`Graph` is reached from a **method body** in exactly three places in this app. Those three places
are exactly the three units with **no test**. One of them is the rule that decides whether
re-transcribing a note overwrites text the person has edited by hand — that is, whether pressing
*Transcribe again* on a note they spent ten minutes correcting destroys the correction. That rule
is 47 lines long, it is subtle, it is right as far as anyone can tell by reading, and nothing
anywhere proves it.

The person's stake is: the defects that have already cost them data got in through the seams no
test could reach, and this is the seam.

## The decision, and what was weighed

**Chosen: finish the job `SettingsViewModel` started. Four signatures, three files, no screen
changes.** Every reach becomes a constructor parameter whose default is the `Graph` member it
replaces, so `viewModel()` at every call site keeps working untouched.

```kotlin
class NotesViewModel(
    private val repository: NotesRepository = Graph.notes,
    private val today: () -> LocalDate = LocalDate::now,
    private val vault: Vault = Graph.vault,
    private val dayTicks: Flow<LocalDate> = midnightTicks(),
    /**
     * The engine for one specific provider+model choice, disposed afterwards. A parameter because
     * `retranscribe` is the rule that decides whether a re-run overwrites text the person edited,
     * and a rule that cannot be tested is a rule nobody has checked.
     */
    private val withEngine: suspend (SttProvider, WhisperModel, suspend (SttEngine) -> Any?) -> Any? =
        Graph::withEngine,
    private val language: () -> String = Graph::sttLanguage,
) : ViewModel()
```

— with the generic written properly rather than through `Any?`; see step 2, this is the one place
the shape needs care.

```kotlin
class VoiceViewModel(
    …,
    private val downloader: () -> ModelDownloader = { Graph.modelDownloader() },
) : ViewModel()

class ChatViewModel(
    private val assistant: Assistant = Graph.assistant,
    private val model: () -> String = Graph::model,
) : ViewModel()
```

**Alternatives considered:**

- *Introduce a DI framework (Hilt, Koin).* Rejected. `Graph.kt:34` states the position — "Manual
  DI: the app is small enough that a framework would be noise" — and it is correct: there are
  eight injectable things and six consumers. A framework would add an annotation processor, a
  build-time cost on every module, and a second way of describing the same graph. The defect is
  not the absence of a framework, it is three call sites that ignore the convention the rest of
  the file follows.
- *Make `Graph` an interface with a test implementation.* Rejected: it moves the god object rather
  than removing it, and every test then has to satisfy the whole interface to exercise one method.
  Parameters name exactly what a unit needs, which is also documentation.
- *Add a `Graph.reset(fakes…)` for tests.* Rejected, and it is the tempting shortcut. A mutable
  process-wide singleton shared across a test class is order-dependent by construction: the suite
  goes green, then goes red when someone reorders it, and nobody can tell which test poisoned
  which. It also does nothing for `ChatViewModel`'s `by lazy assistant`, which is memoised on
  first touch (`Graph.kt:155`).
- *Pass `Graph` itself as a constructor parameter.* Rejected for the same reason as the interface,
  plus it keeps the `lateinit appContext` requirement in every test.
- *Inject the dispatcher in the same change (T-019's rule 1).* **Deliberately not done here**, and
  this is the one boundary worth stating twice. T-019 adds `io: CoroutineDispatcher` to the same
  three classes and wraps the same call sites. Doing both at once produces a diff where a reviewer
  cannot tell an injection from a threading change, and threading changes are the ones that need
  the closest reading. **T-017 changes who supplies the dependency and nothing else; T-019 changes
  which thread it runs on.** T-019 depends on this one, so the order is fixed and the second diff
  is small.

**What this task deliberately does not fix**, although it touches the lines: I-08 (`withEngine`
reads `whisperModel()` outside the lock), A-14 (`WhisperEngine.name` is a constant, so a re-run
records the wrong model), A-09 (*Transcribe again* offers absent models) and I-22 (a mid-download
model switch). Each of those becomes *testable* here and is fixed elsewhere. Say so in the commit
so the next reader does not think they were missed.

**Step 2 — `NotesViewModel`, and the one signature that needs care.** `Graph.withEngine` is
`suspend fun <T> withEngine(provider, model, block: suspend (SttEngine) -> T): T`. A generic
function cannot be held in a property of a plain function type without losing the type parameter.
Three shapes, in order of preference:

1. **A single-abstract-method interface**, which keeps the generic and reads better at the call
   site:
   ```kotlin
   fun interface EngineLease {
       suspend operator fun <T> invoke(
           provider: SttProvider,
           model: WhisperModel,
           block: suspend (SttEngine) -> T,
       ): T
   }
   // default: EngineLease { p, m, b -> Graph.withEngine(p, m, b) }
   ```
   Kotlin does not allow a generic method in a `fun interface`'s SAM position, so this must be a
   normal `interface` with one method and an object default. Slightly more ceremony, no type loss.
2. **Specialise to the one thing `retranscribe` actually does** — it only ever asks for a
   `Result<Transcript>`:
   ```kotlin
   private val transcribeWith: suspend (SttProvider, WhisperModel, ShortArray, String) -> Result<Transcript> =
       { provider, model, pcm, lang -> Graph.withEngine(provider, model) { it.transcribe(pcm, langHint = lang) } }
   ```
   **This is the recommended shape.** It is one parameter instead of two, it removes the generic
   problem entirely, it moves `sttLanguage()` inside the default so the view model stops knowing
   that a language setting exists, and the fake in a test is a four-line lambda instead of an
   object. Its cost is that the view model can no longer hold an engine for anything but a
   transcription — which it never does.
3. `suspend (SttProvider, WhisperModel, suspend (SttEngine) -> Any?) -> Any?` with casts. Rejected:
   unchecked casts in the one rule this task exists to make provable.

Take shape 2 unless a second caller for `withEngine` appears in WP-3, in which case take shape 1
and say why in the commit.

**Step 3 — `VoiceViewModel`.** One parameter, `downloader: () -> ModelDownloader = { Graph.modelDownloader() }`,
and `:157` becomes `downloader().download()`. A **provider**, not an instance, for the reason
`SettingsViewModel.kt:59-61` already records: the person can change the model while the screen is
open and an instance captured at construction keeps answering for the old one.

**VOID (DEC-0020, re-audit 2026-09-20 — the class does not exist):** **Step 4 — `ChatViewModel`.** Two parameters. `Graph.assistant` is `by lazy` (`Graph.kt:155-161`)

## Blast radius, and what NOT to touch

  not a `Graph` reference stays byte-identical. This is the rule that keeps the diff reviewable and

  pointer to the task that owns it.

## Correction to the finding

**The plan cites A-31. That row is a different finding.** A-31 is
`SearchViewModel.kt:68-72`: "`retry()` calls `observe()` again without cancelling the previous
`launchIn`, so each retry leaves another collector on the query flow" — the same defect as I-19,
graded Low by axis A and Medium by axis I. It has nothing to do with `Graph`.

The A-axis row that belongs here is **A-29**: "`NotesViewModel` takes its repository and vault as
parameters but reaches into the `Graph` singleton for the engine and the language — so
`retranscribe`, `delete` and `undoDelete` have **no test at all**, and `docs/modules/app.md:57-61`
offers only 'compilation'." That is the same finding as E-04 from the A side, and it is what the
merge's cross-axis agreement ("`Graph` reached from method bodies, and exactly those units
untested — A, C-03, E-04") is pointing at.

**I-24 should also be listed.** It is the same finding again from the concurrency side, and axis
I's closing note is explicit that whoever takes the injection task should take the threading
defects with it — which the plan does, by making T-018, T-019 and T-021 all depend on this row.

**A-31 / I-19 has no task in the plan.** It is two lines (`SearchViewModel` holds a `Job` and
cancels it, as `NotesViewModel.kt:101` already does) and it belongs with T-022, which is the only
other row that touches search. Note it when this task's board row is written.

One thing the findings understate rather than get wrong: E-04 says "three files, four signatures,
three new test classes. No screen changes." The count is right and the *consequence* is
undersold — `NotesViewModel.retranscribe` is not merely untested, it is the only place in the
product where a rule chooses between two versions of the person's own words, and the branch that
protects the edited one (`:193`, `val untouched = note.transcript?.text?.trim() == note.body.trim()`)
has never executed under a test. That deserves to be the headline of this task rather than a line
in a table.
