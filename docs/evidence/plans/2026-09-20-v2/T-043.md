# T-043 — The handoff sends the next agent somewhere real

- **Severity:** Blocker
- **Work package:** WP-8 (documentation truth)
- **Closes:** F-01, F-02, F-03, F-04
- **Depends on:** nothing. This is the one WP-8 task that should not wait for the others.
- **Needs a headset:** no
- **Estimated blast radius:** 2 documents amended, 1 new document (the device gate), 1 `README.md`
  line, 1 `DEC` row. No source code, and — deliberately — **no rewriting of a dated document's
  body**.

## What is wrong, in the person's terms

The document the README names as the entry point describes a build from nine commits ago. An agent
who trusts it will, in this order:

1. plan a first device session for something that already happened at 17:55 on 2026-09-19
   (F-04, F-16) — wasted, not dangerous;
2. run the device gate and be told to *hold Record*, a gesture deleted in `732c92b`. The likely
   outcomes are a report that REQ-003 cannot be verified, or — the destructive one — a "fix" that
   **reinstates the hold**, undoing DEC-0010, because until 2026-09-20 no register entry existed to
   stop them (F-02);
3. re-run the instrumented suite as instructed, get two failures against a document asserting
   "0 failures, 0 skipped", read that as a regression, and bisect for one that is not there
   (F-03);
4. take "the next agent's task is H-28 and nothing before it" literally and skip the whole
   2026-09-20 surface (F-01);
5. connect to `192.168.0.253:5555`, one hard-coded address, while two headsets exist.

## The relation to `docs/handoff/2026-09-20-v2-entry.md`

**That file already exists and is the entry point.** It is 130 lines, written against `8c5ff9e`,
and it is referenced from `docs/evidence/plans/2026-09-20-v2-plan.md:6`. It carries the state, the
three things not to discover the hard way, a reading order, the first task, the finishing rules,
the two headsets with their serials, the build commands, and the four operator questions.

**This task does not rewrite it and does not duplicate it.** The two documents have different
jobs, and the rule below is the deliverable:

| | `2026-09-20-v2-entry.md` | `2026-09-19-v1-build-handoff.md` |
|---|---|---|
| **Kind** | the **current** handoff — one per project, replaced whole | a **dated record** — one per run, never rewritten |
| **Read by** | an agent starting now | someone asking what was true on 2026-09-19 |
| **Edited** | replaced when the next run ends | never, except to add a supersession banner at the top |
| **Named by** | `README.md`, the plan, and nothing else | nothing; it is reached by browsing `docs/handoff/` |

This is the same convention F-39 endorses for dated specs — *a dated document keeps its body and
carries its drift at the top* — applied to handoffs. The reason it matters here: F-01's own
proposed remedy was "write a 2026-09-20 handoff; until then mark this one superseded", and both
halves are now needed rather than either.

## The decision, and what was weighed

**Chosen: one current handoff, named from exactly one place; every older handoff banner-marked and
otherwise untouched; the device gate extracted into a document of its own that is versioned with
the build it walks.**

**Alternatives considered:**

- ***Rewrite the 2026-09-19 handoff to be correct.*** Rejected: it would destroy the record of
  what was believed on 2026-09-19, which is the only evidence for why decisions of that day were
  made. B-003 on the board is already a row closed against work that was later undone; the trail
  a future agent follows to understand *why the hold existed* runs through this document, and
  overwriting it dead-ends that trail permanently.
- ***Delete the superseded handoffs.*** Same objection, harder.
- ***Leave the device gate inside the current handoff.*** Rejected: the gate is the part that goes
  stale fastest — it names gestures, screens and addresses — and burying it in a document that is
  otherwise stable means the whole document is republished every time a button moves. F-02 is
  precisely a gate outliving its build.
- ***Let the README keep pointing at the build handoff, since the banner redirects.*** Rejected: a
  reader who lands on a superseded document and is redirected has already spent the attention. The
  README is the first file anyone opens and it must name the live entry point.

**Step 1 — `docs/handoff/2026-09-19-research-handoff.md` gets a supersession banner** in the same

**Step 3 — extract the device gate into `docs/evidence/device-gate.md`**, written against the
current build, and cross-referenced from the entry point rather than copied into it.

It replaces the five checks at `:96-103`. The two that the merge says are now the risk go first:

1. **Does the Space open at all?** `732c92b`'s hand-tracking declaration is unverified on hardware
   and `deb604d`'s owner fix is unverified; `421377e`'s test is red for a person-in-the-headset
   reason. This is the one claim in the tree with no device evidence behind it.
2. **Does a dictation commit itself?** DEC-0011: no Save step, no preview.
3. REQ-001 — the panel beside a Meta Virtual Display screen.
4. REQ-002 — **this one cannot be walked until T-028 ships**, because a text note cannot be

5. REQ-003 — **press** *Record*, dictate one Russian and one English sentence, record the latency

6. REQ-006 — only if T-033 keeps the assistant.

And it must carry, at the top:

- **which build the gate is for** — after T-038, the `versionCode`/sha it was written against, so
  a gate that has outlived its build is visible rather than merely wrong;
- **both headsets**, by serial, not by one hard-coded address: the entry point already records
  `<serial-1>` at `192.168.0.253:5555` and `<serial-2>` at `192.168.0.140:5555`;
- **which steps are expected to fail today and why**, so a person cannot mistake a known red for a
  regression. This is F-03's real remedy: `PanelSmokeTest` is a stale assertion (T-001 fixes it);
  `ImmersiveLaunchTest` is a device condition (Guardian dialog).

**Step 4 — the entry point gains two lines**, not a section: a pointer to the device gate, and a
pointer to `docs/handoff/` explaining what the dated files are. Nothing else about
`2026-09-20-v2-entry.md` changes under this task; it is current and it is correct.

**Step 5 — the rule, as a `DEC` row**, because no check can decide it:

> *One current handoff, named from `README.md` and the active plan. A run ends by replacing it and
> banner-marking the previous one at the top; a dated handoff is never rewritten. The device gate
> lives in its own file and names the build it was written for.*

Its `Consequences / affects:` line names `README.md`, `docs/handoff/`, `docs/DOCMAP.md`. Read
`docs/DECISIONS.md:7` for the free id — it says the register's next free id, and reading it is not reserving it.

**Step 6 — `docs/DOCMAP.md`** gains a propagation row: *a run ends → the current handoff is
replaced and the previous one banner-marked*. The doc map's propagation matrix is the place an
agent looks for "what else must change"; the handoff is not in it today, which is part of why nine
commits went by without one.

document had outlived its build; a banner rule that a gate enforces turns "someone should have
updated the handoff" into an exit code.

## Blast radius, and what NOT to touch

- **Touches:** `docs/handoff/2026-09-19-research-handoff.md` (a banner), `README.md` (one line),
  `docs/evidence/device-gate.md` (new), `docs/handoff/2026-09-20-v2-entry.md` (two lines),
  `docs/DOCMAP.md` (one row), `scripts/check-docs.sh` (one check), one `DEC` row.

  self-contradiction at `:8-11`, not to correct the hold. The banner is the whole remedy and the
  contradiction is part of the record — the document disagreeing with itself two sections apart is
  evidence about how that day went.
- **Do not rewrite `docs/handoff/2026-09-20-v2-entry.md`.** It is current. Two lines are added; its
  state section, reading order and rules stay as written. If it is found to be wrong about
  something, that is a correction to *it*, in its own commit, not a rewrite folded into this task.
- **Do not put the device gate's steps in three places.** The gate is one file; the entry point
  links to it; the plan links to the entry point. Every copy is a copy that will be the stale one.
- **Watch for:** the serials in the entry point (`<serial-1>`, `<serial-2>`) are already in
  a tracked file in a repository. T-036 decides what the device register records and whether a
  serial belongs in a public surface; if that answer is "no", these two lines move with it, and
  this task must not add a third copy in the device gate. Reference the register instead.
