## The honest answer first: at what note count does this hurt

The brief asks for a measurement or real numbers, and for the answer "not yet" if that is the
answer. It is, with one exception that matters a great deal.

**The shape.** `NoteDao.observeAll()` (`core-notes/.../db/NoteDao.kt:13-14`) is
`SELECT * FROM notes ORDER BY updatedAt DESC` with no `LIMIT`. It is `combine`d in
`NotesViewModel.observe()` (`:103-106`) with `repository.observeTags()`, which runs
`observeTagBlobs()` — `SELECT tags FROM notes` (`NoteDao.kt:27-28`), another full scan — and then
`flatMap`/`filter`/`distinct`/`sorted` over every row in Kotlin (`NotesRepository.kt:70-78`). Room
invalidates on the `notes` table, so **any** write re-runs both. `EditorViewModel` autosaves every
600 ms while a person types (`EditorViewModel.kt:113`), and each autosave is an `upsert`.

**The size of a note.** A 30-second Russian dictation is roughly 400-500 characters. It is stored as
`body`, again as `transcriptText` (they are the same text for a dictation —
`NotesViewModel.kt:244-247`), and the title is its first 60 characters. So ~1 KB of text per note in
`notes`, and the same text again in `note_fts` (E-20(b)) — but the FTS copy is not read by these
queries.

**Per emission,** in memory: ~1 KB of char data per note materialised out of the cursor, plus object
overhead. So:

| Notes | Text materialised per emission | While typing (per 600 ms) |
|---|---|---|
| 300 (plausible after a month for two people) | ~0.3 MB | ~0.6 MB + two scans |
| 1,000 | ~1 MB | ~2 MB + two scans |
| 10,000 | ~10 MB | ~20 MB + two scans |

At the real note count this is **not a wall**, and shipping `androidx.paging` to solve it would be
paying a dependency for a problem nobody has. It becomes one somewhere between 1,000 and a few
thousand notes — at which point the first symptom is not the query but the `LazyColumn` being handed
a list that long, and the second is dropped frames while typing in the editor.

**The exception, and it is this task's real reason to exist: T-022.**

`NoteDao.search()` (`:31-39`) has no `LIMIT` either, and `NotesRepository.search()` builds a prefix
match — every term becomes `term*` (`NotesRepository.kt:118`). **Today a one-letter Russian query
matches almost nothing, because the `simple` tokenizer does not case-fold Cyrillic** (T-022's
measurement). The moment T-022 lands, `а*` or `п*` matches essentially every Russian note in the
base, and `SearchViewModel` runs that on a 120 ms debounce while the person types
(`SearchViewModel.kt:41-47`). T-022 turns a dormant unbounded query into a live one.

So: the list is a "not yet". The search is a "the day T-022 ships".

## Correction to the finding

**G-10's arithmetic double-counts.** It says text is "materialised as `NoteEntity` **and again** as
`Note` per emission ≈ 2 MB" at 1,000 notes. `NoteEntity.toNote()` (`NoteEntity.kt:42-60`) passes the
same `String` references through — `title = title`, `body = body` — and Kotlin strings are
immutable, so no character data is copied. What the mapping allocates is one `Note`, one `Transcript`
and one `Set<String>` of tags per row: object overhead, not text. The correct figure is roughly half
G-10's, which is why the table above says ~1 MB rather than ~2 MB at 1,000 notes. The finding's
*conclusion* stands; its factor of two does not, and a spec that repeated it would be asserting a
number it had not checked.

**G-10's proposed fix says "Delete `observeTagBlobs`/`observeByTag` with the dead tag UI (G-24)".
Do not.** That advice was written against a build where the tag UI did not exist. **T-029 makes tags
reachable** — chips over the list, `selectTag`, `observeByTag` — and it is in the same plan. Deleting
the tag query here and rebuilding it in WP-5 is exactly the churn the plan's ordering section exists
to prevent. (The cross-reference to G-24 is also wrong: G-24 is about the assistant's context
heading repeating a note's own opening. E-11 is the "nothing renders `state.tags`" finding.)

## The decision, and what was weighed

**Chosen: bound every query with an explicit window, stop re-deriving the tag list on every write,
and write down the number at which paging becomes necessary. No new dependency.**

Four changes:

1. **`observeAll(limit)`** — `LIMIT :limit`, called with 200. The list shows the 200 most recently
   updated notes and a row saying how many more exist, with a *Show all* that raises the window.
2. **`search(query, limit)` and `searchOnce`** — `LIMIT :limit`, called with 200 and with the
   assistant's existing 20 respectively. `searchOnce` already has one (`NoteDao.kt:44-52`); `search`
   does not, and it is the one T-022 arms.
3. **The tag list stops re-deriving on every write** — `distinctUntilChanged()` on the derived
   `List<String>` in `NotesRepository.observeTags()` (`:70-78`). The scan still runs, but the
   `combine` in `NotesViewModel` stops emitting a second, identical state for every keystroke's
   autosave. One operator, one line, and it removes the doubled emission that E-12 is about.
4. **A note count**, so the "…and N more" row can exist: `@Query("SELECT count(*) FROM notes")`.
   **T-025 needs the same count** for its "Sent %1$d of your %2$d notes" disclosure — add it once,
   here, and tell that task.

**Alternatives considered:**

- *`androidx.paging` with a `PagingSource`.* The textbook answer and rejected on cost: a new
  dependency (H-13 and T-040 make every dependency something that must be verified and justified),
  a `LazyPagingItems` rewrite of the list, and a second one for Search — to solve a problem that
  begins somewhere past a thousand notes on a two-person deployment. **Named as the successor**:
  when the base passes ~2,000 notes, or when the frame-time observation below shows a miss while
  typing, this is what replaces the window. Write that trigger into `docs/OPEN_QUESTIONS.md` so the
  decision is scheduled rather than forgotten.
- *A normalised `tags` table with a junction, so the tag list is a real index.* Rejected for now: it
  is schema v4 with a migration, immediately after T-022's v3 and before T-027 has built the
  migration harness. Doing the two migrations in one release with no harness is the exact risk H-24
  describes. It is the right eventual shape and belongs after T-027.
- *A recursive CTE to split the comma blob in SQL.* Rejected: it moves a cheap Kotlin loop into an
  expensive SQL one and makes the query unreadable, for no measured gain.
- *Drop the tag query from the `combine` and fetch tags on demand*, as E-12 proposes. Rejected
  because T-029 renders the chips above the list continuously — "on demand" is "always". The
  `distinctUntilChanged` gets the same benefit without a second loading path.
- *Do nothing, since the numbers say "not yet".* Rejected on the search half only: T-022 makes the
  unbounded `search` live, and an unbounded query that a person triggers by typing one letter is not
  a future problem.

## The on-device observation

The one thing the JVM cannot answer is whether typing stays smooth.

```bash
# seed, then type in the editor for ten seconds with the panel open
adb shell dumpsys gfxinfo ai.passioncode.fabricvr | sed -n '/Janky frames/,+2p'
```

Do it twice — with ~300 notes (today's realistic base) and with 2,000 seeded — and record both in
`docs/evidence/verification.md`. **The second number is what decides when `androidx.paging` stops
being a rejected alternative.** If the 300-note run already janks, the problem is not the query and
this task has diagnosed the wrong thing; say so rather than shipping the window as a fix for
something it does not fix.

## Blast radius, and what NOT to touch

- **Touches:** `NoteDao` (two `LIMIT`s, one `count`), `NotesRepository` (two signatures, one
  operator, one method), `NotesViewModel` (state field + `showAll`), `SearchViewModel` (one
  argument), `AudioAdoption.kt` (moved), two strings, two test files.
- **Do not touch:** the tag UI, in either direction. It does not exist yet and **T-029 builds it** —
  deleting `observeTagBlobs`/`observeByTag` as G-10 advises would delete the thing T-029 is about to
  render. `TodayScreen` — T-030 rebuilds it once; this task ships state, not rows.
  `NotesContextBuilder`'s `MATCH_LIMIT = 20` / `RECENT_LIMIT = 40` — already bounded, and they are
  G-11's ground. The FTS schema — T-022 owns the migration and two schema changes in one release is
  what H-24 warns about.
- **Watch for:** `search`'s new `LIMIT` interacts with `ORDER BY notes.updatedAt DESC`
  (`NoteDao.kt:36`) — the 200 kept are the most **recent** matches, not the best ones. That is a
  known weakness (G-11 wants `bm25` ranking) and this task does not fix it; it must be said in the
  commit, because "200 of your matches" silently meaning "the 200 newest" is the kind of thing that
  becomes a bug report six months later.
