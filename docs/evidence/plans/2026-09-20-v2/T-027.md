# T-027 — A schema change cannot destroy a database

- **Severity:** Blocker
- **Work package:** WP-4 (data: search, storage, export)
- **Closes:** H-24, H-25
- **Depends on:** T-022 (it writes the first migration this harness will test), T-002 (a harness no
  CI runs is a harness that rots), T-023 (an export must exist before anyone experiments with a
  person's database)
- **Needs a headset:** no. One optional device check is named at the end.
- **Estimated blast radius:** 1 reconstructed schema file, 1 build-file line, 1 new test file,
  1 new importer in `:feature-vault`, 1 call site in `:app`, 1 CI step. No production schema change.

## What is wrong, in the person's terms

Nothing they can see. This task is entirely about the class of failure where **the app stops
launching, forever, on a headset that has their notes on it** — and about the recovery story the
architecture claims to have and does not.

## Where it is

**The database has one migration and no floor.** `core-notes/.../db/NotesDatabase.kt:10,42-46`:

```kotlin
@Database(entities = [NoteEntity::class, NoteFts::class], version = 2, exportSchema = true)
…
fun open(context: Context): NotesDatabase =
    Room.databaseBuilder(context, NotesDatabase::class.java, "fabricvr-notes.db")
        .addMigrations(MIGRATION_1_2)
        .build()
```

At version 3, if only `MIGRATION_2_3` is written, a device still on schema 1 raises
`IllegalStateException: A migration from 1 to 3 was required but not found` — on **every** launch,
with no way in and no way out but uninstalling, which destroys everything (T-023).

**Only one schema was ever exported.**

```console
$ ls core-notes/schemas/ai.passioncode.fabricvr.notes.db.NotesDatabase/
2.json

$ git log --oneline -- core-notes/schemas
16a5fb5 fix(notes,vault): deletion finds its file, the change stream cannot drop, the daily note cannot double
```

One commit, the one that introduced v2. `MigrationTestHelper` builds the old database **from the
exported JSON**, so with no `1.json` the one migration that a real install is actually sitting on
**cannot be tested at all**. A-12 proposes exactly that test and cannot be written.

**The recovery the architecture promises is not implemented.** `CONTEXT.md` says "the Room database
is an index over [the vault], never the source of truth". The read-back half exists —
`feature-vault/.../MarkdownSerializer.kt:47`, `fun parse(text: String): Note?` — and:

```console
$ grep -rn "MarkdownSerializer.parse" --include='*.kt' . | grep -v /build/
feature-vault/src/test/.../MarkdownVaultTest.kt:30,45,58,63,71,77,78
```

**Seven hits, all in a test.** No production code ever reads a vault file back. The Markdown
survives every migration failure; nothing can turn it into a database again.

## The good news, measured

Reconstructing `1.json` is mechanical and safe, and the reason is in the git history rather than in
a guess. At `16a5fb5^`:

```console
$ git show 16a5fb5^:core-notes/.../db/NotesDatabase.kt | head -8
@Database(entities = [NoteEntity::class, NoteFts::class], version = 1, exportSchema = false)

$ git show 16a5fb5^:core-notes/.../db/NoteEntity.kt | sed -n '11,12p'
@Entity(tableName = "notes")
data class NoteEntity(
```

So v1 is v2 **minus the unique index on `dayKey`** and nothing else — every column, every type, the
FTS table and its `simple` tokenizer are identical. `exportSchema` was simply `false`, and
`core-notes/build.gradle.kts` at that commit carries no `room.schemaLocation` argument. Neither of
those affects the **identity hash**, which Room derives from the entity definitions: so the `1.json`
that KSP emits from that checkout carries exactly the hash sitting in `room_master_table` on a v1
device. This is a reconstruction of a fact, not an invention of one.

## The decision, and what was weighed

**Chosen: reconstruct `1.json` from history; a `MigrationTestHelper` test per migration edge; a CI
check that a version bump without an exported schema fails the build; and the vault→database
importer, so a migration failure becomes a rebuild rather than a loss. `fallbackToDestructiveMigration`
stays absent until the importer exists, and then only as the last resort it is meant to be.**

**Alternatives considered:**

- *Hand-write `1.json`.* Rejected. The file contains an `identityHash`; a hand-written one that is
  even slightly wrong produces a harness that tests a database no device ever had, and the test
  would be green about the wrong thing. Let the tool that computes the hash compute it.
- *Add `fallbackToDestructiveMigration()` now, as a safety net.* **Rejected, and this is the most
  tempting wrong answer in the task.** It converts "the app will not launch" into "the app launches
  and the notes are gone", silently, with no message. That is strictly worse: the first is a
  recoverable incident with the data still on disk, the second is the data loss itself. It becomes
  defensible **only** after the importer exists, because then the destruction is followed by a
  rebuild from the vault. Even then it needs a DEC saying so.
- *`fallbackToDestructiveMigrationFrom(1)` — destroy only the versions nobody has.* Rejected on
  evidence: we do not know that nobody has a v1 device. Two headsets are in use and no record says
  which schema either was installed at. Reconstructing `1.json` costs an hour and removes the
  question.
- *Skip the importer; the export from T-023 is enough.* Rejected. An export is a thing a person must
  remember to do before the failure. The importer is what makes the vault the source of truth the
  documentation already claims it is — and it is mostly written: `parse` exists and is tested.
- *Test migrations only on device, in `androidTest`.* Rejected as the primary home: `:core-notes`
  already runs Robolectric with `room-testing` on the JVM classpath
  (`core-notes/build.gradle.kts:38,40`), so this can be a unit test that runs on every push. See
  the fallback below if the JVM harness will not construct.
- *Run the importer on every launch as a reconciliation.* Rejected: it walks the whole vault and
  parses every file. It runs **only** when the database is empty and the vault is not — the one
  condition under which it is both cheap and necessary.

## Decomposition

**Step 1 — reconstruct `1.json`.** In a scratch worktree, not on the branch:

```bash
git worktree add /tmp/fabric-v1 16a5fb5^
cd /tmp/fabric-v1
# two edits, both reverting the reason the file is missing:
#   NotesDatabase.kt  : exportSchema = false  ->  true
#   core-notes/build.gradle.kts: add  ksp { arg("room.schemaLocation", "$projectDir/schemas") }
./gradlew :core-notes:kspDebugKotlin
cp core-notes/schemas/ai.passioncode.fabricvr.notes.db.NotesDatabase/1.json \
   <repo>/core-notes/schemas/ai.passioncode.fabricvr.notes.db.NotesDatabase/1.json
cd - && git worktree remove /tmp/fabric-v1
```

Then **check the reconstruction before trusting it**, by diffing it against the committed `2.json`:
the only differences must be `"version": 1` vs `2`, the `identityHash`, and the absence of the
`index_notes_dayKey` entry in `notes.indices`. Any other difference means the checkout was wrong.
Record the diff in the commit message — it is the evidence that the file is a reconstruction rather
than a fabrication, and it is the only evidence there will ever be.

**Step 2 — the harness, and the failing test.** New file
`core-notes/src/test/kotlin/ai/passioncode/fabricvr/notes/db/MigrationTest.kt`.

Add to `core-notes/build.gradle.kts`, beside the existing `androidTest` line at `:20`:

```kotlin
sourceSets["test"].assets.srcDir("$projectDir/schemas")
```

`MigrationTestHelper` reads the schema from assets, and the androidTest source set already has this
line — the unit-test one does not, which is why a JVM migration test has never been possible here
either. `unitTests.isIncludeAndroidResources = true` is already set (`:23`).

The three tests, in the order they should be written:

1. **`v1 migrates to v2 without losing a note`** — A-12's test, finally writable. Create the v1
   database from `1.json`, insert two rows by raw SQL (one with a `dayKey`, one without), close,
   run `MIGRATION_1_2` through `runMigrationsAndValidate`, and assert both texts are readable and
   the unique index exists.
2. **`two notes for the same day collapse to the oldest`** — `MIGRATION_1_2`'s documented behaviour
   (`NotesDatabase.kt:16-19`): it deletes all but the oldest row per `dayKey`, because the index
   creation would otherwise fail. It has never been executed by anything. Insert two rows with the
   same `dayKey` and different `rowid`, migrate, assert one survives and it is the older — **and
   that the evicted row's `note_fts` entry went with it**, which the migration's first `execSQL`
   claims to handle and nobody has checked.
3. **`every migration edge composes`** — after T-022 lands, `runMigrationsAndValidate(db, 3, true,
   MIGRATION_1_2, MIGRATION_2_3)` starting from `1.json`. This is the test that would have caught
   the "v1 device bricks at version 3" failure.

**Watch 1 and 2 fail first** — before step 1 they fail with "Cannot find the schema file in the
assets folder", which is the finding itself expressed as a test failure. Keep that first run's
output in the commit message.

**If `MigrationTestHelper` will not construct on the JVM under Robolectric** — Room 2.7.2 offers
both an instrumentation-based constructor and a driver-based one for JVM use, and which works here
is a five-minute experiment, not a design question — **move the file to
`core-notes/src/androidTest/`**, where `sourceSets["androidTest"].assets` is already wired
(`build.gradle.kts:20`), and say in the commit that it runs in the instrumented suite instead. Do
not spend a day making the JVM route work; the test existing is what matters, and T-001 is making
the instrumented suite trustworthy in the same release.

**Step 3 — the exported-schema rule, enforced.** A schema bump with no committed JSON must fail the
build rather than be noticed later. Add to CI (T-002 owns the workflow file; this adds one step):

```bash
# every @Database version must have an exported schema committed
V=$(grep -oE 'version = [0-9]+' core-notes/src/main/kotlin/.../NotesDatabase.kt | grep -oE '[0-9]+')
for n in $(seq 1 "$V"); do
  test -f "core-notes/schemas/ai.passioncode.fabricvr.notes.db.NotesDatabase/$n.json" \
    || { echo "schema $n.json is missing — export it"; exit 1; }
done
git diff --exit-code -- core-notes/schemas || { echo "schemas changed but were not committed"; exit 1; }
```

Run it after the build, so the second check sees whatever KSP just regenerated. Write the rule into
`docs/DECISIONS.md` as a DEC as well: *every schema version is exported and committed in the change
that creates it* — a CI step nobody can explain gets deleted the first time it is inconvenient.

**Step 4 — the importer.** `feature-vault/src/main/kotlin/ai/passioncode/fabricvr/vault/VaultImporter.kt`:

```kotlin
/**
 * Rebuilds the note database from the vault.
 *
 * `CONTEXT.md` calls the database "an index over the vault, never the source of truth". Until this
 * class existed that was an aspiration: `MarkdownSerializer.parse` was called only by its own test,
 * so a lost or corrupt database meant lost notes with the Markdown still on disk.
 *
 * Runs only when the database is empty and the vault is not — never as a merge, because two
 * sources of truth reconciling silently is a worse failure than the one this recovers from.
 */
class VaultImporter(private val vault: Vault, private val notes: NotesRepository, …) {
    suspend fun importIfEmpty(): Result<Int>
}
```

Walk `vault.root/notes/**/*.md`, `MarkdownSerializer.parse` each, `upsert` the ones that parse, count
and log the ones that do not (`Log2.w`, with the path and no content). Re-adopt the sibling `.wav`
by `audioPathFor`, since the stored `audioPath` in the front-matter is an absolute path that may be
from a previous install. Call it from `FabricVrApp`/`Graph` on `Graph.scope` at start-up.

**Note for the operator:** this turns T-023's exported zip into a genuine **restore** path —
unzip it back into `filesDir/vault` over `adb push` and launch with an empty database. Say so in the
commit; it is the sentence that makes the export worth having taken.

**Step 5 — the floor, still absent.** Do **not** add `fallbackToDestructiveMigration()` in this
task even though the importer now exists. Write the option up in `docs/OPEN_QUESTIONS.md` with what
it would then mean ("a failed migration wipes the index and the vault rebuilds it") and let the
operator decide as a DEC. The rule this task establishes is that destruction is never the default
behaviour of a build; adding it in the same commit as the thing that makes it survivable is how it
ends up shipped without anyone deciding.

## Correction to the finding

**H-25 says "`exportSchema = true` was on, but v1 predates it."** Half right, and the other half is
the reason the reconstruction works. At `16a5fb5^` the annotation reads
`exportSchema = **false**`, and `core-notes/build.gradle.kts` at that commit has no
`room.schemaLocation` argument at all. So v1 was not merely "before the directory existed" — export
was switched off. That is *better* news than H-25's version: nothing about the entities changed, so
turning export on at that checkout emits exactly the v1 schema, identity hash included. H-25's
proposed procedure is right; its explanation of why the file is missing is not, and a reader acting
on the stated reason would check out the wrong commit looking for a directory.

## The optional device check

Not required, and worth ten minutes if a headset is to hand:

```bash
adb shell run-as ai.passioncode.fabricvr sqlite3 databases/fabricvr-notes.db \
  "PRAGMA user_version; SELECT identity_hash FROM room_master_table;"
```

If either headset reports `user_version = 1`, the reconstructed `1.json`'s `identityHash` must equal
what it prints — which would turn the reconstruction from "correct by derivation" into "correct by
observation". If both report 2, record that too: it narrows what is in the field.

## Blast radius, and what NOT to touch

- **Touches:** `core-notes/schemas/1.json` (new), `core-notes/build.gradle.kts` (one line),
  `MigrationTest.kt` (new), `VaultImporter.kt` (new), `VaultImportTest.kt` (new), one call site in
  `:app`'s start-up, one CI step, one DEC, one open question.
- **Do not touch:** `MIGRATION_1_2`'s body. It is what ran on the devices in the field; changing it
  now would mean a migration that behaved one way in production and another in the test that claims
  to cover it. If the tests reveal it is wrong, that is a **new** finding and a new task — write it
  down, do not fix it inside the task that first made it visible.
  `MarkdownSerializer` — the importer consumes `parse`, it does not change it. `MIGRATION_2_3` —
  T-022 owns it. The `@Database` `version` — this task adds no schema version.
- **Watch for:** the importer runs at start-up on `Graph.scope` and upserts, which fires
  `VaultMirror` writing the same files back out. Guard against the loop, or run the import before
  the mirror is started, and assert the file count is unchanged afterwards in the test.
- **Watch for:** `MarkdownSerializer.parse` returns `null` for anything without front-matter and an
  `id` (`MarkdownSerializer.kt:48-56`). An Obsidian user editing the vault by hand will strip
  front-matter sooner or later. That is the "skipped, not fatal" test, and it is the one that
  decides whether the vault stays safe to edit.
