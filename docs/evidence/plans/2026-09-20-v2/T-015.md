# T-015 — The panel's texture and its world size agree

- **Severity:** High
- **Work package:** WP-2 (the immersive host)
- **Closes:** B-08 — see *Correction to the finding*; the plan row reads "B-18"
- **Depends on:** nothing
- **Needs a headset:** no for the fix and the test; **yes for one confirming screenshot**, which is
  cheap and named below
- **Estimated blast radius:** 1 file changed, 1 new JVM test, 1 doc section

## What is wrong, in the person's terms

Everything in the Space is about a fifth too tall. Letters are stretched vertically, the round
*Record* button is an egg, the circular progress spinner is an ellipse, and every Material icon is
elongated. It does not read as a bug — it reads as slightly bad typography, which is worse, because
nobody reports it and every subsequent judgement about legibility, spacing and hit size is made
against a distorted picture.

The same screens in the 2D panel are correct. Only the Space is wrong.

## Where it is

`app/src/main/kotlin/ai/passioncode/fabricvr/ImmersiveActivity.kt:95-104`:

```kotlin
config {
    // Transparent, frameless: the panel floats over passthrough, and the default glass
    // would put an opaque plate between the person and their own room.
    themeResourceId = R.style.Theme_FabricVR_Transparent
    layoutWidthInDp = 1024f
    layoutHeightInDp = 640f
    layoutDpi = 288
    enableTransparent = true
    includeGlass = false
}
```

Four properties are set. The two that decide the **physical** size of the quad in the room —
`width` and `height`, in metres — are not among them, so they keep the SDK's defaults.

The defaults, read out of `PanelConfigOptions`'s synthetic default constructor (the `iload 28`
bitmask block, one branch per parameter, in declaration order
`layoutHeightInPx, layoutWidthInPx, layoutHeightInDp, layoutWidthInDp, layoutDpi, height, width,
radiusForCylinderOrSphere, pivotOffsetHeight, pivotOffsetWidth, fractionOfScreen, mips, …`):

```

 59: ldc    #120 0.75f // height             = 0.75f   (metres)
 71: fconst_1          // width              = 1.0f    (metres)
 83: ldc    #121 100.0f// radiusForCylinderOrSphere
 96: ldc    #122 0.5f  // pivotOffsetHeight
109: ldc    #122 0.5f  // pivotOffsetWidth
122: ldc    #122 0.5f  // fractionOfScreen   = 0.5f
```

And the texture size the SDK computes from our four properties:

```
public final int dpToPx(float):   dp * calcDPI() / 160.0f

public final int calcLayoutWidthInPx():
   layoutWidthInPx  if > 0
   else dpToPx(layoutWidthInDp)  if > 0
   else 2064 * fractionOfScreen

public final int calcLayoutHeightInPx():
   layoutHeightInPx if > 0
   else dpToPx(layoutHeightInDp) if > 0
   else calcLayoutWidthInPx() * height / width      // <- the metre aspect, only as a fallback
```

So the arithmetic is:

| Quantity | Value | From |
|---|---|---|
| texture width | `1024 × 288 / 160` = **1843 px** | our config |
| texture height | `640 × 288 / 160` = **1152 px** | our config |
| texture aspect | 1843 / 1152 = **1.600** | — |
| quad width | **1.00 m** | SDK default |
| quad height | **0.75 m** | SDK default |
| quad aspect | 1.000 / 0.750 = **1.333** | — |
| vertical stretch | 1.600 / 1.333 = **×1.200** | — |

Exactly 20%, not approximately: 1024/640 ÷ 4/3 = 1.6 × 0.75 = 1.2.

The third line of `calcLayoutHeightInPx` is the tell — the SDK **does** derive one from the other,
but only when the dp height is left unset. Setting both dp dimensions opts out of that derivation
and takes on the obligation to keep the metre pair consistent, and nothing in the config block says
so. `docs/ux/screens.md:31-37` reasons carefully about the pixel budget ("1843 × 1152 px, inside
the 2064 × 2208 px ceiling") and never mentions metres at all, which is why nobody caught it.

There is a second, independent check that the numbers above are the real ones: angular resolution.
At the panel's placement distance (`ImmersiveActivity.kt:179`, `DISTANCE_M = 1.3f`):

| | width | height | ppd |
|---|---|---|---|
| **today** | 1.00 m → 42.1° over 1843 px | 0.75 m → 32.2° over 1152 px | 43.8 / **35.8** |
| **after** | 1.00 m → 42.1° over 1843 px | 0.625 m → 27.1° over 1152 px | 43.8 / **42.5** |

A panel whose horizontal and vertical pixels-per-degree differ by 22% is a stretched panel; the
near-equality after the fix is the same fact from the other side, and it is computable in a test.

## The decision, and what was weighed

**Chosen: set `width` and `height` in the same `config {}` block, derived from the same two
constants the dp size is derived from, so the pair cannot drift again.**

```kotlin
config {
    themeResourceId = R.style.Theme_FabricVR_Transparent
    layoutWidthInDp = PANEL_WIDTH_DP
    layoutHeightInDp = PANEL_HEIGHT_DP
    layoutDpi = PANEL_DPI
    // The metre size and the texture size are one decision. The SDK defaults are 1.0 × 0.75 m
    // (4:3) and it derives neither from the other once both dp dimensions are set — so a 1024 ×
    // 640 texture on a 4:3 quad was stretching every glyph and every circle by exactly 20 %.
    width = PANEL_WIDTH_M
    height = PANEL_WIDTH_M * PANEL_HEIGHT_DP / PANEL_WIDTH_DP
    enableTransparent = true
    includeGlass = false
}
```

with, in the companion object beside `DISTANCE_M` and `DROP_M`:

```kotlin
/** The texture, in dp. 1024 × 640 matches the 2D panel, so one Compose layout serves both hosts. */
const val PANEL_WIDTH_DP = 1024f
const val PANEL_HEIGHT_DP = 640f
/** 288 dpi puts the texture at 1843 × 1152 px, inside the SDK's 2064 × 2208 eyebuffer. */
const val PANEL_DPI = 288
/** How wide the quad is in the room. At DISTANCE_M this subtends about 42°. */
const val PANEL_WIDTH_M = 1.0f
```

`height` is **computed**, never written as `0.625f`. A literal is a second source of truth for the
same ratio and the whole defect is two sources of truth for one ratio.

**Alternatives considered:**

- *Write `height = 0.625f`.* Rejected for the reason above. It is correct today and it is the exact
  shape of the thing that broke: a number that has to be changed whenever another number changes,
  with nothing connecting them.
- *Delete `layoutHeightInDp` and let `calcLayoutHeightInPx` derive the texture from the metre
  aspect.* Rejected. It does make the two agree — and it makes them agree at 4:3, so the Compose
  tree gets `1024 × 768 dp` instead of `1024 × 640 dp`. That is a different layout from the 2D
  panel's, which breaks the "one Compose tree, both hosts" property `FabricApp`'s KDoc states, and
  it silently invalidates every layout judgement in `docs/ux/screens.md`. The texture size is the
  decision; the metre size follows it, not the other way round.
- *Change `width` to 1.2 m so the panel is bigger and fix the aspect at the same time.* Rejected as
  part of this task: how large the panel should be in the room is a legibility question that needs
  a person at the distance they actually sit (the merge's *What no reader could settle*, second
  bullet). Doing it here would mix a provable correction with an unprovable preference and make
  the screenshot check meaningless. Keep 1.0 m; if the panel should be bigger, that is one constant
  and a separate row.
- *Set `fractionOfScreen` instead.* Rejected: it is read only in `calcLayoutWidthInPx`'s last
  branch, which our explicit dp width already bypasses. It is dead configuration for this panel and
  setting it would be a third number that looks load-bearing and is not.

## Decomposition

**Step 1 — write the failing test first.**
`app/src/test/kotlin/ai/passioncode/fabricvr/PanelGeometryTest.kt` (new, JVM — no SDK needed, and
that is the point: it reads the same constants the `config {}` block reads):

1. `the panel's texture aspect equals its world aspect`
   ```kotlin
   val textureAspect = ImmersiveActivity.PANEL_WIDTH_DP / ImmersiveActivity.PANEL_HEIGHT_DP
   val worldAspect = ImmersiveActivity.PANEL_WIDTH_M / ImmersiveActivity.PANEL_HEIGHT_M
   assertEquals(textureAspect, worldAspect, 1e-4f)
   ```
2. `the texture fits the SDK's eyebuffer` — `PANEL_WIDTH_DP * PANEL_DPI / 160 <= 2064` and
   `PANEL_HEIGHT_DP * PANEL_DPI / 160 <= 2208`. This is the claim `docs/ux/screens.md:35-37`
   already makes in prose and nothing checks.
3. `horizontal and vertical angular resolution agree within 2 %` — compute ppd both ways at
   `DISTANCE_M` and compare. It is the same assertion as 1 expressed in the units a person
   perceives, and it is the one that would catch a future change to `DISTANCE_M` being mistaken for
   a geometry change.

**Watch 1 and 3 fail.** Before the change `worldAspect` is `1.0/0.75 = 1.333` against a texture
aspect of `1.6`, so 1 fails by 20% and 3 fails by 22%. 2 passes today and must keep passing — it is
the guard on the other side, so that "fix the aspect by raising the dpi" cannot be the fix.

To make the test possible, `PANEL_HEIGHT_M` must exist as a value, not only as an expression inside
the `config {}` lambda. Declare it in the companion:

```kotlin
const val PANEL_HEIGHT_M = PANEL_WIDTH_M * PANEL_HEIGHT_DP / PANEL_WIDTH_DP
```

and use `PANEL_HEIGHT_M` in the config block. That way the test reads exactly the value the panel
is built with, and cannot pass by recomputing the right answer next to a wrong configuration —
which is the way this class of test usually fails to be a test.

**Step 2 — the config block.** As written above. Six lines changed, four constants added.

**Step 3 — `docs/ux/screens.md` → *Panel geometry*.** The section currently ends at the pixel
budget. Add the metres and the invariant:

```markdown
The immersive panel's quad is **1.00 m × 0.625 m** at `DISTANCE_M = 1.3 m`, subtending about
42° × 27°. The metre size is derived from the dp size in `ImmersiveActivity`'s companion, not
written separately: the SDK's defaults are 1.0 × 0.75 m and it derives neither dimension from the
other once both `layoutWidthInDp` and `layoutHeightInDp` are set, so a 1024 × 640 dp texture on the
default quad stretched every glyph by exactly 20 % (B-08). `PanelGeometryTest` asserts the two
aspects are equal.
```

The reason belongs in the doc, not only in the code comment: `screens.md` is where the next person
reasons about panel size, and it is where the omission happened.

**Step 4 — the confirming screenshot.** Not a gate on the code, but the task is not *closed*
without it (see below).

measured pixel width and height in `docs/evidence/verification.md` with the date and serial, and
delete the box in the same commit. Alternatively read back `PanelSceneObject.getPanelShapeConfig()`

SDK rather than proving the render.

## Blast radius, and what NOT to touch

- **Touches:** `ImmersiveActivity.kt` (the `config {}` block and four companion constants), one new
  JVM test file, one `docs/ux/screens.md` section.
- **Do not touch:** `placePanel()` or `DISTANCE_M` / `DROP_M`. Where the panel sits is a separate
  decision, it was deliberately derived from the viewer's pose (`ImmersiveActivity.kt:182-188`), and
  changing distance in the same commit makes the screenshot unattributable. `DISTANCE_M` is *read*
  by the new test; it is not changed by it.
- **Do not touch:** `layoutDpi`. Raising it would also equalise the ppd numbers while leaving the
  aspect wrong, which is why test 2 exists.
- **Do not touch:** `enableTransparent`, `includeGlass` or `themeResourceId` — the passthrough
  decision is `DEC-0002`'s and the comment above them is correct.
- **Do not touch:** the 2D panel's `1024 × 640` declaration. The whole point of keeping the dp size
  is that both hosts lay out identically; a change here that also changed the panel would defeat it.
- **Watch for:** `Grabbable()` (`ImmersiveActivity.kt:140`) lets the person move the panel, not
  resize it, so the aspect is fixed once set. If a resize control is ever added, `PanelSceneObject
  .resize(w, h, …)` takes pixels and does **not** recompute the metre size — the same defect will
  reappear there, and the companion constants are what a resize handler should be built from.

## Correction to the finding

**The plan's `Closes` column cites B-18. That row is a different finding.** `B.md:43` — B-18 is the
touch-target size sweep: "`Tokens.Space` declares 72 dp as the floor … most controls in the product
are Material defaults well below it", covering `Components.kt:55,57` and roughly twenty call sites
across five screens. The panel geometry finding is **B-08** (`B.md:33`), which names
`ImmersiveActivity.kt:95-104` and the `PanelConfigOptions` defaults directly.

Cite B-08. **B-18 is a real Medium finding with no task in the plan**; it belongs with T-030 ("the
Today surface's states are correct"), which already owns `B-03…B-13` and touches the same
components — and its proposed fix (`FabricButton`/`FabricTextButton`/`FabricChip` in
`core-common/ui` with `Modifier.heightIn(min = Tokens.Space.controlHeight)`) reaches all five
screens from one place, so it is cheap there and expensive anywhere else.

One addition to B-08 itself, which is otherwise accurate: its proposed fix is
`height = 1.0f * 640f / 1024f (0.625 m)`, written as an expression over literals. That is the right
number and the wrong shape — the literals `640f` and `1024f` are already in the file three lines
above as `layoutHeightInDp` and `layoutWidthInDp`, and repeating them is how the two got out of
step in the first place. Named constants, used in both places.
