# T-006 — *Undo* restores the note **and** its audio

- **Severity:** Blocker
- **Work package:** WP-1 (stop the data loss)
- **Closes:** A-02; **partly** G-13 — see *Correction to the finding*
- **Depends on:** nothing
- **Needs a headset:** no
- **Estimated blast radius:** 1 interface (+2 methods), 1 implementation, 1 view model, 1 string,
  2 test files. No schema change, no UI layout change.

## What is wrong, in the person's terms

They dictate a note. They delete it by mistake. The line appears:

> Deleted "buy the cable". **[Undo]**

They press *Undo*. The note comes back — the text, the title, the timestamps, the tags. It looks
like nothing happened.

**The recording is gone for good.** Not recoverable, not in a trash, not on the device. And the
note that came back still says it has one: its `audioPath` names a file that no longer exists. The
next time they press *Transcribe again* on that note, the banner reads:

> Something failed: FileNotFoundException.

That is the app telling a person about a Java class. `docs/ux/scenarios.md` SCN-015 promises "the
note returns with its id, its timestamps **and its vault file**". Two of the three come back.

## Where it is

**The delete reaches the vault and the vault unlinks.**
`app/src/main/kotlin/ai/passioncode/fabricvr/ui/NotesViewModel.kt:220-227`:

```kotlin
    fun delete(note: Note) {
        viewModelScope.launch {
            repository.delete(note.id).fold(
                onSuccess = { _state.value = _state.value.copy(justDeleted = note) },
                onFailure = { failure -> _state.value = _state.value.copy(message = failure.toMessage()) },
            )
        }
    }
```

`repository.delete` emits `NoteChange.Deleted`, which `VaultMirror.start` routes
(`feature-vault/src/main/kotlin/ai/passioncode/fabricvr/vault/VaultMirror.kt:40`):

```kotlin
                    is NoteChange.Deleted -> remove(change.id, change.createdAt)
```

and `FileVault.remove` (`feature-vault/.../Vault.kt:110-131`) deletes **everything named after the
id**, the `.md` and the `.wav` together, and then walks the whole vault for stragglers:

```kotlin
            val expected = File(root, "notes/${folderFor(createdAt)}")
            val candidates = mutableListOf(File(expected, "$id.md"), File(expected, "$id.wav"))
            if (!candidates.first().exists()) {
                File(root, "notes").walkTopDown()
                    .filter { it.isFile && it.nameWithoutExtension == id }
                    .forEach { candidates.add(it) }
            }
            val deleted = candidates.distinct().count { it.exists() && it.delete() }
```

**The undo restores the row and nothing else.** `NotesViewModel.kt:229-238`:

```kotlin
    /** Writes the deleted note back, id and timestamps included, so the vault file returns too. */
    fun undoDelete() {
        val note = _state.value.justDeleted ?: return
        _state.value = _state.value.copy(justDeleted = null)
        viewModelScope.launch {
            repository.upsert(note).onFailure { failure ->
                _state.value = _state.value.copy(message = failure.toMessage())
            }
        }
    }
```

The KDoc is half right: the upsert emits `Upserted`, the mirror regenerates the **Markdown** from
the note, and that file does come back. The `.wav` cannot, because nothing holds it. `FileVault.write`
copies the audio only if the source is still there (`Vault.kt:88-94`):

```kotlin
            note.audioPath?.let { source ->
                val from = File(source)
                if (from.isFile) {
                    val to = audioPathFor(note)
                    if (from.absolutePath != to.absolutePath) from.copyTo(to, overwrite = true)
                }
            }
```

`from.isFile` is false, so the block is skipped **silently**. The note is written with an
`audioPath` that resolves to nothing.

**Where the person meets it.** `NotesViewModel.kt:179-184`:

```kotlin
            val pcm = withContext(Dispatchers.IO) {
                runCatchingCancellable { WavWriter.readPcm(File(path).readBytes()) }
            }.getOrElse { failure ->
                _state.value = _state.value.copy(message = failure.toMessage())
                return RetranscribeResult.NoRecording
            }
```

`toMessage()` (`NotesViewModel.kt:258-268`) has no branch for a bare `FileNotFoundException` — it
falls to `else -> AppError.Unknown(this)`, which `UiStateMapper.kt:65-70` maps to
`R.string.error_unknown`, whose text is `Something failed: %1$s.` filled with the exception's
simple name.

`state_no_recording` (`app/src/main/res/values/strings.xml:109`) already exists and says the right
thing — *"This note has no recording to transcribe again."* — but it is only reached when
`audioPath` is **null**, which is exactly the case this defect is not.

## Correction to the finding

**A-02 is correct in every particular** — I re-read each link and the cascade is exactly as
described, including the `FileNotFoundException` wording.

**The plan's booking of G-13 against this task is too broad.** G-13 is "every removal path in the
product, complete", and its proposed fix names three things: retention for the audio, a bulk
*Delete all*, and an export. This task builds **one** of them — the first retention mechanism the
product has ever had — and G-13's own text says that is the right one to build first ("Retention
first: it is the one that stops the problem growing"). Bulk delete and export are T-023's, T-024's
and T-035's ground and must not be pulled in here.

So: **T-006 closes A-02 and the retention half of G-13.** The board row for G-13 stays open with
"bulk delete and export remain" until T-023/T-024 land. Recording a finding as closed by a task
that closed a third of it is how a register stops being readable.

## The decision, and what was weighed

**Chosen: the vault soft-deletes. `remove` moves `<id>.*` into `vault/.trash/<id>/` instead of
unlinking; `restore` moves them back; a retention sweep empties the trash.**

The invariant that makes all of this hold, stated so it can be obeyed: **only the vault deletes
vault files, and the vault's delete is reversible for a bounded time.** That is A-02's own
merge note (`A.md:77-81`), and it is what makes *Undo* an honest word.

### Why the alternatives lose

**Defer the vault delete until the undo window closes.** Rejected on two counts, the first fatal:

1. **There is no undo window.** `clearJustDeleted()` (`NotesViewModel.kt:240`) is declared and
   called by nobody — measured, and it is A-35. `justDeleted` survives until the *next* delete,
   which may be an hour or a week. A deferral keyed on the window closing is a deferral that never
   fires: the `.wav` and the `.md` simply stay, and the delete becomes a silent no-op. Building
   the window first is T-030's, and this Blocker must not wait on a layout task.
2. Even with a window, the deferral has to survive process death, and this project already has
   the counter-example: `VaultMirror`'s pending-retry queue is in-memory (H-27), so a note whose
   vault write failed before a restart is in the database, not on disk, and nothing anywhere
   knows. A deferred delete would acquire the same hole in the other direction.

**Copy the audio aside before deleting.** Rejected — it is the chosen fix with the structure
removed:

- It covers the `.wav` only. The `.md` is regenerated by the mirror on undo, so that happens to be
  fine today — but it is fine by accident, and the moment a note carries a second artefact the
  asymmetry bites.
- The copy needs somewhere to live and a lifecycle. Put it in `filesDir` and it is invisible to
  the person and to any future export (G-01); put it in the vault and it *is* a trash folder,
  named worse. Give it no sweep and it grows forever — about 1 MB per 30 seconds of speech
  (G-02's arithmetic), accumulating on every delete a person ever performs, which is a fresh
  instance of the finding next door.
- It also copies rather than moves, so a delete of a five-minute dictation does ~10 MB of I/O for
  an undo that will usually not happen.

**Clear `audioPath` on undo and say the recording could not be restored.** This is A-02's own
fallback and it is not wrong — it replaces a lie with the truth. Rejected as the *primary* fix
because the truth it tells is "your recording is gone", and the recording is the expensive
artefact: it is what makes *Transcribe again* possible at all, and re-running with a better model
is the whole reason the engine badge exists (`TodayScreen.kt:393-394`). **It is kept as the
degradation path** when the trash has already been swept — see step 4.

### What the trash costs, said plainly

Storage. A `.trash` that nothing empties is G-02 again. So retention is not optional in this task;
it ships with the trash or the trash does not ship.

**Two things here are the operator's, not the developer's:**

| Question | Options | Trade |
|---|---|---|
| How long does the trash hold? | 7 days · 30 days · until a size cap | 7 days is one working week and bounds the growth at ~1/50th of the archive; 30 days matches what people expect of a trash and costs proportionally more. There is no measurement that settles it — it is a judgement about how long "I deleted that by mistake" takes to notice. |
| Is the trash visible? | hidden (`.trash`, dot-prefixed) · a Settings row showing "N deleted notes · X MB" with *Empty now* | Hidden is less to explain and less to build. A visible row is the thing G-13 actually asks for and it is the only way a person can answer "how much is stored and how do I reduce it" without `adb`. |

**Do not choose these in code.** Implement the retention period as a constant with the default the
operator names, in one place, and put the question on the board. If no answer arrives, ship
**30 days, hidden**, and say in the commit that it was a default rather than a decision.

`.trash` is dot-prefixed deliberately: Obsidian ignores dot-folders, so a vault the person
eventually points Obsidian at (T-023) does not show them their own deleted notes as live ones.
**The export in T-023 must exclude it** — note that on T-023's row.

## Decomposition

**Step 1 — write the failing tests first.**

`feature-vault/src/test/kotlin/ai/passioncode/fabricvr/vault/VaultTrashTest.kt` (new; the module
already has `MarkdownVaultTest`, `VaultAudioTest`, `VaultMirrorTest` to pattern-match):

1. `remove moves the note and its recording into the trash` — write a note with an adopted `.wav`,
   `remove(id, createdAt)`, assert `notes/YYYY/MM/<id>.md` and `<id>.wav` are gone **and**
   `.trash/<id>/<id>.md` and `.trash/<id>/<id>.wav` exist.
2. `restore puts both back where the note expects them` — then `restore(id, createdAt)`, assert
   `audioPathFor(note)` exists and the bytes are identical to what was written.
3. `restore reports honestly when the trash no longer holds it` — `purgeTrash` first, then
   `restore`, assert a `Result.failure` carrying `AppError.Storage`, **not** an exception and not
   a silent success.
4. `the sweep removes only what is past the retention` — two trashed notes with different
   timestamps, one fake clock, assert exactly one survives.
5. `removing a note the vault never held is not a failure` — the fold-in below.

`app/src/test/kotlin/ai/passioncode/fabricvr/ui/NotesViewModelTest.kt` (existing; four tests
today):

6. `undo after delete restores the recording, not only the row` — a real `FileVault` over a temp
   root plus a real `VaultMirror`, delete, `undoDelete()`, assert `vault.audioPathFor(note)`
   exists and the restored note's `audioPath` resolves.
7. `undo tells the person when the recording could not be restored` — purge the trash between the
   delete and the undo; assert the note returns with `audioPath == null` **and** a non-null
   `state.message`.

**Run 1, 2, 6 and 7 first and watch them fail.** 1 and 2 fail because `.trash` does not exist; 6
fails on the missing file; 7 fails because nothing sets a message. If 6 passes before the change,
the test is not using a real `FileVault` — the fake in `NotesViewModelTest` does not delete.

**Step 2 — `Vault` gains two methods.** `feature-vault/.../Vault.kt:18-38`:

```kotlin
    /**
     * Puts back what [remove] took, for as long as the trash still holds it.
     *
     * [remove] does not unlink: it moves `<id>.*` aside, because the only Undo this product offers
     * restored the database row and left the recording deleted — the note came back pointing at a
     * file that was gone, and *Transcribe again* answered with a FileNotFoundException.
     */
    suspend fun restore(id: String, createdAt: Long): Result<Unit>

    /** Empties the trash of anything deleted before [before]. Idempotent; safe to run at startup. */
    suspend fun purgeTrash(before: Instant): Result<Int>
```

Every implementor must change. There is exactly one production implementation (`FileVault`) and
the test fakes in `EditorViewModelTest.kt:50-64` and `NotesViewModelTest`; the compiler names them
all.

**Step 3 — `FileVault`.** `remove` moves instead of deleting:

- target directory `File(root, ".trash/$id")`, created with `mkdirs()`;
- move each candidate with `renameTo`, falling back to `copyTo` + `delete` — the same
  cross-filesystem reasoning `adoptAudio` already writes down at `Vault.kt:67-68`, and it should
  be a shared private helper rather than a third copy of that comment;
- **keep the id-walk fallback** at `:114-118`. Files written by an older build used the device's
  zone (the reason the walk exists), and they must be trashed too, not left behind;
- record the deletion time. Do **not** infer it from the file's `lastModified` — that is the
  note's write time, not its delete time. Write a sibling `deletedAt` marker
  (`.trash/<id>/.deleted-at`, one line, epoch millis) or use the directory's own mtime and say in
  a comment which and why.

`restore` moves `.trash/<id>/*` back into `notes/${folderFor(createdAt)}/` and removes the trash
directory. `purgeTrash` walks `.trash/*`, reads each marker, deletes the directories older than
`before`, and returns how many went — a count, so a caller can log it.

**Step 4 — `NotesViewModel.undoDelete`.** Restore, **then** upsert, in that order:

```kotlin
    fun undoDelete() {
        val note = _state.value.justDeleted ?: return
        _state.value = _state.value.copy(justDeleted = null)
        viewModelScope.launch {
            // The recording comes back first: the mirror's write for the upsert below copies the
            // audio only when it is already where the note says it is (Vault.write:88-94).
            val restored = vault.restore(note.id, note.createdAt).isSuccess
            val putBack = if (restored) note else note.copy(audioPath = null)
            repository.upsert(putBack).fold(
                onSuccess = {
                    if (!restored && note.audioPath != null) {
                        _state.value = _state.value.copy(
                            message = UiMessage(R.string.state_undo_without_recording, action = null),
                        )
                    }
                },
                onFailure = { failure -> _state.value = _state.value.copy(message = failure.toMessage()) },
            )
        }
    }
```

Note the guard `note.audioPath != null`: a text note has no recording and must not be told that
one could not be restored.

**Step 5 — the string.** `app/src/main/res/values/strings.xml`:

```xml
<string name="state_undo_without_recording">The note is back. Its recording had already been cleared.</string>
```

Wording is a draft — the brand pack does not exist (B-035) and `copywriting` owns the final text.
Say that in the commit rather than presenting it as final.

**Step 6 — the sweep, and where it runs.** `purgeTrash(now - retention)` on `Graph.scope` from
`Graph.init` (`Graph.kt:163-166`). `Graph.scope` is `Dispatchers.Default` with a `SupervisorJob`,
so it is off the main thread and a failure cannot take the app down. **Do not run it on the main
thread and do not run it synchronously in `onCreate`** — E's startup analysis (`E.md:308-316`) is
that cold start is currently clean and this is the kind of addition that quietly stops being true.

One constant, one place:

```kotlin
/** How long a deleted note's files stay recoverable. Decided by the operator; see T-006. */
private val TRASH_RETENTION: Duration = Duration.ofDays(30)
```

**Step 7 — the fold-in, and only this one.** This task edits `FileVault.remove` and
`VaultMirror.remove`, so A-19/I-07 is in the same two functions: `remove`'s failure branch
(`VaultMirror.kt:65-68`) never clears `pending`, and `FileVault.remove` fails with
`FileNotFoundException` whenever there is nothing to delete — so deleting a note the vault never
held leaves it pending forever, and Settings' *Retry* then **writes the deleted note's Markdown
back into the person's folder**. Two lines: treat "no file for this id" as success (a note with no
file is already removed), and clear `pending` in both branches.

Fold it in, say so explicitly in the commit, and **stop there**. `_failures` being four
unsynchronised read-modify-writes (I-06) is the same file and is *not* this task's — it needs the
`MutableStateFlow<MirrorState>` reshape and its own tests.

## Blast radius, and what NOT to touch

- **Touches:** `feature-vault/.../Vault.kt` (interface +2, `FileVault.remove` rewritten, 2 new
  methods), `feature-vault/.../VaultMirror.kt` (the two-line fold-in only),
  `app/.../ui/NotesViewModel.kt` (`undoDelete`), `app/.../Graph.kt` (the sweep call and the
  constant), `strings.xml` (one string), two test files.
- **Do not touch:** `Vault.adoptAudio` and `Vault.write` — T-007 and T-005 both sit near the audio
  path and a change here would collide. `VoiceViewModel.cancel()`'s delete of the *scratch* WAV —
  that file is not a vault file and T-005 owns its wiring; the invariant in this task is about the
  vault, not about scratch. `_failures` in `VaultMirror` (I-06). `NotesViewModel.retranscribe` —
  A-13's staleness bug is in the same method and is not this task's; **do not "improve" the
  re-read while you are in there.** `clearJustDeleted` / the undo window (A-35) — T-030's.
- **Watch for:**
  - **`FileVault.remove`'s id-walk** (`Vault.kt:114-118`) walks `File(root, "notes")`. `.trash`
    must live **outside** `notes/` — `root/.trash`, not `root/notes/.trash` — or the walk will find
    trashed files and trash them again. Assert that in test 1 by trashing the same id twice.
  - **`MarkdownSerializer`** is untouched, but `.trash` now sits inside the vault root, and
    anything that enumerates the vault must skip it: the future export (T-023), the future size
    counter (T-024), and any Obsidian pointing. Leave a note on both rows.
  - **`VaultMirror` processes changes in program order on one collector** (`I.md:468-471`), so a
    delete followed immediately by an undo cannot interleave — the restore in step 4 runs on the
    view model's scope while the mirror's write runs on `Graph.scope`, and the restore completes
    before the upsert is issued. That ordering is load-bearing; the comment in step 4 says so, and
    test 6 would catch its loss.
  - **`H-27`**: the mirror's pending map is in-memory. A restore whose subsequent mirror write
    fails, followed by a process death, still leaves a hole — smaller than today's, and not this
    task's to close.
