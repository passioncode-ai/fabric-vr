# T-016 — The Space is entered and left without a crash, proven by a test that cannot pass vacuously

- **Severity:** High
- **Work package:** WP-2 (the immersive host)
- **Closes:** C-22, I-27, I-12 — see *Correction to the finding*; the plan row reads "C-05, I-12"
- **Depends on:** T-012 (this test asserts the owners T-012 leaves behind; writing it against the
  four owners means rewriting it a day later)
- **Needs a headset:** **yes to run.** It is an instrumented test and the whole point of it is the
  real activity on the real shell.
- **Estimated blast radius:** 1 test file rewritten, ~6 lines of production test-support changed,
  1 CI note

## What is wrong, in the person's terms

Nobody can tell whether entering and leaving the Space works.

`ImmersiveLaunchTest` exists and is the only thing that watches it. On 2026-09-20 it was red
because the headset was showing a Guardian dialog — the shell had quietly refused to bring the
activity forward — and the message it printed was indistinguishable from "the Space is broken". On
another run it can be green while asserting almost nothing: the crash check it makes cannot fire in
the process it runs in, and there is no check at all for leaving.

So the one thing the person actually experiences — put the headset on, go into the Space, come back
out, and still have their note — is untested at both ends.

## Where it is

`app/src/androidTest/kotlin/ai/passioncode/fabricvr/ImmersiveLaunchTest.kt`, the whole test:

```kotlin
@Test
fun enteringTheSpaceDoesNotCrashTheApp() {
    val activityManager = context.getSystemService(ActivityManager::class.java)
    val startedAt = System.currentTimeMillis()
    ImmersiveActivity.composedAtLeastOnce = false                                    // :34

    context.startActivity(ImmersiveActivity.intent(context))                         // :36
    val deadline = System.currentTimeMillis() + SETTLE_MS
    while (!ImmersiveActivity.composedAtLeastOnce && System.currentTimeMillis() < deadline) {
        Thread.sleep(POLL_MS)                                                        // :41
    }

    val crashes = activityManager
        .getHistoricalProcessExitReasons(context.packageName, 0, MAX_RECORDS)
        .filter { it.timestamp >= startedAt &&
            it.reason == ActivityManager.RunningAppProcessInfo.REASON_UNKNOWN }      // :46

    val fatal = activityManager
        .getHistoricalProcessExitReasons(context.packageName, 0, MAX_RECORDS)
        .filter { it.timestamp >= startedAt &&
            it.reason == android.app.ApplicationExitInfo.REASON_CRASH }              // :51

    assertTrue("the Space crashed the app: …", fatal.isEmpty() && crashes.isEmpty()) // :53-56
    assertTrue("the Space never composed: the shell deferred or refused the launch. …",
        ImmersiveActivity.composedAtLeastOnce)                                       // :60-64
}
```

and the marker it uses, `ImmersiveActivity.kt:165-176`:

```kotlin
@Volatile
var composedAtLeastOnce: Boolean = false
    internal set
```

set once, from inside the composition, at `ImmersiveActivity.kt:116`.

**Four defects, in descending order of how much they cost:**

**1. The crash assertions cannot fire.** `app/src/main/AndroidManifest.xml:40,59` declares both
activities with no `android:process`, and `app/build.gradle.kts:21` uses
`androidx.test.runner.AndroidJUnitRunner`, which runs the instrumentation **inside the target
application's process**. If `ImmersiveActivity` takes the process down, the test process goes with
it — the run reports `Process crashed` and never reaches line 53. And
`getHistoricalProcessExitReasons` reports records for processes that have already **ended**, so a
record with `timestamp >= startedAt` for the still-running process cannot exist. Both filters
therefore always return empty and both assertions always pass. The one thing the test is named
after is the one thing it does not check.

**2. `RunningAppProcessInfo.REASON_UNKNOWN` is the wrong constant** (`:46`). It belongs to the
process-*importance* vocabulary, not to `ApplicationExitInfo`. It happens to equal `0`, which is
also `ApplicationExitInfo.REASON_UNKNOWN`, so the code compiles and means something — "no exit with
an unknown reason" — but it means it by coincidence. A reader cannot tell intent from accident.

**3. Nothing covers leaving.** No `finish()`, no `returnToPanel()`, no assertion that an edit
survived. I-03 — `onDispose { flush() }` firing into a cancelled scope on **every** exit from the
Space — is the highest-severity thing in WP-2 and no test would notice it going or coming back.

**4. Deferral and breakage produce the same failure.** When the shell defers the launch the message
at `:61-62` is a guess dressed as a diagnosis: it says "the shell deferred or refused the launch"
for a condition that is *also* what a broken panel looks like. A red build with that message
teaches an agent to shrug at red.

## The decision, and what was weighed

**Chosen: the test proves three things per run — the Space composed *because of this launch*, it
stopped when it was stopped, and it left without losing an edit — and it distinguishes "the shell
did not start it" from "we broke it" by asking the platform, not by inferring from silence.**

The mechanism for the distinction is the pivot of this task, so state it plainly:

> **Deferral is an environment fact and it makes the test *skipped*, not passed and not failed.
> Breakage is a product fact and it makes the test *failed*.** The two are told apart by whether
> the activity reached `RESUMED`. If it never resumed, the shell never gave it the foreground and
> nothing about this app has been tested. If it resumed and the composition still did not run,
> that is ours.

`androidx.test.runner.lifecycle.ActivityLifecycleMonitorRegistry` reports the stage of every
activity in the process without any production hook. JUnit's `Assume.assumeTrue` turns an
unsatisfied environment precondition into a skip with a message. Neither is new machinery.

**Alternatives considered:**

- *Keep polling `composedAtLeastOnce` and improve the message.* Rejected: a better sentence about
  an inference is still an inference. The test would still report the same state for two different
  causes, and the reason the 2026-09-20 red was ignored is that nobody could act on it.
- *Treat a deferred launch as a failure.* Rejected. It would be red on a headset with a Guardian
  dialog, a headset in the wrong reference space, or a headset a person is wearing at that moment —
  and CI cannot cure any of those. A suite that is red for reasons nobody can fix is a suite nobody
  runs (H-08's whole ground).
- *Treat a deferred launch as a pass.* Rejected outright, and it is worth naming because it is the
  path of least resistance: a green test over a Space that never opened is exactly the failure
  `421377e`'s commit message ("absence of a crash is not presence of a Space") was written against.
- *Keep `composedAtLeastOnce` as a `Boolean` and reset it in `onCreate` (C-22's proposal).*
  Rejected as insufficient rather than wrong. A boolean reset by whoever remembers to reset it
  cannot answer "did it compose **since I asked**" when two things can start the activity; a
  monotonic counter snapshotted before the launch answers it by construction and needs no reset
  anywhere.
- *Replace the marker with a `CompletableDeferred` the test awaits (I-27's second proposal).*
  Rejected narrowly. It is cleaner for one launch and worse for two: the test now launches, stops
  and finishes, and wants three independent "has it happened since I asked" questions. Three
  counters are simpler than three deferreds with a reset protocol between them.
- *Split into three test methods.* Considered and **chosen in part**: enter, stop and exit become
  three `@Test`s so a failure names which half broke, sharing one launch helper. What is *not*
  split is the skip decision — each method calls the same helper, which does the `assumeTrue`.
- *Use `ActivityScenario` to drive the lifecycle deterministically.* Rejected: `AppSystemActivity`
  starts an OpenXR session and the SDK's `VrActivityProcessGuard` refuses a duplicate; driving it
  through a scenario controller is untested ground and the failure mode would be a hang. Stopping
  the activity by launching `PanelActivity` over it is the path a person actually takes.

## Decomposition

**Step 1 — replace the marker with three counters.** In `ImmersiveActivity`'s companion, replacing
`:165-176`:

```kotlin
/**
 * Test handshake, not production state. `ImmersiveLaunchTest` snapshots these before it launches
 * and waits for an *increase*, so "did the Space open" is answered for this launch rather than
 * for some launch. A boolean could not: a process that composed once answers `true` forever, and
 * whoever forgets to reset it gets a green test over a Space that never opened.
 *
 * They are only ever incremented, so no reset protocol exists to get wrong.
 */
val compositionCount = java.util.concurrent.atomic.AtomicLong(0)
```

and at `:116`, in place of `composedAtLeastOnce = true`:

```kotlin
// Incremented from inside the composition, not from onCreate: the crash this records the
// absence of happened while composing, and a marker set before it would have said "fine"
// about a panel that never drew.
SideEffect { compositionCount.incrementAndGet() }
```

**`SideEffect`, not a bare statement.** The current line runs on every recomposition *and* on every
composition attempt that is later abandoned; wrapped in `SideEffect` it runs once per successful
composition. That matters now that the number is read rather than the flag.

`createdCount` and `resumedCount` are **not** added — `ActivityLifecycleMonitorRegistry` already
knows, and a production field that exists only for a test is production code that ships (E's
complaint about `composedAtLeastOnce` at `E.md:211`, and it is right).

**Step 2 — write the failing tests first.** Rewrite
`app/src/androidTest/kotlin/ai/passioncode/fabricvr/ImmersiveLaunchTest.kt`. Shared helper:

```kotlin
/**
 * Launches the Space and returns the activity, or SKIPS the test when the shell never brought it
 * forward. The distinction is the whole point: a deferred launch (Guardian dialog, no controllers
 * paired, the headset off a head) says nothing about this app, while an activity that reached
 * RESUMED and then failed to compose is ours. One is an assumption, the other is a failure.
 */
private fun enterTheSpace(): ImmersiveActivity {
    val before = ImmersiveActivity.compositionCount.get()
    context.startActivity(ImmersiveActivity.intent(context))

    val resumed = await(RESUME_MS) { activityInStage(Stage.RESUMED) != null }
    Assume.assumeTrue(
        "the shell did not bring ImmersiveActivity to the foreground within ${RESUME_MS} ms. " +
            "This is an environment fact, not a product failure: check for a Guardian dialog, " +
            "`adb shell dumpsys activity activities | grep ImmersiveActivity`, and logcat for " +
            "SystemUXController / controller_required. Nothing about the app was tested.",
        resumed,
    )

    val activity = activityInStage(Stage.RESUMED) as ImmersiveActivity
    assertTrue(
        "ImmersiveActivity resumed but its panel never composed within ${COMPOSE_MS} ms. " +
            "The shell DID start it, so this is ours: the panel registration, the owners, or " +
            "the composition itself.",
        await(COMPOSE_MS) { ImmersiveActivity.compositionCount.get() > before },
    )
    return activity
}
```

Three tests over it:

1. **`entering the Space composes the panel`** — call the helper and stop. Its whole body is the
   helper's second assertion. It fails loudly and specifically if the panel does not draw.

2. **`the Space stops collecting when it is stopped`** (I-12) — enter, then launch `PanelActivity`
   over it, wait for `ImmersiveActivity` to reach `Stage.STOPPED`, and assert the **composition's**
   lifecycle owner is at most `CREATED`:
   ```kotlin
   val owner = ImmersiveActivity.capturedLifecycleOwner   // set by T-012's capture hook
   assertEquals(Lifecycle.State.CREATED, owner.lifecycle.currentState)
   ```
   **Watch this fail before T-012 lands**: today it reads `STARTED`, because
   `SpatialPanelOwners.registry` never receives `ON_STOP`. It is the assertion that makes T-012's
   benefit visible, and it is why this task depends on it rather than the other way round.

3. **`leaving the Space keeps an unsaved edit`** (I-03) — enter, drive the editor to a note, type
   into it, `finish()` the activity from the main thread, wait for `Stage.DESTROYED`, then read the
   note back out of the repository and assert the text is there. Getting to the editor from an
   instrumented test on a real immersive activity is the awkward part; two acceptable shapes:
   - start the activity with an intent extra naming a note id, and have `FabricApp` honour it (it
     is also what D-18 wants for state crossing the host boundary, so it is not test-only code); or
   - drive it through `EditorViewModel` directly on the main thread, using the same
     `ViewModelStoreOwner` the panel uses, and assert `flush()` on dispose reached the repository.
   The second is narrower and does not need a production change. **Prefer the second in this task**
   and leave the intent extra to D-18's own row.

**Step 3 — replace, do not repair, the exit-reason check.** Delete both `getHistoricalProcessExitReasons`
filters. They cannot fire in-process (defect 1) and one of them uses the wrong constant (defect 2).
Put the check where it *can* fire: a **`@Before`** that looks at the exit records from **before**
this run and fails if the previous run of the suite ended in `REASON_CRASH`:

```kotlin
@Before fun theLastRunDidNotEndInACrash() {
    val fatal = activityManager.getHistoricalProcessExitReasons(context.packageName, 0, MAX_RECORDS)
        .filter { it.reason == android.app.ApplicationExitInfo.REASON_CRASH }
    // A crash in THIS process kills the instrumentation, so it is never visible from inside the
    // run that caused it. It is visible on the next one. Reporting it here turns an invisible
    // failure into a named one, at the cost of one run's delay.
    assertTrue("the previous run of this app crashed: " +
        fatal.joinToString { "${it.timestamp}: ${it.description}" }, fatal.isEmpty())
}
```

Say in the KDoc that this is a **one-run-late** signal and why it cannot be anything else. That
sentence is the difference between a check and a decoration.

**Step 4 — the deferral evidence goes somewhere durable.** A skipped test tells the operator
nothing if nobody reads the run output. Whatever CI T-002 lands must report skips separately from
passes; a run where `ImmersiveLaunchTest` skipped three times is not a green run, it is an
unobserved one. Add that sentence to T-002's spec and to `docs/evidence/verification.md`'s header:
**a skipped Space test is an open row, not a closed one.**

**Step 5 — `PanelSmokeTest` is not this task's.** It asserts two strings no screen renders
(`F-02`/`F-03`) and it is T-001's. Do not touch it here; a reviewer seeing both files change will
not be able to tell which change made the suite green.

## Definition of Done

- [ ] `composedAtLeastOnce` is gone; `compositionCount` is a monotonic counter incremented from a
      `SideEffect`, and no test resets any production state.
- [ ] A deferred launch **skips** with a message naming the three things to check, and never
      passes.
- [ ] An activity that resumed and did not compose **fails**, with a message that says the shell
      did start it.
- [ ] Tests 2 and 3 were each run against the tree **before** T-012 and watched failing; the commit
      records the two failure messages verbatim.
- [ ] No assertion in the file depends on `getHistoricalProcessExitReasons` for the current
      process.
- [ ] `docs/evidence/verification.md` states that a skipped Space test leaves its row open, and the
      CI configuration reports skips separately.
- [ ] `./gradlew testDebugUnitTest lintDebug` green; `connectedDebugAndroidTest` run on a Quest 3
      with the serial and the date recorded.
- [ ] The commit explains why the old crash check could never fire.

## Blast radius, and what NOT to touch

- **Touches:** `ImmersiveLaunchTest.kt` (rewritten), `ImmersiveActivity.kt` (the companion marker
  and line 116), `docs/evidence/verification.md`, a note in T-002's CI configuration.
- **Do not touch:** `PanelSmokeTest.kt` — T-001. `ModelDownloadReachabilityTest` — unrelated and it
  hits the network. `SpatialPanelOwners` / the owners themselves — T-012 owns them; this task only
  *reads* what T-012 leaves.
- **Do not touch:** `SETTLE_MS`'s successor values without saying why. The old 8 s was one number
  for two different waits; splitting it into `RESUME_MS` (how long the shell may take to give the
  activity the foreground — generous, 10 s) and `COMPOSE_MS` (how long a resumed activity may take
  to draw — tight, 3 s) is what makes the skip/fail split meaningful. A single generous timeout
  turns a broken panel into a skip.
- **Watch for:** the capture hook test 2 needs (`capturedLifecycleOwner`) is T-012's step 1. If
  T-012 lands it as an `androidTest`-only mechanism, this test uses the same one; if it lands a
  production field, push back — the counter above is already one production field more than E
  thinks this file should have.
- **Watch for:** `android:launchMode="singleTask"` on `ImmersiveActivity`
  (`AndroidManifest.xml:63`). A second `startActivity` in the same run re-uses the existing
  instance and composes nothing, so each test must either finish the activity in an `@After` or
  tolerate reuse. Finish it in `@After`, and wait for `Stage.DESTROYED` before returning — not
  doing so is how the second test in a class ends up asserting against the first one's activity.

## Correction to the finding

**The plan cites C-05. That row is unrelated to this test.** `C.md:16` — C-05 is
`AudioRecorder.kt:60-73`: "`recorder.read()` is only acted on when `read > 0`. Every negative
return … falls through and the `while (isActive)` loop spins immediately." That is a busy-loop and
a frozen meter when the microphone is contended, and it belongs with **T-020**, which already owns
the recorder's buffer and lifetime and touches the same twelve lines. **C-05 currently has no task
and would be closed by nothing.**

The row that belongs here is **C-22** (`C.md:33`) — the `composedAtLeastOnce` marker — together
with its axis-I twin **I-27**. I-12 is correctly cited.

**And C-22 / I-27 are both wrong on their facts.** C-22's failure scenario reads: "Once any launch
in a process sets it, a later `ImmersiveLaunchTest` in the same process asserts a fact established
by an earlier test." It does not: `ImmersiveLaunchTest.kt:34` sets
`ImmersiveActivity.composedAtLeastOnce = false` before every launch. I-27 says the same thing more
carefully ("reset only by the test") and then gives a production failure scenario — "a second entry
into the Space in the same process reads a stale `true`" — for a field **nothing in production
reads** (`grep -rn "composedAtLeastOnce" app/src/main` → one write at `:116` and the declaration).
Both rows are Low, and both are Low for a reason that is not the one they give.

The real weaknesses of this test are the four listed under *Where it is*, and **three of them
appear in no audit row at all**: the in-process crash check that cannot fire, the wrong
`REASON_UNKNOWN` constant, and the complete absence of an exit path. The first is the important
one, because `docs/handoff/…:115-118`'s claim of "13 tests, 0 failures" (F-03) was partly built on a
test whose headline assertion is unreachable. Add them to the board as new findings when this
task's row is written, attributed to this spec rather than to the audit.
