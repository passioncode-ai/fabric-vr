# T-038 — A build can be identified from inside the app

- **Severity:** High
- **Work package:** WP-7 (release engineering)
- **Closes:** H-31, H-30
- **Depends on:** nothing. **T-036's answer changes what the device register records, not what this
  task builds.**
- **Needs a headset:** no to build; one observation on a headset to close it
- **Estimated blast radius:** 3 files changed (`app/build.gradle.kts`, `SettingsViewModel.kt`,
  `scripts/install-on-quest.sh`), 1 string, 1 test file, no contract moves

## What is wrong, in the person's terms

Two headsets are running this app. Nobody can tell what is on either of them, including by looking
at the app, and the installer does not say which headset it just installed on.

The Settings screen reads `Fabric VR 0.1.0 (1)` on today's build. It read `Fabric VR 0.1.0 (1)` on
the build from two days ago. It will read `Fabric VR 0.1.0 (1)` on the next one. The question "is the
second headset a week old?" has no answer that does not involve comparing APK bytes.

## Where it is

**The version.** `app/build.gradle.kts:18-21`:

```kotlin
// The build number comes from the caller (`-PversionCode=42`) so a release can be rebuilt
// from the same commit without editing a tracked file.
versionCode = (findProperty("versionCode") as String?)?.toInt() ?: 1
versionName = "0.1.0"
```

The comment describes a mechanism that requires a person to remember a flag. Nobody has ever
passed it, so every APK ever produced is `versionCode = 1`. `versionName` is a tracked constant.

**Where it surfaces.** `app/.../SettingsViewModel.kt:44-45`:

```kotlin
val versionName: String = BuildConfig.VERSION_NAME,
val versionCode: Int = BuildConfig.VERSION_CODE,
```

rendered through `app/src/main/res/values/strings.xml:87`:

```xml
<string name="settings_version">Fabric VR %1$s (%2$d)</string>
```

`adb shell dumpsys package ai.passioncode.fabricvr | grep version` gives the same `1`, so the
platform cannot answer either.

**Which headset.** `scripts/install-on-quest.sh:10-15`:

```bash
# A hard-coded address belongs to one router. When DEVICE is unset, take whichever headset adb can
# already see — a USB cable and a different network both work then, without editing this file.
if [ -z "${DEVICE:-}" ]; then
  DEVICE=$("$ADB" devices | awk '$2=="device"{print $1; exit}')
fi
DEVICE=${DEVICE:-192.168.0.253:5555}
```

`exit` after the first match: the first device in the list wins. With two headsets reachable the
script installs on an arbitrary one, prints `connected.`, starts the activity, and exits 0. Nothing
in its output names which headset got the build. `scripts/push-model-for-tests.sh:12` has the
identical pick.

The script does print a resumed-activity dump and 40 lines of logcat (`:30-33`) — so it says the
app started, on a device it declines to name, at a version that is always 1.

## The decision, and what was weighed

**Chosen: stamp the identity from git at configuration time, carry it in `BuildConfig`, show it in
Settings, and make the installer name the device and assert the version it just wrote.**

Four fields, and each earns its place by answering a question somebody actually asks:

| Field | Source | The question it answers |
|---|---|---|
| `versionCode` | `git rev-list --count HEAD` | *is this build newer than that one?* — monotonic, needs no flag, reproducible from a commit |
| `versionName` | `0.1.0+<short sha>` | *which commit is this?* — the one thing that makes a bug report actionable |
| `GIT_BRANCH` | `git rev-parse --abbrev-ref HEAD` | *is this off `main` or off the working branch?* — non-trivial here, where `main` has no code at all (H-36) |
| `BUILD_TIME` | `git show -s --format=%cI HEAD` | *how old is this?* — **the commit's timestamp, not `now()`** |

**Alternatives considered:**

- ***Keep `-PversionCode` and just remember to pass it.*** Rejected: it is the current design and
  it has produced `1` on every build for the life of the project. A mechanism that depends on a
  person remembering a flag has already been measured, and the measurement is in Settings.
- ***`BUILD_TIME` from `System.currentTimeMillis()` at configuration time.*** Rejected for two
  reasons. It makes every build non-reproducible and invalidates Gradle's up-to-date checks and the
  configuration cache on every invocation. And it answers the wrong question: what a reader wants
  is how old the *code* is, not when someone happened to compile it. The commit timestamp is stable,
  reproducible, and is what "this build is a week old" actually means.
- ***A `BuildConfig` string assembled in Kotlin at runtime from a generated asset.*** Rejected:
  more moving parts for the same result, and the value would not reach `dumpsys`, which is where
  the operator looks first.
- ***Only fix the app, and leave the installer's device pick.*** Rejected: they are one problem.
  A version the app can state and an installer that will not say which device it wrote to leaves
  "which build is the tester on" exactly as unanswerable as it is today. H-30 and H-31 are the same
  question from two ends.

**The Gradle detail that decides the implementation.** Running `git` at configuration time with a
bare `"git rev-list …".execute()` breaks the configuration cache, which Gradle 8.13 has on by
default in many setups and which this project should not be giving up. Use
`providers.exec { … }.standardOutput.asText` — a `ValueSource`-backed provider, which the
configuration cache understands and re-evaluates correctly.

**The fallback is not optional.** A source tarball, a shallow clone with no history, or a build
machine without `git` must still produce an APK. Fall back to `versionCode = 1`,
`versionName = "0.1.0+unknown"`, `GIT_SHA = "unknown"` — and make the Settings string say
`unknown`, out loud, rather than rendering a blank. A version line that silently omits the sha is
the same failure class as the current one.

## Decomposition

**Step 1 — write the failing tests first.**

`app/src/test/kotlin/ai/passioncode/fabricvr/ui/SettingsVersionTest.kt` (new):

1. `the version line names a commit` — build the Settings version state from a `BuildConfig`-shaped
   fixture and assert the rendered string contains the sha, not just `0.1.0 (1)`.
2. `an unknown provenance says so` — with `GIT_SHA = "unknown"`, the rendered string contains the
   word `unknown` and no empty parentheses.

Run them. **Watch both fail** against today's string and state.

**Step 2 — `app/build.gradle.kts`.** Replace `:18-21`. Shape:

```kotlin
fun git(vararg args: String): String = runCatching {
    providers.exec { commandLine("git", *args) }
        .standardOutput.asText.get().trim()
}.getOrDefault("")

val gitSha    = git("rev-parse", "--short", "HEAD").ifEmpty { "unknown" }
val gitBranch = git("rev-parse", "--abbrev-ref", "HEAD").ifEmpty { "unknown" }
val gitCount  = git("rev-list", "--count", "HEAD").toIntOrNull() ?: 1
val gitTime   = git("show", "-s", "--format=%cI", "HEAD").ifEmpty { "unknown" }

defaultConfig {
    versionCode = gitCount
    versionName = "0.1.0+$gitSha"
    buildConfigField("String", "GIT_SHA", "\"$gitSha\"")
    buildConfigField("String", "GIT_BRANCH", "\"$gitBranch\"")
    buildConfigField("String", "BUILD_TIME", "\"$gitTime\"")
}
```

`buildFeatures { buildConfig = true }` must be on — check whether it already is before adding it.

**Step 3 — `SettingsViewModel.kt:44-45`.** Add the three fields beside the two that exist. They are
compile-time constants; no dispatcher question arises.

**Step 4 — the string.** `app/src/main/res/values/strings.xml:87` becomes a line that a person can
read out over a call without ambiguity:

```xml
<string name="settings_version">Fabric VR %1$s (%2$d) · %3$s · %4$s</string>
```

— name, code, branch, build date. **This is user-facing text**: it goes through T-034's route if a
brand pack exists by then, and through a recorded refusal otherwise. The format is positional, so
`values-ru` can reorder it.

**Step 5 — `scripts/install-on-quest.sh`.** Three changes, all of them about refusing to guess:

```bash
# Refuse to guess when more than one device is listed.
if [ -z "${DEVICE:-}" ]; then
  count=$("$ADB" devices | awk '$2=="device"' | wc -l | tr -d ' ')
  if [ "$count" -gt 1 ]; then
    echo "more than one device is connected — set DEVICE= explicitly:"; "$ADB" devices; exit 1
  fi
  DEVICE=$("$ADB" devices | awk '$2=="device"{print $1; exit}')
fi
```

Then, before and after the install, print what is actually there:

```bash
"$ADB" -s "$DEVICE" shell getprop ro.serialno
"$ADB" -s "$DEVICE" shell getprop ro.product.model
"$ADB" -s "$DEVICE" shell dumpsys package ai.passioncode.fabricvr | grep -E 'versionCode|versionName'
```

and **assert** that the installed `versionCode` after the install equals the one in the APK
(`aapt2 dump badging` or the value this build stamped), exiting non-zero if it does not. That
assertion is what closes H-11 and is what the retro's *verify against the build that is installed*
instruction exists for — today it cannot be followed because there is nothing to compare.

Apply the same device-pick guard to `scripts/push-model-for-tests.sh:12`.

**Step 6 — the hard-coded fallback.** `DEVICE=${DEVICE:-192.168.0.253:5555}` stays, because it is
the operator's own headset on their own router and removing it costs a keystroke every time. But it
prints a line saying it is falling back to a hard-coded address, so the case where **no** device is
connected is distinguishable from the case where the right one is.

## Blast radius, and what NOT to touch

- **Touches:** `app/build.gradle.kts` (`defaultConfig`), `SettingsViewModel.kt` (three fields),
  one string, `scripts/install-on-quest.sh`, `scripts/push-model-for-tests.sh`, one new test file.
- **Do not touch:** the signing config in `app/build.gradle.kts:25-55`. It is T-039's and T-037's,
  and putting both changes in one commit makes the migration's diff unreadable at the moment it
  most needs reading.
- **Do not touch:** the `applicationId`. `versionCode` moving is an upgrade; `applicationId` moving
  is a different app, and it would make T-037's problem permanent.
- **Do not remove** `-PversionCode` support outright if anything already passes it — check
  `grep -rn 'versionCode' scripts/ .github 2>/dev/null` first. Where nothing does, the property
  override can stay as an escape hatch layered over the git value, or go; say which in the commit.
- **Watch for:** `versionCode` from `git rev-list --count` **decreases** if history is rewritten or
  if a build is made from a branch behind another. Android refuses a downgrade install. That is
  the correct behaviour and it is why the branch is in the version line — but it will bite the
  first time someone builds from `main` (which has 0 project commits, H-36) and tries to install
  over a `feat/v1-notes-core` build. Note it in the runbook.
