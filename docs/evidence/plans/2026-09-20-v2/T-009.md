## What is wrong, in the person's terms

They deny the microphone twice. Android stops asking. The app does the right thing and says:

> The microphone is blocked for this app. **[App settings]**

They press *App settings*. They land on **Fabric VR's own Settings screen** — a page of API keys,
a speech-model picker and a vault path. Nothing there can grant a permission. Nothing there
mentions the microphone.

There is no other route. The button is the only affordance the app offers, it leads nowhere, and
**dictation is now permanently impossible on that install.** For a product whose one headline
gesture is speaking into a headset, this is the app closing its own front door and handing the
person the wrong key.

`OPEN_SETTINGS` and `OPEN_APP_SETTINGS` are two distinct members of `UiAction` — the taxonomy
already knows they are different things (`error_no_api_key` uses the first,
`error_permission_blocked` the second, and `core-common`'s strings give them different button
labels: `action_settings` = "Settings", `action_app_settings` = "App settings"). Only the wiring
collapses them.

## The decision, and what was weighed

**Chosen: opening a system settings page is a *host capability*, supplied by whichever activity is
hosting the composition — the same shape `PermissionRequester` already uses, and for the same
reason.**

```kotlin
/**
 * Opening the OS page where a blocked permission can be granted again.
 *
 * Hoisted out of the composition for the same reason as [PermissionRequester], and then for a
 * second reason the panel does not have: the immersive host is an OpenXR session, and what
 * happens when a 2D system activity is launched over one is a property of Horizon OS, not of
 * this app. The two hosts therefore answer this differently, and the composition must not know
 * which one it is talking to.
 */
fun interface AppSettingsOpener {
    fun openAppDetails()
}
```

Threaded through `FabricApp` as a third parameter beside `permissionRequester`, and handed to the
three screens that hold an `OPEN_APP_SETTINGS` arm.

### Why not do it in the composable

`LocalContext.current` is right there, and `Intent(ACTION_APPLICATION_DETAILS_SETTINGS,
Uri.fromParts("package", packageName, null))` plus `FLAG_ACTIVITY_NEW_TASK` launches from any
`Context`. Three lines and no plumbing.

**Rejected**, on the ground the whole task turns on: *the two hosts must be allowed to differ.*
On the panel the intent is all there is to it. In the Space it may need to be preceded or followed
by leaving the Space, and it may not work at all — and that is a decision for the activity that
owns the OpenXR session, not for a screen that does not know it is in one. Putting it in the
composable would fix the panel and leave the Space in an unknown state, with no place to put the
answer once it is measured.

Secondary: `LocalContext.current` inside a Spatial compose panel is the context the SDK passed to
`composePanel`'s lambda (`composePanel$lambda$1(Function1, Context)`, per the disassembly in
`I.md`), not necessarily the activity. Launching an activity from a non-activity context is
legal with `NEW_TASK` but produces a *new task*, which is the wrong stacking on the panel.

### Why not add a method to `PermissionRequester`

`PermissionRequester` is a `fun interface` (`app/.../PermissionRequester.kt:11-14`), so both hosts
construct one with a lambda (`PanelActivity.kt:22-25`, `ImmersiveActivity.kt:68-75`). A second
method makes it a plain interface, both hosts grow an `object : …` block, and the two capabilities
become one thing that they are not: one is the runtime-permission request flow, which exists
because `rememberLauncherForActivityResult` needs an `ActivityResultRegistryOwner` the Spatial
panel does not have; the other is an intent. Different reasons, different lifetimes.

**Rejected** — but it is close, and the argument for merging (one parameter instead of two) is
real. If a third host capability appears, merge all three into a `HostCapabilities` interface
then, not now.

### Why not a `UiAction` change

One could delete `OPEN_APP_SETTINGS` and have `Permission(permanent = true)` map to
`GRANT_PERMISSION`, letting the requester handle it. **Rejected**: the system dialog no longer
appears after a hard denial, so `requestPermissions` returns immediately with the same denial and
the person presses a button that does nothing — visibly nothing, which is worse than the current
bug because it looks like a broken button rather than a wrong destination.

### The immersive host: what can be decided, and what must be measured

**Decidable now:** `ImmersiveActivity` is a plain `android.app.Activity` underneath
(`AppSystemActivity` → `VrActivity` → `Activity`; its own KDoc says so at `:34-36`), so
`startActivity` is available and `ActivityResultContracts` are not. That is why the microphone
request there already goes through `requestPermissions`/`onRequestPermissionsResult`
(`:68-88`). The settings intent needs no result callback at all, so nothing blocks it.

**Not decidable from source:** what Horizon OS does with a 2D activity launched from inside a
running OpenXR session. The three plausible behaviours, and they are genuinely different for the
person:

| What the shell does | What the person sees | What our implementation should be |
|---|---|---|
| renders the 2D activity in the shell and suspends the immersive app | the settings page, in their room, and Fabric VR paused behind it | just `startActivity` — nothing else needed |
| refuses the launch (as it refused the immersive launch without the hand-tracking declaration, `732c92b`) | nothing happens | we must return to the panel first and launch from there |
| launches it but leaves the Space in front of it | nothing visible happens; the page is behind them | return to the panel first |

Two of the three require returning to the panel, so the **default implementation until measured
is: leave the Space, then open the page.** `ImmersiveActivity.returnToPanel()` already exists
(`:146-163`) and is the documented hybrid path — a `PendingIntent` handed to Home, then
`finish()`.

**Ordering matters and is easy to get backwards.** `returnToPanel()` ends in `finish()`, so the
settings intent must be started *before* it, or it is started from an activity that is going away:

```kotlin
    private val appSettings = AppSettingsOpener {
        // Start the OS page first: returnToPanel() finishes this activity.
        startActivity(appDetailsIntent())
        returnToPanel()
    }
```

**Measure before believing any of this.** If the first behaviour turns out to be what happens,
drop `returnToPanel()` — being thrown out of the Space to change a setting is a worse experience
than a suspended session, and the code should be the smaller one. The observation is in *Tests*
and it is a headset row.

### After they grant it

A person who grants the permission and comes back finds the banner still reading "The microphone
is blocked for this app." Pressing *Record* does work — `RecordControl`'s button falls to
`else -> onStart()` in the `Failed` state (`TodayScreen.kt:313-320`) and `VoiceViewModel.start()`
re-checks `recorder.hasPermission()` (`:74-79`). But the screen is asserting something false
until they do.

**Chosen: a `recheckPermission()` on `VoiceViewModel`, called on `ON_RESUME`.** Six lines:

```kotlin
    /** The person may have granted the microphone in the OS settings while we were not on screen. */
    fun recheckPermission() {
        val stale = _state.value
        val blocked = stale is VoiceState.NeedsPermission ||
            (stale is VoiceState.Failed && stale.message.action == UiAction.OPEN_APP_SETTINGS)
        if (blocked && !needsPermission()) _state.value = VoiceState.Idle
    }
```

driven from the screen with a `LifecycleEventObserver` on `LocalLifecycleOwner.current`.

`ON_RESUME` is delivered on both hosts today: `PanelActivity` is a `ComponentActivity`, and
`ImmersiveActivity.onResume` calls `owners.onResume()` (`:53-56`), which sets
`Lifecycle.State.RESUMED` (`SpatialPanelOwners.kt:50`). **`ON_STOP` is the one that is never
delivered** (I-12) — this task deliberately depends on the event that works.

**Alternative rejected:** clearing the failure inside `openAppDetails()`. The person has not
granted anything yet; clearing the message would be the app asserting a fix it has not seen.

## Correction to the finding

**D-02 is correct and its proposed fix is correct.** One clarification worth having in the spec,

D-02 names `TodayScreen.kt:287` and `ChatScreen.kt:58`. There is a **third** site —

error taxonomy change reopens it.

And the `UiAction` enum is not the problem: `action_app_settings` = "App settings" already exists
in `core-common/src/main/res/values/strings.xml:32`, so the **button already says the right
thing** and takes the person somewhere else. A label that is accurate about an action that is not
is a particular kind of bad — it is why nobody has noticed.

## Decomposition

**Step 1 — write the failing test first.** There is no composition test in `:app` that is not
`PanelSmokeTest` (T-001 fixes that one), so the honest unit-level test is of the view model and
of the wiring's *shape*:

`app/src/test/kotlin/ai/passioncode/fabricvr/ui/VoiceViewModelTest.kt` — the file T-001 creates
(fold into it if T-001 has landed; create it here otherwise, to the same shape):

1. `granting the microphone outside the app clears the blocked message` — put the view model in
   `Failed` via `onPermissionResult(granted = false, permanent = true)`, flip the fake recorder's
   permission to granted, call `recheckPermission()`, assert `VoiceState.Idle`.
2. `rechecking does not clear a failure that is not about permission` — a `Failed` carrying
   `AppError.SttFailed`; assert the message survives. Without this, a re-check silently swallows
   transcription failures on every resume.
3. `rechecking while the permission is still denied changes nothing` — assert the `Failed` stands.

**Watch 1 fail** — `recheckPermission` does not exist, so it will not compile; write the method
as a no-op body first, watch the assertion fail, then implement.

**Step 2 — `app/src/main/kotlin/ai/passioncode/fabricvr/AppSettingsOpener.kt`**, the `fun
interface` above, plus a shared intent builder so the two hosts cannot write it differently:

```kotlin
internal fun Context.appDetailsIntent(): Intent =
    Intent(
        Settings.ACTION_APPLICATION_DETAILS_SETTINGS,
        Uri.fromParts("package", packageName, null),
    ).addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
```

`FLAG_ACTIVITY_NEW_TASK` is required when launching from a non-activity context and harmless from
an activity; include it once, here, rather than remembering it twice.

**Step 3 — `PanelActivity`.** Beside the existing `requester` (`:22-25`):

```kotlin
    private val appSettings = AppSettingsOpener { startActivity(appDetailsIntent()) }
```

and pass it into `FabricApp`.

**Step 4 — `ImmersiveActivity`.** Beside its `requester` (`:68-75`), the two-step version above,
with a comment naming the measurement it is waiting on and the `returnToPanel()` ordering.

**Step 5 — `FabricApp`** gains `appSettings: AppSettingsOpener` and threads it to `TodayScreen`,
`NoteEditorScreen` (which has no `OPEN_APP_SETTINGS` arm today but renders an `ErrorBanner` at
`:126-131` that routes everything to `retry()` — **do not fix that here**, it is B-11/E-15's, but
give the screen the parameter so the fix is one line when it happens) and `ChatScreen`.

Since both hosts must supply it, make it a **required** parameter, not one with a default. A
default would let a third host forget it and silently keep the current bug.

**Step 6 — the three `when` arms.** Split the collapsed pair:

```kotlin
                        UiAction.OPEN_SETTINGS -> onSettings()
                        UiAction.OPEN_APP_SETTINGS -> onOpenAppSettings()
```

`UiAction` is an enum, so if any `when` is exhaustive the compiler names it. Check whether these
three are exhaustive or have an `else` — `TodayScreen.kt:147` and ~~`ChatScreen.kt:59`~~ (VOID) both end in
`else ->`, so **the compiler will not help**. Grep instead:

```bash
grep -rn 'OPEN_APP_SETTINGS' --include='*.kt' app/src/main
```

must return exactly the three arms and nothing that shares a branch with `OPEN_SETTINGS`.

**Step 7 — the resume re-check.** In `TodayScreen` and `NoteEditorScreen` (the two screens that
host `VoiceViewModel`):

```kotlin
    val lifecycleOwner = LocalLifecycleOwner.current
    DisposableEffect(lifecycleOwner) {
        val observer = LifecycleEventObserver { _, event ->
            if (event == Lifecycle.Event.ON_RESUME) voiceViewModel.recheckPermission()
        }
        lifecycleOwner.lifecycle.addObserver(observer)
        onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
    }
```

**Step 8 — one string, and it is the one that makes the button honest.**
`core-common`'s `error_permission_blocked` is *"The %1$s is blocked for this app."* — true, and it
does not say what the button will do. Consider:

```xml
<string name="error_permission_blocked">The %1$s is blocked for this app. Turn it on in the system settings.</string>
```

Wording is a draft; the brand pack does not exist (B-035) and `copywriting` owns the final text.
**This is a `core-common` string, so it is shared with the assistant's paths** — check
`UiStringsTest` still passes and that no other error reuses it.

## Blast radius, and what NOT to touch

- **Touches:** `app/.../AppSettingsOpener.kt` (new), `app/.../PanelActivity.kt` (+2 lines),
  `app/.../ImmersiveActivity.kt` (+5 lines), `app/.../ui/FabricApp.kt` (+1 parameter, 4 call
  sites), `app/.../ui/TodayScreen.kt` (2 arms, 1 parameter, the resume observer),
  `app/.../ui/NoteEditorScreen.kt` (1 parameter,
  the resume observer), `app/.../ui/VoiceViewModel.kt` (+1 method),
  `core-common/.../strings.xml` (1 string), 1 test file.
- **Do not touch:**
  - `UiStateMapper`. Its two branches are already right; this task is about the other end of the
    wire.
  - `SpatialPanelOwners` and `ImmersiveActivity`'s lifecycle callbacks — **T-012**. This task adds
    a field and a lambda to `ImmersiveActivity`; it must not touch `onCreate`/`onResume`/
    `onPause`/`onDestroy` or the `CompositionLocalProvider` block. If T-012 lands first, the
    `ON_RESUME` in step 7 comes from the SDK's owner instead of ours and nothing here changes.
  - `returnToPanel()`'s body. It is the documented hybrid path and I-13 records that the *back
    dispatcher* never reaches it — a different defect, T-013's. This task calls it directly, which
    works regardless.
  - `PermissionRequester` — its shape, its KDoc, and both implementations.
  - `NoteEditorScreen`'s banner routing everything to `retry()` (B-11/E-15). Give it the
    parameter; do not rewire it.
  - `RecordControl`'s extraction into its own file (E-15) — T-030's. The arm changes in place.
- **Watch for:**
  - `FabricApp` gaining a required parameter breaks any caller. There are exactly two
    (`PanelActivity.kt:30`, `ImmersiveActivity.kt:117`) and the compiler names them. **`PanelSmokeTest`
    launches `PanelActivity`, not `FabricApp`**, so it is unaffected — but confirm, because T-001
    is landing in the same window.
  - `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` needs `import android.provider.Settings`, which
    collides in the reader's head with this app's own Settings screen and with
    `SecureSettings`. Name the import site clearly; do not add a `Settings` alias.
  - The intent can throw `ActivityNotFoundException` on a device with no settings activity. That
    is not plausible on Horizon OS, but `PanelActivity.kt:35` already wraps the immersive launch
    in `runCatching` for exactly that class of surprise — do the same and route the failure through
    `toMessage()`, so a refusal is a message rather than a crash. Three lines, and it costs
    nothing.
