# T-008 — A provider without credentials refuses out loud instead of falling back silently

- **Severity:** Blocker
- **Work package:** WP-1 (stop the data loss)
- **Closes:** D-03, D-10, H-26 — and, as the same three lines, A-15, A-16 and E-09
- **Depends on:** nothing
- **Needs a headset:** no for the code; **yes, once**, for the H-26 carry-over — see *Tests*.
- **Estimated blast radius:** `Graph.kt` (~40 lines deleted, ~30 added), 1 new `AppError` shape,
  2 strings, 1 mapper branch, ~6 lines in `TodayScreen`, 3 test files. No schema change.

## What is wrong, in the person's terms

Three ways for the app to send — or not send — a person's voice somewhere other than where they
said, and say nothing about any of them.

**One.** They open Settings, choose *Cloud service*, paste the address, and forget the key. They
dictate. A transcript appears. They believe it came from the cloud model they chose. It came from
the 190 MB model on the headset, and the note's receipt says `LOCAL` — which is *true and
useless*, because it is indistinguishable from a person who chose LOCAL on purpose. Somebody who
picked the cloud for quality gets the headset; somebody who picked LOCAL for privacy cannot tell
afterwards which happened. (D-03)

**Two.** They saved a cloud key once while exploring, and never an address. Months later they
press *Transcribe again → Cloud service* on an old dictation. The recording is posted to
**`https://api.groq.com/openai`** — a third party they never named, over the open internet. (D-10)

**Three.** They are the operator. They had a whisper-server on their own LAN, configured under the
old rule where a saved URL was preferred. They install the new build. Their speech quietly starts
running on the small on-device model instead. Nothing says so. The URL is still in the Keystore,
doing nothing, and **they cannot even see that it is still there** — the Settings field that
would show it renders only when the provider is already `SERVER`, which theirs is not. No wrong
choice was made at all. (H-26)

## Where it is

### D-03 — the `else -> null` that becomes a silent local run

`app/src/main/kotlin/ai/passioncode/fabricvr/Graph.kt:85-101`:

```kotlin

        val serverUrl = settings.get(SecureSettings.KEY_WHISPER_SERVER_URL)?.takeIf { it.isNotBlank() }
        val cloudUrl = settings.get(SecureSettings.KEY_CLOUD_STT_URL)?.takeIf { it.isNotBlank() }
        val cloudKey = settings.get(SecureSettings.KEY_CLOUD_STT_KEY)?.takeIf { it.isNotBlank() }

            sttProvider() == SttProvider.CLOUD && cloudUrl != null && cloudKey != null ->
```

With `remote == null`, `SttRouter` takes the bottom branch and the visible-degradation machinery

The last line returns the local engine's own transcript, `source = SttSource.LOCAL`,
`fallbackReason = null` (`core-notes/.../Note.kt:4,19`). The class KDoc says "The degradation is

## The decision, and what was weighed

**Chosen: one function decides where speech goes, it never invents an address, and "chosen but not
configured" is an engine that refuses with its own words — not a `null` that disappears.**

### One rule, one function (E-09)

Replace `sttEngine()`'s inline `when`, `cloudClient()` and `serverClient()` with a single private
`remoteEngine(provider: SttProvider): SttEngine?` used by both entry points:

```kotlin
    /**
     * The engine for a chosen provider, or a refusal with a reason. **Never null for a provider
     * the person chose**, and never an address they did not type.
     *
     * There used to be two answers to "is the cloud configured" in this file: `sttEngine()`
     * required a URL and a key and returned null otherwise, so the router ran the on-device model
     * and recorded `LOCAL` — indistinguishable from a person who chose the device on purpose.
     * `cloudClient()` required only a key and filled the address in with Groq, so re-running an old
     * recording "with the better model" posted it to a third party nobody named.
     */
    private fun remoteEngine(provider: SttProvider): SttEngine? = when (provider) {
        SttProvider.LOCAL -> null                      // the only null: nothing remote was asked for
        SttProvider.CLOUD -> {
            val url = settings.get(SecureSettings.KEY_CLOUD_STT_URL)?.takeIf { it.isNotBlank() }
            val key = settings.get(SecureSettings.KEY_CLOUD_STT_KEY)?.takeIf { it.isNotBlank() }
            when {
                url == null -> FailingEngine(AppError.SttNotConfigured(provider.key, Missing.ADDRESS))
                key == null -> FailingEngine(AppError.SttNotConfigured(provider.key, Missing.KEY))
                else -> runCatching { CloudTranscriptionClient(url, { settings.get(KEY_CLOUD_STT_KEY) }, model) }
                    .getOrElse { FailingEngine(AppError.InsecureUrl(url)) }
            }
        }
        SttProvider.SERVER -> {
            val url = settings.get(SecureSettings.KEY_WHISPER_SERVER_URL)?.takeIf { it.isNotBlank() }
            if (url == null) FailingEngine(AppError.SttNotConfigured(provider.key, Missing.ADDRESS))
            else runCatching { RemoteWhisperClient(url) }.getOrElse { FailingEngine(AppError.InsecureUrl(url)) }
        }
    }
```

`LOCAL` is the **only** case that returns null, and it means "nothing remote was asked for", which
is the one honest null in the function.

Note the `runCatching` on construction: `CloudTranscriptionClient`'s constructor throws
`SttException(AppError.InsecureUrl)` when `NetworkPolicy` refuses the endpoint
(`CloudTranscriptionClient.kt:45-47`). Today `cloudClient()` swallows that into `null`
(`Graph.kt:109-116`) and the person is told nothing; here it becomes a refusal that says the URL
is the problem. **T-010 fixes what `NetworkPolicy` considers reachable; this task fixes what
happens when it refuses.** The two are independent and both are needed.

### Why a `FailingEngine` and not a `null`

Because `SttRouter` already has exactly the right behaviour for a remote that fails: run the local
engine and stamp the transcript `LOCAL_FALLBACK` with the reason (`SttRouter.kt:29-30`). A
refusing engine turns "unconfigured" into "failed", which is the case the router was built for,
and the whole of the degradation path comes for free.

**Alternatives considered:**

- *Have `sttEngine()` return `Result<SttEngine>` and refuse the dictation outright.* Rejected: it
  turns a recoverable situation into a dead end. Someone with a local model who forgot their cloud
  key should still get their words — just be told where from. The only case that should fail hard
  is "no remote configured **and** no local model", which the router already handles at `:32-34`.
- *Keep returning `null` but have `VoiceViewModel` compare the chosen provider against the
  transcript's `source`.* Rejected: it puts the rule in a view model, where `NotesViewModel`'s
  re-run path would have to reimplement it, and `Graph` is the seam that owns the decision.
- *Keep the Groq default and merely disclose it.* Rejected. The provider chip exists precisely so
  the person decides where their voice goes; a default address defeats it, and "we told you in a
  hint" is not a decision. `SUGGESTED_BASE_URL` stays in the file as the **placeholder text** in
  the Settings field (`SettingsScreen.kt:203` already uses it that way) — a suggestion a person
  can accept, which is what the constant's name says. It stops being a fallback.

### The error shape

**Chosen: one new shape, `AppError.SttNotConfigured(provider: String, missing: Missing)` with
`enum class Missing { ADDRESS, KEY }`.**

**Alternatives considered:**

- *Reuse `AppError.NoApiKey`.* Rejected — that is A-16, the defect. Its one sentence names
  OpenRouter and the assistant.
- *Two shapes, `NoSttKey` and `NoSttEndpoint` (A-16's and D-10's separate suggestions).* Rejected
  narrowly: two shapes mean two mapper branches, two strings and two test cases for one concept,
  and `AppError` already has eleven constructors. One shape with a discriminant, and the mapper
  picks the string.
- *Add a `what: String` to `NoApiKey`.* Rejected: `NoApiKey` is a `data object` (`AppError.kt:31`)
  and every existing use is the assistant's. Changing it to a class touches the assistant's paths
  for no reason.

`AppError` is a sealed class, so the compiler will name every `when` that must grow — there is
exactly one that matters, `UiStateMapper.map`, and it is exhaustive by construction. That is the
check.

Two strings in `core-common/src/main/res/values/strings.xml` (the module that owns error text):

```xml
<string name="error_stt_no_address">No address saved for %1$s. Transcribed on this headset.</string>
<string name="error_stt_no_key">No key saved for %1$s. Transcribed on this headset.</string>
```

Both carry `UiAction.OPEN_SETTINGS`. The wording is a draft — the brand pack does not exist
(B-035) and `copywriting` owns the final text; say so in the commit rather than presenting it as
settled.

### D-03's second half: the person has to be *told*

A router that records a reason nobody renders has not closed "the app says nothing". D-03's own
*Verify by* asks for "a UI assertion that the note row says so".

**Chosen: the minimum honest surface — extend the confirmation line that already exists.**
`TodayScreen.kt:169-175` already shows `state_saved_and_copied` for `CONFIRMATION_MS` (2 500 ms,
`:460`) after a dictation. When the committed transcript's `source` is `LOCAL_FALLBACK`, that line
also names where it came from, using **`R.string.stt_source_local_fallback`** — a string that
already exists at `app/src/main/res/values/strings.xml:107` ("this headset (fallback)") and is
currently dead (E-13 lists it among 25 unused keys, and notes that its deadness is precisely why
"`SttRouter`'s carefully visible degradation is invisible").

**Alternatives considered:**

- *Render it in `RecordControl`.* Rejected: E-15 extracts `RecordControl` into its own file and
  T-030 rebuilds the Today surface. Writing into it now means writing it twice.
- *Render it on the note row, permanently.* Rejected for this task: `fallbackReason` does not
  survive a reload — `Note.toEntity()` has no column for it (A-10), so the row would show it until
  the next query and then stop. Persisting it is a schema change and belongs with T-027.
- *Leave all rendering to T-030.* Rejected: it would ship a Blocker's fix with the Blocker's
  symptom intact, and the six lines are reusable — T-030 inherits the rule, not the code.

**Do not attempt A-10's full treatment** (the reason persisted, named in the editor's meta line,
a notice that survives a restart). That is a High finding with a schema question attached and it
is not this task's.

### H-26 — the carry-over, specified

A one-shot settings migration in `Graph.init`, guarded by its own marker so it runs once:

```kotlin
    /**
     * DEC-0014 replaced "a whisper-server is preferred when its URL is set" with an explicit
     * provider. A person who configured a server under the old rule has no KEY_STT_PROVIDER, so
     * byKey(null) answers LOCAL and their server goes quiet — and SettingsScreen renders the URL
     * field only for SERVER, so they cannot see that the value is still there either.
     *
     * Runs once, keyed by a schema marker rather than by "is the provider absent", so a person who
     * deliberately moves back to LOCAL is not dragged onto SERVER again on the next launch.
     */
    private fun carryOverSettings() {
        if (settings.get(KEY_SETTINGS_SCHEMA) != null) return
        val server = settings.get(SecureSettings.KEY_WHISPER_SERVER_URL)?.takeIf { it.isNotBlank() }
        val provider = settings.get(SecureSettings.KEY_STT_PROVIDER)
        if (provider == null && server != null) {
            settings.put(SecureSettings.KEY_STT_PROVIDER, SttProvider.SERVER.key)
            carriedOver = true          // read once by Settings to show the notice
        }
        settings.put(KEY_SETTINGS_SCHEMA, "2")
    }
```

Three things about it that are easy to get wrong:

1. **The marker, not the absence, is the guard.** Keying on "provider is absent" would re-apply
   the migration every launch for someone who chose LOCAL deliberately while a server URL was
   still saved.
2. **It must not run on the main thread.** `settings` is the Keystore, and this project has
   measured the first use at tens of milliseconds (`SettingsViewModel.kt:97`); I-21 adds that key
   *generation* on first run can block far longer inside the `@Synchronized secretKey()`. Run it
   on `Graph.scope`, like the vault mirror at `Graph.kt:165`. **`Graph.init` is called from
   `FabricVrApp.onCreate`** (`FabricVrApp.kt:6-9`) — the app's cold-start path.
3. **A migration that changes where a person's voice goes must say so.** The notice is one line;
   it belongs in Settings, next to the provider chips, and it is shown once. `carriedOver` is a
   value `SettingsViewModel` reads on `reload()`.

**Alternative considered and rejected:** *make `byKey(null)` return `SERVER` when a URL exists.*
That would be a rule about the default hidden inside an enum's companion, invisible from
`Graph`, and it would re-apply forever. A migration is a one-time act and should look like one.

**The second half of H-26 — the invisible field — is one condition.** `SettingsScreen.kt:238`
becomes `if (state.provider == SttProvider.SERVER || state.serverUrl.isNotBlank())`. A saved value
is always visible, whatever provider is selected. Six characters, and it is the difference between
a person being able to diagnose their own setup and not.

## Correction to the finding

**D-03's *Verify by* asks for something the code cannot currently produce, and the spec has to say
so.** It reads: *"`SttRouterTest` case: CLOUD + blank key → the transcript carries `LOCAL_FALLBACK`
and a non-null `fallbackReason`"*. `SttRouter` has no knowledge of providers or keys — it takes
two engines (`SttRouter.kt:12-15`). The case belongs in a **new** `GraphSttEngineTest` over
`remoteEngine`, plus an existing-shape `SttRouterTest` case that feeds it a `FailingEngine`. Two
tests, two modules, and neither is the one D-03 names. A-15 gets this right where D-03 does not.

**H-26's "ten lines in `Graph.init`" is an underestimate in one respect that matters:** it does
not account for the notice. Ten lines gets the routing right and leaves the person uninformed
about a change to where their voice goes, which is the same class of silence the finding is
about. Budget the notice.

## Decomposition

**Step 1 — write the failing tests first.**

`app/src/test/kotlin/ai/passioncode/fabricvr/GraphSttEngineTest.kt` — **and read this before
starting it.** `Graph` is an `object` with a `lateinit var appContext`, so it is not constructible
twice and even Robolectric cannot reset it between cases (`E.md:249`). `remoteEngine` must
therefore be extracted as a **pure function of a `SecureSettings`**, not a method on `Graph`:

```kotlin
internal fun remoteEngineFor(
    provider: SttProvider,
    settings: SecureSettings,
    clientFactory: (String, () -> String?, String) -> SttEngine = ::CloudTranscriptionClient…,
): SttEngine?
```

`Graph.remoteEngine(provider)` becomes a one-line call into it. That is the only way these five
cases can be tested at all, and it is E-04/T-017's pattern arriving early for one function. Say
so in the commit; do not extend it to the rest of `Graph` here.

Cases:
1. `cloud with a key and no address refuses, and names the address` — asserts
   `SttNotConfigured(…, ADDRESS)`, **and** that no `CloudTranscriptionClient` was constructed.
   This is D-10 and it is the one that matters most: assert the *absence* of the client, not just
   the error, or a future default slips back in.
2. `cloud with an address and no key refuses, and names the key`.
3. `server with no address refuses`.
4. `local asks for nothing remote` — returns null.
5. `a chosen provider never yields null` — a property over all three providers × the four
   configuration states; only LOCAL may be null.

`feature-stt/src/test/.../SttRouterTest.kt` (six cases today, `MockWebServer` + a `FakeEngine` at
`:22-31`):

6. `a refusing remote degrades visibly` — `SttRouter(local = localOk(), remote =
   FailingEngine(SttNotConfigured))`; assert `source == LOCAL_FALLBACK` and `fallbackReason` is
   the `SttNotConfigured`, not null.

`core-common/src/test/.../UiStateMapperTest.kt`:

7. `a missing speech address and a missing assistant key say different things` — A-16. Assert the
   two ids differ. The module's split is deliberate (`UiStateMapper.kt:7-9`): this asserts *which
   id*, and the instrumented `UiStringsTest` asserts that the id resolves to words — **add the new

`app/src/test/.../SettingsViewModelTest.kt` or a small `SettingsCarryOverTest`:
