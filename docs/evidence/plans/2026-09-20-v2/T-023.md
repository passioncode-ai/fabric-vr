# T-023 — The notes can leave the device

- **Severity:** Blocker
- **Work package:** WP-4 (data: search, storage, export)
- **Closes:** G-01, H-23
- **Depends on:** nothing in code. **T-037 depends on this**, and that dependency is the reason this
  task is scheduled where it is.
- **Needs a headset:** **yes.** The decision below rests on one fact about Horizon OS that no
  document settles — see *The probe, before any code*.
- **Estimated blast radius:** 1 new file in `:feature-vault`, 1 Settings row, 3 strings, 1 test
  file. No schema change, no manifest permission, no new dependency.

## What is wrong, in the person's terms

The product definition (`docs/product/product-definition.md:60-63`) says the storage is «vault —
папка пользователя … совместимая с Obsidian». `docs/ux/foundation.md:155` carries it as ST-008,
priority **must**: "every note mirrored as a Markdown file, so that I can take my notes with me."

On this build the person cannot take them anywhere. The vault is
`File(appContext.filesDir, "vault")` (`app/.../Graph.kt:47`) — app-private internal storage. There
is no picker, no share, no external directory, no export:

```console
$ grep -rn "ACTION_OPEN_DOCUMENT_TREE\|DocumentFile\|MANAGE_EXTERNAL\|getExternalFilesDir\|FileProvider\|ACTION_SEND\|MediaStore\|ACTION_CREATE_DOCUMENT" app core-* feature-*
(nothing)
```

and `android:allowBackup="false"` (`app/src/main/AndroidManifest.xml:29`), so `adb backup` does not
reach it either. The only string that mentions the vault at all is `settings_vault_hint`
(`app/src/main/res/values/strings.xml:86`) — "Every note is mirrored there as Markdown. Tap the path
to copy it." It hands the person an absolute path to a directory they cannot open, from a headset
with no file manager.

**The whole "notes you own" claim is false on this build.** Not weakly supported — false.

## Why this gates the signed release

`app/build.gradle.kts:27-41`: release signing comes from an untracked `keystore.properties`. Both
headsets today carry a **debug**-signed APK. A release APK is signed with a different key, so
`adb install -r` fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE` and the only way through is
`adb uninstall`, which removes `filesDir` **entirely**: the notes database, the whole vault with
every `.wav`, the 190 MB model, and the Keystore-encrypted OpenRouter and cloud keys (the
`fabricvr_settings_v1` alias is scoped to the app's uid and dies with it).

`README.md` already hands the reader `adb uninstall` as a routine command. The day someone runs
`:app:assembleRelease` and installs it, everything the operator and the second person have written
is gone, silently.

So: **T-037 must not be attempted until this task has shipped and an export has actually been taken
off a headset.** That is a sequencing fact, not a preference, and it is the single most expensive
ordering mistake available in the whole plan.

## The probe, before any code

One fact decides between the candidate routes and it is not in any document: **does Horizon OS carry
a system document picker?** Web search establishes that Quest ships no file manager at all (the
Gallery app shows captures only; Meta's own guidance points people at Meta Quest Developer Hub on a
desktop, i.e. at `adb`). It does **not** establish whether `com.android.documentsui` is present. An
app that fires `ACTION_CREATE_DOCUMENT` with no handler throws `ActivityNotFoundException` and takes
the panel down.

**What the vendor's own documentation settles, measured 2026-09-20 with `metavr docs`
(Meta VR CLI 1.3.2.2.2, the official Horizon OS CLI, installed at `/opt/homebrew/bin/metavr`):**

```console
$ metavr docs search "file manager browse files on device user storage Downloads"
# 1. Explore File Manager (unreal)   2. (spatial-sdk)   3. (native)
#   "To open the File Manager, select File Manager from the left navigation pane in MQDH.
#    When a Meta Quest device is plugged in, the File Manager will show files related to
#    that specific device."

$ metavr docs search "share intent ACTION_SEND file storage access framework document picker"
# 2. Sharing (android-apps):
#   "if the app registers itself to receive SEND_INTENT the same way it would on Android …
#    the app then becomes available in the current Meta Horizon OS share sheet …
#    allowing users to send photos, videos, links and more to your app."
```

Two facts, and neither is a guess:

1. **The only file manager Meta documents is MQDH — a desktop application that talks to the headset
   over `adb`.** There is no on-headset file browser in any of the three SDK documentation sets.
   Whatever folder the export lands in, the person reaches it from the Mac.
2. **The share sheet exists and is about *receiving*.** Meta's page is written from the perspective
   of an app that wants to be a share target, and the content it names is "photos, videos, links".
   Nothing is documented as a receiver for an arbitrary archive.

Neither fact settles the **document picker**, and it is the one that decides whether alternative B
is even available. `metavr adb devices` returned an empty list on this machine on 2026-09-20 — **no
headset was attached, so the probe below is outstanding, not skipped.**

Run these three on a headset before writing a line (`metavr shell` is the same thing as
`adb shell` here — use whichever the machine has):

```bash
# 1. Is there a document picker at all?
adb shell cmd package resolve-activity -a android.intent.action.CREATE_DOCUMENT \
  -c android.intent.category.OPENABLE -t application/zip
adb shell pm list packages | grep -i -e documentsui -e 'provider.*document'

# 2. Can anything receive a shared file?
adb shell cmd package query-activities -a android.intent.action.SEND -t application/zip

# 3. Does shared storage behave normally?
adb shell ls -la /sdcard/Download /sdcard/Received
```

Record all three outputs in `docs/evidence/verification.md`. They are the evidence for the decision
below; if (1) comes back with a real activity, the rejected alternative B becomes available as an
*addition*, and this spec says where it would slot in.

## The decision, and what was weighed

**Chosen: a single zip of the vault, written to `MediaStore.Downloads` (`/sdcard/Download/`) from a
row in Settings. No picker, no permission, no share sheet, no new dependency.**

The reasoning is one property: **`/sdcard/Download` is shared storage, so it is the only candidate
that is not deleted by `adb uninstall`** — which is precisely the event this task exists to survive.
Everything else is secondary, and everything else about Horizon OS is uncertain in a way this is
not.

```kotlin
val values = ContentValues().apply {
    put(MediaStore.Downloads.DISPLAY_NAME, "fabric-vr-vault-$stamp.zip")
    put(MediaStore.Downloads.MIME_TYPE, "application/zip")
    put(MediaStore.Downloads.IS_PENDING, 1)
}
val uri = resolver.insert(MediaStore.Downloads.EXTERNAL_CONTENT_URI, values) ?: error(…)
resolver.openOutputStream(uri).use { … ZipOutputStream … }
values.clear(); values.put(MediaStore.Downloads.IS_PENDING, 0)
resolver.update(uri, values, null, null)
```

On `minSdk = 34` (`app/build.gradle.kts:15`) this needs **no permission at all** — an app may always
insert into its own `MediaStore.Downloads` entries under scoped storage. `IS_PENDING` matters: it
keeps a half-written multi-hundred-megabyte zip invisible until it is complete, so a person who
pulls the file mid-write cannot get a truncated archive and believe they have a backup.

**Alternatives considered, each with what it costs on Horizon OS specifically:**

- **`ACTION_CREATE_DOCUMENT` + the person picks a location.** The textbook Android answer, and
  rejected as the *primary* route on one fact and one risk. The fact: **there is nowhere better to
  pick** — measured above, the only file manager Meta documents is MQDH on the desktop, so whatever
  folder they choose they reach the same way they reach `/sdcard/Download`: over `adb`/MQDH from the
  Mac, or with a third-party file manager they would have to install first. The risk: if the probe shows no `documentsui`, the intent throws and
  the export button crashes the app. Paying a crash risk for a choice with no better options is a
  bad trade. **If probe (1) finds a picker**, add it later as a second, secondary row (*Export
  to…*), wrapped in `resolveActivity != null`, and keep the Downloads row as the one that always
  works.
- **`FileProvider` + `ACTION_SEND`.** Rejected on the measurement above. Horizon OS does have a
  share sheet, and Meta's own page describes it entirely from the *receiving* side — an app
  registers for `SEND_INTENT` and becomes available as a target for "photos, videos, links". The
  question is not whether a sheet exists, it is **what on a headset can receive a 300 MB zip**. Nothing in the
  shipped set can: the Gallery takes images and video, the browser does not accept uploads from a
  share, and there is no mail or messaging client. A share sheet with zero useful targets is a
  button that opens an empty list, which is worse than no button. It also cannot survive an
  uninstall, because it moves nothing until the person acts.
- **Move the vault itself to `getExternalFilesDir(null)/vault`.** Tempting, and rejected twice over.
  First: it is *still* app-specific storage — Android deletes `Android/data/<pkg>/` on uninstall, so
  it does not solve the problem this task exists for. Second: on Android 11+ `Android/data` is
  hidden from MTP and from SAF, so the "reachable from the Mac" benefit is largely gone too. It
  would be a migration of every note's path for no durability gain.
- **Move the vault to shared storage proper (`/sdcard/Documents/FabricVR`) and write it live.**
  The version of this that actually delivers ST-008 — Obsidian on a desktop pointed at a synced
  folder — and rejected **for now**, not forever. It changes `Vault.root`, so every stored
  `audioPath` (absolute, `NoteEntity.audioPath`) needs migrating, `VaultMirror` needs to handle a
  root that can disappear, and `FileVault.remove`'s `walkTopDown` recovery scan starts walking a
  directory the person can edit under it. That is a week of careful work with a data migration in
  it. **The export is two days and unblocks the release.** Record the live-vault question as an open
  decision so the export is not mistaken for the answer to ST-008 — it is the answer to "an
  uninstall must not be fatal", which is a smaller and more urgent question.
- **SAF-picked vault root (`ACTION_OPEN_DOCUMENT_TREE` at first run, vault written through
  `DocumentFile`).** The route G-01 lists first, and the strongest long-term answer: a persisted
  tree URI survives uninstall, so the notes genuinely outlive the app. Rejected here for three
  reasons compounding: it depends on the same unproven `documentsui`; `DocumentFile` I/O is
  several times slower than `File` and `VaultMirror` writes on every note change; and putting a
  system picker in front of a person on their **first run** — before they have a single note —
  is the opposite of T-031's job. It belongs to the same future decision as the previous item.
- **Do nothing and write a README warning.** Rejected: H-23's own fix list has it as item (c), an
  addition, not a substitute. A warning in a file on the Mac does not stop the command that destroys
  the headset.

## Decomposition

**Step 1 — the probe.** Above. Do not skip it because the chosen route does not need a picker: its
output is what justifies the rejections, and T-037 will need it too.

**Step 2 — write the failing test first.** New file
`feature-vault/src/test/kotlin/ai/passioncode/fabricvr/vault/VaultExportTest.kt`. The zip building is
pure I/O over a `File` tree and an `OutputStream`, so keep `MediaStore` out of the unit under test:

```kotlin
interface VaultExporter {
    /** Writes the vault as a zip into [sink]. Returns what went in. */
    suspend fun writeTo(sink: OutputStream, includeAudio: Boolean): Result<ExportSummary>
}
data class ExportSummary(val noteFiles: Int, val audioFiles: Int, val bytes: Long)
```

Tests, each watched failing (the class does not exist yet, so they fail to compile first — write
the interface, then the tests, then the body):

1. `every markdown file in the vault is in the zip` — three notes across two `yyyy/MM` folders;
   assert the zip's entry names are the vault-relative paths.
2. `notes-only export omits the wav files` — `includeAudio = false` leaves a 5 MB wav out and the
   summary says `audioFiles = 0`.
3. `a file that disappears mid-export does not abort the zip` — delete one file after the walk and
   before the read; assert the other two are present and the summary counts two. A vault being
   mirrored into while it is exported is the normal case, not the edge case.
4. `the zip round-trips` — read it back with `ZipInputStream` and compare bytes for one file.

**Step 3 — `VaultExporter`** in `feature-vault/src/main/kotlin/ai/passioncode/fabricvr/vault/`.
Walk `vault.root`, stream each file into a `ZipOutputStream`, entry name relative to the root.
Failures go through the module's existing shape — `runCatchingCancellable` and
`Result.failure(VaultException(AppError.Storage("vault.export", it)))`, matching
`FileVault.write` (`Vault.kt:96-102`) — so the banner already knows how to render it.

**Step 4 — the Android half**, in `:app`, because `MediaStore` needs a `ContentResolver` and
`:feature-vault` is deliberately platform-light. Put it beside `AudioAdoption.kt`, or in
`SettingsViewModel` if it stays under ~40 lines. `IS_PENDING = 1` while writing; clear it on
success; `resolver.delete(uri)` on failure, so a failed export leaves no half file claiming to be
a backup.

**Step 5 — Settings.** A row under the existing *Vault* heading (`SettingsScreen.kt:256-275`),
below `settings_vault_hint`:

- a button *Export the vault* (`action_export_vault`);
- a choice of what goes in, because the difference is three orders of magnitude (see T-024's
  arithmetic — a year of dictation is ~7 GB of audio against a few MB of Markdown). Two
  `FilterChip`s: *Notes only* / *Notes and recordings*, defaulting to **Notes only**;
- while running: the existing `LinearProgressIndicator` pattern from the model download
  (`SettingsScreen.kt:179-186`) and a file count;
- on success, the **path it wrote**, selectable, and a sentence saying what to do with it.

Strings (`app/src/main/res/values/strings.xml`):

```xml
<string name="action_export_vault">Export the vault</string>
<string name="label_export_scope">What goes in</string>
<string name="label_export_notes_only">Notes only</string>
<string name="label_export_with_audio">Notes and recordings</string>
<string name="settings_export_done">Exported to %1$s. Copy it off the headset before reinstalling.</string>
<string name="settings_export_running">Exporting… %1$d files</string>
```

The last clause of `settings_export_done` is the whole point of the row and must not be softened in
the copy pass. Note for T-032 and the copywriting pass: these are EN drafts like the rest.

**Step 6 — the README.** Next to every `adb uninstall` in `README.md`, one line: what it destroys,
and that *Export the vault* is the step before it. H-23 item (c); it is one commit and it is part of
this task's Definition of Done, not a follow-up.

**Not in this task:** the **import** side. H-24 item (2) — rebuilding the database from the vault
using `MarkdownSerializer.parse` — is **T-027's**, because it is the recovery story for a failed
migration and it needs T-027's harness to be worth anything. Say so in the commit so the next reader
does not think export/import shipped as a pair.

## The on-device observation that proves it works

No test proves the thing this task exists for. **The observation is this, in order, on a headset
that has real notes:**

1. In the app: Settings → *Export the vault* → *Notes and recordings*. Wait for the path.
2. **From the Mac, with the headset connected and the app never touched again:**
   `adb pull /sdcard/Download/fabric-vr-vault-<stamp>.zip .`
3. `unzip -l fabric-vr-vault-<stamp>.zip | tail -1` — the file count matches what Settings said.
4. `adb uninstall ai.passioncode.fabricvr`
5. `adb shell ls /sdcard/Download/fabric-vr-vault-<stamp>.zip` — **it is still there.** This is the
   assertion the whole task is for: the export outlived the app.
6. Reinstall, and open one of the unzipped `.md` files on the Mac in Obsidian. The front-matter and
   the text are the note.

Steps 4–6 destroy the headset's data, so do them on the second headset, or after step 2 has been
verified. Record all six in `docs/evidence/verification.md` against ST-008 and H-23. **Until step 5
has been observed by a person, T-037 stays blocked** — a green unit suite is not evidence about an
uninstall.

## Blast radius, and what NOT to touch

- **Touches:** one new file in `:feature-vault`, one small Android helper in `:app`, the *Vault*
  block of `SettingsScreen.kt` (lines 255-275), `SettingsViewModel` state and one action, six
  strings, `README.md`.
- **Do not touch:** `Graph.vault`'s root (`Graph.kt:47`). Moving the vault is the rejected
  alternative and it is a migration of every stored `audioPath`. `FileVault.write` /
  `adoptAudio` / `remove` — the exporter reads the tree and writes nothing into it.
  `AndroidManifest.xml` — this route needs no permission, and adding `WRITE_EXTERNAL_STORAGE`
  "to be safe" is both useless on API 34 and a new thing to justify at store review.
  `allowBackup="false"` — flipping it is a different decision with its own privacy argument, and
  it would not have saved the data anyway.
- **Watch for:** the vault is being written into by `VaultMirror` on `Graph.scope` while the export
  walks it — hence test 3. The export of a year's audio is gigabytes: it must stream, never build a
  `ByteArray`, and it must not run on the main thread (T-019's rule applies; use the module's `io`
  dispatcher the way `FileVault` does at `Vault.kt:48`).
