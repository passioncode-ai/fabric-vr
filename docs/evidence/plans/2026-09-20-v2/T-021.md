# T-021 — One download at a time, and it cannot be started twice

- **Severity:** High
- **Work package:** WP-3 (threading and ownership)
- **Closes:** I-05, G-06, G-07, I-22, A-21, A-22 — see *Correction to the finding*
- **Depends on:** T-017 (`VoiceViewModel` must already take its downloader as a parameter)
- **Needs a headset:** **yes for one reproduction** — fill the storage and press Download, to
  confirm which throwable `ENOSPC` actually arrives as
- **Estimated blast radius:** 4 production files, 1 new owner class, 3 test files, 2 strings

> `mb()` no longer prints *"0 MB free"* on a device with 900 kB.

## What is wrong, in the person's terms

They press *Download* on the Today banner because dictation says the model is missing. Then they
open Settings — which is where the model list is — and press *Download* there too, because the
screen says the model is not downloaded.

Both downloads write into the same file. Each hashes only its own bytes, so both fail the checksum,
both delete the file, and the person is told "The downloaded file was corrupt and was removed."
They try again. **380 megabytes of headset Wi-Fi, twice, and the model can never finish.**

And if the headset is simply full — which it will be, because five models total 1.4 GB and every
dictation keeps its WAV forever — the app says **"The download stopped. Check the network."** The
person checks the network, retries, spends another 190 MB, fails again, and never learns the
actual cause. There is a correct string for this sitting unused three lines away.

## Where it is

**Two owners, one file.**

```kotlin

    downloadJob = viewModelScope.launch {
        try {
            Graph.modelDownloader().download().collect { progress -> … }     // :157
        } catch (c: CancellationException) { _state.value = VoiceState.Idle; throw c }
    }
}

// app/.../ui/SettingsViewModel.kt:190-215
fun downloadModel() {
    downloadJob?.cancel()
    downloadJob = viewModelScope.launch {
        try {
            modelDownloader().download().collect { progress -> … }           // :195
        } catch (c: CancellationException) { … }
```

Each `downloadJob?.cancel()` cancels **its own** job and knows nothing about the other's. Both
resolve through `Graph.modelDownloader()` (`Graph.kt:59-60`) → `FileModelStore.modelFile()` →
`File(root, modelName)`, and `ModelDownloader.download()` (`:72-73`) writes
`File(target.parentFile, target.name + ".part")` — the same path for both.

Both view models are alive simultaneously: Today stays on the back stack while Settings is open
(`FabricApp.kt:41-78`, `nav.navigate(Routes.SETTINGS)`).

The interleaving:

```
Main(Today)     downloadModel() -> flowOn(IO) -> FileOutputStream(partial, append=false)   :118
Main(Settings)  downloadModel() -> flowOn(IO) -> FileOutputStream(partial, append=false)   :118
IO#1 / IO#2     both write 64 KB chunks into one file, each digesting only ITS OWN bytes
IO#1            finishes: digest != store.expectedSha256 -> partial.delete() -> CHECKSUM    :149-152
IO#2            finishes: writes into a deleted inode; renameTo fails or renames garbage    :159-163
```

The pinned SHA-256 (`WhisperModel.kt:21-25`, `FileModelStore.kt:47`) is what stops the garbage
reaching whisper, so this is a **wrong-result** race, not a corruption one. That is why it presents
as "the checksum keeps failing" rather than as a crash.

**The error mapping.** `ModelDownloader.kt:141-146`:

```kotlin
} catch (t: Throwable) {
    partial.delete()
    Log2.e("stt.model.download_failed", t)
    emit(DownloadProgress.Failed(AppError.ModelDownload(AppError.ModelDownload.Reason.NETWORK, t)))
```

**Every** throwable from the write loop — including `ENOSPC` — is `Reason.NETWORK`.
`UiStateMapper.kt:25-26` maps that to `error_model_network`, "The download stopped. Check the
network." `Reason.DISK` and its correct string `error_model_disk` ("There isn't room on this
headset for the speech model.") exist and are reachable from exactly one place: a failed
`renameTo` at `:159-163`, which is the *least* likely way to run out of space, since the rename is
within one directory.

**No free-space check anywhere.**
`grep -rn "StatFs\|usableSpace\|getAllocatableBytes\|getFreeSpace" app core-* feature-*` → nothing
in main source. The five models, from `WhisperModel.kt:21-25`:

|---|---|---|
| `tiny` | 32,152,673 | 35.4 MB |
| `base` | 59,707,625 | 65.7 MB |

**And the model can change underneath a running download** (I-22, A-21). `SettingsViewModel
.downloadModel()` resolves `modelDownloader()` once, at launch, pinning it to model A;
`saveWhisperModel(B)` → `put` → `reload()` recomputes `modelPresent` from `modelStore()`, which now
answers for **B**. The screen shows "not downloaded" with a *Download* button while A is still
transferring. Tapping it runs `downloadJob?.cancel()` (`:191`) → A's flow hits
`catch (CancellationException)` → `partial.delete()` (`ModelDownloader.kt:139`). A's resumable
partial is gone, silently, and the progress bar in between was A's bytes under B's name.

The resume path is well built (`:65-70`, `:99-113`, a `Range` header and a digest replay over the
existing bytes) and **A-22 observes it can essentially never engage**, because leaving the screen
cancels the job and the cancellation deletes the partial.

## The decision, and what was weighed

**Chosen: one owner for downloads, keyed by model, living in `Graph`; a free-space precondition
before the first byte; and an error classifier with a test per class.**

### 1. The single owner

```kotlin
/**
 * The process's downloads, one per model, started once.
 *
 * Two view models could each start a download of the same model into the same `.part` file, both
 * digesting only their own bytes: both failed the checksum, both deleted the file, and the model
 * could never finish. A second `start` for a model already downloading now JOINS it.
 *
 * Progress is a StateFlow per model rather than a Job per view model, so a download outlives the
 * screen that began it — which is also what makes the resume path in ModelDownloader reachable
 * at all (it was unreachable: leaving the screen cancelled the job, and cancellation deletes the
 * partial).
 */
class ModelDownloads(
    private val scope: CoroutineScope,
    private val downloaderFor: (WhisperModel) -> ModelDownloader,
    private val freeBytes: () -> Long,
) {
    private val lock = Mutex()
    private val running = mutableMapOf<WhisperModel, StateFlow<DownloadProgress>>()

    /** Idempotent. A second call while [model] is downloading returns the same flow. */
    suspend fun start(model: WhisperModel): StateFlow<DownloadProgress>
    fun progress(model: WhisperModel): StateFlow<DownloadProgress>?
    suspend fun cancel(model: WhisperModel)
}
```

`Graph` exposes `val downloads: ModelDownloads`. Both view models call `downloads.start(model)`
and collect the returned flow; neither holds a `Job`.

**The scope is the part to get right.** `Graph.scope` (`Graph.kt:39`) is
`SupervisorJob() + Dispatchers.Default`, is never cancelled, and today carries exactly one
coroutine — I-29 says that is acceptable *only* because of that. A 190 MB transfer is a
long-running, cancellable thing with an owner, which is precisely what I-29 says must not silently
join that scope. **Give `ModelDownloads` its own `CoroutineScope(SupervisorJob() + Dispatchers.IO)`,
created by `Graph` and documented as process-lifetime**, and say in `Graph.scope`'s KDoc that this
is a second scope and why.

### 2. The free-space precondition

Before the first byte, inside `ModelDownloader.download()` so no caller can forget it:

```kotlin
val partialHave = if (partial.exists()) partial.length() else 0L
val need = ((store.expectedBytes - partialHave) * SPACE_MARGIN).toLong()
val free = freeBytes()
if (free < need) {
    Log2.w("stt.model.no_space", "need" to need, "free" to free)
    emit(DownloadProgress.Failed(AppError.ModelDownload(Reason.DISK)))
    return@flow
}
```

`SPACE_MARGIN = 1.1` — ten per cent, because the filesystem needs metadata and because a headset
that is within ten per cent of full will fail the next thing it does anyway. The probe is a
parameter (`freeBytes: () -> Long`) with a production default of
`StorageManager.getAllocatableBytes(uuid)` where available, falling back to
`StatFs(root.path).availableBytes`. `getAllocatableBytes` counts space the system could reclaim
from other apps' caches, which is the number Android will actually give us; `StatFs` is the
pessimistic one. Parameterising it is also the only way the test in step 1 can exist.

`renameTo` needs no extra space — source and target share a directory — so the requirement is the
model's own size and nothing more.

### 3. The error classifier

```kotlin
internal fun classify(t: Throwable): AppError.ModelDownload.Reason = when {
    t.isNoSpace() -> Reason.DISK
    else -> Reason.NETWORK
}

private fun Throwable.isNoSpace(): Boolean = generateSequence(this, Throwable::cause).any {
    (it as? android.system.ErrnoException)?.errno == android.system.OsConstants.ENOSPC ||
        it.message?.contains("ENOSPC") == true
}
```

Walking the cause chain matters: `FileOutputStream.write` surfaces `ENOSPC` as an `IOException`
whose **cause** is an `ErrnoException`, not as the `ErrnoException` itself. Matching on the message
as well as the errno is belt and braces — the message form is what actually appears in most Android
versions' `IOException("write failed: ENOSPC (No space left on device)")`, and the errno form is
the one that survives a locale change. **Which of the two fires is exactly what the on-device
reproduction below is for**; keep both until it is known, then keep both anyway and say why in the
comment.

Everything that is not out-of-space stays `NETWORK`, which is honest: a classifier that guesses at
five network sub-cases would be inventing distinctions the person cannot act on.

### 4. The model-switch case (I-22, A-21)

With downloads keyed by model, changing the selection no longer cancels anything: A keeps
downloading under its own key and Settings shows B's state. Two consequences to handle explicitly:

- Settings must show **the selected model's** state *and* say that another download is running.
  One line: *"`medium` is still downloading (43 %)."* Without it, the person's 539 MB transfer
  becomes invisible.
- `removeModel()` (`SettingsViewModel.kt:183-188`) must refuse while that model is downloading,
  or the delete races the writer.

### Alternatives considered

- *Have the second caller's `start` cancel the first and take over.* Rejected: the 380 MB is
  already partly transferred and the two callers want the same bytes. Joining costs nothing and
  cancelling costs the transfer.
- *Serialise on a lock inside `ModelDownloader` so the second call waits and then finds the file
  complete.* Rejected: a suspended second caller shows a progress bar at 0 % for the whole of the
  first download. Sharing the flow shows the truth.
- *A `WorkManager` job.* Rejected for v1. It would survive process death and give retry-with-
  backoff for free, and it is the right answer if downloads ever need to continue with the app
  closed. It also adds a dependency, a worker, a notification channel and a foreground-service
  type on a platform (Horizon OS) where none of that has been tried in this project. Name it in
  the decision record as the upgrade path.
- *Check free space in the view models before calling `download()`.* Rejected: two call sites, and
  a third arrives with the next screen. The precondition belongs in the one function that writes.
- *Use `StatFs` alone and skip `getAllocatableBytes`.* Acceptable fallback, chosen as the fallback.
  `getAllocatableBytes` is better because Android may be holding reclaimable cache that `StatFs`
  reports as used, so `StatFs` alone will sometimes refuse a download that would have succeeded —
  a false refusal is a worse failure than a true one here, because the person has no way to
  disprove it.
- *Fix the "keeps failing the checksum" symptom by not deleting the partial on a checksum
  mismatch.* Rejected: keeping bytes that failed a pinned digest is the one thing
  `DEC-0016`/`DEC-0017` exist to prevent.

## Blast radius, and what NOT to touch

- **Touches:** `ModelDownloader.kt` (one parameter, one precondition, one classifier), a new
  `ModelDownloads.kt`, `Graph.kt` (one scope, one property, one KDoc), `VoiceViewModel.kt` and
  `SettingsViewModel.kt` (`downloadModel`/`cancelDownload`), `SettingsScreen.kt` (one row), two
  strings, three test files, `DECISIONS.md`, `docs/modules/feature-stt.md`.
- **Do not touch:** the checksum and the redirect allow-list (`ModelDownloader.kt:82-91,148-158`,
  `ModelStore.kt:12-25`). They are `DEC-0016` and `DEC-0017`, they are the reason this race is a
  wrong-result race rather than a corruption one, and their KDoc records a measured incident
  (Hugging Face's CDN on a different registrable domain, 2026-09-19).
- **Do not touch:** the resume logic (`:65-70`, `:97-113`). This task *makes it reachable* by
  keeping the download alive past the screen; changing it in the same commit would mean nobody
  could tell which change made resume work.
- **Do not touch:** `WhisperModel`'s digests or byte counts. `WhisperModel.kt:9-10` says it
  plainly — "They are not estimates and must never be adjusted to make a download pass."
- **Do not touch:** `removeModel()`'s scope (G-08 — it deletes only the selected model and nothing
  lists the directory). Step 6 builds the listing this needs, but finishing G-08 means a new
  Settings section and a total-size display, which is its own row and has none.
- **Watch for:** `stateIn(scope, SharingStarted.Eagerly, …)` starts the transfer at `start()`, not
  at first collection. That is intended (test 9) and it means a `start()` that nobody collects
  still downloads 190 MB. Both call sites collect; a third must too, or must call `cancel`.
- **Watch for:** `onCompletion { … running.remove(model) }` inside a `Mutex` that `start` also
  holds — do not take the lock from inside the flow's own coroutine synchronously, or a
  cancellation during `start` deadlocks. Launching the removal on the scope (as written) avoids it;
  a test for "start, cancel, start again succeeds" is worth adding if this shape survives review.
- **Watch for:** `android.system.ErrnoException` and `OsConstants` are Android classes, so
  `classify` cannot live in a pure-JVM source set without Robolectric. `feature-stt`'s unit tests
  already use Robolectric, so this is fine there — but do not move the classifier to
  `core-common`'s JVM tests without checking.

## Correction to the finding

The three cited rows are accurate. Three additions and one sharpening:

1. **I-22 and A-21 are closed by this change and are cited by nothing.** Keying downloads by model
   is what stops a selection change cancelling a transfer and silently deleting its partial. They
   are the same finding from two axes (axis I from the downloader's side, axis A from the Settings
   state's side) and both are currently unowned.
2. **A-22 is closed in passing, and it is the most valuable one.** "Cancellation deletes the
   `.part` file, and the collection runs in `viewModelScope` — so leaving the screen throws away
   the whole partial download; the resume branch can therefore only ever engage after a process
   death." The resume path is the best-engineered part of `ModelDownloader` — a `Range` header, a
   206-vs-200 check, a digest replay over the existing bytes — and it has never run. Moving the
   download off `viewModelScope` makes it reachable. On headset Wi-Fi, for 190–574 MB, that is the
   change the person will actually notice.
3. **G-06's proposed classifier is too narrow as written.** It suggests
   `t is IOException && (t.message?.contains("ENOSPC") == true || t is java.io.FileNotFoundException)`.
   Two problems: `FileNotFoundException` on an existing directory is *usually* permissions, not
   space, and folding it into `DISK` would tell a person with a permissions problem to free up
   room; and the `ENOSPC` `ErrnoException` is frequently the **cause** rather than the throwable,
   so `t.message` misses it. Walk the cause chain and drop the `FileNotFoundException` clause. G-06
   also says "better, check free space up front", which is G-07 — the two rows are one fix and
   should be one row.
4. **I-05's severity is understated at High, and the reason is worth recording.** Its user-visible
   shape is not "a race sometimes corrupts a download"; it is "the download **can never succeed**
   for as long as both screens are in the back stack, and the app blames the file for being
   corrupt each time." A person following the app's own instructions — the Today banner says
   *Download*, Settings says *Download* — reaches that state by doing exactly what they are told.
   It stays High because there is a path that works (use one screen, never the other), but the
   discoverability of the broken path is the argument for fixing it early.
