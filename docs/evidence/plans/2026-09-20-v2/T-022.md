# T-022 — Russian search works

- **Severity:** Blocker
- **Work package:** WP-4 (data: search, storage, export)
- **Closes:** G-04, E-20, A-24
- **Depends on:** T-002 (CI — the migration test is worthless if nobody runs it); WP-0
- **Needs a headset:** no for the fix, **yes for one observation** (a database written by the
  installed build, migrated in place — named at the end)
- **Estimated blast radius:** 3 production files (`NoteEntity.kt`, `NotesDatabase.kt`, `NoteDao.kt`),
  1 new exported schema (`3.json`), 2 test files, no contract moves

## What is wrong, in the person's terms

The operator dictates in Russian. Whisper capitalises the first word of every sentence and every
proper noun, so a note's stored text reads `Разрешение экрана`, `Панель`, `Москва`. They open
Search and type the word they remember — `Разреш`, or `Панель` with the capital their keyboard gives
them — and **nothing comes back**. Typed all-lowercase the same word finds it. Nothing on the screen
says why; `search_no_match` reads «Nothing matches «Панель».» and is, on its own terms, telling the
truth.

The same index feeds the assistant's retrieval (`searchAny`), so the assistant silently degrades to
"the forty most recent notes" and answers confidently from the wrong window (G-11).

ST-004 is priority **must** and JTBD-02 is the second of the product's three jobs. Both are dead for
the only person using the product.

## Measured, not suspected

Run on this machine, 2026-09-20, `sqlite3 3.51.0 2025-06-12 13:14:41 f0ca7bba1c5e` (macOS system
sqlite3). The FTS4 implementation is the same one Android ships; the tokenizer names are the same.

```console
$ sqlite3 :memory: "CREATE VIRTUAL TABLE t USING fts4(x, tokenize=simple);
    INSERT INTO t VALUES('панель размером и Разрешение экрана');
    SELECT 'панель*  -> ' || count(*) FROM t WHERE x MATCH 'панель*';
    SELECT 'Панель*  -> ' || count(*) FROM t WHERE x MATCH 'Панель*';
    SELECT 'разреш*  -> ' || count(*) FROM t WHERE x MATCH 'разреш*';
    SELECT 'Разреш*  -> ' || count(*) FROM t WHERE x MATCH 'Разреш*';"
панель*  -> 1
Панель*  -> 0
разреш*  -> 0
Разреш*  -> 1

$ sqlite3 :memory: "CREATE VIRTUAL TABLE t USING fts4(x, tokenize=unicode61);
    …same four queries…"
панель*  -> 1
Панель*  -> 1
разреш*  -> 1
Разреш*  -> 1
```

Read the `simple` block twice. It is not "Cyrillic does not work" — it is **exact-case matching**:
the query must carry the same case as the indexed token, in both directions. `Разрешение` was
indexed capitalised, so only `Разреш*` finds it; `панель` was indexed lowercase, so only `панель*`
does. A person cannot know which of their words Whisper capitalised, so the failure is
indistinguishable from "that note does not exist."

**A second measurement, so nobody expects more than the change delivers.** `unicode61` folds case.
It does **not** fold `ё`/`е`, and no `remove_diacritics` setting makes it:

```console
$ sqlite3 :memory: "CREATE VIRTUAL TABLE t USING fts4(x, tokenize=unicode61);
    INSERT INTO t VALUES('ёлка Йод счёт');  … "
елка   -> 0        ёлка   -> 1        йод    -> 1        иод    -> 0        счет   -> 0

$ …tokenize=unicode61 "remove_diacritics=2"  (the most aggressive setting)
елка -> 0          счет -> 0          разреш* -> 1
```

`й`/`и` staying distinct is correct — they are different letters. `ё`/`е` staying distinct is a real
residual annoyance for a Russian writer, because Whisper emits `ё` and people type `е`. It is **out
of scope here** and is named in the Definition of Done as a follow-up, because folding it means
normalising at write time in Kotlin and that is a separate change with its own migration.

## The same class of bug, checked — and three of the four are clean

The task brief asks whether the Kotlin side has the same defect. It does not, and the reasons are
worth writing down so the next reader does not re-audit them.

| Place | Verdict | Why |
|---|---|---|
| `NotesRepository.kt:171` — `private val TOKEN = Regex("[\\p{L}\\p{N}_]+")` | **Correct** | `\p{L}` is a Unicode general category on the JVM and matches Cyrillic. Proof without a new test: `NotesRepositoryTest.kt:109-117` passes today with `repo.search("разреш")` — if `TOKEN` did not match Cyrillic the built match string would be blank and `search()` would return `emptyList()` at `:119`. |
| `NotesRepository.kt:81-82` — `escapeForLike()` | **Correct for its job, safe by accident** | `LIKE` in SQLite is case-insensitive for ASCII only — the same defect class. It is safe here only because both sides are already lowercase: `TagParser.parse` lowercases at `TagParser.kt:13`, and the tag passed to `observeNotes(tag)` comes from `state.tags`, which is built out of the stored blobs. **Add the test anyway** (below): the safety is a property of two files agreeing, not of the query. |
| `TagParser.kt:9,13` | **Correct** | `(?<![\p{L}\p{N}_])#([\p{L}\p{N}_-]+)` matches `#Идея`, and `.lowercase()` in Kotlin is `Locale.ROOT`-invariant — no Turkish-I trap. `TagParserTest` has no capitalised-Cyrillic case; add one. |
| `NoteFts` tokenizer | **Wrong** | Above. |

## The decision, and what was weighed

**Chosen: `@Fts4(tokenizer = FtsOptions.TOKENIZER_UNICODE61)`, schema version 3, a migration that
drops and rebuilds `note_fts` from `notes`.**

**Alternatives considered:**

- *Lowercase the query terms in `search()`/`searchAny()` and ship nothing else.* **Rejected, and it
  must not be shipped as a substitute** — it is a half-fix that looks like a whole one. It makes
  `Панель` find `панель`, and leaves `панель` unable to find the capitalised `Панель` that Whisper
  actually wrote, which is the common direction. The measurement above shows both directions fail.
  Lowercasing the query *after* the tokenizer change is a harmless no-op and may be kept if the
  implementer wants the behaviour to be independent of the tokenizer; it earns nothing on its own.
- *Lowercase the text written into `note_fts` as well as the query.* Rejected: it works, and it makes
  the index a second, differently-cased copy of the text whose correctness depends on every writer
  remembering. The tokenizer is the one place the rule belongs, and SQLite already implements it.
- *`unicode61` with `remove_diacritics=2`.* Rejected on the measurement: it changes nothing for
  Cyrillic (`елка -> 0`, `счет -> 0` above) and silently changes Latin behaviour for no stated reason.
- *ICU tokenizer.* Rejected: not compiled into Android's bundled SQLite; would mean bundling
  `androidx.sqlite` with a custom build — a large dependency change to fix case folding.
- *`fallbackToDestructiveMigration()` instead of a migration.* Rejected outright: it deletes the
  notes. T-027 is the task that says why that floor cannot exist yet.

**Step 3 — bump the version and generate the schema.** `NotesDatabase.kt` → `version = 3`. Build
`:core-notes` so KSP writes `core-notes/schemas/ai.passioncode.fabricvr.notes.db.NotesDatabase/3.json`.
**Open it and copy the exact `createSql` for `note_fts`.** Room validates an FTS table by comparing
the create statement it generates against the one in the database; a hand-written `CREATE VIRTUAL
TABLE` that differs by a space or by argument quoting fails the identity check at open time, on the
person's headset, after the migration has already run. The generated string is the only safe source.

**Step 4 — the migration.** In `NotesDatabase.kt`, beside `MIGRATION_1_2`:

```kotlin
/**
 * v2 → v3 rebuilds the search index with the `unicode61` tokenizer. The index is derived data —
 * every row in it is recoverable from `notes` — so it is dropped and rebuilt rather than migrated.
 * The CREATE statement below is copied verbatim from the generated `3.json`; Room compares it
 * against its own at open time and a single differing character bricks the app on launch.
 */
val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("DROP TABLE IF EXISTS `note_fts`")
        db.execSQL(/* the createSql from 3.json, verbatim */)
        db.execSQL(
            """
            INSERT INTO `note_fts` (`noteId`, `title`, `body`, `transcript`)
            SELECT `id`, `title`, `body`, IFNULL(`transcriptText`, '') FROM `notes`
            """.trimIndent(),
        )
    }
}
```

`IFNULL` matters: `NoteDao.upsert` writes `note.transcriptText.orEmpty()` (`NoteDao.kt:74`), so an
empty string is what the index holds for a note with no transcript, and a `NULL` would make the row
differ from one written by the app.

Register it: `.addMigrations(MIGRATION_1_2, MIGRATION_2_3)` at `NotesDatabase.kt:44`.

**Step 5 — what happens to an existing database, stated plainly.** Two headsets carry data written
by the current build.

| Database is at | On first launch after this change | The person sees |
|---|---|---|
| v3 (fresh install) | nothing to do | working search |
| v2 (both headsets today) | `MIGRATION_2_3` runs: index dropped, rebuilt from `notes` in one transaction | a launch a few hundred milliseconds slower, then working search |
| v1 (no known device, but possible) | `MIGRATION_1_2` then `MIGRATION_2_3`, composed by Room | the same |
| v2, migration throws | `IllegalStateException` on **every** launch, forever | a dead app and no way in — this is exactly the failure T-027 exists to make impossible, which is why T-027 depends on this task and must land in the same release |

**No note text is at risk**: `notes` is not touched. The worst case is a lost *index*, which is
rebuildable. Say that in the commit; it is the reason this migration is safe to write before T-027's
harness exists, and the reason T-027 is still required before the next one.

**Step 6 — A-24, the orphaned FTS row.** `NoteDao.insertNote` is `@Insert(REPLACE)`
(`NoteDao.kt:55-56`) against a table with a unique index on `dayKey` (`NoteEntity.kt:12-15`).
`REPLACE` deletes the colliding row silently, and `upsert` then only calls `deleteFts(note.id)` —
the **evicted** note's index row survives with no note behind it, so it keeps appearing in search
results that resolve to nothing (the `JOIN` drops them, so the person sees a search that finds
fewer things than it says it found, and the index grows forever).

Mechanical half — do this:

```kotlin
@Query("SELECT id FROM notes WHERE dayKey = :dayKey AND id != :id")
suspend fun idHoldingDay(dayKey: String, id: String): String?

@Transaction
suspend fun upsert(note: NoteEntity) {
    // REPLACE evicts a row that collides on the unique dayKey index, and the eviction is silent.
    // Its index row would otherwise outlive it.
    note.dayKey?.let { key -> idHoldingDay(key, note.id)?.let { deleteFts(it) } }
    insertNote(note)
    deleteFts(note.id)
    insertFts(…)
}
```

**Product half — the operator decides.** The eviction itself (today's daily note, typed into, is
destroyed when yesterday's deleted daily note is restored by *Undo*) is a behaviour question, not an
index question:

| Option | What happens on Undo of a deleted daily note when today already has one | Cost |
|---|---|---|
| **A (recommended default)** | the restored note comes back **without** its `dayKey` — it keeps its text and stops being "the daily note for that day" | one line in `NotesViewModel.undoDelete()`; a person loses nothing and gains a note whose date heading is now just its title |
| B | the Undo is refused with a message | needs a new string and a new failure path the person did not ask for |
| C | the two are merged | the most "correct" and the most surprising: two texts silently become one |

Implement A unless the operator says otherwise, and record the choice as the register's next free id in
`docs/DECISIONS.md` (0019 is the highest today). Write the test either way:
`NotesRepositoryTest`: `restoring a deleted daily note does not silently replace today's note`.

## The on-device observation

One thing no JVM test can show: that a database **written by the installed build** survives the
migration in place. On a headset that already has notes, before installing:

```bash
adb shell run-as ai.passioncode.fabricvr sqlite3 databases/fabricvr-notes.db \
  "PRAGMA user_version; SELECT count(*) FROM notes; SELECT count(*) FROM note_fts;"
```

Install, launch, then run it again: `user_version` is 3, and the two counts are unchanged. Then, in
the app, search for a word you know is capitalised in one of your notes. Record both transcripts in

## Blast radius, and what NOT to touch

- **Touches:** `NoteEntity.kt` (one annotation argument), `NotesDatabase.kt` (version + one
  migration), `NoteDao.kt` (one query, three lines in `upsert`), `3.json` (generated),
  `NotesRepositoryTest.kt`, `TagParserTest.kt`, possibly one line in `NotesViewModel.undoDelete()`.
- **Do not touch:** `MIGRATION_1_2` — its body is load-bearing for any v1 device and T-027 is the
  task that finally gets to test it. `contentEntity` — E-20(b), explicitly deferred.
  `NotesRepository.TOKEN` — it is correct, and changing it changes what is *asked for* as well as
  what is indexed, which would invalidate the measurement above. `escapeForLike` — correct.
- **Do not add** `fallbackToDestructiveMigration()`. Not as a safety net, not "temporarily". It is
  the one line that turns a migration bug into permanent data loss, and T-027 owns the question of
  when a floor may exist.
- **Watch for:** `searchAny` filters terms to `length >= 3` (`NotesRepository.kt:134`) — after this
  change a two-letter Russian query still returns nothing from the assistant's retrieval, and that
  is a different (and defensible) rule. Do not "fix" it here.
