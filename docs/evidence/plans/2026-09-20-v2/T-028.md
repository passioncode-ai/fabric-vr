# T-028 — A text note can be created

- **Severity:** Blocker
- **Work package:** WP-5 (the Today surface)
- **Closes:** A-01, **B-02 (in part — see the split below)**, D-01 (in part; T-029 owns the rest)
- **Depends on:** **WP-1, WP-2 and WP-3, all of them.** Not a formality — see *Why this waits*.
- **Needs a headset:** yes for one observation (the Space host, not the panel)
- **Estimated blast radius:** `TodayScreen` (header + one new card), `NotesViewModel` (one signature
  change), 3 strings, 1 Compose test file. No view-model logic is written — it all exists.

## Why this waits, and why the screen is rebuilt once

Every WP-5 task edits the same file. `TodayScreen.kt` is 460 lines and it is where A-01, B-02,
B-03…B-13, B-20, D-01, D-05, G-17 and half of T-025 all land. **The plan's ordering exists so that
this file is rewritten once against a written spec, not edited nine times.**

Concretely, landing this before WP-1/2/3 would mean:

- T-005/T-006 change `RecordControl`'s parameters and the note row's actions;
- T-012 changes which owners the composition sees in the Space, which decides whether a
  `DropdownMenu` on the note row works at all (B-09);
- T-020 changes what `VoiceState.Recording` carries.

Any of those landing after this one means re-opening the same functions. **Read T-030 before
starting**: it is the spec for the screen's structure, and this task's control has to sit inside
that structure. If T-030 has not been written yet, write these two together.

## What is wrong, in the person's terms

There is no way to make a text note.

The method exists — `NotesViewModel.createNote()` (`app/.../ui/NotesViewModel.kt:150-154`):

```kotlin
suspend fun createNote(): Note? =
    repository.upsert(NotesRepository.newNote()).fold(
        onSuccess = { it },
        onFailure = { failure -> _state.value = _state.value.copy(message = failure.toMessage()); null },
    )
```

The string exists — `action_new_note`, "New note" (`app/src/main/res/values/strings.xml:29`).

**No screen calls either.** `grep -rn "R.string.action_new_note\|createNote" app/src/main/kotlin`
returns the declarations and nothing else. The editor is reachable only through a note row
(`TodayScreen.kt:209` → `onOpenNote`), and on a fresh install there are no rows — so the first
thing a person sees is an empty state that says *"Nothing here yet. Hold Record and say something,
**or start a note**."* (`today_empty`, `strings.xml:102`) and offers neither of the two things it
names.

`git log -S action_new_note -- app/.../TodayScreen.kt` names the commit that removed it:

```
732c92b feat(ui): one button, no windows — and the manifest line the Space was blocked on
```

The control was collateral of a deliberate simplification. The simplification was right — DEC-0010
deleted the hold gesture and the capture sheet for good reasons — and taking *New note* with it was
not part of that decision and is not recorded in any DEC.

SCN-001 step 1 is "Tap *New note*". SCR-01 promises a date header, today's daily-note card,
*New note*, tag chips, per-row time and a microphone glyph. **None of the six are rendered.**

## How B-02 is split, so nothing falls between the two tasks

B-02 names six missing elements. They are divided by what they are for, not by convenience:

| SCR-01 element | Owner | Why there |
|---|---|---|
| *New note* control | **T-028** | it is the missing capability |
| the date header | **T-028** | it is the label on the day card and meaningless without it |

| tag filter chips | **T-029** | filtering is its own behaviour with its own empty case |
| per-row time | **T-030** | it is a row-rendering detail in the screen T-030 rebuilds |

B-02's fix offers "either render them or cut them from the docs and delete the view model surface".
**We render.** The reasoning is in the view model itself: five state fields and three methods were
written, tested and kept through a rewrite. The product was described this way in `screens.md`,
`scenarios.md` and `flows.md`, and the operator has never been shown the version without them.
Deleting a documented capability because its button was lost in a refactor is a decision, and it
has not been made.

## The decision, and what was weighed

**Chosen: *New note* is a labelled action in the header, beside Search; the day card sits above the
record button; creating a note opens the editor.**

**Where it sits, and what lost:**

- *In the header, labelled.* Chosen. The header is the row of things that take you somewhere
  (`TodayScreen.kt:117-139`), and creating a note is exactly that. It must carry a **text label**,
  not only an icon: B-25 is the finding that five unlabelled icon actions already sit there, two of
  them the same glyph, and adding a sixth silent one makes that worse. T-030 owns turning the whole
  header into labelled actions; this task's control ships labelled from the start either way.
- *A second big button beside Record.* Rejected. The record button is 128 dp and the screen's
  entire point (`TodayScreen.kt:63-72`: "The whole product on one screen: press once to record").
  A second button of comparable weight makes the person choose before they have done anything.
- *Only in the empty state.* Rejected. It would be unreachable the moment a first note exists,
  which is the same bug in a smaller form.
- *A floating action button.* Rejected. It overlaps the list, and in a headset an element floating
  over content is a target with nothing behind it to steady the aim against.

**What happens after — chosen: it opens the editor, with the keyboard not yet focused.**

- *Open the editor.* Chosen. `createNote()` returns a `Note` with an id
  (`NotesRepository.newNote()`, `NotesRepository.kt:35-43`) and `Routes.editor(id)` exists
  (`FabricApp.kt:22`, `:45`). A new note that stayed on Today would be an untitled empty row —
  indistinguishable from a bug.
- *Do not auto-focus the title field.* **This is not a style preference, it is B-01.** In the Space
  a panel is an `android.app.Presentation` on a `VirtualDisplay`, and `PanelDisplayBase.dispatchEvent`
  returns **without dispatching** while `imm.isAcceptingText()` is true — so the moment the keyboard
  opens, the panel stops receiving taps entirely, including *Back*. Auto-focusing on entry is
  exactly the trap `SearchScreen.kt:46` already sets. The editor opens; the person taps the field
  when they want it. T-014 owns text entry in the Space; this task must not make its job harder.
- *Create inline on Today with an expanding row.* Rejected: a second editing surface to keep in
  step with the real editor, for a product whose principle is one screen and no windows.

**The day card — chosen: a row above the record button showing `state.dayLabel` and today's note.**
`NotesViewModel` already loads it (`loadDailyNote()`, `:119-128`) into `state.today` and keeps
`state.dayLabel` correct across midnight (`:92-97`, the `dayTicks` flow). Tapping it opens the
editor on that note. This also fixes something the first-run trace (axis D) calls out: today's
daily note is created silently at launch and then "will appear on the next emission as an
unexplained row bearing today's date". With a card it is explained.

## Decomposition

**Step 1 — write the failing tests first.** New file
`app/src/androidTest/kotlin/ai/passioncode/fabricvr/TodayScreenTest.kt` (a Compose test; T-001 is
making the instrumented suite honest, and this is one of the tests that has to be trustworthy).
Assert by resource, never by literal — B-03 is the finding that a hard-coded `"New note"` in
`PanelSmokeTest` is what made the suite red:

```kotlin
private fun s(@StringRes id: Int) = InstrumentationRegistry.getInstrumentation()
    .targetContext.getString(id)

@Test fun `a new note can be created from Today`() {
    rule.onNodeWithText(s(R.string.action_new_note)).assertIsDisplayed().performClick()
    // the editor is open on a note that did not exist before
    rule.onNodeWithText(s(R.string.label_title)).assertIsDisplayed()
}

@Test fun `today's note is reachable from a card`() {
    rule.onNodeWithText(s(R.string.label_today_note)).assertIsDisplayed().performClick()
    rule.onNodeWithText(s(R.string.label_title)).assertIsDisplayed()
}

@Test fun `the editor does not open with the keyboard up`() {
    rule.onNodeWithText(s(R.string.action_new_note)).performClick()
    rule.onNodeWithText(s(R.string.label_title)).assertIsNotFocused()
}
```

Run them. **Watch all three fail** — the first two with "no node with text", the third because
there is nothing to focus. The third is the one that will look pointless in six months; its comment
must say B-01, or someone will add auto-focus back as a convenience.

Add one JVM test, because a Compose test cannot see the returned id:

## Correction to the finding

**A-01's proposed verification says: "assert a node with `action_new_note` exists and that clicking
it calls `createNote`."** The second half cannot be asserted from a Compose test against
`PanelActivity` — the view model is obtained through `viewModel()` (`TodayScreen.kt:83`) and the
test has no handle on it. The split above is what actually holds: the Compose test asserts the
control exists and that clicking it **reaches the editor**, and the JVM test asserts `createNote`
persists. Together they cover the claim; either alone does not. Stated because a developer
following A-01 literally will spend an afternoon trying to inject a fake view model into a Spatial
panel activity.

## Blast radius, and what NOT to touch

- **Touches:** `TodayScreen.kt` (header, one new composable, one call), `NotesViewModel` (nothing —
  `createNote` is already `suspend` and already returns the note), three strings if `DayCard` needs
  them, one new test file, one DEC.
- **Do not touch:** `RecordControl` and everything in it — T-005, T-030 and T-025 all have work
  there and this task has none. `today_empty` — T-032. The tag chips — T-029, and adding a chip row
  "while you are in the file" is how two tasks produce one conflict. `NotesViewModel.selectTag` /
  `state.tags` — same. `createVoiceNote` — a different creation path with different rules
  (`NotesViewModel.kt:243-254`).
- **Watch for:** `createNote()` creates a note with a blank title and body, so after T-026's window
  it appears at the top of the list as `label_untitled`. If the person backs out without typing,
  they have made an empty note. That is acceptable (`NotesRepository.newNote` is how the product has
  always created notes) but it should be **named in the commit**, because the alternative —
  deleting an untouched empty note on exit — is a real design question and the next reader should
  know it was seen and left.
- **Watch for:** the day card and *New note* both navigate to the editor, and `EditorViewModel`'s
  autosave/flush on dispose (`NoteEditorScreen.kt:67`) is T-007's ground. Do not change how the
  editor is entered beyond passing an id.
