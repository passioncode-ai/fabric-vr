# T-011 — Crash capture that survives a reboot, readable from Settings

- **Severity:** Blocker
- **Work package:** WP-1 (stop the data loss and the silence)
- **Closes:** H-01, H-02, H-03
- **Depends on:** nothing. **Related:** T-023 (export) — `filesDir` is unreachable to a person, so a crash file written there is only useful once something can read it out; this spec solves that with the clipboard rather than waiting for T-023.
- **Needs a headset:** for the final observation only; the handler itself is JVM-testable.
- **Blast radius:** 1 new file in `core-common`, 2 lines in `FabricVrApp`, one Settings row, one string. No contract moves.

## What is wrong, in the person's terms

The app crashed on 2026-09-19 and the operator reported the crash. **The project had no way to answer
that.** What actually happened was a person on a laptop, on the same network, running

```
adb shell dumpsys activity exit-info ai.passioncode.fabricvr
```

and reading an `ApplicationExitInfo` record the system happened to keep. That is not a diagnostic
capability. It is a lucky accident of Android keeping a ring of exit reasons, and it works only
while the headset is awake, on this LAN, and paired to this laptop.

The second headset belongs to someone else. When the app fails there — and after 27 Blockers it
will — **nothing produces an artefact anyone will ever read**. The person can say "it broke"; there
is no yesterday to look at.

## Where it is

`app/src/main/kotlin/ai/passioncode/fabricvr/FabricVrApp.kt` — the whole class:

```kotlin
class FabricVrApp : Application() {
    override fun onCreate() {
        super.onCreate()
        Graph.init(this)
    }
}
```

No `Thread.setDefaultUncaughtExceptionHandler`. Over the whole tree,
`grep -rn 'UncaughtException|setDefaultUncaught' --include='*.kt'` returns nothing.

`core-common/src/main/kotlin/ai/passioncode/fabricvr/common/Logging.kt:35-46` — the only sink:

```kotlin
private fun emit(level: Char, message: String, t: Throwable?) {
    if (onDevice) {
        when (level) { 'I' -> Log.i(TAG, message); 'W' -> Log.w(TAG, message); else -> Log.e(TAG, message, t) }
    } else {
        System.err.println("$level/$TAG: $message"); t?.printStackTrace()
    }
}
```

On a Quest 3 the per-app logcat ring is a few hundred kilobytes and is cleared on reboot and under
buffer pressure. There are five `Log2.e` call sites in the entire tree, so even the ring is nearly
empty.

## The decision, and what was weighed

**Chosen: a default uncaught-exception handler that appends one record to a bounded file in
`filesDir/crash/`, plus a Settings row that shows the most recent and copies the file to the
clipboard.**

Nothing is sent anywhere. Two headsets do not need a backend, and adding one would put the
operator's stack traces — which can carry note text in a message — on somebody's server.

**Alternatives considered:**

- *Firebase Crashlytics or Sentry.* Rejected for this size. Both need a project, a key in the app, a
  network dependency at startup, and a privacy story; the family's `error-tracking` skill exists for
  products with users, and this has two. Revisit if T-036 answers "second user" — the spec for that
  decision names this as a consequence.
- *Read `ApplicationExitInfo` at next launch instead of installing a handler.* Rejected as the
  primary mechanism, **kept as a supplement**: the system's own record survives a process death our
  handler cannot catch (a native abort in whisper, a low-memory kill), but it holds no stack for a
  native crash, is capped at a handful of entries, and cannot record anything our code knows. Do
  both: the handler for what we can catch, a one-time read of `getHistoricalProcessExitReasons` at
  startup for what we cannot.
- *Ship logs over the network to the laptop.* Rejected: the second headset is not on this LAN, and
  a log shipper is a background service with a retry policy — more machinery than the problem.
- *Write to external storage so `adb pull` works without the app.* Rejected here and deferred to
  T-023, which is choosing a shared-storage route for the vault anyway; when it lands, the crash
  directory can join the export rather than inventing a second path.

## Decomposition

**Step 1 — write the failing tests first.**
`core-common/src/test/kotlin/ai/passioncode/fabricvr/common/CrashLogTest.kt` (new):

1. `a crash is written as one record with its stack` — call `CrashLog.record(dir, throwable, meta)`
   directly, read the file, assert it holds the exception class, the message, the top frames and the
   metadata line.
2. `the file never grows past its bound` — record 200 crashes into a directory whose bound is 64 KB,
   assert the file is at or under the bound and that the **newest** record survived. Getting this
   backwards — keeping the oldest — is the usual bug, and it keeps the crash nobody needs.
3. `a value never reaches the file` — record a throwable whose message contains a string shaped like
   a key, assert the written text contains `Log2.redact`'s shape and not the value. **This is the
   project's standing rule and the reason this task is not simply `printStackTrace` to a file.**
4. `recording a crash cannot itself crash` — pass an unwritable directory; assert `record` returns
   without throwing. A handler that throws replaces a diagnosable crash with an undiagnosable one.

Run them. Watch all four fail.

**Step 2 — `core-common/.../CrashLog.kt`** (new). A plain object, no Android dependency beyond
`java.io`, so the tests above are JVM tests:

```kotlin
object CrashLog {
    /** Bounded so a crash loop cannot fill the device that is already failing. */
    const val MAX_BYTES = 64 * 1024

    fun record(dir: File, error: Throwable, meta: Map<String, String>): Unit
    fun latest(dir: File): String?
    fun all(dir: File): String
}
```

A record is: an ISO-8601 UTC timestamp, the build identity (T-038 supplies it — until then the
`versionName` and `BuildConfig.DEBUG`), the thread name, the exception chain with stack frames, and
the `meta` map. Redact every value through `Log2.redact` before writing. Append, then truncate from
the **front** to `MAX_BYTES`.

**Step 3 — install the handler** in `FabricVrApp.onCreate`, before `Graph.init`, because a failure
inside `Graph.init` is exactly the kind worth catching:

```kotlin
private fun installCrashHandler() {
    val previous = Thread.getDefaultUncaughtExceptionHandler()
    Thread.setDefaultUncaughtExceptionHandler { thread, error ->
        runCatching { CrashLog.record(crashDir(), error, mapOf("thread" to thread.name)) }
        previous?.uncaughtException(thread, error)   // let the platform still kill us
    }
}
```

**Chaining to `previous` is not optional.** Swallowing the exception leaves a process alive in a
state nobody designed, which is worse than the crash.

**Step 4 — the system's own record, for what the handler cannot catch.** At startup, read
`ActivityManager.getHistoricalProcessExitReasons(packageName, 0, 5)`, and for any entry newer than
the last one recorded, append a record naming the reason, the description and the timestamp. Store
the high-water timestamp in `SecureSettings` so the same exit is not recorded twice. This is what
would have caught the `OnBackPressedDispatcherOwner` crash without a laptop.

**Step 5 — the Settings row.** Under a heading the person can find: the date of the most recent
crash and its exception class, a *Copy the crash log* button putting `CrashLog.all()` on the
clipboard, and a *Clear* button. When there is no crash, the row says so — an empty diagnostics
section that simply is not rendered teaches nobody that the feature exists.

**Step 6 — the install script.** `scripts/install-on-quest.sh` already tails logcat after a launch.
Add a line that pulls the crash file if one exists, so the laptop path keeps working and gets
better.

## Definition of Done

- [ ] The four JVM tests exist and were watched failing first.
- [ ] A crash in either activity leaves a record in `filesDir/crash/` that survives a reboot.
- [ ] The record contains no secret value — proven by test 3, not by reading it.
- [ ] The handler chains to the previous one; the process still dies.
- [ ] Settings shows the latest crash and copies the log.
- [ ] `./gradlew testDebugUnitTest lintDebug` green; four gates green.
- [ ] **On the headset:** force a crash (a debug-only menu item, or `adb shell am crash`), reboot the
      headset, open Settings, and read the record. That observation is the acceptance; a passing
      JVM test does not prove the file survives a reboot.

## Blast radius, and what NOT to touch

- **Touches:** a new `CrashLog` in `core-common`, `FabricVrApp` (two lines), `SettingsScreen` and
  `SettingsViewModel` (one row), one string, `install-on-quest.sh` (one line).
- **Do not touch:** `Log2`'s existing behaviour. It is the logging path and it degrades correctly
  off-device; this is a second, separate sink for one kind of event.
- **Do not** send anything anywhere, and do not add a dependency. If T-036 decides the second
  headset is a real user, that decision reopens this — and its spec says so.
- **Watch for:** `FabricVrApp.onCreate` now does work before `Graph.init`; keep it to installing a
  handler that cannot throw. A crash *in the crash handler* is the one failure mode that leaves
  nothing at all.
