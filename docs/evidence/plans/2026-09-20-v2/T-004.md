# T-004 — `main` carries the project, so a fresh clone builds

- **Severity:** High
- **Work package:** WP-0 (honest build)
- **Closes:** H-36, H-37
- **Depends on:** nothing — and it should not wait. Every day it waits, the repository's front door
  says the project does not exist.
- **Needs a headset:** no
- **Estimated blast radius:** one branch merge (37 commits, fast-forward, no conflicts possible),
  `settings.gradle.kts` (+8 lines), `README.md` (a clone command and a JDK line),
  `gradle.properties` (a comment). No source changes.

## What is wrong, in the person's terms

Someone is handed this repository — a second machine, a second person, an agent starting cold.
They clone it. They read the front page. It says:

> Research complete, no code yet (2026-09-19)

There is no `gradlew`, no `settings.gradle.kts`, no `.gitmodules`, no module. Measured:

```
$ git ls-tree --name-only origin/main
README.md
docs
```

Twenty-five modules-worth of finished work, an audit of 291 findings and a plan of 46 tasks exist
— on a branch whose name appears nowhere on the page they are looking at. **A fresh clone cannot
build this project, and the blocker is step two of the walk.**

If they get past that — because somebody told them the branch name — the next thing that stops
them is not in the repository either. Gradle 8.13 refuses to run on a JDK that is too new, and
nothing in the build says which JDK this is. The entire mechanism is a sentence in the README
telling them to `export JAVA_HOME` to Android Studio's JBR. Forget it and the failure reads
`Unsupported class file major version …`, which names neither the JDK nor the fix.

## The decision, and what was weighed

### 1. `main` gets the code by a **fast-forward merge**, not a pointer and not a squash

**Chosen:**

```bash
git fetch origin
git checkout main
git merge --ff-only feat/v1-notes-core
git push origin main
```

`--ff-only` is not a preference; it is an assertion. `git merge-base origin/main HEAD` equals
`origin/main`'s tip, so `feat/v1-notes-core` is a strict descendant and the merge is a pointer
move. If `--ff-only` refuses, **something has changed since this spec was written** — somebody
pushed to `main` — and the refusal is the check working. Stop and re-read, do not switch to a
plain `git merge`.

**Alternatives considered:**

- *One line at the top of `main`'s README: "the code is on `feat/v1-notes-core`".* This is H-36's
  own second option, and it is thirty seconds. Rejected as the answer, kept as the fallback: it
  stops the bleeding but a fresh clone still holds no code, `git ls-tree` still shows two entries,
  and CI (T-002) would never run against the default branch. Use it **only** if branch protection
  blocks the merge and the operator is not available.
- *Squash the 37 commits into one.* Rejected, and this one would actively break the build's own
  gate. `scripts/check-docs.sh` section 9 prints `ok: every commit reference in docs/evidence
  resolves AND is reachable from HEAD`. The audit reports and the decision register cite roughly
  thirty short SHAs — `732c92b`, `deb604d`, `421377e`, `2f91df7`, `4bddfcc`, `f770049`, `bb82929`,
  `830ad0a`, `16a5fb5`, `ff7787b` and more. A squash makes every one of them unreachable and the
  documentation gate fails on the first run after the merge. The history *is* the evidence here.
- *Rebase `main` onto the branch, or rewrite either.* Rejected for the same reason, plus: never
  force-push to make a handoff pass.
- *A merge commit (`--no-ff`).* Rejected: it adds a commit that says nothing. There is no parallel
  history to record.
- *Open a pull request.* Not rejected — **this is the operator's call**, see below.
- *Tag the merge (`v0.1.0`).* Deliberately **not** in this task. There are no tags today, and a
  version tag implies a release; `versionCode` is still the literal `1` (H-31/T-038) and no build
  has ever been signed (T-039) or installed (T-037). A tag now would name a thing nobody can
  install. T-041 owns tags.

### 2. Two questions belong to the operator, not the developer

**(a) Is `main` protected, and does this organisation want direct pushes?** `git ls-remote` cannot
answer it and neither can a developer. If `passioncode-ai/fabric-vr` requires a pull request, the
same fast-forward is done through one — merge method **"Rebase and merge" or "Squash" must both be
refused**; only "Create a merge commit" or a true fast-forward preserves the SHAs the doc gate
resolves. Say that in the PR description. Offer the operator the two shapes and their cost:

| Shape | Cost | Buys |
|---|---|---|
| direct `git push origin main` | none, if permitted | the default branch carries the project today |
| a PR with a fast-forward merge | one round trip, and GitHub's default merge button may not preserve SHAs — check the repo's allowed merge methods first | a reviewable record, and it works under protection |

**(b) Does `feat/v1-notes-core` stay the working branch after this?** Both answers are defensible
and the plan does not decide it:

- *Keep it.* The remaining 42 tasks continue where they are, and `main` is re-fast-forwarded at
  each work-package boundary. T-002's `release` job already names both refs. Cost: `main` is
  behind again within a day, and H-36 recurs in a milder form.
- *Move to `main`.* Simpler, one branch, no drift. Cost: every task lands on the default branch
  with no staging, which in a repository with no CI history and 27 open Blockers is a real risk
  until T-002 is green.

**Recommendation, not a decision: keep `feat/v1-notes-core` until T-002's CI has produced one
green and one red run, then move to `main`.** Whichever the operator picks, write it into
`README.md` and into the handoff, because "which branch is the truth" is the question that caused
this task.

### 3. The JDK is *checked*, not *provisioned* — for now

**Chosen: a version guard in `settings.gradle.kts` that fails with a message naming `JAVA_HOME`
and the supported range.** Six lines, no new plugin, no download, no change to what compiles.

**Alternatives considered:**

- *A `foojay-resolver-convention` plugin plus `kotlin { jvmToolchain(17) }` in each module.* This
  is the correct long-term answer and H-37 names it: Gradle then *provisions* the right JDK
  instead of requiring one, and the machine's `JAVA_HOME` stops mattering. Rejected **for this
  task** on three counts: it adds a plugin resolved from the Gradle Plugin Portal, which
  `settings.gradle.kts:11` allows but which nothing here has exercised; it changes the JVM that
  compiles Kotlin in six modules at once, under a KSP/AGP/Kotlin trio already pinned for measured
  reasons (DEC-0004, H-16, H-17); and it would silently download a JDK on the operator's machine
  the first time they build. All three are fine **behind CI**, and CI does not exist yet (T-002).
  Do it as a follow-up, with the toolchain bump, not as part of unblocking a clone.
- *`org.gradle.java.home` in `gradle.properties`.* Rejected outright: it is a machine-specific
  absolute path in a tracked file. It would work on exactly one laptop and break every other
  clone, which is the opposite of this task.
- *Nothing, and a stronger README sentence.* Rejected: the README sentence already exists and H-37
  is the finding that it is not enough. Prose is not a check.

**The supported range.** H-37 states that Gradle 8.13 does not run on JDK ≥ 24. Treat that as a
lead and **confirm it against Gradle's own compatibility matrix before writing the bound** — a
guard with the wrong upper bound is worse than none, because it refuses a working machine. The
lower bound is 17, which is what every module targets. The developer machine of record is 21.

## Decomposition

**Step 1 — verify, then merge. In this order, and record each output in the commit message.**

```bash
git fetch origin --prune
git status --porcelain                      # must be empty
git rev-list --count HEAD..origin/main      # must be 0
git merge-base origin/main HEAD             # must equal origin/main's tip
git diff --stat origin/main..HEAD -- docs/  # sanity: main's docs are a subset, not a divergence
bash scripts/check-docs.sh && bash scripts/check-secrets.sh && python3 docs/ux/lint.py
./gradlew testDebugUnitTest :app:lintDebug
```

The last two lines matter: **`main` must not become red the moment it gains the code.** If the
gates or the suite are not green on `feat/v1-notes-core`, this task waits for T-001. That is the
one real ordering constraint here, and the plan does not record it — say so on the board.

Then:

```bash
git checkout main
git merge --ff-only feat/v1-notes-core
git push origin main
```

**Step 2 — verify the merge landed, from outside the working copy.**

```bash
git ls-remote --heads origin                       # main and feat now equal
git ls-tree --name-only origin/main                # must list app, gradle, settings.gradle.kts, …
git show origin/main:settings.gradle.kts | head -1 # the file exists on the default branch
```

Then the real test: **clone into a temporary directory and walk the README** (step 6).

**Step 3 — `settings.gradle.kts`, the JDK guard.** At the top, before `pluginManagement`:

```kotlin
// The JDK Gradle itself runs on is not the same thing as the bytecode target each module sets
// (JavaVersion.VERSION_17). Nothing in this build provisioned one, and the whole mechanism was a
// sentence in the README telling the reader to export JAVA_HOME. A fresh machine whose default
// java is too new fails with "Unsupported class file major version", which names neither the JDK
// nor the fix. This says both.
//
// Not a toolchain: provisioning a JDK changes what compiles six modules under a pinned
// Kotlin/KSP/AGP trio (DEC-0004), and that belongs behind CI, not in front of a first clone.
val running = JavaVersion.current()
require(running >= JavaVersion.VERSION_17 && running <= JavaVersion.VERSION_21) {
    """
    This build needs JDK 17–21; it is running on $running.
    Android Studio ships one:
      export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
    """.trimIndent()
}
```

**Confirm the upper bound before committing it.** 21 is the JDK of record on the developer
machine and the one T-002 pins in CI; a wider bound is fine if Gradle 8.13 genuinely supports it,
and a *wrong* wider bound turns a clear failure into a confusing one. Record where the bound came
from in the comment.

**Step 4 — `gradle.properties`.** Add a comment above the existing six lines saying the JDK is
enforced in `settings.gradle.kts` and why it is not `org.gradle.java.home`. Two lines. It is the
file a person opens looking for exactly this.

**Step 5 — `README.md`.** Three things, all small and all measured absences (H.md's fresh-clone
walk, steps 1, 5 and 6):

1. A clone command. The README names none, so the reader has to know the URL:
   `git clone git@github.com:passioncode-ai/fabric-vr.git` — with the note that SSH needs a key
   with access to a private org repo, and that HTTPS plus a PAT also works.
2. The JDK line, matching the guard exactly. If the guard says 17–21, the README says 17–21.
3. Which branch is the working branch, per the operator's answer to question 2(b).

**Adjacent and deliberately not booked here:** `sdkmanager --licenses` (H-38) is the *other* hard
stop on a fresh machine, and it is one README line. Fold it in if the operator agrees, but it is
H-38's row and this task closes H-36 and H-37 — say which you did.

**Step 6 — prove it from a fresh clone.** This is the Definition of Done and it cannot be
inferred:

```bash
cd "$(mktemp -d)"
git clone git@github.com:passioncode-ai/fabric-vr.git && cd fabric-vr
git rev-parse --abbrev-ref HEAD                 # main
ls settings.gradle.kts gradlew app              # all present
git submodule update --init --recursive
echo "sdk.dir=$HOME/Library/Android/sdk" > local.properties
./gradlew testDebugUnitTest
```

Paste the outcome into the commit message. If it fails, the failure is the finding — record it
and open a row rather than fixing it quietly under this task.

**Step 7 — `git branch --set-upstream-to=origin/feat/v1-notes-core feat/v1-notes-core`** (H-40).
Local-only, costs nothing, and it is one more thing a second machine does not have to be told.
It is a Low finding riding along; name it in the commit.

## Tests

There is no unit test for a branch. The checks are commands, and each has an output that is the
assertion:

| Check | Command | Asserts | How to watch it fail first |
|---|---|---|---|
| the merge is a pointer move | `git merge --ff-only feat/v1-notes-core` | exits 0 | it refuses if anyone has pushed to `main`; that refusal is the guard |
| the default branch carries the build | `git ls-tree --name-only origin/main` | lists `settings.gradle.kts`, `gradlew`, `app`, `.gitmodules` | run it before the merge: two entries |
| cited commits survive | `bash scripts/check-docs.sh` on `main` | section 9 green — every SHA in `docs/evidence` resolves and is reachable from HEAD | do the merge as a squash in a scratch clone and watch section 9 fail; **do not** do this on `origin` |
| the JDK guard fires | `JAVA_HOME=<a JDK 24+ or a JDK 11> ./gradlew help` | fails with the message naming `JAVA_HOME` and the range | remove the `require` and watch the raw "Unsupported class file major version" instead — that is the message this replaces |
| the JDK guard does not over-fire | `JAVA_HOME=<Android Studio JBR 21> ./gradlew help` | exits 0 | set the upper bound to 17 and watch a correct machine be refused |
| a fresh clone builds | step 6, whole | `testDebugUnitTest` exits 0 | run it before the merge: it stops at `ls settings.gradle.kts` |

## Definition of Done

- [ ] `git ls-remote --heads origin` shows `main` at the same commit as `feat/v1-notes-core`, and
      the merge was a fast-forward (no merge commit in `git log --oneline --merges origin/main`).
- [ ] `git ls-tree --name-only origin/main` lists the build.
- [ ] `bash scripts/check-docs.sh` is green **on `main`**, section 9 included — the SHAs the audits
      cite are reachable.
- [ ] `settings.gradle.kts` refuses an out-of-range JDK with a message naming `JAVA_HOME`, and the
      range was confirmed against Gradle's compatibility matrix, not taken from the audit.
- [ ] `README.md` carries the clone command, the JDK range (identical to the guard) and the name
      of the working branch.
- [ ] A fresh clone into a temporary directory reached a green `testDebugUnitTest`, and the
      transcript is in the commit message.
- [ ] The operator's answers to 2(a) and 2(b) are written down somewhere durable — the README and
      the handoff — not left in a conversation.

## What could go wrong

Named, because this is the one task in WP-0 that touches the shared remote.

1. **`main` is protected.** The push is rejected. Do not force anything. Fall back to the PR shape
   in 2(a), and check the repository's allowed merge methods first — a "Squash and merge" default
   would destroy the SHAs the doc gate resolves, silently, at the moment the button is pressed.
2. **Somebody pushes to `main` between the check and the push.** `--ff-only` catches it. Re-run
   step 1 from the top rather than reaching for `git merge`.
3. **`main` becomes red at the moment it becomes real.** The default branch is what a new reader
   and (after T-002) CI judge the project by. Gate this task on the suite being green, which today
   means T-001.
4. **The merge publishes stale claims to the front page.** `main`'s README today is honestly out
   of date; `feat`'s README is *dishonestly* out of date — F-16 ("nobody has watched it run yet",
   contradicted by `verification.md:162`) and F-17 (the Voice bullet names a hold gesture, one
   model, and a server-preference rule that no longer exist, and does not mention the cloud
   provider that receives the recording at all). After this merge those sentences are the
   project's front door. **They are T-045's to fix, not this task's**, but the merge is what makes
   them urgent — say so on the board in the same commit, and consider whether the operator wants
   F-17's Voice bullet corrected in the same breath, since it is the paragraph that tells a reader
   where their voice goes.
5. **The JDK bound is wrong.** Too narrow and a working machine is refused with an authoritative-
   sounding message; too wide and the guard passes a JDK Gradle will reject anyway. Confirm it.
6. **Submodule surprise on the fresh clone.** `third_party/whisper.cpp` is fetched over HTTPS from
   `ggml-org/whisper.cpp` at `third_party/whisper.cpp@927cfce3` (a submodule commit, not one of ours) (v1.9.4) and needs no key — verified by H's walk, step 3.
   `--recursive` is a no-op (H-21). If it fails, it is a network problem, not this task's.
7. **A second remote or a fork.** `git remote -v` shows exactly one, `origin`. If a fresh clone
   in step 6 resolves somewhere else, stop.

## Blast radius, and what NOT to touch

- **Touches:** the `main` ref on `origin`; `settings.gradle.kts` (+8 lines at the top);
  `gradle.properties` (a comment); `README.md` (three additions).
- **Do not touch:** any commit that already exists — no rebase, no squash, no amend, no
  force-push, on either branch. `gradle/libs.versions.toml` — the pins are DEC-0004's and H-16's,
  and bumping anything here would make a merge and a dependency change one commit.
  `app/build.gradle.kts` — `versionCode`/`versionName` are T-038's; signing is T-039's.
  No tag, for the reason above.
- **Watch for:** `settings.gradle.kts` is evaluated before anything else, so a syntax error there
  breaks every Gradle invocation including the IDE sync. Run `./gradlew help` after editing it,
  before committing.
- **Neighbouring breakage:** T-002's workflow has
  `if: github.ref == 'refs/heads/main' || github.ref == 'refs/heads/feat/v1-notes-core'`. If the
  operator answers 2(b) with "move to `main`", that condition and the branch name in the README
  must change together, or the release job stops firing and nobody notices — which is the same
  class of silent gap this whole work package exists to close.
